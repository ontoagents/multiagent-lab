# 本体 / 语义层赛道开源全景：OpenBKN 的同类与相邻项目

> 调研时间：2026-09-22 ｜ 数据源：GitHub Search/Repo API（星数、语言、许可证、push 时间）+ 各仓库 README 精读
> 星数等客观数据采集自 GitHub API；项目定位与技术特点基于 README 一手信息。部分项目 star 增速异常，见文末「甄别提示」。

---

## 零、先给结论：这个赛道怎么切

「给 Agent 用的企业级语义/本体层」目前**没有事实标准**，但有清晰的分层，每层的竞争逻辑完全不同：

```text
┌─ 消费层 ── MCP / Skills / Agent Runtime ──────── EvoOntology(ACL级)、UModel Skills、OpenBKN SKILL.md
├─ 本体平台层 ── 对象/关系/行动/风险 + 治理 ───── OpenBKN、UModel(阿里)、Utopia、TrustGraph、open-foundry
├─ 语义/指标层 ── 指标定义 + Text2SQL + BI ────── Cube、WrenAI、MetricFlow、ktx、QueryWeaver
├─ 本体工程层 ── 本体的 plan/diff/验证/版本 ──── open-ontologies、OBO ODK、ROBOT、OpenBKN 的 CHECKSUM
└─ 底座层 ── 图库 / triplestore / git-for-data ─ TerminusDB、TypeDB、Neo4j、Oxigraph
```

**没有一家做到 Palantir 全集**（数据+逻辑+行动+安全四位一体 + 受治理写回 + 决策谱系）。差别在于各家选择先补哪一块。

## 一、A 类：最直接的同类（本体平台 / Foundry 替代）

### 1. [alibaba/UnifiedModel](https://github.com/alibaba/UnifiedModel) — 与 OpenBKN 定位最接近

| 项 | 值 |
|---|---|
| Star / 语言 / 许可 | 401 / Go + TypeScript / Apache-2.0 |
| 活跃度 | 2026-09-22（本调研当天） |

**UModel（统一模型）**：厂商中立的**语义运行时**（semantic runtime），把分散的 schema、实体、业务对象、遥测链路、拓扑关系收敛成一个 workspace-scoped **对象图**。

核心设计几乎可以和 OpenBKN 一一对应：

| UModel | OpenBKN |
|---|---|
| Model Packs（定义 Business Object / Operation Object / dataset / storage / topology） | BKN Lang 的 `.bkn` 类型文件树 |
| EntityStore（写运行时实体与拓扑） | VEGA 数据虚拟化 + 事实数据 |
| Query Service，统一 SPL 面：`.umodel` / `.entity` / `.topo` | Context Loader 的 `search_schema` / `kn_search` |
| AgentGateway + MCP | Execution Factory（tool / MCP / Skill） |
| **三种可加载 Agent Skills**（`/plugin install umodel@unifiedmodel`，支持 Claude Code / Qoder / Codex / Cursor） | `skills/openbkn` + `create-bkn` + `create-skill` |

**独有亮点**：
- **Entity-linked RunbookSet Skills** —— Skill 不是全局挂着的，而是**绑定到具体实体**上，Agent 走到哪个对象就加载哪个 Playbook。这个思路比 OpenBKN 的整网络 SKILL.md 粒度更细、上下文更省。
- 明确划分 OSS core 边界：云端控制面、多租户授权、阿里云内部包、领域专有读 API 不进开源核心 —— **和 OpenBKN 的 OpenBKN License 手法不同，但目的一致**（开源 vs 商业分层）。

**借鉴点**： Skills 与实际类似。三种技能的一次性安装的 CLI 指导 — 这一段几乎可以直接照搬。

### 2. [deeplethe/utopia](https://github.com/deeplethe/utopia) — 「企业世界模型」，本赛道 star 最高且最完整

| 项 | 值 |
|---|---|
| Star / 语言 / 许可 | 9726 / Rust + TS / Apache-2.0 |
| 成熟度 | **v0.1**，schema 版本间演进，迁移只向前无回滚 |

自称 "first open-source enterprise world model"，并且**明确拒绝被框定为「开源版 Palantir」**——原话：

> It is a different route to enterprise intelligence, built bottom up from knowledge governance to trustworthy decisions and simulation.

真正的核心不是口号，是这几个别人没做透的东西：

- **双时态知识图谱（bitemporal graph）**：每条事实携带两个时间轴 ——「世界上何时为真」和「系统何时相信」。订正事实是关闭旧版本并链接新版本，**而非覆写**。这一条直接支撑「复盘当时依据什么做的决策」。
- **边可被实体化（reified edges）**：边上能带自己的属性。这恰好补上一份源于 Timbr 对比里提到的 Palantir 弱点（需用中间对象表达关系属性）。
- **冲突三类三解**：事实冲突 / 违反公理（自环、传递环、基数）/ 本体自相矛盾，各自给出「关闭旧的 / 放宽公理 / 两者都接受」的处理界面。
- **Agent 自裁决 + 人工复核队列闭环**：低置信交给人工，人工判决再回头用于调优 Agent。
- **Decision Ledger**：append-only，且「记录比它描述的对象活得更久，甚至比所属知识库活得更久」。
- **离线可部署**，一个 Rust binary + 一个 Postgres（全文检索 Tantivy 内置、向量走 pgvector、任务队列表）。
- 内置 5 个 ontology pack 冷启动：schema.org / W3C Org / PROV-O / FOAF / IOF Core。
- 配套子项目 [Ontology2SQL](https://github.com/deeplethe/ontology2sql)，在 BIRD Mini-Dev 上号称 SOTA。

**借鉴点**：双时态模型 + decision ledger 是 OpenBKN 的 BKN Trace 之外**另一条更强的证据链路线** —— 一个解决「该不该做」，一个解决「当时怎么想」。想做受监管场景，这两个都要借鉴。

### 3. [semantica-agi/semantica](https://github.com/semantica-agi/semantica) — Graph-Native Context Infrastructure

| 项 | 值 |
|---|---|
| Star / 语言 / 许可 | 13375 / Python / MIT |
| 成熟度 | v0.6.8，模块可独立导入 |

六层架构：接入 → 处理（抽取/冲突/去重）→ 图谱 → 智能层（本体/推理/溯源/决策）→ 存储（RDF/LPG/向量）→ 输出（REST/MCP/CLI/可视化）。

最有辨识度的一点：**把「决策」建成一等图节点**（Decision 作为 node），从而构建「决策因果链」。加上 OWL/SHACL/SKOS 显式本体驱动、SHACL 校验作为合规门、时间旅行、混合检索。

**借鉴点**：决策作为一等公民 + 审计导出。以及它对 Python 生态的友好度远超 Go 系，适合做快速 PoC。

### 4. [trustgraph-ai/trustgraph](https://github.com/trustgraph-ai/trustgraph) — Semantic Intelligence Layer

| 项 | 值 |
|---|---|
| Star / 语言 / 许可 | 2741 / Python / Apache-2.0 |

自称 "The Context Operating System for AI"，走的是 **RDF/OWL + PROV-O 溯源**的正统 semantic web 路线：

- **Workspace / Flow 隔离 + 版本化上下文**，用 OS 的方式管理语义上下文
- 强调「用显式本体替代向量匹配来消幻觉」
- 自托管全栈（Cassandra / Qdrant / Garage / Pulsar / vLLM），`npx @trustgraph/config` 一键起，UI:8888
- Runtime 追踪回源语义；UI 侧有 Agent Console + GraphRAG 溯源视图

**注意**：README 未明确提 MCP，集成面比 OpenBKN/UModel 窄。

## 二、B 类：本体工程化（Ontology DevOps）—— 最建议搭配学习的一类

### [fabio-rovai/open-ontologies](https://github.com/fabio-rovai/open-ontologies) ★ 强烈推荐

| 项 | 值 |
|---|---|
| Star / 语言 / 许可 | 531 / Rust + Lean 4 / **MIT** |

定位一句话：**Terraform for ontology**。README 原话：

> The tool is like Terraform, and this is on purpose. But **the plan is semantic, not syntactic**. A text diff is `git diff`, and you have `git diff` already.

它解决的是一个真实且致命的问题 —— **文本 diff 看不出语义后果**。README 给的例子极好：

```
$ printf 'load base.ttl\nplan proposed.ttl\n' | open-ontologies batch -
#   整个改动：  ex:hasParent rdfs:domain ex:Person

added_classes         0
removed_classes       0
blast_radius          0 triples affected
risk_score            low
                      ──────────────────────────────────────────
conservativity        not_conservative_under_rule_table
new consequences      901          rule table owl-rl, in 0.04s
```

**一行"完全正确"的改动，文本 diff 只有一行，却产生 901 条此前不存在的推论。**这正是所有本体项目的隐形地雷。

更硬核的是**可独立验证的证明**：engine 产出 derivation certificate，配套一个 **Lean 4 写的、与 engine 零共享代码的 checker**（`oo-cert`），第三方不需要装这个软件、不需要联网就能复验；写入伪造结论会被拒绝并指名违反哪条规则。这份态度值得尊敬：

> If the tool measures a property, the tool says *measured*. If a prover gives an opinion, that opinion never takes the vocabulary of the checker.

能力清单：OWL/RDFS 推理 + 证书、自定义规则（SWRL/RIF Core/Horn table）、SHACL 校验（附 W3C 套件测量值而非断言）、可满足性（给出回放可验证的有限模型）、本体**变更 plan / blast radius / risk score / 锁定 IRI / apply / 监控 / drift / rollback**、CSV~Parquet~PostgreSQL~DuckDB 灌 RDF、MCP server。

**与 OpenBKN 的对比（关键）**：

| | OpenBKN | open-ontologies |
|---|---|---|
| 变更可见性 | `DiffNetworksFromTar` → Creates/Updates/Deletes（**结构级**） | plan + blast radius + new consequences（**语义推论级**） |
| 完整性 | CHECKSUM（防篡改） | Lean 4 证书（防伪造 + 可复验） |
| 推理栈 | 无（刻意放弃） | OWL RL / Horn / tableaux + 形式化验证 |

两者其实是**互补**的：OpenBKN 管"资产包级别的版本与分发"，open-ontologies 管"语义层面的变更后果"。自建本体时这两套都该有。

## 六、按目的选型建议

**如果你是「想学本体怎么工程化」**
1. 先用 [microsoft/Ontology-Playground](https://github.com/microsoft/Ontology-Playground) 建立直觉（零安装）
2. 读 [edmcouncil/fibo](https://github.com/edmcouncil/fibo) 或 [google/digitalbuildings](https://github.com/google/digitalbuildings)，学「真实本体长什么样」
3. 读 [fabio-rovai/open-ontologies](https://github.com/fabio-rovai/open-ontologies) 的 README —— 它会让你明白本体变更为什么危险
4. 读 OpenBKN 的 BKN Lang 样例 + UModel 的 Model Pack，学「怎么给 Agent 建模」

**如果你是「要在公司自建轻量本体」**
- 借鉴 **UModel 的 Model Pack + Skills 绑定粒度** + **OpenBKN 的 Risk 一等公民 + SKILL.md 闭环**
- 版本管控上：轻量走 OpenBKN 的 CHECKSUM/diff；要求高就参考 open-ontologies 的 blast radius 或直接用 TerminusDB 拿 git-for-data
- **不需要行动写回的话，先别上全套本体**，Cube/MetricFlow/ktx 这类语义层可能就够了

**如果你是「要做受监管场景（金融/医疗/政企）」**
- 优先级排序：**Utopia 的双时态 + Decision Ledger > open-ontologies 的可复验证书 > OpenBKN 的 BKN Trace**。前两者解决「事后自证清白」，后者解决「过程可追溯」，都要。
- 注意 Utopia 目前 v0.1，迁移只向前无回滚

**如果你是「研究 Agent + 本体」**
- [ruc-datalab/EvoOntology](https://github.com/ruc-datalab/EvoOntology)（人大 Fan Ju / Du Xiaoyong 团队，arXiv 2609.15779）是最近最有学术价值的一个：**本体层不是静态资产，而是从执行轨迹里持续自演化的状态**。
  - Content / Schema / Tool 三层分离
  - 通过 MCP 暴露 `browse_semantics` / `resolve_semantics`，按需取语义而非全量注入
  - **Gated versioning**：Candidate 只有在配对评测中相对 Parent 有可复现提升才publish
  - 实测（四骨干的分析子集）：DDR-Bench 10-K 69.5 → 89.5（**+20.0**），BIRD EX 63.6 → 72.4（+8.8），InsightBench +1.0
  - 这恰好补上 OpenBKN 缺的一环：**本体的自动进化与效果验证**

## 七、甄别提示（重要）

调研中有几处需要你自己复核，我在这里明确标注：

1. **Star 数异常**：Semantica（13375）、Utopia（9726）、OpenFoundry 相关评测提及的 193 star —— 这些在半年到一年内冲到该量级，**增速偏快**。建议查看 star-history 曲线形态再做判断，不要单看绝对值。
2. **上游渊源**：`kweaver-ai/adp` 与 `openbkn-ai/bkn-foundry` 高度同源（VEGA / 业务知识网络 / ADP 目录名一致）；此前公开资料称 OpenBKN 系 2026-05 从 KWeaver fork 重品牌化。对照两仓 diff 能看出 OpenBKN 的真实增量。
3. **成熟度标注**：本文标注的 v0.1 / v0.6.8 等来自 README 自述。Utopia 明确写了「schema 演进，迁移只向前，无回滚」——生产用需自行评估。
4. **性能类宣称**：open-ontologies 的数字附了可复跑命令与 test fixture；EvoOntology 附了 arXiv 编号与 benchmark 适配器。这两家的可核验性明显好于那些只给「准确率提升 X%」的项目。
