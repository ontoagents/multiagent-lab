# Snowflake 本体方案调研（构建 / 运行 / 使用）

## 0. 结论速览

**问题**：调研 Snowflake 在"本体"这一主题上的构建、运行、使用全链路方案，评估对本项目（eino-multiagent-lab 本体线）的借鉴价值。

**Snowflake 的本体版图一句话**：Snowflake **没有 Palantir 式的独立"Ontology"产品**，而是把本体能力拆成两层——①**分析语义层**（Semantic Views：逻辑表/事实/维度/指标/关系的 schema 级对象，服务指标治理与 BI/Agent 一致口径）；②**本体/KG 增强层**（官方工程路线：KG_NODE/KG_EDGE 关系表建模 + 递归 CTE 遍历 + Flattened GraphRAG 画像预计算 + 术语映射，服务多跳/层级/同义词推理）。两层叠加 Horizon Catalog/Horizon Context 治理与 Cortex Agent 消费面构成完整栈。

**三维度速览**：

| 维度 | 核心方案 | 一句话评价 |
| --- | --- | --- |
| **构建** | Semantic View Autopilot（AI 生成，GA 2026-02-03）/ Semantic Studio（Git 版本 AI IDE）/ SQL-YAML DDL 三工具链；KG 走"行业本体资产（OWL/RDF/SKOS）导入关系表"或"Cortex LLM 抽取→RelationalAI 建图"两条路 | 构建自动化程度高（schema→语义视图"天→分钟"），但**本体建模表达能力刻意保持薄**（无 OWL 公理，层级/关系用表+CTE 模拟） |
| **运行** | **无独立图数据库**：KG 全在 Snowflake 表内，递归 CTE 做动态深度遍历（等价 SPARQL property path），RBAC/行级策略在语义层继承 | 复用数仓基础设施换掉图引擎——运维极简但遍历性能与表达能力有天花板（1MB YAML/50-100 列等） |
| **使用** | Cortex Analyst/Agents/Snowflake Intelligence（CoCo/CoWork）+ BI 连接器；官方 benchmark：语义视图 baseline 50.0% → +KG 60.0% → +Flattened GraphRAG 70.0% → +术语映射 **78.2%**（22 题×5 次） | **增量最有价值的结论：~80% 增益来自"概念画像预计算"数据层，而非运行时遍历**；工具宜少不宜多 |

**对本项目映射结论**：六线逐项映射后 **5 项已有覆盖（部分路线更强）**、**1 项值得借鉴**（消费侧"概念画像"检索单元 → REQ-313 P2 需求池）、2 项观察池。项目 Oxigraph+SPARQL 真图引擎路线在表达能力上优于 Snowflake 关系表模拟路线；Snowflake 反超的是**构建自动化（Autopilot 从既有资产反推）与 benchmark 驱动的优化方法论**——后者恰是本项目学习目标（LG 系）的可借鉴素材。

## 1. Snowflake 本体能力全景

> 定位澄清：Anthropic 式"本体"在 Snowflake 语境被官方称为 **"Relationship and identity layer (often called 'ontology' in the enterprise)"**——概念、关系、规则的机器可读表示 + 身份消解 + 同义词 + 约束，可以是 OWL/RDF、也可以是 curated join graph 或概念到治理数据产品的绑定（E2）。官方明确：**"ontology is not the goal, high-quality data agent is"**。

### 1.1 构建维度

**① Semantic Views（分析语义层，2025-06 推出）**——schema 级数据库对象，把业务语义存进数据库本体（E3/E4）：

- 五要素：**logical tables**（业务实体：客户/订单）、**facts**（行级数值，"helper"角色）、**dimensions**（类别属性，回答 who/what/where/when）、**metrics**（聚合 KPI，SUM/AVG/COUNT）、**relationships**（逻辑表间 join 路径）；
- 携带同义词、描述、verified queries（问题→SQL 对）、public/private 访问修饰、custom instructions；
- 取代 legacy semantic model（YAML-on-stage），获得原生 RBAC/共享/元数据目录集成；语义定义被视为 **metadata**，进入 Horizon Catalog 治理面。

**② 构建工具链三接口**（E3/E5）：

| 工具 | 形态 | 关键能力 |
| --- | --- | --- |
| Semantic View Autopilot | Snowsight AI 向导（GA 2026-02-03） | 从 schema 自动生成语义视图；可喂 SQL 查询/CSV verified queries 反推语义与关系；可导入 Tableau/Power BI 文件——"建模时间从数天到数分钟" |
| Semantic Studio | Workspaces 内 AI 辅助 IDE（preview） | 对话式（CoCo）建模/测试/部署，**Git 版本控制**，CoCo 集成 |
| SQL DDL / YAML | `CREATE SEMANTIC VIEW` + YAML spec + `SYSTEM$CREATE_SEMANTIC_VIEW_FROM_YAML` | 程序化/版本化路径；ACCOUNT_USAGE 与 INFORMATION_SCHEMA 全套语义元数据视图（SEMANTIC_VIEWS/RELATIONSHIPS/FACTS/DIMENSIONS/METRICS） |

**③ KG/本体构建两条路**（E1/E6）：

- **行业本体资产导入**：官方工程博客以 SNOMED CT、UMLS、Gene Ontology、Cell Ontology（33,651 词、~50,000 边）、GS1、FIBO 等 OWL/RDF/SKOS 资产为输入，导入 KG_NODE/KG_EDGE 关系表（§2.1）；参考实现开源在 **Snowflake-Labs/ontology-on-snowflake**（E7）；
- **LLM 抽取建图**：RelationalAI（Snowflake Native App，"Knowledge Graph Coprocessor"）+ Cortex LLM 从非结构化文本抽实体关系 → 建图索引 → 图算法（社区发现）→ 摘要检索问答（E6，QirK 论文复现）；Horizon Context 补充自动化富化——从 **query logs / dbt models / BI 仪表盘** 抽业务上下文自动生成/充实语义视图（E5）。

**④ 治理内建**：敏感数据分类/掩码/行级策略随语义定义继承；AI guardrails；OpenLineage API 接血缘（E5）。

### 1.2 运行维度

**① 无独立图数据库的 KG 运行时**（E1）：KG_NODE（id/type/VARIANT 属性列）+ KG_EDGE（src/dst/edge_type/置信度/时间戳）直接用 Snowflake 表承载，复用其分布式存储、自动扩缩、查询优化与安全治理；官方明言"without requiring a separate graph database"。

**② 递归 CTE = 动态深度图遍历**（E1）：可变长路径遍历（对比固定 self-join 需硬编码跳数），frontier 逐步扩张至无新节点/深度上限/超时；防环用 path array `WHERE NOT e.dst = ANY(p.path)`；官方附录直接给出 **SPARQL `rdfs:subClassOf+` ↔ 递归 CTE 的等价对照**（property path 对应自引用 UNION ALL 扩张）。

**③ Flattened GraphRAG（预计算画像，运行时免遍历）**（E1）：离线递归 CTE 遍历全层级（实测最多 15 层 subClassOf），为每个概念节点聚合出一份**画像文档**——正式名+定义+全部同义词+一阶邻域（父母/子女）+二阶邻域样本+**全部后代聚合出的数据类别**——索引进 Cortex Search（关键词+向量混合检索）；运行时 agent 检索画像→抽出接地的领域上下文→喂给 Cortex Analyst 生成 SQL；代价是画像质量决定系统质量、需周期重建。

**④ 术语映射层（last-mile 覆盖）**（E1）：在 agent 系统提示词里硬编码少量人工策展映射（如"Squamous Epithelial Cell (CL:0000076) → Skin/Lung/Esophagus/Bladder/Cervix"与复合词定义），作为检索体系之上的确定性 override；官方定位"**该层要薄：supplement the index, do not replace it**"。

**⑤ 治理在语义层继承**（E5）：Horizon Context 宣称"governance applied at the level of meaning, not just at the table level"——财务限定的指标定义在 Power BI/Salesforce/任意 agent 查询时依然受限。

**⑥ 实际天花板**（E8，第三方汇总）：1MB YAML spec 上限、Cortex Analyst 50~100 列上限、无跨账号复制、Business Glossary 排在 2026 H2 路线图。

### 1.3 使用维度

**① 消费入口矩阵**（E3/E9）：Cortex Analyst（REST API，text-to-SQL against 语义视图）/ Cortex Agents（语义视图+搜索+工具注册为 agent 工具）/ **Snowflake Intelligence**（现成 agentic 应用，即 CoWork，ai.snowflake.com，内建可视化+traceability+verified answers）/ BI 连接器（Tableau/Power BI/Sigma/Omni 直查语义视图）。

**② 官方 benchmark（本调研最重量级证据）**（E1）：生物医学数据集（PRISM 4,518 药 × 578 癌细胞系 2.6M+ 活性测量 × Cell Ontology），22 道针对性难题 × 每题 5 次测稳定性：

| Agent 配置 | 工具数 | 均分(/2.0) | 成功率 |
| --- | --- | --- | --- |
| 标准语义视图（baseline） | 1 | 0.93 | 50.0% |
| + Knowledge Graph（7 存储过程工具） | 7 | 1.14 | 60.0% |
| + Flattened GraphRAG | 2 | 1.38 | 70.0% |
| + GraphRAG + 术语映射 | 2 | **1.55** | **78.2%** |

四条官方观察（原文要点）：
1. **Fix the data layer first**——GraphRAG 预计算（后代聚合画像）拿到约 **80% 的总增益**，无需任何人工映射；
2. **Fewer tools can also give good results**——2 工具 GraphRAG 与 7 工具 KG agent 同级表现，且 run-to-run 方差最低（工具多=编排出错面大）；
3. **Targeted hardcoding closes the last gap**——术语映射的增益集中在层级遍历推导不出的复合词，但该变体**方差最高**，结论：映射层要薄；
4. **优化环可复制**——Cortex Code 的 eval-refine-compare 循环（跑 22 题评测→分析失败模式→改 prompt→复测）产出了大部分关键设计决策。

**③ Agent Context 五层参考架构**（E2）：Analytic semantic model（指标/维度/实体）/ Relationship & identity layer（=ontology：规范实体+类型关系+跨系统 ID 映射+同义词）/ Business procedures（版本化 playbook）/ Evidence & provenance（答案的可查溯源：选了什么语义对象、什么过滤、为何取舍冲突源）/ Policy & entitlements。量化：仅给 agent 增加一份纯文本"data ontology"（join keys、表粒度、cardinality/fanout 提示），跨语义视图问答 **准确率 +20%、工具调用 −39%、端到端延迟 −20%**。

**④ 官方自认边界**：multi-ontology、multi-relation-type 的**跨系统协调是"follow-on architecture concern"，官方尚未解决**（E1/E8）——Snowflake 的本体工具链只管仓库内数据，跨 CRM/BI/dbt 的实体统一消解不在其内。

## 2. 生态位对比（第三方视角交叉）

| 视角 | 结论 | 来源 |
| --- | --- | --- |
| vs Palantir Ontology | Snowflake 语义层=**分析型**（指标治理+BI/Agent 一致口径）；Palantir Ontology=**运营型**（对象+属性+链接的语义元素 + 动作/函数/动态安全的 kinetic 元素，业务数字孪生，直接驱动操作应用）。2025-10 两家达成 Iceberg 零拷贝互操作战略合作——互补而非互斥 | E10 |

| 跨系统批评 | timbr：语义视图只见 Snowflake 数据；Atlan：企业平均 15~30 工具，仓内 context 对 60~80% 数据资产盲区；解法主张=统一实体消解后**回注 Snowflake**（而非另起平行图）+ MCP 交付 | E8 |
| 行业标准化 | **Open Semantic Interchange（OSI）**：Snowflake 主导的厂商中立 YAML 语义元数据互换标准，2026-02 定稿，54 家厂商参与——"本体/语义层互操作"是行业公认方向 | E5 |

**映射结论**：🆕 新建 0 个模块、⏸ 后置 2 项观察、1 项 P2 需求池登记（REQ-313，性质是对既有 REQ-287 检索单元的增强而非新模块）。低侵入对位成立。

## 5. 借鉴决策

### D1（🆕 → REQ-313，P2 需求池，待拍板）：伴生检索"概念画像"检索单元

- **借鉴点**：Flattened GraphRAG 的画像文档结构——每概念聚合（正式名+定义+全部同义词+一阶邻域+后代聚合属性），作为检索单元索引进混合检索；官方 benchmark 中该项贡献 ~80% 增益、且运行时零遍历、工具面最小、方差最低。
- **项目落点**：REQ-287 三臂（FTS5 兜底+定义文本向量+图臂）RRF k=60 之上的**第四种检索单元**：按本体类节点聚合伴生 KG 的同名实体+别名+一阶关系+后代（ Parents 链）描述为一份"画像"，进向量臂/lexical 臂索引。与 REQ-288 社区摘要互补：社区=图拓扑聚类（Louvain），画像=本体层级聚合（Parents 链）——一个横着一个顺着。
- **最小化设计**：P1 可先查询时聚合（不物化、零新表），收益验证后再物化+增量刷新（挂 REQ-303 增量 IO 管线）；画像生成过 qualitygate（REQ-171 口径）。
- **反转条件**：真机 eval（72 号评估框架）显示画像单元相对三臂现状无显著提升，或聚合成本不可接受 → 维持三臂现状，画像思路仅保留给"概念详情页摘要"展示用。

### O1（⏸ 观察池）：本体遍历只读工具产品化

官方存储过程三件套（ancestors/hierarchy-path/cohort-expand）对智能体查询体验有直接价值；项目已有 companion 查询+278 影响分析覆盖主路径。是否需要把"祖先链/层级路径"做成一等只读工具（而非 SPARQL 表达），等消费侧（第五栏观测台）真实使用反馈再定。触发条件：用户/智能体在对话中高频手写遍历 SPARQL 失败。

### O2（⏸ 观察池）：Agent Context 五层作为消费侧叙述参考

E2 五层框架（语义模型/关系身份/程序/溯源/策略）可作为"消费与审计"栏信息组织与文档叙述的对照参考；纯文档层面，不立项。

### L1（📚 学习素材，零实现）：递归 CTE ↔ SPARQL property path 对照

官方附录的等价对照是绝佳教学内容：同一 subClassOf+ 遍历，关系库用 UNION ALL+path array 防环，RDF 库一条 property path 搞定——可直接进 REQ-92 SPARQL 工作台的教学注解/09 方法论素材，直观回答"为什么选图引擎"。

### L2（📚 学习素材，零实现）：benchmark 驱动优化方法论

22 题×5 次、固定失败模式分析、eval-refine-compare 循环、方差作为一阶指标（不只看均值）——可反哺 72 号本体创建评估体系与 20 号冒烟清单的"评估题集"思路：为伴生检索/消费问答维护小型固定 eval 集，改动跑分对比。

### 与 Palantir/行业趋势的对位判断

项目"个人本体资产 + 学习平台"定位更接近 Snowflake 的**分析型语义层+Agent 消费**形态，而非 Palantir 运营型 Ontology；行业两大动向（构建自动化 Autopilot 化、语义互操作标准化 OSI）项目都已站在标准侧（W3C 栈）——路线无需调整，方向性确认即本次调研的首要产出。
