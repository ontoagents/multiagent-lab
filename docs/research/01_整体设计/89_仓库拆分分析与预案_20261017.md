# 89 仓库拆分分析与预案

> 状态: Review（待拍板）
> 日期: 2026-10-17
> 分析对象: eino-multiagent-lab 单仓（多模块 monorepo）
> 置信度: high（全部结论基于仓库实况与本仓 git 历史，无外部假设）

## 1. 结论摘要

- **当前判断：未到拆仓时机，但已到「仓内治理」时机。** 产品形态（桌面安装包=三 Go 服务+前端+引擎一键安装的同版本捆绑分发）、单主人+多 agent 的协作结构、服务间已就位的 HTTP 松耦合，三者共同决定拆仓此刻是负收益。
- **真正的痛点不在「一个仓库」，在「多个 agent 共享同一物理工作区」**：push 竞争、rebase 冲突、未提交改动互踩、`.git/objects` 出现 `tmp_obj_*` 垃圾、REQ 撞号——拆仓不解决这个，独立工作区纪律才解决。
- **将来的拆分按触发条件分两阶段**：第一步（最可能）拆出内容仓（platform-knowledge+seeds，占近期提交量 ~45%）；第二步（仅当发版节奏分叉或组件复用脆弱性反复）才动静态网站与组件包。**客户端永远不拆出产品仓**（理由见 §6.2）。
- 本文档同时给出「不等拆分、现在就该做」的 4 项仓内治理（§7）。

### 2.2 耦合关系（拆分可行性核心证据）

**Go 侧：干净。** 三服务间纯 HTTP 松耦合（backend→`BUILD_SVC_URL`/`RUNTIME_MGR_URL`；ontology/runtime→backend `PLATFORM_URL` 回调）；库级依赖仅 ontology-service 与 runtime-manager → pkg/ontology/spec（go.work + replace ../）。E2

**构建期：四处跨目录耦合（真正的脏点）。**

| 耦合 | 方向 | 形态 | 已知坑 |
| --- | --- | --- | --- |
| C1 | website → web/src | 直接跨目录 import 可视化组件（content.ts、DemoPage、Implementation、styles.css、vite.config 5 处） | bare import 自 web/ 向上解析依赖，缺 web/node_modules 即 Rollup 构建失败（CI 注释明文记录踩坑） |
| C2 | website → platform-knowledge + ontology-service/internal/seed + web/src/api/types.ts | 构建期内联内容单源 | workflow 触发 paths 横跨 4 个顶层目录 |
| C3 | web → seeds | Vite `?raw` 内联（fs.allow ['..']） | dev 与 CI 均依赖仓库相对结构 |
| C4 | apps/desktop → web/dist | frontendDist=壳占位，实际安装包内嵌 web 构建产物（build.ps1 -SkipWeb 复用 CI 预构建） | 安装包=三 Go 服务+launcher 壳+web/dist+Oxigraph 安装器，**版本必须同 tag** |

**发布侧：已是双仓格局。** 私有开发主仓 + public 发布仓（ontoagents/multiagent-lab）；client-release.yml 以 `if: github.repository == 'ontoagents/multiagent-lab'` 隔离发布面；website 独立 workflow 部署 Pages。E7

**协作侧：多 agent 共享同一工作区。** push 被拒/ non-fast-forward、rebase 中断残留、他人未提交改动互踩、`.git/objects/tmp_obj_*` 半写垃圾、REQ 编号撞号——本会话及近期多轮亲历。E6

## 3. 拆分时机评估

### 3.1 经典拆分信号对照

| 信号 | 本仓现状 | 判定 |
| --- | --- | --- |
| 多团队/外部贡献者需要权限与所有权隔离 | 单主人 + 若干 agent，无外部贡献者 | ✗ 不存在 |
| 模块发布节奏分叉（独立部署、独立版本线） | 桌面安装包强制全栈同版本（C4）；SaaS 未上线 | ✗ 不存在，且产品形态反向强制一致性 |
| CI 互拖导致等待与浪费 | 两条 workflow 均已 paths 过滤；客户端按手动 tag | ✓ 已在仓内解决 |
| 代码库膨胀致 clone/检索不可接受 | pack 30.62 MiB，尚轻；但 4 周 700 commits 增速需观察 | ✗ 暂未触发（列入监控） |
| 高频低相关提交污染主干历史 | 文档类占 ~45%，代码历史确被稀释；`git log -- <path>` 可部分缓解 | △ 感知存在，未到痛阈值 |
| 跨目录构建耦合反复踩坑 | C1 已实际踩坑并写进 CI 注释；C2 触发面跨 4 目录 | ✓ 已发生，真实痛点 |
| 并行开发冲突频发 | 共享工作区模式高频冲突（E6） | ✓ 高频，**但根因是共享工作区而非单仓** |

**判定：6/7 信号未达阈值，2 个已达但均可由仓内手段解决。现在拆仓 = 为不存在的问题付真实的迁移与版本对齐成本。**

### 3.2 反面约束（拆仓会立刻变贵的三件事）

1. **版本对齐**：安装包要求三服务+前端同 tag。拆仓后需跨仓 tag 对齐/replace 指向远端/前端组件 semver 三套机制，任一失步即出坏包。
2. **C1/C2/C3 内容与组件内联**：website 的内容单源、web 的 seeds 单源都依赖同仓相对路径。拆仓必须引入 submodule 或发包，CI 复杂度上升而非下降。
3. **REQ-需求-代码同仓联动**：docs 需求文档与 backend/web 实现同生命周期演进（REQ 注册表、登记簿、冒烟清单），拆走反而制造跨仓引用。

## 4. 方案选型

| 评估标准 | 权重 | A 维持单仓+治理（推荐） | B 两仓（+内容仓） | C 四仓深拆 |
| --- | ---: | :---: | :---: | :---: |
| 版本一致性成本 | 25 | 5 | 4 | 2 |
| 协作冲突缓解 | 20 | 4（独立工作区纪律为主） | 4 | 5 |
| 构建脆弱性改善 | 15 | 3（出口收敛） | 3 | 4（组件包化） |
| 维护/迁移成本 | 15 | 5 | 4 | 2 |
| 可逆性 | 15 | 5 | 4 | 3 |
| 对未来 SaaS/开源演化的准备度 | 10 | 3 | 4 | 5 |
| **加权合计** | | **4.55** | **4.05** | **3.30** |

- **推荐：A（现在）→ B（第一触发条件出现时）→ C（仅第二触发条件出现时）。** B/C 不是对立选项，是同一演化的两个台阶；C 的「产品仓」内核与 B 相同。
- 反转条件：见 §5.1 触发条件清单——任何一个为真时，A 的收益曲线跌破 B/C。

## 5. 拆分预案

### 5.1 触发条件（满足任一才启动对应阶段，不到不动）

| 编号 | 触发条件 | 启动动作 |
| --- | --- | --- |
| T1 | platform-knowledge/seeds 内容无界增长，clone 体积/时间成为可感知负担（监控点：pack > 200 MiB 或 clone > 1 min），或知识库需要独立对外开源/协作 | **阶段一（B）**：拆内容仓 |
| T2 | 服务端 SaaS 化立项，服务端与桌面客户端发版节奏分叉 | **阶段二（C）**：产品仓内核保持，desktop 与 server 发布线分离预案启动 |
| T3 | website 对 web 组件的构建脆弱性（C1 类坑）在同一季度复发 ≥2 次 | **阶段二（C）**：组件包化 @agentlab/viz |
| T4 | 引入外部贡献者/多团队，出现真实权限边界需求 | 按所有权重划仓库拓扑（届时重新评审） |

### 5.2 阶段一（B）：拆出内容仓

```text
multiagent-lab（产品仓，保持 monorepo）
├── backend / ontology-service / runtime-manager / pkg
├── web / apps/desktop / deploy / tools
└── docs（需求与代码同生命周期，不拆）

multiagent-lab-content（内容仓）
├── platform-knowledge/
└── seeds/
```

- 消费方式二选一：**git submodule（推荐起步）**——产品仓锁内容仓 commit，CI 显式 update，C2/C3 改读 submodule 路径；后续量大可升级为内容 npm 包（构建期内联逻辑不变，只换来源）。
- 收益：~45% 高频文档提交移出产品历史；内容仓可独立公开。
- 成本：submodule 同步纪律（内容更新=内容仓 commit+产品仓 bump 指针）；C2 触发条件由跨目录 paths 变为指针变更。

### 5.3 阶段二（C）：静态网站与组件深拆（仅 T2/T3 触发）

```text
multiagent-lab（产品仓，内核不变）
multiagent-lab-website（官网仓）
multiagent-lab-viz（组件包，发布为 npm @agentlab/viz）
multiagent-lab-content（内容仓，阶段一产物）
```

#### 5.3.1 静态网站（website）拆后管理

- **独立仓 + 独立 Actions**：现有 website-deploy.yml 原样平移（本已是独立 workflow），触发由跨目录 paths 简化为本仓 push；GitHub Pages 部署逻辑零改动。
- **内容来源**：内容仓以 submodule（锁 commit）或内容 npm 包引入，构建期内联 platform-knowledge 模块导读页与 seed spec 的机制不变，只换读取路径。
- **组件来源**：`@agentlab/viz` npm 包（从 web/src/components 抽 Graph3D/SpecGraph 等可视化组件，web 与 website 同装此包），semver 版本化，彻底消灭 C1 的 bare import 向上解析依赖。
- **发布节奏**：内容更新→自动重建（同现状）；组件升级→包版本升级手动/ Dependabot。

#### 5.3.2 客户端（apps/desktop）拆后管理

- **原则：desktop 不拆出产品仓。** 依据：Tauri 壳仅 3 个 .rs 文件（薄壳无独立演化需求）；安装包=三服务+launcher+web/dist+引擎安装器的同版本捆绑（C4），拆出即引入跨仓版本对齐成本；发布链（v* tag → public 仓双平台 CI → Release）与仓库拓扑无关，平移即可。
- T2（SaaS 化）触发后的分离形态：`server 仓`（backend+ontology+runtime+pkg，API 版本化对外）与 `desktop 仓`（web+Tauri 壳+deploy/windows|macos 打包链）；desktop 消费 server 按 API 契约版本兼容，不再强制同 tag。**此形态仅在服务端独立对外提供服务时才有收益。**
- 客户端发布的 public 镜像仓（ontoagents/multiagent-lab）维持现状：开发主仓 push 不同步出包（if 条件已隔离），v* tag 即出包。

### 5.4 执行机制（真拆时）

1. **保历史迁移**：`git filter-repo --subdirectory-filter <dir>` 迁出，保留完整提交历史。
2. **双跑一个版本周期**：原路径与新仓同步提交，CI 全绿、下游消费（website 构建/客户端打包）验证通过后，删除原目录收口。
3. **回滚设计**：阶段一/二均为目录级迁移，回滚=目录并回主仓+恢复原 CI，无数据风险；submodule 改回目录亦同。
4. **迁移 checklist**：两条 workflow 改写、README/AGENTS.md 路径同步、vite.config 与 fs.allow 调整、go.work 不动（内容不涉 Go）、public 镜像脚本路径核对。

## 6. 关键决策记录

| 决策点 | 结论 | 放弃的选项 | 理由 | 反转条件 |
| --- | --- | --- | --- | --- |
| 现在是否拆仓 | 不拆，做仓内治理 | 立即拆 B/C | 版本一致性+迁移成本 > 当前痛点收益；痛点根因在共享工作区 | §5.1 任一触发 |
| docs 是否随内容仓拆走 | docs 留产品仓 | docs 归内容仓 | 需求文档与代码同生命周期（REQ 注册表/冒烟清单/登记簿联动） | 文档协作方独立成团队 |
| desktop 是否独立仓 | 不独立，留产品仓 | desktop 独立仓 | 薄壳+同版本捆绑分发；拆出纯增成本 | T2 SaaS 化落地 |
| 组件复用方案 | 现阶段先出口收敛，T3 后包化 | 立即抽 npm 包 | 抽包需要私有 registry/版本管理，当前一处消费方（website）不足以摊薄 | T3 复发 |
