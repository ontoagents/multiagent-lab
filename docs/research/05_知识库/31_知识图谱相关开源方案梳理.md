## 一、摘要

资料库对知识图谱侧开源方案的覆盖，核心集中在 **OpenKG（开放知识图谱）社区 2025-2026 年度成果**（合集 A【27/31】专文）以及散见各篇的图数据库/图谱 RAG 组件。结构非常完整，呈**四层递进**：

```
数据层   OneGraph      ── 千万级三元组知识基础设施 + E/R/G/T 服务矩阵
推理层   OpenSPG + KAG ── 语义底座（动态本体） + Agentic RAG 求解/思考
Agent 层 SkillNet      ── 20万+ 技能本体，过程性知识工业化
评测层   OneEval       ── 覆盖 5 类知识库 × 5 领域的持续进化评测
```

**结论性判断**：OpenKG 这套"数据—推理—技能—评测"闭环，是目前资料中唯一同时具备**规模数据、可执行推理、Agent 技能、动态评测**的开源图谱生态，对本平台（Agent + 本体）参考价值最高；其中 **OpenSPG 的动态本体**正好桥接了本体侧与图谱侧。

## 三、OpenKG 生态详解（资料核心）

> OpenKG（中文开放知识图谱，OpenKG.cn）旨在推动以中文为核心的知识图谱数据的开放、互联及众包，并促进知识图谱算法、工具及平台的开源开放（A:5197）。
> 依托 **SIGData、SIGSPG、SIGTool、SIGModel、SIGAgent、SIGEval** 六个兴趣小组协同（A:5016）。

### 3.1 OneGraph ｜ ★★★★★（数据层）

- **定位**：从"规模缩放"走向"结构缩放"的大规模双语知识基础设施，访问 onegraph.openkg.cn。
- **规模与质量（实测数据）**：
  - OneGraph **V2 累计超过 3,679 万个三元组**，涵盖人文学科（2,500 万）、工程技术（450 万）等核心领域；
  - **数据准确率 86%**，**节点稠密度 2.78**。
- **服务矩阵**：设计 **OneGraph-E / R / G / T** 体系，覆盖知识抽取、精准检索、**EoG（Enrich-on-Graph）生成增强**、思考四类图谱增强服务；**已开放 OneGraph-R / G 服务工具**。
- **实测成效**：在 CEval 评测中，OneGraph V2 将 DeepSeek 等主流模型准确率 **从 80.7% 提升至 86.1%**；经图谱指令微调的 **Llama3 8B 在规划能力上超越 GPT-3.5（175B）**。
- **核心论点（可借鉴）**：
  1. **合成数据的结构溢价**：用 LLM 把模型内部隐性直觉转化为显性逻辑（占比达 59.7%），可突破人类标注天花板；
  2. **以结构稀疏性对冲参数不确定性**：引入严谨本体结构（如 OntoTune 方法）比单纯语料堆砌更有效。
- **适用场景**：为中文 LLM 提供事实锚点、图谱增强抽取/检索/生成、领域迷你图谱（任务驱动的精准建设）。
- **出处**：A:5018-5053

### 3.2 OpenSPG ｜ ★★★★★（语义底座 / 动态本体）

- **定位**：承担类似 **Palantir Dynamic Ontology（动态本体）** 的角色，构建严谨的"实体空间"；访问 openspg.github.io/v2。
- **核心机制**：
  - 通过 **Schema 定义严谨的实体、关系与属性约束**，为大模型提供确定性事实底座；
  - **KAG Index Diffusion** 机制：把本体知识、实体、关系、时间空间知识与原文段落**映射到统一语义空间**，解决传统向量检索的**四类错位**——**指代错位 / 时空错位 / 数值错位 / 逻辑错位**。
- **关键洞察**：静态知识库难以适应快速变化的业务；具备**自演化能力的动态本体**能在问题求解过程中持续发现并补全知识缺口，是**连接数据层与推理层的关键桥梁**。
- **对本平台的价值**：这是资料中把"本体"落在图谱工程上的最直接方案——**它是本体侧与图谱侧的交汇点**，建议作为平台语义底座的首选候选做 PoC。
- **出处**：A:5066-5069、A:5088-5095

### 3.3 KAG：KAG-Solver + KAG-Thinker ｜ ★★★★★（推理层）

- **定位**：GitHub **OpenSPG/KAG**，以 **Agentic RAG** 范式把应用升级为"自主规划与混合执行"。
- **KAG-Solver（执行枢纽）**：
  - 采用 **Planner（规划）→ Executor（执行）→ Generator（生成）** 闭环架构；
  - Executor 动态调用**逻辑演绎器、代码计算器、或基于 OpenSPG 的检索器**，实现从"盲目匹配"到"**语义路径搜索**"的转变。
- **KAG-Thinker（推理内化）**：
  - 把推理能力**从框架层内化到模型层**，融合自然语言推理与**符号表达式（Logical Form）**推理；
  - 通过变量、运算器、运算规则给模型简明逻辑约束，实现可稳定求解与逐步验证；交互式迭代合成高质量 SFT 语料。
- **KAG 0.8 工程进展**：支持**自由定制 Builder 流水线**（低成本知识加工）、**全面接入 MCP 协议**（无缝连接外部数据源与工具链）、优化跨文档长链条求解（迭代式求解 / DAG 引导求解）。
- **核心洞察**：框架推理与内化推理**互补共生**——KAG-Solver 提供可解释可调试路径，KAG-Thinker 把能力蒸馏进模型参数，形成"外部脚手架训练 → 内化为原生能力 → 反哺框架优化"的螺旋闭环；**符号推理并未过时**，而是以 Logical Form 新形态嵌入神经网络推理，成为"逻辑护栏"。
- **适用场景**：法律/金融/医疗等高准确率要求的知识密集型推理、跨文档长链条推理。
- **出处**：A:5071-5087

### 3.4 SkillNet ｜ ★★★★★（Agent 层 / 技能工程）

- **定位**：访问 skillnet.openkg.cn，把**过程性知识（Know-how）**规模化沉淀为可执行、可分发的"技能单元"，解决 Agent 规划的"逻辑断层"。
- **关键区分**：传统 KG 存储**陈述性知识（Know-what，事实三元组）**；Agent 真正需要的是含思维链（CoT）、结构化逻辑和行业经验的**过程性知识（Know-how）**。
- **资源规模（实测数据）**：
  - **总资源量突破 200,000+ 项**原始技能储备；
  - **精选资源 139,685+ 项**（经标准化评估过滤，可直接调用）。
- **三层本体结构**：
  1. **技能分类体系（Skill Taxonomy）**：category + tag 组织为多层级结构（如 Development/AIGC/Science → frontend/llm/physics）；
  2. **技能关系图（Skill Relation Graph）**：标签实例化为技能实体（如 Matplotlib、Playwright），关系边含 **similar_to / compose_with / belong_to / depend_on**；
  3. **技能包库（Skill Package Library）**：通过 packaged_in 封装为技能包（如 data-science-visualization），支持模块化发布复用部署。
  - 由 **Skill Ontology** 动态演化：新标签可扩展，大模型推断潜在关系并实例化完善关系图。
- **五维评估框架**：**安全性 / 完备性 / 执行性 / 适配性 / 效率**（Safety、Completeness、Executability、Maintainability、Cost-Awareness）。人类一致性实验表明自动评估与专家标注高度一致。
- **对比洞察**：与 **Claude Context Graph** 形成差异——Context Graph 是"长期背景记忆"（告诉 Agent **是什么**，辅助 RAG 召回），**SkillNet 是"行动方法论"（告诉 Agent 怎么做**，提供经验证的思维路径与执行 SOP）。二者互补。
- **趋势**：从"建设数据库"转向"**建设技能库**"——这是对本平台 Agent 层最直接的方法论启示。
- **出处**：A:5100-5145

### 3.5 OneEval / Dynamic OneEval ｜ ★★★★（评测层）

- **定位**：访问 oneeval.openkg.cn，2025-04 发布 V1.0，经 4 次迭代至 **V1.3**。
- **覆盖范围**：**5 种知识库类型**（文本、表格、知识图谱、代码、逻辑）× **5 个领域**（通用、税务、经济、法律、学术）。
- **榜单实测发现（V1.3）**：
  - **第一梯队集体未达及格线**：Claude 4.5-sonnet-thinking 37.65 分居首，Gemini 3-pro 37.02 分，DeepSeek-V3.2 32.60 分；
  - **偏科显著**：DeepSeek-V3.2-thinking 擅长代码与 KG 推理、表格推理较弱；Gemini 3-pro 逻辑推理与税务领先；GPT-5.2-Thinking 综合跌出前五。
- **Dynamic OneEval（创新点）**：三阶段闭环——**① 结构化错误分析 → ② 双视角实例合成（知识施压 / 推理施压）→ ③ 多标准门控筛选（多 LLM 投票保真）**。当前覆盖文本/KG/表格三类知识库，含 **30 种主要难点类型 + 100+ 细粒度难点类型**；首轮最高分 Gemini 3-pro 仅 **46.4%**，难度远未饱和。
- **核心洞察**：
  1. 不同**知识形式构成正交挑战维度**——KG 推理瓶颈在多跳路径选择与隐含约束校验（误差链式累积）；文本推理考验跨句整合与抗干扰；表格推理偏结构化操作精确性；
  2. 动态评测从"被动测量"转为"**主动施压**"，评测本身演化为随模型进化自适应升级的"对抗系统"；
  3. **少量失败样例可撬动大规模高质量评测**，为低成本可持续评测基础设施提供可行路径。
- **对本平台的价值**：可直接作为平台推理能力的持续评测回路与"诊断报告"生成器。
- **出处**：A:5146-5189

### 3.6 OpenKG 的社区联动（延伸）

OpenKG 已明确将围绕**记忆增强、知识增强的具身智能体、本体驱动的数据治理管线**，分别与 **OpenMem（记忆张量）**、**OpenJiuwen（华为）**、**OpenBMB（面壁智能）** 社区深度联动（A:5191）。

## 四、图存储与计算

### 4.1 属性图（Labeled Property Graph）
- **Neo4j**：以属性图模型为代表，节点有标签/属性、边有类型/属性，**不追求 OWL 形式化推理，但查询性能好、工程落地快**（C:86、C:167）。是"最后组装处"最常见的载体：NebulaGraph/Neo4j + 自定义语义模型 + RBAC（C:1276）。
- **NebulaGraph**：国产开源图数据库，作为 Palantir 不可直接部署时的**国产替代选项**（C:2233）。
- **ArangoDB**：多模型开源图库（F:1341）。
- **AbutionGraph**：国产动态图谱引擎，是 OntoFlow 的执行层（"OntoFlow 负责建，AbutionGraph 负责跑"），强调轻量化——无需安装部署的引擎版即可完成设计阶段验证（C:2682-2782）。

### 4.2 三元组 / RDF 存储
- **Apache Jena**：Java 生态完整 RDF/SPARQL 框架，适合需要对标 W3C 标准的项目（C:167、D:1087）。
- **GraphDB**（Ontotext）：开源三元组库，原生支持 RDF/SPARQL（D:1087）。
- **Eclipse RDF4J**：开源 RDF 框架（D:536）。

> **选型原则（资料原话）**：语义推理与规则校验 → 三元组库；关系挖掘与图算法 → Neo4j 属性图（D:1099）。

## 五、知识抽取与图谱构建

- **OntologyAutoGeneration**（liuhuanyong 开源）：六段流水线（数据解析→术语抽取→概念形成→关系发现→约束生成→RDF 序列化），支持 **RDB DDL / 文本文档 / 对话日志**等异构源输入，是"数据源→图谱/本体"的开源实现（C:169、C:207）。
- **ppocrv6（PaddleOCR）**：轻量 OCR，在多模态大模型盛行的当下仍有独立价值，负责扫描件/图片的版面与文字检测（A:2398-2448）。
- **MinerU / ppocr-vl**：多模态文档大模型，负责复杂版面的非结构化→结构化抽取（A:2448）。
- **OneGraph-E**：OpenKG 提供的抽取侧图谱增强服务工具（已开放），可作为自建抽取能力的对照基准（A:5034）。

## 六、图谱 RAG 家族（横向对比）

| 方案 | 来源 | 核心特点 | 适用场景 |
|---|---|---|---|
| **GraphRAG** | 微软开源 | 配置文件约束实体/关系类型；把检索从"找相似文本"升级为"找实体+关系+规则" | 通用图谱增强检索、抑制幻觉 |
| **LightRAG** | 港大开源 | 图结构融入文本索引，实体关系网络实现多跳推理 | 图谱 RAG（用友 LOM 的方案引用） |
| **Graphiti** | Zep AI 开源 | **时序感知**，追踪事实随时间变化 | 需要知识演化的场景 |
| **RAG-Anything** | 港大开源 | 多模态 RAG | 文档/图表混合场景 |
| **OntoRAG** | 开源 | **本体 + KG + LLM** 模块化，产出可靠可解释领域感知 RAG | 专业领域问答，要求可解释性 |
| **KAG** | OpenSPG 开源 | **Agentic RAG**（Planner/Executor/Generator）+ 符号 Logical Form 内化 | 高准确率知识密集型推理 |

**关键边界**：GraphRAG 的关系仍是 LLM 生成的**轻量级关联**，不是形式化本体——从"检索增强"走到"推理增强"必须引入本体（C:77、D:144-149）。资料实验证实：**ontology-guided KG-RAG 在多项任务上超过向量 RAG 与纯 GraphRAG 基线**（A:1098）。

## 七、图谱 + Agent（执行闭环）

- **Palantir Ontology MCP（闭源但协议开放）**：2026-01 把本体暴露为 MCP 服务，**LangChain、CrewAI、微软 Copilot Studio、Google ADK** 可作为 MCP 客户端接入，智能体可读取对象、执行预定义动作、查询数据（C:146）。
- **KAG 0.8 全面接入 MCP**：开源的等价路径，可直接连接外部数据源与工具链（A:5080）。
- **Neo4j + Drools + ERP API 的朴素方案**：Cypher 查出 ID → for 循环调 Drools → for 循环调 ERP API。**局限**：图谱中是 ETL 过来的副本，与源系统存在同步延迟；逻辑与语义分离、维护困难（A:2727-2753）。
- **SkillNet**：把"要用哪些技能、以什么顺序组合"沉淀为可检索可组合的技能本体 + 技能包分发（A:5100-5145）。

## 八、治理、血缘与评测底座

- **Apache Atlas / LinkedIn DataHub / Metaphor / Schema Registry**：在现有数据平台之上用 Schema Registry + Knowledge Graph 构建语义层的组合方案（D:894）；Atlas 常用于承载自定义 Object-Link 模型（C:2231）。
- **Legend（高盛，2020 经 FINOS 开源）**：金融数据建模与治理标杆，七年打磨；建议参考 **FIBO**（金融行业业务本体）等行业标准扩展（C:3283、C:3376）。
- **OpenLineage**：开源血缘协议，与 Legend 等共建互操作治理框架（C:3378）。
- **OAEI / LLMs4OL**：本体对齐与本体学习评测基准（A:678-707）。
- **Dynamic OneEval**：动态、可持续、抗污染的推理评测基础设施（A:5165-5181）。

## 九、对本平台（Agent + Ontology）的落地建议

1. **把 OpenSPG 作为语义底座的首选候选**：它是资料中唯一把"动态本体 + 图谱 + 向量统一语义空间"实现出来的开源方案，正好充当"本体层"和"图谱层"之间的桥。重点验证其 **KAG Index Diffusion** 对四类错位（指代/时空/数值/逻辑）的修正效果。
2. **推理层用 KAG 的双引擎思路**：短期靠 **KAG-Solver**（Planner/Executor/Generator，可解释可调试）保证可控，长期用 **KAG-Thinker** 把推理蒸馏进模型，形成"脚手架→内化→反哺"闭环。KAG 0.8 已支持 MCP，能与外部工具链直连。
3. **Agent 能力建设走 SkillNet 路线**：不要只建"事实库"，要建"**技能库**"——按三层本体（分类体系 / 关系图 / 技能包）+ 五维评估（安全、完备、执行、适配、效率）组织 Agent 的 Know-how。这是资料中判断的 2026 方向：知识工程重心从"建设数据库"转向"建设技能库"。
4. **数据层可借 OneGraph 做冷启动与基准**：3,679 万三元组、86% 准确率，可直接用于中文事实锚点与效果基线（CEval 80.7→86.1 是可复用的对标方式）；但业务专属部分仍需"任务驱动的精准建设"。
5. **存储采用属性图 + 三元组双栈**：Neo4j/NebulaGraph（国产）承载图算法与关系查询，Jena/GraphDB 承载 RDF 语义与推理；参考 AbutionGraph 的"轻量引擎版先在验证态跑通"路径降低试错成本。
6. **评测用 OneEval + 自建**：把 OneEval / Dynamic OneEval 的三阶段闭环（错误分析 → 双视角合成 → 多标准投票保真）作为平台评测基础设施的方法论模板，实现"持续抗污染"。
7. **治理先行**：Atlas/DataHub/Legend/OpenLineage 是图谱规模化的前置条件；资料反复强调本体/图谱落地失败多因治理与管理缺位（F:793、C:2203）。
