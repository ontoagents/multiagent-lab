# 知识图谱构建方式研究报告

> **研究起点**：微信公众号「三人行AI」文章《文本如何变成知识图谱：两条方法路线与三个开源项目》（2026-08-18，链接：https://mp.weixin.qq.com/s/Smg2kYs5zsUy4YsaQppE-g ）
> **研究方法**：以起点文章为纲，扩展检索公众号生态中转载与同源的技术方案（GraphRAG、LightRAG、KAG、OneKE、KGGen、iText2KG、Graphiti 等），横向梳理、对比与归纳。
> **整理日期**：2026-09-23

---

## 一、研究背景

当前许多知识库仍停留在「切块 → 向量化 → 召回 → 生成」的直线式 RAG 流程。这种方式适合回答与原文表述相近的问题，但在**跨段落关系、实体别名、事件顺序、知识缺口**等场景下表现不佳。知识图谱通过「节点表示实体/事件/概念、边表示关系」，额外记录了"谁和谁有关、通过什么关系有关、关系出现在哪里"，从而把检索方式从**相似度匹配升级为路径推理**。

核心共识（贯穿起点文章与各方案）：

- 图谱不是自动获得的"事实层"，而是**模型抽取出的一套结构化假设**，必须保留来源、上下文和人工校验入口；
- **抽取只是起点，可信、可检索、可维护才是终点**。

## 二、起点文章解读：两条方法路线 + 三个开源项目

### 2.1 路线一：自由发现型（先让模型看见概念关系）

不预设 schema，让 LLM 阅读文本块自主抽取概念与语义关系，适合没有固定 schema 的探索场景。

**流程**：

1. 语料切块并分配 `chunk_id`；
2. LLM 从每块抽取概念和语义关系（权重 W1）；
3. 同块共同出现的概念增加"上下文邻近关系"（权重 W2）；
4. 合并同一节点对：累加权重、拼接关系描述；
5. NetworkX 做图分析，Pyvis 生成交互可视化。

**关键细节**：同一对概念间保留两类证据（语义边 + 共现边），避免"同段出现"被误读为"存在事实关系"。

**优缺点**：启动快、适合探索；但模型可能补入原文没有的概念、实体名漂移、共现边过重。

### 2.2 路线二：本体约束型（Graph Maker，先定义观察什么）

用户先定义实体标签和关系类型（通过 Pydantic 模型定义 Ontology），模型按本体集中抽取。

**流程**：

1. Pydantic 定义 Ontology（如 Person / Place + "居住于""访问"关系）；
2. 语料切成 200–500 token 的文本块；
3. 封装为带 `text` + `metadata` 的 Document；
4. 逐文档生成子图并汇总；
5. 边模型保存节点标签、关系、来源 metadata 和 order（可观察关系随文本块顺序出现，适合书籍/长报告/时间线材料）；
6. 写入 Neo4j，用 Cypher、图算法、Bloom、向量检索服务后续查询。

**工程化处理**：提示词约束实体类别减少别名漂移；JSON 解析失败时拆分输出恢复可解析的边；为关系保留上下文。

**优缺点**：可控性强，但 schema 需要领域知识——太宽失去约束、太窄漏掉信息。建议**先用小样本建立本体，再用真实抽取结果反向修订**。

### 2.3 三个开源项目

| 项目 | 定位 | 技术栈 | 适合谁 | 边界 |
|---|---|---|---|---|
| `rahulnyk/knowledge_graph` | 轻量概念图谱实验场 | Mistral 7B (OpenOrca) + Ollama 本地推理、Pandas 暂存、NetworkX 图指标、Pyvis 可视化、Docker 启动 | 想理解文本建图原理、快速本地实验、验证 GRAG 想法的人 | 研究型原型，无实体去重、归一化、增量更新、权限和证据追踪 |
| `nashsu/llm_wiki` | 持续维护的个人知识库 | 三层设计（原始来源 / Wiki 内容 / Schema 规则），Ingest–Query–Lint 工作流，两阶段导入（先结构化分析、再生成 Wiki 页面），增量缓存、持久化导入队列、失败重试、目录监听、级联清理 | 积累论文/网页/PDF/笔记为长期知识资产的人；希望 Agent 有可查询工作记忆的团队 | 能力面广、部署与模型配置复杂度高；质量依赖人工 Review 流程 |
| `microsoft/Ontology-Playground` | 本体设计可视化工作台 | React + TypeScript 静态 Web、Cytoscape.js 渲染、Zustand 状态管理、RDF/XML 往返校验、领域预置本体目录、GitHub PR 协作 | 领域建模、培训、schema 评审、Fabric IQ 生态探索 | 不负责文档摄取、图数据库存储和 RAG 运行时 |

### 2.4 起点文章的落地链路建议

```
原始文本/网页/PDF
    ↓
自由发现：寻找候选概念与关系
    ↓
本体设计：确定实体、属性、关系、基数和别名
    ↓
约束抽取：分块生成子图，保留来源与顺序 metadata
    ↓
归一化与校验：合并别名，过滤低置信关系，保留证据
    ↓
Wiki/图数据库：分别服务人工维护与结构化查询
    ↓
混合检索：向量召回 + 图扩展 + 原文核对
```

### 2.5 起点文章指出的六个风险

1. **幻觉关系**：边必须带来源片段或 chunk_id，回答时回原文核对；
2. **共现不等于事实**：展示与检索时区分语义边、共现边、推断边；
3. **图的规模失控**：设置最小权重、关系白名单、节点合并与分层展示；
4. **JSON 可解析 ≠ 可信**：Pydantic 校验通过也要核对类别、方向、时序、证据；
5. **本体维护成本**：标签/属性/关系进入数据管道后影响提示词、约束、查询和展示，先小样本验证；
6. **可视化 ≠ 可用知识**：验收标准是能否找到证据、解释路径、修正错误、随来源更新保持一致。

## 三、公众号生态中的其他主流方案

以下方案均检索自公众号平台转载或同源技术文章（GraphRAG 实战指南、腾讯新闻「为 AI agent 构建智能上下文记忆」「港大开源 LightRAG」、53AI 知识图谱专栏、「知识图谱科技」公众号转载的 Graphiti 解读等），按目标用途分为六类。

### 3.1 图增强 RAG 类（以"建图提升问答质量"为目标）

#### （1）Microsoft GraphRAG —— 社区发现 + 层次化摘要

- **流程**：实体抽取 → 关系抽取 → 写入图数据库（Neo4j Cypher）→ **Leiden 社区发现** → 对每个社区生成 LLM 摘要 → 查询时 map-reduce 汇总社区部分答案；
- **两种查询模式**：Global Search（全局摘要，回答"这个数据集主要讲什么"）、Local Search（邻域展开，回答具体实体问题），后续加入 DRIFT 混合搜索；
- **使用**：`pip install graphrag` → `graphrag init --root ./demo` → `graphrag index` → `graphrag query --method global`；
- **代价**：构建成本高（大量 LLM 调用），增量更新需重建社区结构（曾有数据：等规模新数据更新约需 1399 万 token）；微软随后推出 **LazyGraphRAG** 把摘要推迟到查询时，索引成本降至原来的约 0.1%；
- **适用**：文档实体密集、关系对回答至关重要的专业领域深度推理（法律、企业知识库、生物医学）。

#### （2）LightRAG（港大 HKUDS，EMNLP 2025）—— 更快、更省、可增量

- **核心思路**：实体/关系抽取建图 + **双层检索**（低层：具体实体细节；高层：宏观主题），向量 + 图谱融合；
- **优势**：检索阶段一次 API 调用（对比 GraphRAG 需数百次）；**原生支持增量更新**，新实体/关系无缝并入现有图，无需重建；
- **定位**：个人开发者与中小团队性价比最高的图增强 RAG；GraphRAG 更适合预算充足的大型企业知识库。

#### （3）nano-graphrag —— 极简参考实现

- 约 1100 行 Python 复刻 GraphRAG 核心（抽取、社区报告、查询模式），可插拔存储后端；
- **适用**：学习 GraphRAG 机制、快速实验，不适合直接生产。

#### （4）HippoRAG / HippoRAG 2 —— 神经生物学启发的检索

- 模仿海马体记忆索引：embed 查询 → 打分种子节点 → 在开放知识图谱上跑 **Personalized PageRank（PPR）**，单步收集多跳证据；
- 多跳问答比强 RAG 基线最高提升约 20%，比迭代检索（IRCoT）便宜 10–30 倍、快 6–13 倍；
- HippoRAG 2（ICML 2025）深化段落整合，把 KG-RAG 定位为"非参数化持续学习"（即记忆）；
- **适用**：vendor-neutral 的学术基线、多跳推理问答。

### 3.2 领域知识服务类

#### KAG / OpenSPG（蚂蚁集团）—— 逻辑符号引导的混合推理

- **动机**：RAG 的向量相似度与知识推理相关性差距大，对数值、时间关系、专家规则不敏感；
- **四项双向增强**：① 对 LLM 友好的知识表示（LLMFriSPG，兼容无 schema 抽取与有 schema 专业构建）；② **知识图谱与原文片段互索引**；③ 逻辑符号引导的混合推理引擎（规划/推理/检索三类算子，融合图谱推理、逻辑计算、Chunk 检索与 LLM 推理）；④ 基于语义推理的知识对齐；
- **效果**：hotpotQA F1 相对提升 19.6%，2wiki 提升 33.5%；已用于蚂蚁电子政务、电子健康问答；
- **定位**：专业领域知识服务的完整框架（含 SPG 语义建模、端到端建图、查询）。

### 3.3 信息抽取工具类（以"把文本抽干净"为目标）

#### （1）OneKE / DeepKE（浙大 ZJUNLP + 蚂蚁）

- **OneKE**：双语（中英）schema 驱动的 LLM 抽取模型，支持 NER/RE/EE 多任务，采用"基于 Schema 的轮询指令构造"提升泛化；
- **DeepKE**：覆盖监督、低资源、零样本、文档级、多模态场景的抽取工具箱；DeepKE-LLM 支持接 ChatGLM、LLaMA、GPT 系列；
- **适用**：金融、医疗、政务等中文垂直领域的生产级抽取。

#### （2）KGGen（斯坦福 stair-lab，NeurIPS 2025）

- **痛点**：主流自动抽取图谱实体/关系类型过多、极度稀疏、连通性差（OpenIE、GraphRAG 均缺实体解析与关系归一化）；
- **方法**：两步抽取（先列实体、再基于实体列表抽规范三元组，保证一致性）→ **迭代聚类算法对实体和关系解析去重**，显著降低稀疏性；
- **配套**：发布首个 text-to-KG 基准 **MINE**，在基准上比现有抽取方式高出约 18%；
- **使用**：`pip install kg-gen`。

#### （3）iText2KG（WISE 2024）—— 零样本增量建图

- **四模块**：Document Distiller（按用户 schema 把原始文档改写为语义块，提高信噪比）→ Incremental Entity Extractor（用余弦相似度把局部实体匹配到全局实体，实体名+标签双嵌入防误并，如 Python:Language 与 Python:Snake）→ Incremental Relation Extractor → Neo4j 集成与可视化；
- **防幻觉处理**：LLM 发明的实体替换为输入列表中最相似实体；漏配关系的实体重新提示抽取；max_tries 限制结构化输出重试；
- **特点**：零样本、主题无关、无需后处理、支持增量追加文档。

#### （4）轻量化零样本路线（GLiNER / GLiNER2 / RexUniNLU / UIE）

- 零样本 NER/关系抽取模型（如 GLiNER2 约 205M 参数、RexUniNLU 约 375MB）可在消费级硬件运行，零样本 F1 在关系抽取上显著优于 LLM 方案；
- **趋势判断**（2026 工具链测评文章）：零样本成为信息抽取"新基线"；**LLM 驱动（DeepKE-LLM、iText2KG、KGGen）与极致轻量化两条路并行**，按隐私、预算、硬件选型。

### 3.4 框架集成类（以"工程快速接入"为目标）

#### （1）LangChain LLMGraphTransformer + Neo4j

- 用 `allowed_nodes` / `allowed_relationships` 约束抽取（本质是本体约束路线的框架化实现）；
- `graph.add_graph_documents(graph_documents, include_source=True)` 保留来源；
- Neo4j 官方还提供 mcp-neo4j-cypher / mcp-neo4j-memory MCP Server，让 Claude、Cursor 等 AI 助手直接交互式抽取并写入图。

#### （2）LlamaIndex PropertyGraphIndex

- 原始文本切 chunk 后作为 label 为 "chunk" 的节点，与抽取出的实体节点通过 **MENTIONS** 关系连接；实体名生成向量；
- 抽取器可换：默认隐式抽取 / `SchemaLLMPathExtractor`（schema 约束 + strict 模式 + max_triplets_per_chunk 限额）；
- **三种检索思路**：Text-to-Cypher（自然语言转图查询）、Vector Search（图数据库内向量检索）、Keywords Search（关键词扩展图检索）；检索器组合有 VectorContextRetriever、LLMSynonymRetriever、TextToCypherRetriever 等。

#### （3）Neo4j 生态

- Neo4j LLM Graph Builder、Unstructured.io 管道（解析 → 清洗 → Neo4jUploader）、Data Importer、LangChain/LlamaIndex 双集成；
- **适用**：已选定 Neo4j 作为图存储底座的团队，"抽取器可插拔、存储层统一"。

### 3.5 时序记忆类（以"Agent 动态记忆"为目标）

#### Graphiti / Zep —— 双时间线知识图谱

- **痛点**：GraphRAG 类批量索引在数据频繁更新时需大规模重算、检索延迟高（数十秒），不适合 Agent 记忆；
- **核心机制**：
  - 增量写入：新 episode（对话/文档/事件）→ 抽实体和关系事实 → 与图内已有事实对比 → **关闭旧事实有效期、写入新事实**，而非删除；
  - **双时间线（bi-temporal）**：每条边带 validity window（事实在现实中的生效区间）+ transaction time（系统何时得知），并用 provenance 追溯来源 episode；
  - 例：项目 X --使用--> 方案 B（有效期截至 7/8）与 --使用--> 方案 C（自 7/8 起）并存，可回答"现在用什么"和"之前用过什么、为何换"；
- **检索**：图遍历 + 向量检索 + BM25 混合；
- **效果**：DMR 基准超 MemGPT；LongMemEval 准确率提升最高 18.5%、延迟降低约 90%；
- **注意**：由 LLM 决定旧边失效，单次模型调用决定"什么是真的"是需要权衡的设计选择。

#### Mem0 —— 抽取-整合式生产记忆层

- 显式的抽取与整合管线，graph-enhanced 变体在时间类问题上的得分大幅领先（58.13% vs OpenAI 记忆的 21.71%）；选择性检索使 p95 延迟降低约 91%、token 用量降约 90%。

### 3.6 个人知识库类（公众号热门的落地形态）

- **SparkNoteAI**：开源笔记转知识图谱系统，Markdown 笔记 + 多平台采集（微信公众号/小红书/B站/YouTube 异步导入）→ LLM 提取概念与关系 → Neo4j 存储 → 2D 力导向图可视化；Docker 私有化部署；
- **sage-wiki 自动化管线**（CSDN 案例文章）：微信机器人采集公众号文章 → 同步服务器 → sage-wiki + DeepSeek/Ollama 双 Provider 编译 → 输出 Obsidian 概念图谱，全程无人值守。

| **LlamaIndex PropertyGraphIndex** | 框架集成 | chunk 节点 + MENTIONS | 弱 | ✓（insert） | Neo4j 等 | 抽取器/检索器可插拔 | 深度归一化需自建 |
| **Graphiti / Zep** | 时序记忆 | 增量 episode 抽取 + 边失效 | 实体解析 ✓ | **✓（核心卖点）** | Neo4j | 双时间线、实时更新 | LLM 决定边失效有风险 |
| **Mem0** | 记忆层 | 抽取 + 整合管线 | ✓ | ✓ | — | 生产记忆层、延迟低 | 偏 Agent 场景 |
| SparkNoteAI / sage-wiki | 个人知识库 | LLM 抽取 → Neo4j/Wiki | 弱 | ✓ | Neo4j/Obsidian | 面向个人、可视化好 | 非严格语义图谱 |

## 五、共性技术要素归纳

无论哪条路线，完整的"文本 → 知识图谱"系统都可以拆成六个共性环节，各方案的差异本质上是对每个环节的不同取舍：

### 5.1 分块与预处理

- chunk 粒度普遍在 200–500 token（Graph Maker），需兼顾模型上下文与输出复杂度；
- 进阶做法是 iText2KG 的"文档蒸馏"——先按 schema 把原始文档改写成语义块，提高信噪比。

### 5.2 抽取（自由发现 vs 本体约束）

- **自由发现**：探索期先看图再建模（起点文章路线一）；
- **本体约束**：Pydantic/Literal 白名单、schema 轮询指令（Graph Maker、LangChain、LlamaIndex SchemaLLMPathExtractor、OneKE）；
- **两阶段混合**是最被推荐的实践：自由抽取找候选 → 专家收敛成本体 → 约束抽取重跑。

### 5.3 归一化（决定图"碎不碎"）

- "Sauron / the Dark Lord Sauron / the Dark Lord" 必须合并，否则度数、社区、检索全被稀释；
- 方案光谱：提示词约束（Graph Maker）→ 余弦相似度匹配（iText2KG，实体名+标签双嵌入权重 0.6/0.4）→ 迭代聚类（KGGen）→ LLM 对齐（KAG）；
- 最低保留字段：规范名称、别名列表、来源片段、置信度、人工合并记录；**实体合并要可撤销**。

### 5.4 存储

- 一次性实验：Pandas + NetworkX；
- 生产检索：Neo4j（Cypher、Bloom、向量插件）是绝大多数方案的共同底座；
- 人工维护：Wiki 文件层（版本控制、可阅读、跨工具协作）。

### 5.5 检索（图不是向量库的替代品）

- 公认稳妥链路：**关键词/向量召回种子节点 → 受限图扩展（预算 + 边类型过滤）→ 原文证据核对 → 生成回答**；
- 变体：GraphRAG 社区 map-reduce（全局）、LightRAG 双层路由、HippoRAG PPR 单步多跳、Graphiti 三路混合（图遍历 + 向量 + BM25）、Text-to-Cypher（精确查询）。

### 5.6 治理与溯源

- 来源追踪（chunk_id / provenance / 来源片段）是所有成熟方案共同强调的底线能力；
- 图更新语义：LightRAG 追加式合并；Graphiti 用**边失效 + 双时间线**处理事实变更；llm_wiki 用导入队列 + Lint + 人工 Review；
- 本体要当作活文档：版本号、变更说明、校验规则、迁移策略。

## 六、选型建议

**按场景快速选型**（综合起点文章"一句话选型"与各方案公开数据）：

| 你的场景 | 推荐起点 |
|---|---|
| 学习原理、本地快速实验 | `rahulnyk/knowledge_graph` → `nano-graphrag` |
| 个人资料库持续积累、供 Agent 查询 | `nashsu/llm_wiki`；中文多平台采集可参考 SparkNoteAI |
| 中小团队企业知识库问答、预算敏感 | **LightRAG** |
| 超大规模语料的全局性深度问题、预算充足 | **Microsoft GraphRAG**（关注 LazyGraphRAG 成本优化） |
| 专业领域（政务/金融/医疗）多跳推理 | **KAG / OpenSPG** |
| 中文垂直领域生产级抽取 | **OneKE / DeepKE** |
| 图太碎、实体名混乱 | **KGGen**（聚类去重）或 **iText2KG**（增量去重） |
| 已用 Neo4j，想快速接入现有应用 | LangChain LLMGraphTransformer / LlamaIndex PropertyGraphIndex |
| Agent 长期记忆、事实会随时间变化 | **Graphiti / Zep**；轻量可选 Mem0 |
| 团队要先对齐"业务世界怎么描述" | **microsoft/Ontology-Playground** 设计 schema，再接抽取管道 |

**推荐组合链路**（对起点文章链路的工程化补充）：

```
原始文本/网页/PDF
    ↓  文档蒸馏/清洗（iText2KG Distiller、Unstructured.io）
自由发现抽取候选概念（低成本 LLM / GLiNER 零样本）
    ↓  专家收敛
本体设计（Ontology-Playground 可视化设计 + RDF 导出）
    ↓
约束抽取生成子图（Graph Maker / OneKE / SchemaLLMPathExtractor）
    ↓
归一化去重（KGGen 聚类 / iText2KG 余弦匹配，保留别名与证据，可撤销）
    ↓
持久化（Neo4j：生产检索层 + Wiki 文件层：人工维护层）
    ↓
混合检索（向量/BM25 召回 → 受限图扩展 → 原文证据核对）
    ↓
持续运维（增量更新：LightRAG/Graphiti；质检：llm_wiki 式 Lint + 人工 Review）
```

## 七、风险清单（各方案共同教训）

1. **幻觉关系**：边必须带来源，回答回原文核对；
2. **共现 ≠ 事实**：语义边、共现边、推断边分类管理；
3. **规模失控**：最小权重、关系白名单、节点合并、分层展示；
4. **格式校验 ≠ 事实校验**：结构化输出通过也要抽查；
5. **本体维护成本**：小样本验证再推广，变更需迁移策略；
6. **图更新语义不清**：事实变更时"追加新边还是覆盖旧边"要提前设计（Graphiti 的边失效 + 双时间线是当前最完整的答案）；
7. **LLM 决定"真值"的风险**：如 Graphiti 由单次模型调用判定旧事实失效，关键场景需人工兜底；
8. **验收标准**：不是"图好不好看"，而是能否找到证据、解释路径、修正错误、随来源更新保持一致。

## 九、结语

起点文章给出的演进主线——**自由发现概念 → 用本体约束抽取 → 把知识持续写回 Wiki → 用可视化工具治理 schema**——在公众号生态的更广方案池中同样成立，且可以进一步细化为一条完整的工程谱系：

- **抽取层**从"LLM 自由发挥"演进到"schema 轮询指令"（OneKE）与"聚类去重"（KGGen）；
- **检索层**从向量相似度演进到社区摘要（GraphRAG）、双层路由（LightRAG）、单步多跳 PPR（HippoRAG）与三路混合（Graphiti）；
- **更新层**从一次性批量索引演进到增量插入（LightRAG）与双时间线边失效（Graphiti）；
- **定位层**从"生成一张图"演进到"Agent 可依赖的记忆层"（Zep/Mem0/KAG）。

下一代知识增强系统的差异，可能不只在模型参数量，而在**它是否知道哪些关系有证据、哪些只是候选、哪些知识已经过期，以及 schema 改变时如何重建**。图谱的价值不是节点会动，而是每条关系都能回到证据。
