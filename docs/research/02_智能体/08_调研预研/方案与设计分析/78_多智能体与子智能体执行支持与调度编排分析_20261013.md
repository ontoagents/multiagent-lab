## 1. 一句话结论

**平台的协作「机制层」成体系且有几处被低估的强项（同轮多委派真并发、per-member 全量装配与授权面、HITL 嵌套穿透、事件面完整），但「调度层」几乎不存在——任务分解、成员路由、并行扇出、失败恢复全部依赖协调者 LLM 自发行为，平台零原语零兜底：成员上下文只有一段任务描述字符串、成员产出只有末条文本、成员任何错误直接终止整个 run、无 per-member 超时与预算。** 对复杂任务而言，当前形态=「一个强协调者带一群一次性外包工」：能跑通演示级协作，但韧性（错误改道）、可控性（中途引导/取消单个成员）、可重复性（结构化编排）三个维度在任务变复杂时会被依次击穿。建议优先补「容错与资源控制包装器」（错误降级回喂+per-member 超时，P1 低改动高收益），控制面增强沿 REQ-208 领取，结构化编排维持 REQ-205 触发驱动并明确击穿信号。

## 2. 支持现状盘点（一手取证）

### 2.1 协作模式与委派机制

| 模式 | 机制 | 语义 | 状态 |
| --- | --- | --- | --- |
| `agent_as_tool`（推荐） | `adk.NewAgentTool(ctx, 成员Inst)`，function name=成员名（assembler.go:256） | 协调者把成员当工具调用；成员全量装配（各自模型/工具/技能/MCP/审批/hooks/伴生，buildOne assembler.go:336-373） | ✅ 主路径 |
| `transfer`（对照） | `adk.SetSubAgents`（assembler.go:319） | 控制权转移：目标成员以相同 runCtx 会话接管（共享消息列表，flow.go:554-571），成员亦可 transfer 回协调者（chatmodel.go:883） | ✅ 保留；44 号 NOT RECOMMENDED，治理定案并入 REQ-208 |
| `single` | assembleSingle | 项目仅一成员时退化为单 agent | ✅ |

**project 关系模型**：project + project_agent(role=coordinator|member)；协调者优先 `project.coordinator` 缺省首成员；`workflow_mode`（sequential/parallel/loop）**确认为空壳**——非 free 仅装配告警降级（assembler.go:201-204），全仓无 NewSequentialAgent/NewParallelAgent/NewLoopAgent 残留。

### 2.2 委派执行语义（agent_as_tool 全链路，Eino 源码实证）

- **深度恒为 1**：成员经 `buildOne` 装配，`assembleTools` 只合并 builtin/技能/MCP/本体四类，**不含任何 AgentTool**（全仓 NewAgentTool 仅 assembler.go:256 协调者侧）——成员不能再委派。
- **并发：同轮多委派是真并行**（**翻正常见误解**）：backend 未设 `ToolsNodeConfig.ExecuteSequentially`，Eino 默认并行（compose/tool_node.go:208-211、985-1017 `parallelRunToolCall` 起 goroutine + wg.Wait）——协调者一轮响应里同时发起 N 个成员调用会**并发执行**。39 号 P-3「同步阻塞」的准确语义=**单个** agentTool.InvokableRun 内部循环同步等成员跑完（agent_tool.go:216-249），占住协调者的当前迭代；不是整轮串行。
- **成员上下文=一段字符串**：NewAgentTool 未带 Option（未启用 `WithFullChatHistoryAsInput`），默认输入 schema 仅 `request` 一个字符串参数（agent_tool.go:32-40），解出后变**单条 user 消息**（:184-193）；成员 session 只继承父 Values 键值对、不继承消息（runctx.go:537-558）——**成员看不到对话历史，任务描述质量决定产出上限**。
- **成员产出=末条文本**：返回成员最后一条消息文本作为 tool result（agent_tool.go:264-279，REQ-203 定案「结果压缩无需开发」）；中间过程（流式文本/工具轮）仅经事件流转发（EmitInternalEvents），**不进父 session/checkpoint**（agent_tool.go:80-83）。
- **错误传播=整 run 终止**（**最大韧性缺口**）：成员任何错误（LLM 报错/迭代超限 ErrExceedMaxIterations）→ agentTool 返回 error（agent_tool.go:230-231）→ ToolsNode 直接上抛（tool_node.go:1097-1102）→ backend `rc.runErr` → `run.error` 终止（runner.go:909/445）。**没有「错误降级为 tool result 文本回喂协调者改道」的机制**。
- **中断/审批穿透**：成员内 ask_human/审批挂起经 CompositeInterrupt 拍平为可恢复点列表（compose/interrupt.go:140-229），checkpoint 序列化显式承载嵌套（adk/interrupt.go:198-221），backend 取 IsRootCause 中断点定向恢复（runner.go:734-787，ResumeWithParams Targets）→ agentTool 走 bridgeCheckpointID 分支恢复成员内部（agent_tool.go:199-213）。机制链路成立，**平台无嵌套端到端测试**（§7）。

### 2.3 资源控制与迭代预算

| 控制项 | 现状 |
| --- | --- |
| 迭代上限 | 协调者与成员**各自独立**（各自 ag.MaxIteration→normalizeMaxIter≤0 归一 25）；语义=模型生成轮数上限，**不等于委派次数上限**；生效值经 REQ-311 A4 透出 |
| 成员迭代耗尽 | =成员报错=按 §2.2 终止整个 run（原文 "exceeds max iterations" 透出） |
| per-member 超时 | **无**——agentTool 复用 run 级 ctx（agent_tool.go:197），全链仅 run 级 WithCancel（runner.go:216-228） |
| per-member token 预算/重试 | **无**——唯一重试 DoWithRetry(N=2) 只用于装配期 MCP 拉取 |
| 停止 | Stop→cancel 可穿透委派（extractAndDeriveAgentToolCancelCtx，agent_tool.go:325-329）✅ |

### 2.4 状态共享与记忆

- 落库统一：成员与协调者文本增量合并为**一条 assistant 消息**（runner.go:412-419）；委派调用与成员内部工具轮以 tool.call/result 事件落 run_event——消息表不区分成员产出。
- 下一轮历史：`mergeToolTurns` 把委派轮**与成员内部工具轮一并拍平**进协调者可见的合并时间线（context.go:147-171）——多 agent 场景下工具归因是 A1 设计的固有近似。
- **成员无记忆**：实例每轮装配时重建，无持久状态；跨轮续作只能靠协调者在新一次 arguments 里转述。「防火墙语义是特性非缺陷」（56 号开放问题⑤）。

### 2.5 感知面与控制面现状

- **感知面（已成型）**：subagent.enter/exit 事件（payload 仅 agent(+via) 两字段）；REQ-217 嵌套轨迹缩进；REQ-311 A5 智能体泳道/委派徽标/委派聚合统计；并行线已交付 B1 协作拓扑图（CollabTopology，按 enter/exit 聚合次数/在栈/transfer 标注）。委派决策理由（为何选该成员）零专留痕——唯一载体是 tool.call arguments 文本（71 号诚实边界④）。
- **控制面（薄弱）**：无中途引导（steer）、无取消单个成员（只有整 run Stop）、无后台委派（发起后协调者被占住）、无 per-member 重启/重跑。**REQ-208 三件套（后台委派+steer 中途引导+冷恢复）正是控制面的补全**，挂 M42 触发驱动未领取。
- **已知失真点**：①transfer 一次移交疑似产生两条 enter（动作级 via=transfer + AgentName 切换），拓扑计数可能双计（时序推断，未验证）；②智能体泳道是单栈模型，两个成员真并行开段时只能画成嵌套（前端实现推断，未验证）。

## 3. 复杂任务执行中的调度编排实况

以「一次复杂任务」（多步骤、需多成员、含失败与中途确认）走查当前实际发生什么：

1. **任务分解**：发生在协调者 LLM 的思考里（instruction+成员 description 是唯一路由依据，requireAgentToolFields 强制成员有描述）。平台无 planner、无任务单结构、无分解留痕——分解质量=协调者模型质量。
2. **路由与委派**：协调者把任务写进 tool arguments 的 request 字符串；**路由错误无纠正回路**（没有「委派错了重选」机制，只有协调者自己看到结果后自行调整）。
3. **并行扇出**：可用但不可靠——只有协调者在**同一轮响应里**发多个 tool_call 才并发；顺序思维链的模型天然倾向逐个委派，平台无「必须并行」的编排原语或提示词工程。真并行时感知面还有栈式失真（§2.5）。
4. **失败恢复**：**最脆的一环**——成员 LLM 抖动/迭代耗尽=整个 run 终止，前序已完成工作只留在事件里；协调者没有「该成员失败了，换人/重试/降级」的机会。复杂任务时长与成员数放大此风险（每次委派都是一次全有全无赌注）。
5. **资源失控面**：长任务成员可无限占用（无超时）；成员 token 消耗不可预算不可截止；协调者 max_iteration 与委派次数无映射（预算看板语义失真）。
6. **状态/记忆**：成员一次性——跨轮、跨成员的知识传递全靠协调者转述；长任务的上下文累积全压在协调者一个上下文窗口里（成员侧反而干净）。
7. **确定性流程**：需要「固定步骤/必并行/节点级审批」的任务（如固定 ETL 流水线）当前只能靠 prompt 约束模型自觉——workflow_mode 空壳，REQ-205 触发驱动的立场=「自由协作优先」。**击穿信号**（建议作为 M40 启动判据，沿 18 号既有触发条件具体化）：①同一项目会话被反复用于结构雷同的多步流程（用户开始写「先 A 后 B」类约束提示词）；②出现「并行三个成员都完成才能继续」的硬依赖（自发并发不保证）；③需要流程级重跑/断点续跑（现只能整轮重问）。
8. **HITL**：成员内审批/ask_human 机制上可穿透恢复（§2.2），且 per-member 审批策略独立生效（成员工具按各自 tool_approval 包装）——授权面 per-member 是当前的一个**强项**（与 49 号 Dots「授权不随委派扩散」原则同向）。

## 5. 演进建议（待拍板，不立项）

### P1（容错与资源控制包装器——低改动高收益，纯装配层）

- **A1 成员错误降级回喂**：在 NewAgentTool 外包容错包装器（assembler 已有 normalizeEmptyArgsTool 包装先例）——捕获成员 error→结构化错误文本作为 tool result 回喂（含错误类型/成员名/已耗迭代）+发 run.warning 事件；协调者获得改道/重试/向用户说明的机会。**边界**：中断类错误（审批挂起）必须继续上抛不可吞（CompositeInterrupt 语义）；run.error 对「协调者自身错误」语义不变。
- **A2 per-member 超时与预算**：包装器内 context.WithTimeout（member 级配置，缺省不设或取 agent 级新列）；超时同 A1 路径降级回喂。token 预算依赖 usage 归因（成员 model.step 已带 agent 名，可聚合），一期先做超时。
- **A3 委派单结构化**：NewAgentTool 输入 schema 从单 request 字符串扩为 {task, context?}（或平台侧包装器解析约定字段），委派时落结构化 delegation 记录（事件或表）——委派卡/拓扑图/审计获得一等数据；顺带治 G7。

### P2（上下文与并行增强）

- **B1 成员上下文注入选项**：装配期可选注入「相关上下文包」（会话摘要/绑定文件清单/本体 guide——成员已有本体 guide 注入先例），治 G3 的「裸字符串」；Eino `WithFullChatHistoryAsInput` 不建议直开（共享全历史=隔离防火墙失效，44 号 transfer 教训同源）。
- **B2 并行感知修正**：泳道从单栈改区间模型（enter/exit 按成员名配对而非栈）、拓扑计数去 transfer 双发（先按 §7 未验证项做端到端复核实证）。
- **B3 深度>1 评估**：成员再委派（成员装配时可选挂载其他成员）——成本=循环委派防护+预算树；触发驱动，出现真实分层协作诉求再启动。

### 观察项/触发驱动（维持既有占号）

- **REQ-208（后台委派+steer+冷恢复）**：控制面补全的正解，维持触发驱动；G5 的用户痛点声响是领取信号。
- **REQ-205（workflow 编排）**：维持触发驱动，建议采纳 §3.7 三条击穿信号作为 M40 启动判据具体化。
- **55 号 C3 LongRun**：与后台委派同根（委派不占协调者迭代），M40 设计时联动。
- **成员记忆/跨轮状态**：随伴生线/记忆线演进（成员绑定伴生本体已支持——成员知识沉淀有载体，会话记忆无）。

### 架构健康面（明确不动）
