# 动态工作流 L0 前置取证评估（五模式断点量化）

> **定位**：REQ-560/M367 交付主体（79 号评审终稿 §二 L0 层 + §三 第 0 步）。评估件沿 M294 Rerank 评估收口先例（做/不做均回写+触发条件落档）；**受益者口径如实声明：本评估的任务样本取自开发者本人 E1 自用场景（本仓库的日常开发动线），不构成「定位件优先例外」强度——无论结论如何，WF 批领取严格按 M359+ 里程碑序排队不插队**（79 号 §六拍板项 2，本评估采产品评审倾向=按序，待开发者终裁）。
> **评估方法与诚实边界**：断点量化=**静态语义分析+代码证据**（每断点给 file:line 亲证锚点，本轮全部逐条复核——runner.go 因 REQ-551 recallMemory/run.started 插入整体 +10~12 行漂移，本档引用均为漂移后新锚点）；**活跑未执行**——本机与隔离冒烟环境均无模型连接（healthz `model_default_conn: not_configured` 亲证），真实多代理活跑复验挂账（触发=任一配置模型连接的环境可用时，复验清单见 §四）；静态分析对「模式语义缺原语」类断点是决定性的（缺条件边/缺汇聚/缺重跑是 schema 级缺失，非调参可弥合），对「计划质量/成本」类问题无发言权——后者本档不作断言。

## 一、五任务断点量化

评估任务全部取自本仓库真实开发动线（E1 自用）；「现有承载」= 现有五模式（free/sequential/parallel/loop/plan_execute）+agent_as_tool 委派的最优组合跑法；「断点」= 该跑法下无法表达或必然退化的语义，均给代码级证据。

### T1 文档勘察 → 多代理评审 → 立项落档（三阶段异质流水线+门禁回环）
- **任务**：给定需求池条目，先勘察相关代码与文档，再由 2~3 个评审视角（架构/风险/产品）独立评审，意见汇合后人工裁决，落档立项。（79 号/106 号/107 号皆此动线的产物——E1 高频。）
- **现有承载**：plan_execute 可表达线性三步（Steps []string，eino prebuilt/planexecute/plan_execute.go:80 亲证——字符串步骤列表）；评审并行须改 parallel 模式（成员即节点固定拓扑，assembler.go:845 assembleWorkflow）。
- **断点**：①**评审→裁决→落档是条件分叉**（意见不合→回勘察；裁决否→终止）——planexecute 的 execute→replan 循环（plan_execute.go:851-870 MaxIterations 环）重规划的是**同一执行器的线性计划**，无「按评审结果走不同分支/终止」的显式条件边原语；②**人工裁决卡点无法嵌在阶段之间**——interruptState 为会话级单槽且只承载 ask_human/approval 两 Kind（runner.go:841-843 亲证），工作流节点挂起仅有 Node 标注字段（:851）无 gate Kind 与恢复分流，人审只能靠审批包装层的工具审批（stepApprovalWrap，assembler.go:1541 附近）或对话外人工介入打断运行；③三阶段成员集不同——planexecute 执行器=首个成员固定（assembler.go:347-352 注释「执行器=首个成员」+planexecute.Config 仅传 Planner/Executor/Replanner :964 亲证），勘察者/评审者/落档者无法分阶段换人。
- **DAG 增益判定**：**高**（条件边+门禁节点+分阶段成员三缺并存；缺一可忍，三缺并存在 E1 主动线上每单必踩）。

### T2 多代理并行评审 + 汇聚汇总（并行 join 语义）
- **任务**：同一交付物交 3 个评审智能体并行独立评审，全部完成后汇总为对照结论（79 号立项前的三镜头评审即此形态）。
- **现有承载**：parallel 模式（adk 并行原语，assembler.go:899 case 分支族）——成员并行执行。
- **断点**：**无汇聚 join 节点**——assembleWorkflow 把成员拼为并行组后无「全成员完成后运行汇总者」的原语位（adk.NewParallelAgent 语义=并行发出、事件按流归集，assembler.go:899 附近 case 分支无 join 配置位）；汇总目前靠协调者读 trackAgent 启发式事件流（runner.go:1019-1031 workflow.node 由 lastAgent 名称迁移启发式驱动亲证）事后人工补跑——「并行结果→下一阶段输入」这一步在现有模式里是**人工桥**。
- **DAG 增益判定**：**高**（join/汇聚是 DAG 合成器的第一类价值；parallel 模式缺的就是它）。

### T3 出题流水线（反例——如实记录零增益）
- **任务**：CQ 出题→快筛→掌握度落库（REQ-524 已交付，M331）。
- **现有承载**：线性 handler 链（docs/03:874 ✅ 亲证），plan_execute 亦可表达。
- **断点**：**无断点**——线性管道对 DAG 零增益（79 号 product#2 判断，本轮维持：出题闭环不充当动态工作流的首个用例，REQ-545 独立轨道不受本评估影响）。
- **DAG 增益判定**：**零**（如实记录，防「为图而图」叙事把它当 killer 用例）。

### T4 修复 → 验证 → 重跑循环（节点级重跑缺失）
- **任务**：修一处 CI 缺陷→跑门禁→若红则按失败项修对应文件→重跑（本会话 REQ-549/550/551 交付轮的真实动线；KG 批 CI 收口轮同类）。
- **现有承载**：loop 模式（MaxIterations 3，assembler.go:901 NewLoopAgent 亲证；告警「loop 迭代上限固定 3」:855）。
- **断点**：①**迭代上限 3 不可配**——修复类任务第 4 轮常见（79 号护栏锚点句亲证），当前只能拆会话手工续；②**无按节点重跑**——失败后只能整循环重来，无「从验证节点重跑、上游修复输出保留」的原语（REQ-205⑤ 只读可视化边界内，现有五模式无任何重跑通道；79 号 arch#4 已把 rerun 端点前移 L1 列为交付件）；③验证红/绿的**分支终止条件**同 T1 断点①。
- **DAG 增益判定**：**中高**（loop-back 边+节点重跑两项；上限可配属护栏件非结构性缺失）。

### T5 研发数据批量接入（动态成员集断点）
- **任务**：接入五类研发数据源（REQ-554 立项中），每类源由对应能力智能体处理，成员集随任务清单动态变化。
- **现有承载**：agent_as_tool（固定成员集——project_agent 成员表装配期定型，assembler.go:845 assembleWorkflow 入参 members 由 ListProjectAgents 载入 :848-850 亲证；成员 prompt 装配期一次定型 :1073-1084 区段）。
- **断点**：①**成员集装配期冻结**——运行期按任务增减成员无原语（79 号「固定成员集」断言的代码坐实）；②后台委派产物为 2000 rune 纯文本摘要（delegate_bg.go:33 DelegateResultDigestCap 亲证），跨阶段类型化传递不可能（变量表缺失=79 号 arch#2 两档语义的动机）。
- **DAG 增益判定**：**中**（成员固定对五类源可预先配齐五成员缓解——断点真实但可用配置绕行；类型化传递缺失才是硬断点，归变量表件）。

### 断点汇总（量化结论）
| 断点原语 | 命中任务 | 现有最近似承载 | 证据 |
| --- | --- | --- | --- |
| 条件边/分支终止 | T1 T4 | planexecute replan（线性重规划） | plan_execute.go:80/:851-870 |
| 人审门禁节点（gate Kind+恢复分流） | T1 | 工具审批包装/会话级单槽 interruptState | runner.go:841-843/:851；assembler.go:1541 区 |

**结论**：E1 高频动线（T1/T2/T4）命中 7 项断点中的 5 项结构性缺失（schema 级、调参不可弥合）；T3 为零增益反例已如实隔离；T5 有配置绕行。**「现有五模式+委派不够用」在开发者自用动线上成立**——但成立域=E1 自用，画像用户场景证据为零（如实）。
