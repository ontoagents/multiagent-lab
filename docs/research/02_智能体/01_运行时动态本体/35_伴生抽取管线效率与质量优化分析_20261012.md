# 伴生抽取管线：效率与质量优化分析（2026-10-12，待拍板）

> 触发：开发者反馈「实际测试发现在智能体对话中抽取伴生本体时，抽取效率和质量没有达到预期。分析抽取伴生本体的实现过程，在抽取过程配置可视可配、IA、架构设计等方面有哪些可以改进的地方」。本文为 REQ-303 立项依据（分析档，未立项未实施）；伴生线主事实源见 [31 号动态薄本体可行方案](31_动态薄本体_可行方案.md)。

## 一、现状链路盘点（代码级，2026-10-12）

```
Run 收尾（run.finished）
 └→ OnRunComplete：开关+归属校验+本体级互斥（running）
     └→ extractRounds：抽取互斥 + pendingExtract 补抽标记（REQ-282 B1）
         └→ ExtractNew（逐窗串行）：
             1. ListMessages(convID) —— 全量拉会话消息
             2. remainingAfter(游标) —— 内存过滤增量
             3. knownEntityLabels —— 图内实体对齐清单（REQ-194①+别名平铺）
             4. splitWindows —— ≤16 消息 / ≤8k 字符 / ≤3 窗（超出积压标记续抽）
             5. 逐窗 GenerateStructured（每窗独立 extractTimeout 预算）
                → parseExtractOut（REQ-300 容错+回喂重试一次）
                → pruneCompanionCandidates（自指/批内去重/悬空注记，REQ-283）
                → ScanGenusCandidates（A3 属类规则）
                → MarkAssociations（E2 关联标记，需 embedding）
                → CreateCompanionCandidates（批落库）
                → 自动入图（≥阈值 且 批内分位 ≥0.5）→ 游标推进
             6. 事件族透出：started（fresh/windows/pending/budget）→ 每窗 candidates
               （count/items/pruned_detail）→ done/error
```

配置面现状：agent 侧板伴生配置=绑定本体（REQ-216）+领域聚焦提示（REQ-187①）+抽取连接覆盖（187②）+自动入图阈值（187③）；过程可视=对话内伴生卡（REQ-281，started/done 事件）+TraceDrawer 伴生分组。

## 二、效率问题（E 系，5 项）

| # | 问题 | 代码证据 | 影响 |
|---|---|---|---|
| E1 | **消息全量拉取** | `ListMessages(convID)` 无游标条件（messages.go:25），每轮抽取拉全部历史消息（含 meta 大字段），仅为内存过滤增量 | 长会话（1000+ 消息）每轮 IO/内存浪费线性增长；游标之后通常仅几条新消息 |
| E2 | **窗间串行** | 逐窗串行 LLM 调用；3 窗×思考模型分钟级=整轮 3 分钟+ | 抽取延迟线性叠加；REQ-282 每窗独立预算已治「超时」，未治「时长」 |
| E3 | **温度不可控** | `GenerateStructured` 签名无温度参数（structured.go:33），用连接默认温度 | 抽取是结构化任务适合低温（0~0.3）稳定 JSON 输出；高温增加格式漂移（REQ-300 数组根等解析失败的概率源）与幻觉 |
| E4 | **语料原样进 prompt** | renderCorpus 直接拼消息正文（截 600 字符/条）——markdown 代码块/表格原样携带 | 代码块 token 浪费+噪声干扰抽取（代码里的标识符易被误抽为概念） |
| E5 | **深积压追平慢** | 积压>3 窗时 pendingExtract 下轮续抽（每轮最多 3 窗） | 长对话后需多轮对话才能追平抽取；中间窗口语堆积越久质量越差 |

## 三、质量问题（Q 系，4 项）

| # | 问题 | 代码证据 | 影响 |
|---|---|---|---|
| Q1 | **窗边界切断语义** | splitWindows 按消息条数/字符硬切 | 一个话题切两窗——跨窗概念/关系漏关联（31 号 §16.1 G4 已识别未治） |
| Q2 | **跨轮重复候选** | pruneCompanionCandidates 只批内去重（REQ-283）；落库前与 pending 候选无比对 | 同事实跨轮重复产候选（同名同定义），确认流重复噪音（入图侧有印证聚合兜底，候选侧无） |
| Q3 | **单遍抽取无精炼** | 一遍 LLM 抽取即落库；定义常为一句话 | 概念浅（定义无细节/无同义词）；可选「精炼轮」（批量补定义/同义词）缺失 |
| Q4 | **对齐清单只有名称** | buildAlignmentSection 注入名称列表（>80 聚类取样） | LLM 判断「对话中的 X=已有实体 Y」缺定义依据——异名漏归并（31 号 §17.2 E1 同源，遗留未做） |

## 四、配置可视可配（C 系，3 项——开发者点名维度）

| # | 问题 | 现状 | 改进 |
|---|---|---|---|
| C1 | **抽取参数黑盒** | 窗尺寸 16/8k、最大窗数 3、批尺寸、重试次数全为 Go 常量硬编码 | 伴生配置页「抽取高级设置」（每 agent：窗尺寸/最大窗数/温度；全局 env 兜底默认） |
| C2 | **提示词黑盒** | companionPrompt 硬编码于 companion 包（REQ-187 hint 仅追加）；OntoChat 已有 PromptDef 只读可见先例（ontochat/prompts.go + GET /prompts） | 伴生抽取/挖掘提示词注册进只读可见体系：GET /api/companion/prompts+侧板「查看抽取提示词」（只读，单源） |
| C3 | **过程可视半成品** | 事件族字段已齐（started: fresh/windows/pending/budget；每窗 candidates: count/pruned），伴生卡只渲染 started/done 两态；失败详情需手动开 TraceDrawer | 伴生卡窗级进度渲染（N/M 窗·产出 X 条·积压 Y）+失败「查看详情」直达 TraceDrawer 伴生分组+游标/上次抽取时间可视 |

## 五、IA 与架构设计评估

**架构健康面（保持）**：旁路管线零侵入主链路 ✓；每窗独立预算+游标停上窗末的失败语义 ✓；解析容错+回喂重试（REQ-300）✓；事件族过程留痕（REQ-281）✓；绑定本体化后图作用域清晰（REQ-216）✓。

**IA 建议**：
1. 伴生卡升级「伴生沉淀面板」：状态区（引擎/游标/待确认/上次抽取）+过程时间线（事件族渲染）+「立即抽取」手动按钮（增量补抽，复用 pendingExtract 管道）——自动为主、手动兜底；
2. 失败可达性：伴生卡失败态加「查看详情」直达 TraceDrawer 伴生分组（现在两跳且无引导）；
3. 抽取配置与绑定同页（侧板伴生配置）维持——会话级覆盖（REQ-302 已立项）落地后伴生卡加「当前本体」展示，配置 IA 不新增页面。

## 七、验收草图（P1）

长会话（500+ 消息）触发抽取——DB 查询仅扫游标后消息（EXPLAIN 可证）；伴生卡实时显示「第 N/M 窗·产出 X 条」；侧板可见当前抽取提示词全文与参数值；参数调整后下一轮抽取生效。
