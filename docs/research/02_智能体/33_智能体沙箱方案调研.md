## 0. 结论速览

1. **M10 阶段一（Docker 单机）骨架完成度远超"未激活"的表观状态**——agentd 二进制骨架（manifest 拉取 + 内存 SQLite + 容器内密钥 + /run SSE）、DockerBackend（Start/Stop/Status + 对账 + healthz 等待 + 资源限制 `--memory=512m --cpus=1`）、SANDBOX_IMAGE 开关、compose 注释开关均在库。**缺口主要是"没跑通过"**：无端到端实测记录、agentd 镜像构建未验证、生命周期无前端可见性、网络/文件边界未成体系。
2. **推荐路线**：方案 A（per-agent agentd 长驻容器）为基线，按 10a→10e 阶段化推进（§3）；**per-run 一次性容器**作为 A 的调度变体（可选）；**K8s Pod** 为 P2 部署形态扩展；**gVisor/Kata** 作为与 A/B/D 正交的运行时叠加选项；**E2B 类外部沙箱服务仅作参考，不引入**（依赖纪律同 D-O15 逻辑）。
3. 排期建议：M10 拆四阶段入待办，10a（最小闭环实测）可由任一开发会话以小成本领取；10b 起按迭代排。

## 1. 目标与约束

- **隔离对象**：Agent 执行体 = ADK 装配 + 模型调用编排 + 工具执行（current_time / 本体 onto_* / 知识检索 / 项目文件工具）。不是任意代码解释器——那是"工具级沙箱"（见 §2 方案 F），两者不混谈。
- **平台约束**（继承 01 §7 / Q-17 / D-O15）：
  - 本地单机学习平台；低成本；一条 run-dev 启动心智；
  - 不引入 Python 运行时（D-O15）；新引入开源依赖须先登记 15 号；
  - Q-17 反转条件仍有效：无 Docker/K8s 环境则长期 inprocess，docker 后端可延后——本次调研即"反转条件满足时怎么做"的预案成品化。
- **必须保留的跨边界语义**：SSE 事件时间线（REQ-117 调试档/装配快照/工具耗时）、对话级工具审批覆盖（REQ-135②）、项目目录文件边界（REQ-114）、/mcp 对外服务（REQ-131）、知识库/本体挂载。

## 2. 候选方案对比

### 方案 A：per-agent agentd 长驻容器（现状骨架，M10 原设计）

主平台按需拉起 `eino-lab/agentd` 容器（每 Agent 一个，名 `agt-{agentID}`），启动时凭一次性 MANIFEST_TOKEN 拉 manifest（agent/模型连接明文 key/技能），容器内完成 ADK 装配；主平台经容器端口映射调 `/run`（SSE 透传）。历史权威在主平台（runDocker 已实现消息组包）。

- 隔离强度：进程/文件系统隔离；资源限制已内置（512MB/1CPU 可参数化）。
- 冷启动：镜像本机已有则秒级（healthz 等待 60s 上限）；首轮体验可接受。
- 实现成本：**低**——骨架已在，缺实测、生命周期 UI、边界体系化。
- 学习价值：最高（LG-15 全部触点：镜像/下发/生命周期/资源限制/一致性验证=验收 14）。
- 风险：容器内 manifest 含明文模型 key（边界即容器；Token 一次性缓解下发链路）；`-P` 随机端口在本机多容器下可控。

### 方案 B：per-run 一次性容器

每次运行拉起新容器、run 完即毁（`docker run --rm`）。隔离最强（无跨运行状态残留）。

- 成本：在 A 上加调度变体（生命周期改为一次性 + 历史仍主平台权威，agentd 已无状态化设计，改造成本小）。
- 代价：每轮对话冷启动延迟（首次拉镜像后 ~1~3s）；多轮 ReAct 若全程容器内则一次 run 一个容器即可（agentd 单进程内完成迭代），可接受。
- 定位：**A 的配置变体**（`SANDBOX_MODE=agent|run`），作为学习对照（"长驻 vs 一次性"的隔离/性能教学点）。

### 方案 C：rootless Podman（运行时替代）

与 Docker CLI 兼容（`PODMAN` 参数化），rootless 无守护进程。Linux 单机下更安全的默认；macOS/Windows 经 podman machine（仍是 VM，收益降低）。

- 定位：P3 可选——作为"容器运行时可替换"的教学对照，不在主线。

### 方案 D：K8s Pod per agent / per run（原 P2）

本地 kind/k3d/minikube；Pod 方案（Deployment 长驻或 Job 一次性）+ ResourceQuota/LimitRange + NetworkPolicy 出口白名单（仅模型 API 与主平台 SVC）。

- 成本：中——需 K8s 客户端依赖（client-go 或 kubectl exec 包装）、RBAC、镜像仓库（本地 registry/load）。
- 价值：LG-15 的 K8s 部分；与 compose 形态对照学习编排差异。
- 定位：P2 阶段（10d），前置 A 跑通。

- **备选运行时（2026-09-25 开发者指示登记）**：**Agent Substrate**（开源，K8s 之上的高密度 agent 沙箱运行时——宣称较原生 K8s 10 倍沙箱密度、secure-by-default、支持百万级沙箱与逻辑 Agent 跨节点调度）+ **Kubernetes Agent Sandbox**（隔离有状态单例工作区的生命周期管理）——二者定位为 10d K8s Pod 后端的**运行时/调度层备选**，M20 后期评估引入（学习平台当前单机规模用不上，登记备查）；InfoQ《Rethinking the Deployment Unit for AI Agents on Kubernetes》为设计语境。

### 方案 E：强隔离运行时叠加（gVisor / Kata Containers）

gVisor（Google，runsc：用户态内核拦截系统调用）与 Kata（轻量 VM）以 **container runtime** 维度叠加在 A/B/D 之上（`docker run --runtime=runsc` / K8s RuntimeClass），不改平台代码。

- 定位：**可选叠加**（10e）：一条开关的教学对照（"同一 Agent，换运行时，隔离边界变化"）；默认不启用（gVisor 对 SSE 长连接/网络转发有兼容性面，需实测）。
- 依赖纪律：均为成熟开源（Apache-2.0），引入方式是运行时选择而非代码依赖，15 号登记即可。

### 方案 F：外部沙箱服务（E2B / Daytona / Firecracker 自建）

E2B 等提供 AI 场景的 microVM 沙箱（代码执行器定位），自托管版本存在。

- **不引入**：定位错配（它们解决"不可信代码执行"，本项目 Agent 执行体是可信自有代码）；重依赖与离线约束冲突（D-O15 同逻辑）；作为"工具级沙箱"（未来若做代码解释器工具）的参考登记 🔭。

## 4. 安全边界设计要点（跨方案通用，10b 落地清单）

1. **资源**：memory/cpus/pids-limit 按 Agent 参数化（默认 512m/1cpu/100）；
2. **网络**：容器内仅需要两类出口——模型 API（公网）与主平台回访（host.docker.internal/服务名）；进程网络默认 bridge 隔离，10d 起 NetworkPolicy 白名单化；/mcp 对外端口不挂进沙箱容器；
3. **文件**：项目目录以 **bind-mount 只读/读写显式声明** 替代宿主直读（REQ-114 沙箱语义延伸）；容器内临时目录即弃；
4. **密钥**：沿用现设计——一次性 MANIFEST_TOKEN 下发明文 key，边界=容器内（密钥不出容器的内存 SQLite + 容器内密钥文件）；Token 一次性 + 短时效可再收紧；
5. **审批**：Agent 级/对话级审批语义在沙箱路径同样生效（审批挂起事件透传主平台，交互面仍在主平台 UI）；
6. **防循环**：装配期 /mcp 自引用拦截（已交付）在容器内 agentd 同样生效；跨容器调用链深度上限（事件头 depth）入 10b；
7. **观测**：SSE 透传保序；事件 `source` 增 external 标注；容器 stdout 采集入 16 号日志目录。
