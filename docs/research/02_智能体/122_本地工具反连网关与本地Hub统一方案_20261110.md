# 122 · 本地工具反连网关与本地 Hub 统一方案

> 状态：Active v1.0 ｜ 2026-11-10 ｜ REQ-622-fa8d / M432-fa8d 立项底稿与详设单源（01 §3.31）
> 决策：2026-11-10 开发者拍板「**放弃 frp 过渡，直接选择服务网关和本地 Hub 方案**」
> 归属：智能体模块（01 §3.31）；方案级文档（过程调研区，非现状叙述源——现状问题改 handbook）

## 0. 决策记录与沿革

- **问题起点**：开发者的智能体平台部署在公网（自研自维护，可定制开发；不允许外部客户端 SSH 连接服务器），用户经 Web 浏览器访问；而 TBtools-II 等生信工具运行在用户本地 Windows 桌面（NAT 内网，TBtools RPC 仅绑 `127.0.0.1:8765`）。目标：服务端 agent 能调用本地桌面工具。
- **调研实证**（2026-11-02~11-09，平台外本地原型）：TBtools-II 内置 JSON-RPC over HTTP 服务（188 方法/110 业务工具）非原生 MCP，已在本机完成「MCP stdio 桥接 + 平台 kind=stdio 连接器」全链真机验证（探针 110 工具/真实 FastaStat·热图渲染/LLM 自主选工具出图）；tbtools-cli（PyPI，9 编排原语）经 node shim 透传接入并修复三缺陷（mcp SDK v2 移除 FastMCP 需 pin `mcp<2`；FastMCP/anyio 进程内 spawn 继承 stdin 句柄挂死需 `stdin=DEVNULL` 补丁；非 UTF-8 环境下 CLI 输出含 ⚠️ 即 GBK UnicodeEncodeError 崩溃需 `PYTHONUTF8=1`）。原型资产在仓库外本机（`D:\Programs\TBtools\mcp-bridge\`），其发现/调用/参数 schema 解析逻辑是本方案 Hub 的直接前身。
- **方案权衡沿革**：网络层隧道（Cloudflare Tunnel/ngrok）因第三方收费/域名依赖被开发者排除；Tailscale 需服务器宿主装客户端与「服务器零协作」约束冲突；`ssh -R` 反向隧道被「不允许 SSH」约束排除；frp 自建（frps 旁路跑服务器）曾列为过渡方案，**2026-11-10 开发者拍板放弃 frp 过渡**——frp 需本地双进程双配置、无配对 UX、按「端口×工具」矩阵扩展不可持续，一次性直达应用层反连网关。
- **本方案两条用户级要求**：连接稳定可靠（第一优先）；用户简单便捷（配对即用、日常零操作）。

## 1. 问题定义与硬约束

1. **硬约束 A（方向性）**：本地桌面在 NAT 后、TBtools RPC 只绑回环——服务器永远无法主动连入本地；一切通道必须由**本地主动出站**建立，服务端调用沿已建立通道下行。
2. **硬约束 B（服务器侧）**：公网部署、自研可定制开发（可加功能），但不允许 SSH、不接受第三方收费隧道——通道的服务端组件必须是平台自研模块，且不增加服务器运维面上的新协议暴露（除平台自身端口外仅复用现有 TLS 入口）。
3. **硬约束 C（信任边界）**：agent 是公开服务——服务端被攻破或 prompt injection 的最坏情况 = 在用户桌面执行任意工具；本地工具接入必须默认全拒绝、逐个显式挂载、审批/审计管线强制在环。
4. **通用性要求**：不止 TBtools——桌面上的**有 MCP 能力**（stdio/HTTP MCP server，生态存量最大）与**无 MCP 能力**（自定义协议本地服务/CLI）工具都要能接；且同一套方案兼容 **agent 在远程服务端**与 **agent 在本地客户端**两种运行位置（2×2 矩阵，§3.2）。

## 2. 目标与非目标

**目标**：
- G1 服务端 agent 可调用本地桌面工具（MCP 与非 MCP 统一为 MCP 工具形态进入现有装配/审批/审计管线）；
- G2 稳定可靠：本地仅出站连接、断线自愈、服务端诚实降级、端到端可探测；
- G3 简单便捷：一次性安装（自启），配对三击以内完成，日常零操作（开机即在线）；
- G4 通用：新增桌面工具 = 本地配置加一行（标准 MCP）或写一个适配器（非 MCP），通道与平台零改动。

**非目标（v1 边界，诚实标注）**：
- 不做本地入站监听的任何形态（无端口映射/无公网暴露的本地服务）；
- 不做跨用户工具共享市场（每设备绑定单用户账号）；
- 不做 GUI 自动化类工具（留适配器扩展位，不内置）；
- 不承诺本地离线时的任何工具能力（离线=诚实降级，不缓存伪造结果）。

## 3. 统一分层架构

### 3.1 四层模型

```
L4 平台侧   MCP 客户端连接器（kind=mcp）＋ 工具审批/审计管线            —— 全场景复用零改动
             │
L3 接入层   场景A 远程：服务端网关（MCP 门面 ↔ WSS 通道）│ 场景B 本地：127.0.0.1 回环 HTTP
             认证=设备令牌（一次性配对码兑换）                        认证=回环令牌文件
             │                                                        │
             │        L2 聚合层（本地 Hub 守护进程，全场景同一套）        │
             └────────►│ 工具聚合 · 命名空间 · 健康模型 · 配置 · 版本握手 │◄────────┘
                       │ 对外恒定暴露「一个 MCP 端点」                    │
                       ├────────────────────────────────────────────┤
                       │ L1 能力挂载层（四类来源，插拔式）                │
                       │  ① stdio MCP server（spawn 挂载）              │
                       │  ② HTTP MCP server（回环直连挂载）              │
                       │  ③ 非 MCP 适配器插件（自定义协议→MCP 工具）      │
                       │  ④ 内置高危模块（文件/命令——默认关闭）           │
```

**核心抽象**：L1+L2（Hub）与 agent 位置完全解耦——Hub 永远是常驻本地服务，恒定对外暴露「一个聚合后的 MCP 端点」；唯一随场景变化的是 L3 transport 与其认证。服务端 agent 与本地 agent 消费的是**同一个 Hub、同一份工具清单语义**。

### 3.2 场景矩阵（2×2 全覆盖）

| | 工具有 MCP 能力 | 工具无 MCP 能力 |
|---|---|---|
| **agent 在远程服务端** | Hub 挂载（①spawn/②回环直连）→ 服务端网关经 WSS 透传 MCP 调用 | Hub 内**适配器插件**翻译为 MCP 工具（TBtools 适配器为样板）→ 同上 |
| **agent 在本地客户端** | 本地平台实例 `kind=mcp` 连接器直连 Hub 回环端点 | 同走适配器；连接器仍只见 Hub 一个端点 |

本地场景平台侧不需要网关组件；远程场景需要网关。四种组合的平台侧配置面完全同构（`kind=mcp` + url + 凭据），仅 url 指向不同（门面 vs 回环）。

### 3.3 关键设计决策（ADR 摘录）

| 决策 | 选择 | 理由（对照被否方案） |
|---|---|---|
| D1 MCP 协议逻辑放哪 | 本地守护进程内（复用原型桥的发现/schema 解析/调用逻辑）；服务端门面是 MCP-over-(HTTP↔WS) 透明转接器 | 门面保持协议哑管道——平台装配器零改动；适配器/发现逻辑随 Hub 本地演进，服务端不随工具生态膨胀 |
| D2 服务端连接器形态 | 复用 `kind=mcp`（门面呈现为标准 MCP Streamable HTTP 端点），**不新增 connector kind** | 连接器 CRUD/探针/凭据加密/60s 工具缓存/degraded 降级/审批审计全部现成；新 kind 的唯一收益是防呆，成本是全链路改造 |
| D3 Hub 形态 | 常驻本地服务（自启 + 托盘状态），对上回环 HTTP 端点；**不用**平台 stdio 连接器直接 spawn Hub | 平台 stdio 连接器每调用独立 spawn——Hub 承载长命子挂载（stdio MCP server/适配器状态），per-call 重建代价高且状态漂移；常驻同时服务多消费者（本地 agent/其他本地 MCP 客户端） |
| D4 通道 | WSS 出站长连接（复用平台 TLS 入口），心跳+退避重连+设备令牌 | 唯一同时满足硬约束 A/B 的通道；无第三方依赖 |
| D5 非 MCP 工具 | 适配器插件统一归一为 MCP 工具 | 远程/本地两场景共用适配器资产；平台永远只说 MCP |

## 4. 本地 Hub 设计（L1+L2）

### 4.1 能力挂载层（L1）

| 来源 | 挂载方式 | 例子 |
|---|---|---|
| ① stdio MCP server | Hub 作为 MCP client spawn（生命周期由 Hub 管理，非 per-call） | npx/node/python 的生态 MCP（filesystem/git/Playwright…） |
| ② HTTP MCP server | 回环直连（`127.0.0.1:*`），走标准 Streamable HTTP | 未来的 TBtools HTTP 桥等 |
| ③ 非 MCP 适配器 | 适配器插件：声明工具名/schema/执行入口，运行时翻译调用到本地协议 | **TBtools RPC 适配器**（原型桥逻辑迁入：`system.listMethods`+`describeMethod` 文本 spec→JSON Schema 动态发现、`ok:false`→`isError` 约定）；CLI 类可归纳为「命令适配器」模板（argv 模板+产物声明） |
| ④ 内置高危模块 | 文件读写/命令执行——**默认关闭**，显式授权 + 目录/命令白名单 | 谨慎规划，v1 可不实现仅留位 |

### 4.2 聚合层（L2）职责

- 工具聚合与命名空间：`{设备名}__{server}__{tool}`，多源重名消解；
- 统一健康模型：每挂载源 online/offline/degraded，端点级总健康（TBtools 未运行=该源 offline，其余源不受影响）；
- 统一配置面：`hub.config.json`（挂载清单/开关）+ 托盘 UI（状态灯/挂载勾选/配对入口）；
- 协议版本握手（`proto` 字段，两端同源可演进）、MCP 生命周期语义（tools/list 聚合、listChanged 通知传递）；
- 本地审计日志（本地视角：何时何调用何工具何参数摘要——远程场景服务端另有全量审计）。

### 4.3 运行形态

- 开机自启（计划任务/NSSM/服务三选一，安装脚本落地）；崩溃自动拉起；无状态转发（每次调用独立），重启零恢复成本；
- 配置热加载：挂载清单变更后 tools/list 即时反映（平台侧另有 60s 缓存，最迟一个 TTL 生效——沿 REQ-356 口径如实标注）。

## 5. 服务端反连网关设计（L3-远程）

### 5.1 组件

1. **WS 端点**（`wss://…/api/reversegw/ws`）：本地 Hub 出站连入；设备会话表（device_id→连接），同设备重连踢旧连（单活）；
2. **MCP 门面**（`/rv/{device}/mcp`）：对平台呈现为标准 MCP Streamable HTTP 端点——收到 MCP JSON-RPC 请求→经 WS 下发→等响应→回给 MCP 客户端；并发多路复用（门面分配 `mid`，模型并行调多工具是常态）；
3. **配对与设备管理**：一次性配对码（短时效）→ 兑换长期设备令牌；设备列表 UI（在线状态/挂载工具清单/吊销）。配对成功后**自动创建** `kind=mcp` 连接器行（url 指门面、凭据=设备派生令牌，AES-256-GCM 落库沿现有机制）。

### 5.2 复用与新增边界

- **复用（零改动）**：连接器 CRUD/测试探针（=端到端健康检查：服务器→门面→WS→Hub→TBtools）/工具缓存/降级事件/凭据加密/审批审计管线；
- **新增（网关内）**：WS 会话管理、心跳与在线判定、`mid` 复用、配对协议、设备令牌签发与吊销、按设备限流与消息大小上限；
- **平台主服务隔离**：网关独立进程部署（与主服务解耦——自研组件的 bug 面不波及平台核心，此点对应 frp「独立进程」优势的主动吸收）。

## 6. 通道协议草案（方案级）

| 帧方向 | 类型 | 载荷语义 |
|---|---|---|
| Hub→网关 | `hello` | 设备标识/proto 版本/能力摘要（TBtools 版本等）；网关回 `hello_ack`+挂载核对 |
| 双向 | `ping`/`pong` | 心跳（间隔 <15s，防家用路由 NAT 会话超时；连续丢失 N 次判离线） |
| 网关→Hub | `mcp` | MCP JSON-RPC 请求体（门面分配 `mid`） |
| Hub→网关 | `mcp` | MCP JSON-RPC 响应体（回 `mid`）；执行失败含人话错误 |
| Hub→网关 | `status` | 挂载源健康变更推送（TBtools offline 等）→ 门面 tools/list 如实反映 |
| 网关→Hub | `policy` | 服务端下发：吊销/限流/配置核对（配对变更时） |

消息语义约定：MCP 请求超时由门面控制（默认对齐平台工具超时上限）；Hub 对不可达挂载源返回结构化错误（含人话指引「启动 TBtools-II 或 rpc-start」），不静默吞错。

## 7. 可靠性设计

| 失败模式 | 行为 |
|---|---|
| 家庭网络闪断/NAT 重建 | WS 断→指数退避重连（1s→30s 封顶+抖动）→重新 hello；期间服务端连接器 degraded（平台现成语义：本轮不带工具继续跑），恢复后 60s 缓存过期自动续上 |
| Hub 进程崩溃/升级 | 自启服务拉起；无状态转发，重启零恢复；升级窗口=短暂 degraded |
| 服务器发版重启 | Hub 永久重试，服务恢复即自动回连；设备令牌不失效 |
| 设备重复连接 | 新连踢旧连（单活），避免双连接状态漂移 |
| TBtools 未运行 | Hub `status` 上报，门面 tools/list 对该源返回空/错误；其余源正常——**部分降级而非全有全无** |
| 端到端自检 | 平台现有「连接器测试」探针即全链健康检查（服务器→门面→WS→Hub→本地工具），UI 一键验证 |

稳定性来源三支柱：固定会话身份（设备令牌，非漂移地址）+ 两端同源可控的自愈策略（心跳/重连参数可验证）+ 平台既有诚实降级语义。失败语义上显式区分「设备离线」（fail-fast 人话）与「工具执行失败」（isError 结果）——此为相对网络层隧道（frp 端口黑洞式不可达）的语义优势。

## 8. 安全模型

- **信任边界**：公开 agent 服务获得触达用户桌面的通用通道=最大攻击面。默认全拒绝、用户逐源显式挂载；高危模块独立开关+白名单；
- **审批/审计**：反连工具进入平台统一工具管线——REQ-14 审批、run_event 审计、readOnlyHint 分级（REQ-231 面）自动生效，作为硬约束而非附加项；
- **认证**：一次性配对码（短时效单次）→设备令牌（可吊销可轮换，吊销即断连）；门面与 WS 双端校验；TBtools RPC 永不出回环；
- **传输**：WSS 复用平台 TLS；本地零入站端口（仅出站连接）——本地安全面不随工具数量发散；
- **限流与配额**：按设备限流、消息大小上限、并发 `mid` 上限（防服务端故障放大到桌面）。

## 11. 诚实边界与开放问题

**边界**：
- 本地桌面关机/离线=工具不可用（诚实降级），平台不做任何结果缓存伪装；
- 家庭网络质量决定 WS 稳定性下限（心跳可保活但不可救物理断网）；
- 非 MCP 适配器每类工具一份开发量（TBtools 已有原型，其他按需）；
- Windows 单机优先（原型与实证均在 Windows；Hub 跨平台为设计目标但 v1 验收面仅 Windows）；
- stdio MCP server 的进程生命周期由 Hub 托管（长驻），与平台 stdio 连接器「每调用 spawn」语义不同——两者并存不混用，文档需向用户讲清选择口径。

**开放问题**（实现期定）：
- 门面并发上限与 `mid` 超时回收策略的具体数值；
