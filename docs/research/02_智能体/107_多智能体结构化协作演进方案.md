## 一、背景与目标

平台多智能体协作已随 TurnLoop 引擎（REQ-385）、后台委派底盘、确定性工作流三档与 plan_execute 线性计划执行进入主链路，但协作形态整体仍偏「对话式」——计划由协调者以自由文本承载、分歧靠协调者自由文本汇流、过程可视性依赖逐事件人读、外部上下文接入散点化、演示交付缺一键通路。本档将八个领域的设计汇编为**结构化协作演进批**立项底稿，主线即「对话式协作 → 结构化协作」：

1. **计划结构化**（§三）：DAG 计划与调度，运行期动态并行编排；
2. **分歧结构化**（§四）：方案分歧以协议化 verdict 识别、人工裁决、结构化回注续跑；
3. **上下文结构化**（§五）：五类研发数据源统一接入既有连接器体系；
4. **过程资产化**（§六/§八）：运行事件流导出为自包含回放文件；多智能体协作建立过程账本（参与度/介入/耗时）；
5. **运行控制补全**（§九）：pause 安全点挂起与 redo 锚点重放重跑；
6. **交付环境兜底**（§七）：演示环境一键灌装、只读凭证与远程可访问部署路径（P0 编排缺陷修复先行）；
7. **能力自证**（§十）：设计文档与主流框架对比报告提纲（文档件）。

八域彼此独立、可并行领取；共同取向是**全部骑在既有底座上做增量**（见 §二），不新建运行引擎、不引入 Python 运行时（D-O15）、不重复造轮子（D-O5）。

## 三、结构化任务编排（DAG 计划与调度）

### 3.1 目标与能力定义

在既有编排谱系（确定性工作流三档 / plan_execute 线性计划执行 / 自由协作）之上补全运行期动态并行编排形态：需求输入后由规划者 LLM 产出结构化计划（JSON——节点=子任务+成员指派+产出契约，边=依赖关系），调度器校验无环后按入度就绪并行派发节点至后台委派底盘执行，支持失败策略（重试/跳过/终止）、汇合聚合、全量 DAG 状态事件与前端 DAG 视图、重启对账与挂起恢复。

### 3.3 方案设计

**选型：workflow_mode=dag 档作用户入口，实现为服务层计划-调度器（不另立领域实体/会话形态，不走 ADK 工作流原语）。** 理由：①ADK 三原语是装配期静态拓扑，而 DAG 计划由规划者在运行期才产出，硬做成自定义 adk.Agent 则调度循环的 goroutine 态无法进 gob checkpoint，与既有中断语义不自洽；②节点执行本就复用委派底盘（服务层行为），runOnce 分流缝现成（runner.go:503），runFinalize 收尾单源（verify 背压/不变量检查）零改动继承；③「独立计划-调度层」若做成新入口/新导航，违背单用户产品面克制且与工作流档割裂——分歧只在入口归属，归 workflow_mode 档成本最低（项目设置选择器/未知模式降级/快照告警全复用）。D-O5：不引外部工作流引擎（分布式常驻服务与单机自部署相悖），成环检测与入度调度为轻量纯函数；D-O15：零 Python 依赖。

**装配与执行**：dispatch 增 dag 分支（缺执行器落穿沿 plan_execute 先例，assembler.go:377）→ BuildResult.Workflow={Mode:"dag"}（assembler.go:69）→ runOnce 分流 s.runDagPlan：协调者模型结构化输出计划 JSON → 校验（无环/可达/成员指派合法；连败两次 run.error，不虚构兜底计划）→ 建 dag_plan/dag_node → 调度循环（并行度上限 4 起步）按入度就绪派发 DelegateManager.Start → 节点终态回填、入度递减解锁后继，直至汇合。

**数据模型（迁移号按 §〇 口径以落地轮 migrations 目录实况顺延领取，建表沿 072 ALTER/CREATE 风格；撰写时点目录最新 078，079/080 已被 docs/18 口头占用〔REQ-545/546〕）**：dag_plan(id/conversation_id/run_id/plan_json/status) + dag_node(id/plan_id/node_key/title/contract/member_agent_id/depends_on/status/attempt/result_digest/delegate_id/error/时间戳)。节点状态机 pending→ready→running→done|failed|skipped；计划状态 running/completed/failed/stopped/paused。

**失败策略与聚合**：节点失败重试 1 次（attempt 有界）→ 仍败按 plan 级 on_failure 二选一：skip_downstream（默认，失败沿下游与汇合传播 skipped）/ abort（Interrupt 全部 running 节点+未派发节点置 skipped）；join 节点输入=上游 done 节点 result_digest 拼装（≤2000 rune，沿 DelegateResultDigestCap 口径）；计划收尾由协调者模型一次聚合生成（如实标注 failed/skipped 节点），作为最终助手消息走 runFinalize 落库。

**事件面（event_names.go 追加常量，沿注册表单源风格）**：dag.plan.created / dag.node.started / dag.node.completed / dag.node.failed / dag.node.skipped / dag.plan.finished；data 携带 plan_id/node_key/attempt/member/summary；落库沿 EventSchemaVersion=2 盖戳，消费方按 type 白名单兼容读、无契约翻转；节点内 delta/tool 事件不向父会话转发（防事件风暴，过程细节看子会话）。

**与既有机制集成**：①审批/工具面/沙箱——节点=子会话一等会话，成员工具面/审批/CLI 沙箱全量继承既有语义，计划层不加审批点；②挂起恢复——子会话 ask_human/审批中断走既有 interrupt_state/Resume（runner.go:846/:1221）；③重启对账——沿 LoadOrphans 先例扫描孤儿委派对账节点态、计划置 paused，resume 端点重算入度（done 不重跑、ready 续派）；④REST——GET /api/conversations/{id}/dag-plans、GET /api/dag-plans/{id}、POST /api/dag-plans/{id}/abort 与 /resume，沿 handlers_delegates.go 风格；⑤前端——CollabTopology 扩展 DAG 视图（复用 @xyflow/react nodeTypes，节点五态徽标，事件回放驱动，回放零新后端可先行；abort/resume 随 REST 落地挂管理钮）；⑥todo_write 保持模型自写外显轨，不做强一致。

### 3.4 验收要点

1. 并行派发证明：两无依赖节点的子会话运行时间窗重叠（dag.node.started 事件时间戳交叉），且并行度不超上限。
2. 失败策略：桩模型令上游节点必败→重试 1 次→下游 skipped 传播、join 不死锁、计划终态 failed；dag.* 事件链完整，经事件回放端点可重建节点时间线。
3. 成环拒绝：规划者产出含环 JSON→校验失败报人话错误、不落库不入调度；连续两次失败按 run.error 收束。
4. 重启对账与恢复：运行中重启→running 节点经孤儿委派清点对账、计划置 paused；resume 后 done 节点不重跑（子会话无新运行）、剩余节点续跑至完成。
5. 回归不变：sequential/parallel/loop/plan_execute 四档装配产物与事件行为不变（assembler_workflow_test 全绿），未知模式降级语义不变。

### 3.5 诚实边界

不做执行期动态重规划与条件分支/循环边（纯 DAG 无环——重规划语义归 plan_execute 档、条件路由归自由协作档，DAG 档定位「计划一次成型+失败策略兜底」）；不做节点级人工审批点（审批在成员子会话既有工具面）与计划模板库/跨会话复用；不做分布式调度（单机单用户进程内 goroutine，重启对账沿委派底盘先例）；父会话只透出节点级粒度事件，节点内过程细节须进子会话查看；join 聚合基于结果摘要而非全文（全文在子会话）；计划质量依赖模型结构化输出能力，校验失败如实报错、不虚构兜底计划。

### 3.6 优先级论证与工作量粗估

归属智能体工程引擎层（01 域）：现有谱系（静态确定性三档/线性计划执行/自由协作）均不能表达「运行期多分支并行+汇合」，DAG 档是引擎编排能力补全而非新产品面；复用度高（委派底盘/事件契约/分流缝/拓扑面板均现成），边际成本低、收益为编排能力档位补全——建议排在编排类需求前列，于 plan_execute（REQ-455）之后立项成档。工作量粗估：整件约 2~3 REQ 当量；建议拆二交付——D1 后端（规划提示词+DAG 校验+调度器+事件+对账恢复+REST）约 2 REQ 当量，复用底盘度高、单轮可出调度闭环；D2 前端 DAG 视图与管理钮约 0.5~1 REQ 当量，独立一轮。

## 四、方案分歧结构化识别与人工裁决闭环（conflict）

### 4.1 目标与能力定义

为多成员协作动线补齐「方案分歧→人工裁决→回注续跑」闭环：审查成员按结构化评审协议提交 verdict JSON，平台在确定性规则档上识别分歧，命中即以既有挂起-恢复管线挂起运行并外显方案对比裁决卡；开发者采纳 A 案/B 案或给出第三案后，裁决结果结构化回注双方上下文继续执行。全过程以 conflict.* 事件落库，轨迹泳道与重放标注冲突点与裁决。能力口径：识别=结构化且平台确定性判定，裁决=必经人工，执行=复用既有管线；平台不做自动仲裁、不做产物自动合并。

### 4.3 方案设计（三个新件+一表，全走既有缝）

1. **`submit_review` 内置工具（识别+挂起合一）**：审查成员可用工具，入参 `{position, plan_summary, objections[], alternatives[]}`。执行体=记录 verdict（发 `review.submitted`）→ 平台侧纯 Go 规则档评估 → 命中分歧即 StatefulInterrupt（携带双方立场摘要的 ConflictInfo，形态同构 ask_human）→ 未命中返回 ack、协调者自然续跑。选型理由：判定点收敛在工具执行体内=确定性可单测、零新增运行实体、无 LLM 裁量；不做独立评审员/LLM judge（成本与幻觉边界，见诚实边界）。
2. **规则档 `conflict_policy`（项目级 JSON）**：默认档内置零配置可用（评审 disagree→挂起裁决）。规则条目两类触发：①review 点（上述工具体内确定性评估）；②event 点（如 verify_failed→打回产出方）——verify 在运行收束后执行（`verify.go:8-13` 既有边界），无活运行可挂起，故 event 触发落 `conflict_review(pending)` 行+conflict.detected，裁决后经**回注消息**发起新运行（与 ① 的 suspended 态并列，见 §4.5）。装配注入沿 ApprovalPolicy 模式（`approval.go:117-121`）。
3. **裁决卡前端扩展**：run.interrupted kind='conflict' 分支（`ChatWindow.tsx:1258` 挂起卡 + `eventRegistry.ts:17` 文案 + toInterruptState），卡面呈现双方方案对比与「采纳 A/B/第三案」动作。

### 4.4 数据模型

新增 `conflict_review` 表：`id, conversation_id, run_id, kind(review|event), rule_id, parties JSON（成员/角色/产物摘要）, verdicts JSON（verdict 原文）, state(suspended|pending|resolved|dismissed), resolution JSON{adopt: a|b|third, third_text, rationale, decided_at, decision_source}, checkpoint_ref, created_at`。迁移号按 §〇 口径以落地轮 migrations 目录实况顺延领取（撰写时点目录最新 078_ontology_hit_cited.sql；079/080 已被 docs/18 口头占用〔REQ-545/546〕，落地先查 docs/18 领号）。挂起载体仍是 interrupt_state 单槽（kind='conflict' + conflict_id 指针），表存全量审计；不迁移既有列、不动 scope CHECK。verdict schema 以 chat 包常量单源，解析失败 fail-closed 保守按 disagree 处理（judge.go 兜底口径）。

### 4.5 API/事件面

沿 event_names.go 常量风格，docs/02 §8 镜像同轮：新事件 `review.submitted / conflict.detected / conflict.resolved`；挂起外显复用 `run.interrupted`（kind='conflict'）。API 两个：`POST /api/conversations/{id}/conflicts/{cid}/resolve`（adopt + third_text + rationale）；`GET /api/conversations/{id}/conflicts`（审计/回放）。resolve 语义分两态：suspended→清 interrupt_state + ResumeParams.Targets 定向恢复（复用 Service.Resume 全链含并发闸，裁决文本经 GetResumeContext 进工具返回值）；pending→裁决文本+分歧要点摘要作为回注消息发起新运行（显式落消息流，用户可见）。两态统一落 resolution + conflict.resolved（decision_source=manual，审计对齐 approval.granted）。

### 4.6 与既有机制集成

审批/ask_human——共用会话级单槽，互斥语义不变（单会话同时仅一个挂起）；委派/多成员——评审协议经装配层注入审查成员（member_profile 同缝），CLI/A2A 外部成员以任务描述文本约定协议；工作流——工具级 interrupt 对工作流节点天然兼容（Node 定位 REQ-205③ 已在 `runner.go:826-842`），节点内评审注入不做；回放/泳道——conflict.* 落 run_event（`migrations/001_init.sql:63`）后，TraceDrawer 泳道沿既有标记机制加冲突点（检测/裁决两点标记+adopt 结果），重放文案走 describeEvent 单源。

### 4.7 验收要点

1. 双成员分歧默认档：评审 disagree → 发出 conflict.detected 与 run.interrupted(kind=conflict)，interrupt_state 落库、conflict_review 落行，前端渲染方案对比裁决卡（headless 冒烟含渲染与决议动作）。
2. 裁决续跑：resolve(adopt=b) 后运行从 checkpoint 定向恢复，工具返回裁决文本与双方分歧要点摘要，resolution 与 conflict.resolved 落库且 decision_source=manual。
3. 第三案：adopt=third 携 third_text 时，恢复后模型收到第三案全文。
4. 规则档两态：suspended 态 resolve 走恢复续跑；verify_failed 触发的 pending 态 resolve 走回注消息新运行；规则档关闭时零行为变化（既有动线回归不动）。
5. 重启不丢：冲突挂起后重启 backend，仍可 resolve 并恢复续跑（checkpoint 落库链）。
6. 泳道呈现：TraceDrawer 在冲突检测/裁决两点渲染标记与 adopt 结果，重放含三新事件文案。

### 4.8 诚实边界

- **不做自动仲裁/多数投票/产物自动合并**：裁决必经人工；采纳后的执行组织仍由协调者完成，平台不 diff/merge 双方产物。
- **不注入双方全量运行轨迹**：回注只含结构化摘要（分歧要点+产物摘要），预算沿 REQ-531 注入口径。
- **外部成员（CLI/A2A）协议无硬约束**：遵守依赖任务描述约定；解析失败保守按 disagree，挂起频率偏保守是已知代价。
- **event 类规则是运行后裁决（pending）**，不做运行中断（verify 在收束后执行的既有边界）。
- 单会话同时仅一个挂起裁决（会话级单槽既有语义，非新增限制）；工作流节点内评审协议注入不做；规则档只做项目级，无会话/全局覆盖与热更新。

### 4.9 优先级论证与工作量粗估

**论证**：多成员动线（DevTeam 模板/后台委派/成员画像路由）已交付，但分歧汇流仍只有协调者自由文本——多成员分叉处既是审计断链点也是用户失控制点；而承重件（checkpoint 落库、Resume 定向恢复、工具级挂起、事件契约单源、泳道标记）全部现成，属「管线已铺、缺语义层」的典型低边际成本增量。与 REQ-525（挂起触达）/REQ-527（Run 解耦重挂）同人机协同族，方向与平台评审批工程化收口一致。**排序**：建议排在 Q-24 工作区批（M355~M358）之后；领号先查 docs/18 注册表（当前登记至 REQ-551/M358，本批拟号见 §〇）。**当量 2~3 个 REQ**：①识别与规则档（submit_review/verdict 解析/规则评估+默认档+conflict.detected，后端为主）②conflict_review 表与 resolve（迁移/Resume 两态集成/审计事件）③前端裁决卡+泳道标注（挂起卡 kind 分支+eventRegistry 登记两处+冒烟轮）。粗估 1.5~2 个工作日（对照 REQ-543 词表注入单 REQ 单日粒度）；①②可后端先行交付，③独立冒烟轮。

- 与盘点口径差异：背景所写「GET /api/run-events」实为 `GET /api/conversations/{id}/run-events`（server.go:321）；「emitAndRecord ≈L274-282」实为门控/注入点，函数体在 L1848。

### 6.3 方案设计

**总架构（零迁移、读写分离）**：导出=后端只读投影（run_event→版本化 envelope→附件下载）；导入回放=纯前端离线行为（FileReader 校验 envelope→喂数据源改造后的 EventReplayDrawer），不写本地库。选型理由：导入若落库会制造外键悬空的伪 conversation 并污染统计/检索/伴生触发，违背最小写路径；导出复用 ListEventsQ 单一取数面，与 REQ-527 回放续看、REQ-217 轨迹过滤共享查询语义，边际成本最低，符合 D-O5 不重复造轮子。全程零 Python 依赖（D-O15）。

**文件格式（format_version 与事件契约版本正交）**：

```json
{
  "format": "ontoagents-replay", "format_version": 1,
  "generated_at": "...", "generator": "ontoagents@<version>",
  "source": {"conversation_id", "run_id", "agent_name", "title", "scope"},
  "fidelity": {"message_delta": false, "model_step": false,
               "tool_result_truncated": true, "schema_versions": [1, 2],
               "event_count": 42, "terminal_type": "run.finished"},
  "events": [{"id", "type", "data", "created_at", "schema_version"}]
}
```

events[] 直接采用 store.RunEvent 的 JSON 形状（与前端 RunEventDTO 同构），导出、导入均零变换。`format_version`（文件结构版本，导入端按大版本兼容）与 events[].`schema_version`（事件契约版本，沿 models.go:210 只增不改口径）两个维度互不绑定。fidelity 块按该 run 实际落库内容如实统计——把 EventReplayDrawer.tsx:64 hasDebugRecorded 的启发式标注升级为导出侧显式声明。

**API/事件面**：新增 `GET /api/conversations/{id}/events/export?run_id=`（注册沿 handlers_diag 附件先例）；仅允许导出已达终态的 run（该 run_id 已出现 run.finished/run.error/run.interrupted 之一，event_names.go:9-12），进行中运行拒绝并给可懂提示；文件名 `replay-{run_id}-{日期}.json`。事件类型值域一律引用 event_names.go 常量，不在导出路径新增或改写任何事件；tool_result_truncated 复用 REQ-224 既有截断标记判定。

**前端导入回放**：EventReplayDrawer 数据源抽参——新增可选 `events` prop，传入即离线模式（跳过 api.listEvents，纯本地渲染），在线路径零改动；TraceDrawer 加「导出此运行」按钮，聊天页加「导入回放文件」（Upload beforeUpload→JSON.parse→校验 format/format_version→喂 Drawer），离线态标题加徽标；RunEventDTO（`types.ts:332`）补 schema_version 字段声明（后端本就返回）。

**与既有机制集成**：审批/挂起恢复——approval.*、run.interrupted（`runner.go:928`）均为 schema_version=2 落库事件，导出自然包含；离线回放将其渲染为时间线节点，不提供决议/Resume 操作（审批动作只对活运行有效，文件是只读快照）。委派——subagent.delegate 由后台委派底盘直接 InsertEvent（`delegate_bg.go:67`）不经 SSE，导出从 run_event 取数，覆盖面天然优于 live 流；subagent.enter/exit、steer.* 同理按落库原样导出。回放续看（REQ-527）——导出与续看共用 ListEventsQ(run_id, asc) 取数语义，文件是「断连续看」的文件化对应物。

**保真度口径抉择（拍板）**：不调整默认落库口径（message.delta/model.step 维持 debug_persist 门控）——逐字符 delta 落库会让 run_event 表在单机 SQLite 下无谓膨胀，影响所有历史还原路径，全局成本换局部收益不成立；选「导出时如实提示」：fidelity 自声明+导入端复用 EventReplayDrawer.tsx:145-153 的警示形态。需高保真留档的用户在发起运行时勾选调试事件入库即可，缺数据的历史文件如实标注而非静默留白。

### 6.4 验收要点

1. 导出一致性：同一 run_id，导出文件 events[] 与 `GET /api/conversations/{id}/run-events?run_id=` 升序取数逐条相等（type/data/created_at/schema_version），且含 delegate_bg 后台委派事件。
2. 终态门禁：对进行中 run 请求导出返回 4xx 人话错误；出现 run.finished 后导出成功。
3. 保真度声明：未开 debug_persist 的 run 导出 fidelity.message_delta=false，导入回放展示「未记录调试细节」警示；开启后导出文件可完整打字机回放。
4. 离线回放：导入文件后前端零 API 请求（断网可回放），步进/自动播放/调速/级别过滤/诚实标注全部可用；format_version 超前文件被拒绝并提示而非崩溃。
5. 零迁移：不改任何表结构（migrations 无新增），run_event 写路径零改动。

### 6.5 诚实边界

不做：导入入库（文件不写本地库，不进统计/检索/伴生/出题语料）；进行中 run 导出；跨 run/跨会话聚合导出；文件加密与签名（明文 JSON，含完整工具参数与结果，分享前自行审阅，脱敏选项留后续）；补齐历史缺口（未开 debug_persist 的存量运行永远缺 delta/step，如实标注不可再生）。

### 6.6 优先级论证与工作量粗估

审计导出对应合规/工程画像的留档刚需，案例分享对应教学画像的演示刚需；技术上全面依附既有设施（REQ-527 回放取数、REQ-149 门控与诚实标注、REQ-217 run 维索引、REQ-224 截断标记、REQ-410 导出先例），不动事件契约与存储层，是低成本高复用件。不依赖 Q-24 工作区批与决策结构化借鉴批，可独立交付，建议排 P2（本批归入 P0 先行五件，见 §十一——依赖最少、可插空先领）。粗估 1~1.5 REQ 当量：后端导出端点+终态门禁+单测约 0.5；前端数据源抽参+导入入口+fidelity 呈现约 1（含 headless 冒烟）。

### 7.1 目标与能力定义

**一键演示 seed（脚本灌装，零新后端面）**：新增 deploy/demo-seed.sh + demo-reset.sh（bash+curl，D-O15 零 Python；设 PLATFORM_TOKEN 时自动携 X-Platform-Token）。幂等=「演示·」命名前缀查重跳过，重置按前缀走既有 DELETE API（本体删除受绑定者 409 保护）。灌装内容：演示项目×1、演示智能体（规划者+示例成员）与 REQ-417 种子任务 A/B 任务会话、种子本体（seed.K8sOps 经 /api/ontologies 反代面创建，端点形态实现时与构建平面实测对齐）、可选 A2A 自回环连接器（先探测 agent-card 可达才建，不可达如实跳过——沿 REQ-431 真回环先例）。**不自动触发 LLM 轮**：seed 只灌配置与内容，是否用本地零 Key 预设或自有 Key 由演示者决定。选型脚本而非前端模板：服务器/CI/无浏览器场景可执行，且不扩大鉴权审计写面。**演示文案硬性要求（评审②采纳落点）**：灌装与演示文案**不得复用 REQ-417 模板内历史叙事字样**——点名 `web/src/components/DevTeamTemplate.tsx:7`（模板头注）与 `:177`（演示动线标题）两处（复核：本轮实读两行均含历史叙事词汇；全仓 grep 另有 HybridTeamTemplate.tsx:8 一处同类命中），任务简报一律以模板 SEED_TASKS brief 原文为准（已核无禁词），全部落库文案按 §〇 禁词口径 grep 自检归零后方可交付。

**API/事件面**：零新增路由、零新增事件。seed 全走既有 REST；演示动线消费既有事件契约（event_names.go：approval.request、run.interrupted、subagent.delegate 等）与 run-events 回放——审批/挂起恢复/委派/回放演示零新后端能力，远程只读访客经 GET run-events 跟进过程，事件风格与 REQ-537 单源口径完全一致。

## 八、多智能体协作过程账本（metrics）

### 8.1 目标与能力定义

为多智能体协作 run 建立「过程账本」：每次运行结束后可按成员回答三个问题——**参与度**（各成员 token 消耗、工具调用次数、在位时长占比）、**介入频次**（人工审批/插话 Steer/ask_human 挂起/守卫拦截的计数与决议结构）、**阶段耗时**（成员在位区间与工作流节点区间耗时）。数据全部从既有 run_event 事件流派生，聚合为 run 级指标 API 与前端指标面板；与 agenteval 离线评测互补（指标记账、评测打分）。零新增事件类型、零新依赖（D-O5/D-O15），沿 REQ-397 per-tool 归因与 UsageStats 聚合两条先例扩展。

### 8.2 现状与复用点（已逐条读码核实）

### 8.3 方案设计

**架构**：不新增事件类型，三层——发射面补归属字段 → 复用 run_event 落库 → store 层事件派生聚合，数据模型零迁移。

1. **成员参与度**：token 归属在 chunk usage 结算点（`runner.go:1136-1139` 调 settleUsageDelta 处）按 rc.lastAgent 记差值入 agentUsageAgg——与 REQ-397 toolUsageAgg 同点同构；run.finished 增 usage_by_agent（finishData），**默认开启、不经 debug 门控**（与 model.step 的关键差别）。工具归属：emitToolCall/tool.result data 增 "agent": rc.lastAgent。**选型理由**：发射点归属 vs 聚合时按 enter/exit 栈推断——栈推断在 steer 抢占与并行调用下漂移，lastAgent 由 trackAgent 单点维护（`runner.go:1008`）可靠且与泳道同源。发言占比不逐 delta 归属（写放大考量），以 token 占比+在位时长（enter/exit created_at 差）替代。tool 层事件（approval.granted/denied、hook.denied）归属经 ctx 挂「当前成员」可变引用（WithEventSink ctx 键同款模式，trackAgent 切换时原子更新）；若落地实测 eino ctx 传播不支持，回退口径=该三类事件按 run 级计数、成员归属降级沿 run.interrupted.node 先例面，交付注如实标注。
2. **介入频次**：approval.request/granted/denied 补 agent 字段后聚合；口径=approval.request+run.interrupted（kind 分列 ask_human/approval）+steer.pushed+hook.denied+run.preempted 计数，granted/denied 出决议结构比。委派频次沿用 subagent.delegate：按 phase 分布计数，成功率=completed/(completed+failed)。
3. **阶段耗时**：纯派生不加事件——成员在位=enter/exit 对差；工作流节点=workflow.node started/completed 差；总账=run.finished elapsed_ms。
4. **API/事件契约**：GET /api/stats/run/{run_id}/metrics（单 run 三出料：参与度/介入/阶段，`handlers_stats.go` 扩）；GET /api/stats/usage 增 group_by=member（数据源=run.finished.usage_by_agent）。data 补字段向后兼容、EventSchemaVersion 不动；新常量进 event_names.go（REQ-537 单源纪律）并顺带补录 workflow.node/state.changed。
5. **与既有机制集成**：审批/挂起恢复（checkpoint Resume）零改动，补字段后多级委派挂起自动入账；delegate_async 子会话独立 run 各自记账，父 run 只按 delegate 事件计数、不穿透汇总；工作流节点耗时零改动；回放/泳道共用同一后端聚合口径（单源，前端不复算），TraceDrawer 增「指标」页签，SettingsPage 使用统计区扩 member 分组，REQ-111 导航 IA 不动。
6. **与 agenteval 互补**：agenteval=离线基准（人为任务、质量评分、跑前跑后对比）；本件=在线账本（真实 run、成本与协作画像、无人为任务）。指标不评分、评测不记账；SummarizeEvents 属评测侧独立投影（实时 SSE），本件聚合在 store 层（落库事件），数据源与口径互不混用。

### 8.4 验收要点

1. 多成员 run（委派/transfer）完成后 run.finished 含 usage_by_agent，各成员 total_tokens 之和与 run 级 usage.total_tokens 闭合（偏差仅并行均摊余数）。
2. tool.call/tool.result 带 agent 字段，与 subagent.enter/exit 泳道切换一致（与 TraceDrawer 对拍）。
3. 审批挂起→批准/拒绝各一次，单 run 指标介入计数 +2 且决议结构 1:1；steer 一次 steer.pushed 计 +1。
4. GET /api/stats/run/{run_id}/metrics 三出料与事件流逐条对账一致；工作流 run 节点时长=started/completed 差。
5. debug=0 的普通 run 亦得全量指标（不依赖 model.step 落库）；group_by=member 跨 run 聚合与单 run 之和一致。
6. EventSchemaVersion 不变，既有回放/泳道零改动可用（按 docs/20 对话模块节冒烟）。

### 8.5 诚实边界

- token 差值归因继承 REQ-397 近似：并行调用均摊、余数归首个，不做精确分摊；agent_as_tool 嵌套子调用若 ADK 事件未透出 AgentName 则归 root 如实计入，不做推测归属。
- obs.timing 维持不带 agent（callbacks 经顶层 Runner 注入不达嵌套 agent，`callbacks.go:9-12` 注），审计面与参与度面分工不变。
- 发言占比不做逐文本归属；不做成员「绩效分」——质量评价归 agenteval，两域不混。
- 首版不物化聚合表（单机学习尺度沿 UsageStats 内存派生；面板卡顿再沿 ontology_hit 先例物化，迁移号按 §〇 口径届时顺延领取）、不做跨会话 OLAP、不做父 run 对子会话的穿透汇总。

### 8.6 优先级论证与工作量粗估

**论证**：TurnLoop（REQ-385）/委派/工作流已使多智能体协作成为主链路，但「谁在干活、成本花在哪、人在哪介入」目前只能靠轨迹面板逐事件人读，缺账本视角；本件与 REQ-397（per-tool 归因）、REQ-311（泳道）同属一条演进线，是平台全面评审批后工程化收口的自然延伸，并为 agenteval 任务设计与成员配置调优提供证据面。建议 **P1**：不阻断主链路，价值随多成员使用密度上升。**工作量**：最近同构先例 REQ-397 为单件一轮交付（M193）；本件拆两件为宜——A=事件补归属字段+usage_by_agent+聚合层+单 run API+单测（≈0.6 REQ 当量，含 tool 层 ctx 归属实证）；B=前端指标面板两挂点+member 维度+headless 冒烟（≈0.4 REQ 当量）。合计 ≈1 REQ 当量、两个注册行。

## 九、运行生命周期 pause/redo 与产物预览（人工控制域，批次名 humanloop）

### 9.1 目标与能力定义

为运行生命周期补齐两段缺失语义并打通产物消费末梢：**pause**=非决策点安全点挂起——用户在运行中任意时点主动挂起（区别于 ask_human/approval 等待输入的决策点挂起），运行在 Eino TurnLoop 安全点收束、进度落库、跨进程重启可恢复；**redo**=事件锚点重放重跑——从事件流选定重做锚点，沿 checkpoint 定向恢复底座或消息边界截断重新执行，溯源链保留原过程审计；**产物 Demo 预览**=沙箱产物静态页最简预览通路（内联沙箱渲染）。三者全部复用既有抢占/checkpoint/事件回放底座，不新建运行引擎。

### 9.2 现状与复用点（均已读码核实）

- 抢占安全点原语：`backend/internal/chat/turnloop.go:80` Steer 经 `TurnLoop.Push(WithPreempt(AnySafePoint))` 在安全点（AfterChatModel/AfterToolCalls，turnloop.go:8-9 头注）打断当前轮；`turnloop.go:155-181` OnAgentEvents 轮界先 `flushTurnAssistant` 即刷落盘（:158）再处理 Preempted 分支。
- checkpoint 底座：`backend/internal/chat/runner.go:826` `checkPointIDOf="ckpt_"+runID`；`backend/internal/store/messages.go:217-240` checkpoint 表（gob blob 按 ID 幂等覆盖）；eino@v0.9.22 `adk/turn_loop.go` cleanup 实证：**显式 Stop 退出仍保存 turnloop checkpoint（unhandled items+runner 状态）**——这是 pause 持久化的框架依据。
- 恢复主链：`runner.go:1221` Service.Resume（acquireRun 同闸 :1223、interruptState 强校验 :1230-1233、runTurnLoop+ResumeParams 定向恢复 :1302-1306）；终态四分支 `runner.go:571-585`（stopped/run.error/interrupted/completed）。
- 事件契约与回放：`backend/internal/chat/event_names.go:7-42` 事件常量单源（REQ-537）；`handlers_runs.go:150-180` runEvents 回放（run_id 过滤+offset 增量，REQ-527）；`handlers_runs.go:189-215` steer 409 形态；RunEvent.SchemaVersion 只增不改（`store/models.go:210-217`）。
- 状态留痕：`store/state_log.go:21-30` setter 统一 prev→next 留痕；`handlers_conversations.go:165-181` phase 状态机。
- fork 现状相符：`handlers_conversations.go:214-261` 派生只拷消息，过程事件/挂起状态/todo 留原会话（:214-216 注）。
- 产物面：`tool/savefile.go:1-3` save_file 落盘+元数据；`runner.go:1180-1185` artifact.saved 事件；`handlers_projects.go:94-114` downloadProjectFile 仅 octet-stream attachment——**无内联预览**；沙箱执行世界 `chat/assembler.go:623-662`（sandbox_mode=docker）。
- 迁移先例：`store/migrations/063` 等 `ALTER TABLE conversation ADD COLUMN`；`store/store.go:22-23` embed migrations（复核：embed 语句确在 :22-23；目录最新 078_ontology_hit_cited.sql——评审③修正落点，原文「现 76 号」有误；下一可用迁移号按 §〇 口径以落地轮实况顺延）。

### 9.3 方案设计

**pause：安全点挂起（复用抢占原语，持久化落库）**。`POST /api/conversations/{id}/pause` → Service.Pause：置 pauseRequested 标记并 `Push(runItem{Kind:"pause"}, WithPreempt(AnySafePoint))`（与 Steer 同通道，turnloop.go:80 同构）；无进行中 TurnLoop 或 CHAT_TURNLOOP=0 → 409（沿 steer 形态）。OnAgentEvents Preempted 分支（:160-171）检测标记后不续跑、改调 `tc.Loop.Stop()` 优雅收束——框架 cleanup 落 checkpoint（pause 条目入 unhandled items），已完成轮产物已由 flushTurnAssistant 落库；终态发 `run.finished reason=paused`（对称 reason=interrupted :584），pause_state 落库 `{checkpoint_id, run_id, paused_at}`。恢复 `POST .../unpause`：取 checkpoint_id 复用 runTurnLoop 同键装载（turnloop.go:98-99 语义），GenInput 首轮识别 `Kind=="pause"` 走 buildRunContext 全量历史重建续跑（:123-132 同构），无答复；开新 runID，run.started 带 `resumed:"paused"`（对称 resumeConversation handlers_runs.go:260）。

**盘点口径修正**：盘点称「resume 沿既有 Service.Resume」——核实为：执行面（runTurnLoop 装载/事件管线/并发闸/runFinalize）全量复用，但 Resume 入口强依赖 interruptState.TargetID 与用户答复（runner.go:1230-1233、:1303-1305），pause 恢复无答复，故入口需 `ResumePaused` 薄变体（选型理由：零破坏既有审批/ask_human 语义，避免向 Resume 塞分支）。**抉择**：持久化落库而非进程内守候——桌面客户端合盖/重启下进程内句柄必丢；pause_state 用独立列而非复用 interrupt_state（Resume 强校验 TargetID，混用会逼「无答复恢复」伪装成审批答复）。

**redo：事件锚点重放重跑（同会话重做链）**。锚点两档（诚实粒度）：①**checkpoint 锚点**（挂起/暂停/Stop 时点有快照）→ 复用定向恢复装载，以合成 `Kind:"redo"` 条目携带纠偏指令续跑（与 pause 条目同机制）；②**消息边界锚点**（用户消息/assistant 轮）→ 删除锚点之后的消息（run_event 追加式不删，原过程可回看），沿 runOnce 重发新 run。**不做任意 tool.call 级重放**——checkpoint 仅在轮界/挂起/停止时点存在，无快照支撑。**抉择：新 runID+`redo_of:{run_id,event_id}` 溯源键，拒绝复活旧 runID**（盘点称「同 run 重放重跑」——核实为字面同 runID 不可行：run_event 以 run_id 为检索主键（ListEventsQ），复活会污染既有事件序与审计链）；重放（回看，REQ-527 已交付）与重跑（重新执行）语义分离，模型非确定性下重放不产生新结果。

**产物 Demo 预览（最简形态）**。`GET /api/projects/{id}/files/{fid}/preview`：仅白名单文本产物（text/html）内联返回，响应强制 `Content-Security-Policy: sandbox allow-scripts` + `X-Content-Type-Options: nosniff`（无 allow-same-origin——LLM 生成 HTML 触不到 localStorage/cookie，XSS 面被隔离）；前端沙箱 iframe 嵌入。容器端口发布声明化（动态 dev server 类 demo）留观察，不入首版。

**数据模型 / 事件面 / 集成**。迁移（号按 §〇 口径落地轮顺延领取）：`ALTER TABLE conversation ADD COLUMN pause_state TEXT NOT NULL DEFAULT ''`（063 同构）；Store 增 SetConversationPauseState 走 recordStateChange 自动留痕。事件面：event_names.go 增 `run.paused`/`run.resumed`/`redo.anchored` 三常量（REQ-537 单源风格，结构纯增量沿 SchemaVersion v2）。phase 状态机增 `paused` 分支（handlers_conversations.go:172-181 同位）。集成约束：pause/unpause 共用 acquireRun 闸与 runFinalize 收尾；工作流 Runner（sequential/parallel/loop）首版不支持（沿 turnloop.go:19-20 诚实边界）；fork 清空面扩展至 pause_state（沿 :233 现状）；delegate_bg 子运行不暴露 pause（语义单路）。

### 9.4 验收要点

1. 运行中 pause：run.finished reason=paused、phase=paused、state_log 有 pause_state 留痕；unpause 后新 runID 续跑且重做前历史完整可见（headless 冒烟）。
2. 暂停跨重启：pause 后重启后端，unpause 仍沿 checkpoint 续跑（单测钉桩——「无答复恢复」ADK 语义以本测试确认，不通过则回退进程内守候+重启降级 stopped 的诚实口径）。
3. redo 消息锚点：锚点后消息截断、redo.anchored 含 redo_of 与截断计数、新 run 正常收束；原 run 事件经 run-events 仍完整可回放。
4. redo checkpoint 锚点：从暂停/挂起锚点带纠偏指令重跑，恢复过程事件与常规 Resume 同构。
5. 预览路由：HTML 产物内联渲染且 iframe 沙箱生效；非白名单类型 415。
6. CHAT_TURNLOOP=0 时 pause 与 checkpoint 锚点 redo 均 409/降级提示，不产生半挂起态。

### 9.5 诚实边界

pause 不支持 token 级中断（Eino 框架语义，安全点粒度=AfterChatModel/AfterToolCalls）；工作流运行不支持。redo 不做任意事件级时间旅行（无快照）、不复活旧 runID、重跑消耗真实 tokens。预览仅静态单文件 HTML，不做在线编辑/版本对比/动态服务类 demo；容器端口发布声明化留观察。fork 仍不拷过程事件与 pause_state（维持 REQ-478③ 诚实边界）。

### 9.6 优先级论证与工作量粗估

pause（≈0.5 REQ 当量）：全链复用抢占/flush/checkpoint 通路，新增面=两入口+终态分支+一列迁移，风险集中在「无答复恢复」单点（验收 2 兜底）。redo 消息锚点（≈0.4）：截断+新 run+溯源事件，零引擎改动。预览路由（≈0.2）：一端点+前端 iframe。redo checkpoint 锚点（≈0.3，依赖 pause 先行）。合计 ≈1.4 REQ 当量；建议交付序 pause→redo 消息锚点→预览→checkpoint 锚点。任意事件级重放重跑（需全量事件快照引擎，≈3+ 当量）明确不做，若后续有真实诉求再入需求池评估。
