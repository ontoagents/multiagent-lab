## 3. 总体设计

### 3.1 管道视图（v0.2 双轨：RAG 子模块 + GraphRAG 子模块）

**子模块 A「向量检索 RAG」**（`kb.mode='rag'`，v0.1 现状原样保留）：

```
索引管道（异步，状态机）                    检索管道（对话内同步）
┌────────────┐   ┌──────────┐   ┌─────────────────┐
│ 文档入库    │→ │ 切分器    │→│ Embedding(模型连接)│
│ txt/md/粘贴 │   │ 块/重叠   │  │ OpenAI 兼容       │
└────────────┘   └────┬─────┘   └────────┬────────┘
                      ↓                   ↓
              chunk 表(正文+状态)     VectorStore 接口(可插拔)
                      ↓            ┌────┴─────┐
                索引状态回写        │ Qdrant(P1)│  │ SQLite fallback│
              (待处理/处理中/就绪/失败) └──────────┘  └───────┘

对话提问(选了知识库+RAG) → retrieve(query, topK, threshold) → 片段+得分
   → 拼接上下文 → SSE `retrieval` 事件(来源+摘要，REQ-17) → Agent 生成
```

**子模块 B「GraphRAG 检索」**（`kb.mode='graphrag'`，v0.2 新增，复用本体侧 semantica worker）：

```
索引管道（异步，状态机）                检索管道（对话内同步）
┌────────────┐   ┌──────────┐   ┌──────────────────┐
│ 文档入库    │→ │ 切分器    │→│ Embedding(模型连接)│
│ txt/md/粘贴 │   │ 块/重叠   │  │ OpenAI 兼容       │
└────────────┘   └────┬─────┘   └────────┬─────────┘
                      ↓                   ↓
              chunk 表(正文+状态)    ─→ 调用 semantica worker
                   (chunk 池共享)         :8093 POST /graphrag/ingest
                                          (chunk → KG 抽取 → 实体/关系)
                                              ↓
                                       semantica 侧 graph_store
                                       (主平台不重存)

对话提问(选了知识库+GraphRAG) → POST /api/kbs/{id}/graphrag-search
   → 反代 → semantica :8093 /graphrag/query
   → SSE `retrieval` 事件(类型=graphrag，含 entities/relations/claims) → Agent 生成
```

**两条管道共享 chunk 池**：文档入库一次，chunk 同时写入 `chunk` 表 + 触发 GraphRAG 子模块的 semantica 抽取（若该 KB 启用 graphrag 模式）；切换检索模式不需要重新入库。

### 3.2 可插拔 Store 抽象（自 02 §6.9 原样承接，接口不变）

```go
type VectorStore interface { // 两种实现
    Upsert(ctx, kbID string, chunks []Chunk) error
    Search(ctx, kbID string, vec []float32, topK int, minScore float64) ([]Hit, error)
    DeleteByDoc(ctx, kbID, docID string) error
}
// QdrantStore（P1 首选）：eino-ext 现成 indexer/retriever 适配优先（M6 首日核对可用组件清单后定稿对接方式），
//   无适配则直连 Qdrant REST（collection=kb_{id}，cosine，point id=chunk id）
// SQLiteStore（fallback）：沿用 v0.5 SQLiteRetriever（余弦 TopK），保留为无外部依赖对照（不删）
```

- 选择逻辑：配置 `KB_STORE=qdrant|sqlite`；Qdrant 启动探测不可达 → 自动落 SQLite fallback 并在索引状态提示（降级语义，不阻断建库；探测为部署层逻辑，不属接口成员）。
- **不编造组件**（02 §6.9 既有约定，转为 KB-O1）：eino-ext 具体 indexer/retriever 适配是否齐备在 M6 实现首日核对官方仓库后定稿；均不适用则 Qdrant 直连 REST，仍属开源优先范畴。

### 3.3 数据模型（自 02 移入；v0.2 增 `kb.mode` 字段）

三表沿用 02 v0.5 结构（`kb` / `doc` / `chunk` + 状态字段）；`knowledge_chunk` 增列 `store_backend TEXT DEFAULT 'sqlite'`、`vector_ref TEXT`；**v0.2 增 `kb.mode` 区分检索路径**：

| 表 | 关键列 | 说明 |
| --- | --- | --- |
| `kb` | id, name, brief, top_k, threshold, **`mode` TEXT DEFAULT 'rag'` ('rag'`/`'graphrag')`, created_at | 库级检索参数（REQ-57）+ 检索模式（v0.2 新增 D-KB4）；同一库只有一种 mode，切换 mode = 重建 KG 或换库 |
| `doc` | id, kb_id, name, status, chunk_count, dim, updated_at | 文档单位（REQ-51/54）；status：待处理/处理中/就绪/失败 |
| `chunk` | id, doc_id, kb_id, content, status, store_backend, vector_ref(BLOB 或 Qdrant point id) | 正文恒存 SQLite；Qdrant 路径向量存 Qdrant，fallback 路径 BLOB 直存；**两子模块共用 chunk 池**（rag 直接用 vector_ref，graphrag 把 chunk 文本喂 semantica 抽 KG） |

- 对话关联：`conversation.kb_id`（01 REQ-19a）留 02 平台库；知识库侧不感知会话。
- **KG 落点（v0.2 决定）**：GraphRAG 子模块的实体/关系/事件**只落 semantica worker 侧 graph_store**，不在主平台 SQLite 重存；主平台在检索时通过 `/api/semantica/*` 反代调 worker 查询接口（04 §4.9 已有的反代机制）。好处：避免双库一致性负担 + 让 KG 与本体侧 semantica 共享审计/版本管理能力。

**3.5.6 学习价值闭环**

- **文本 → RAG 片段**（检索用，不持久化为本体资产）
- **文本 → KG**（semantica 消费，作为 GraphRAG 子模块检索端点数据）

## 3.5 KG 增强设计（v0.9 新增，REQ-127~130 / M16）

**数据模型扩展**（SQLite，保持三表主体；I6 口径回修 M36/KB-13：实际表名 `kg_relationship`，历史 `kg_relation` 系笔误）：
- `kg_entity` 增 `alias`（**分号分隔**（M36/KB-7② 实现口径；本节早版「JSON 数组」口径作废），消歧合并后的人工别名；重建/合并自动保留归并）、`description`（抽取或人工补写）；
- `kg_relationship` / `kg_claim` 增 `review_status`（approved | rejected，**默认 approved** 保证存量兼容——rejected 不参与检索与展示）；
- 新表 `kg_community`：community_id / kb_id / level / member_entity_ids（JSON）/ summary（LLM 生成缓存，重建失效）/ summary_method。

**API 面**（沿既有 `/api/kg/{kbID}`、`/rebuild` 前缀扩展）：
- 图谱浏览：GET /entities?search=&limit= 、GET /neighbors/{entityId}?hops=1..2&relation_types= 、GET /stats；
- 检索增强：graphrag-search 增参 entity / hops / relation_types；claims 结果附 chunk_id 与出处摘录+句级偏移（B1：`chunk_excerpt`+`span_start/end`，前端 <mark> 高亮；检索命中 hits 附 `spans`）；
- 治理：POST /merge（别名/同名合并）、POST /review（approve/reject）、GET /quality（method 分布/孤儿实体/高频关系类型）、GET /merge-suggestions（M36/KB-7 起规则+向量双臂：名称包含 + 名/描述 embedding 相似，类型不同附「慎并」警示，仅建议人工确认）、PUT /entity-alias（M36/KB-7② 别名人工标注）；
- 全局问答：POST /communities/rebuild（Louvain 社区 + 摘要生成）、POST /global-search?q=（社区摘要检索）。

**关键设计决策**：
1. 社区检测选 **label propagation**（无外部依赖、近线性复杂度、学习尺度够用）；不做 Louvain/Leiden 工业实现——集成成本高于学习价值时换轻量路线（与 D-O15 同一判断逻辑）；〔v0.11 注：M35/KB-5 已升级 gonum Louvain 为主路径，label propagation 退役〕
2. 社区摘要**按需生成 + 缓存**（首次 global-search 触发），不做重建时全量预生成——对应 KB-O4 成本口径；
3. 多跳遍历用 SQLite 递归 CTE 实现（学习尺度 2 跳内无性能问题）；前端邻域图复用第五栏 React Flow 组件；
4. 抽取配置（模型/提示词覆写/本体挂载/语料预算）为**库级**设置，存 kb 元信息，不改全局默认连接语义；M36/KB-6③ 起抽取 prompt 可挂本体词表白名单（**运行期单向 本体→KB**，词表经构建平面 spec 只读投影，见 11 §3.1 交集契约 P3）。

**模块边界（M36/KB-13 固化）**：知识库×本体交集治理五原则见 11 §3.1（单一资产归属/展示位≠管理入口/运行期单向/可解释标记/命名单一真源）；本模块 KG 为唯一治理入口，本体「消费与审计」栏为只读观测台（标注数据来源）。

**风险与缓解**：抽取质量波动（提示词治理 + 审核队列）；全局问答 token 成本（摘要缓存 + KB-O4 预算评估）；实体消歧误合并（仅人工触发 merge，不做自动合并；向量建议附类型警示防误并）。

## 3.6 LLM Wiki 类型设计（v0.13 新增，REQ-241 / M67，✅ 已交付 2026-10-02）

**定位**：知识库第三类型 `kb.mode=wiki`（M14 双子模块 + REQ-241 第三类型，新库可选、存量库不动）——**写时合成层，不替代 RAG/GraphRAG**（三类型并存可对照，SC-K9）。模式沿 Karpathy LLM Wiki（51 号调研拍板落地）：文档入库在 chunk 池之外由 LLM 摄取生成**互链 Markdown 页面层**，查询读页非检索片段。

**数据模型**（迁移 040）：
- 新表 `wiki_page`：id / kb_id / page_type（`summary | entity | concept | topic | synthesis | index`）/ title / content_md / sources_json（溯源 chunk_id 数组，页 → chunk 池下钻原文）/ created_at / updated_at；重建全量替换（沿 kg_community 语义）；
- `knowledge_doc` 增 `wiki_hash`（chunk 拼接 sha256 摄取指纹——重建时未变更文档跳过 summary 生成，零 LLM 调用）；
- **wiki 库零向量依赖**：Import/Reindex 走 chunksOnly 路径（chunk 落库不 embed 不写向量，StoreBackend=none），无需 embedding 连接即可用；能力开关归一保持 false/false（路由按 mode 进 wiki 臂）。

**摄取管线**（kb 包 wiki.go；LLM 生成经 `WikiLLMFunc` 注入——chat→kb 已有依赖反向 import 成环，main 装配转接 chat.GenerateStructured，`WIKI_LLM_CONN_ID` 可选指定连接）：
1. **summary 页**（每文档 1 次 LLM）：文档全文（6000 rune 截断）→ Markdown 摘要 + 实体/概念清单（一次调用同时产出聚合页输入）；
2. **聚合页批量**（1 次 LLM）：各 summary + 清单 → entity/concept/topic/synthesis 四类页面（JSON pages 数组，title/content/docs；未知类型与空页丢弃、重名去重）；docs 引用经确定性后处理转 chunk_id 并集溯源（库外标题忽略=诚实缩源）；
3. **index 页**：确定性生成零 LLM（[[标题]] 目录）；
4. 互链：LLM 输出 content 内 `[[页面标题]]` 维基链接；页面标题即导航锚（前端预览）；
5. 成本模型：N 文档 → N+1 次调用（未变更跳过时=变更数+1；零变更 0 调用不替换）——前端成本预估警告如实呈现（KB-O4 口径）。

**检索臂**（route.go SearchUnified 最前置分支，`mode=wiki`）：ListWikiPages → 查询词 2-gram（中文 bigram+空格分词，kg.gramTerms 同思路 kb 包副本——跨包引 kg 会经 chat 成环）对 page.title（×3）+content 覆盖评分、整题命中加成 1.0 → TopK 页面为 hits（strategy=wiki）；index 页不参与命中；无命中 degraded=true 引导重建。hits 增 `sources`（chunk_id 解析为 doc 标题+seq 的可读定位，只增字段）；`retrieval` 事件 `source=wiki`（沿 community 先例）。

**API 面**：GET /api/kb/{id}/wiki/pages（页面清单含全文）、POST /api/kb/{id}/wiki/rebuild（手动全量重建，body conn_id 可选；返回 pages/llm_calls/skipped_docs/duration 成本可见）；检索试运行复用 search-preview（wiki 库自动路由）。UI：知识库页第三 Tab（wiki 库两页签=Wiki 页面〔按类型分组 Collapse+Drawer Markdown 预览+溯源数+重建 Popconfirm 成本警告+生成连接选择〕/ 文档与检索），建库表单第三选项。

**边界（诚实标注）**：v1 手动全量重建（沿 REQ-130 先例），增量后台维护与 lint 体检（51 号 B2/B3 观察候选）为后续触发项；页面质量依赖抽取模型；学习尺度 ~百文档内（模式自述 index+评分检索边界）；文档删除即时移除其 summary 页、聚合页留待重建收敛。

### 5.3 WeKnora 0.8.0 深度评估（开发者点名对象）

**能力对比（WeKnora 0.8.0 vs 本项目知识库当前范围）：**

| 技术栈 | Go 后端 ✓ / **Vue 3 前端**（与已拍板蚂蚁生态 React 冲突）✗ / Python 解析服务（多一个运行时）✗ | Go + React（蚂蚁生态） | 部分冲突 |

| 许可与活跃 | MIT、~24.4k stars、微信 AI 团队维护（E1） | Qdrant Apache-2.0；eino-ext 云原生社区 | 均可商用 |

**逐条回答"是否有比 WeKnora 0.8.0 更合适的方案"：**

1. **若问题是"知识库功能谁更强"**：WeKnora 0.8.0 在开源 RAG 平台里属第一梯队（功能面全、MIT、微信 AI 背书、活跃），RAGFlow 0.27 的深文档理解/知识编译与之互有胜负，Dify 偏应用平台。**没有明显更强的成品平台**。
2. **若问题是"对 eino-multiagent-lab 哪个更合适"**（真实语境，E7）：**维持现状方案（eino-ext + Qdrant + SQLite fallback）更合适**，WeKnora 不是替代项：
   - **学习目标冲突**（LG-11）：本项目知识库的存在意义是学 RAG 闭环搭建；引入成品即放弃该学习目标——相当于用现成答案替代练习题。
   - **架构职责重叠**：WeKnora 自带会话、Agent、编排、沙箱——与本平台核心（Eino ADK 多智能体编排）整体重复；引入等于"平台里再装一个平台"。
   - **集成成本不对称**：其价值集中在文档解析与进阶检索（OCR/GraphRAG/混合检索），全部在 11 KB-2 需求池（本项目明确不做）；为池内需求引入整套外部系统不划算。
   - **技术栈摩擦**：Vue 3 前端无法融入已拍板的 React/蚂蚁生态界面体系（06 v0.7）；Python docreader 增加运行时；标准部署多容器超单机学习尺度（Lite 模式虽轻但那样只用它的 SQLite 检索，价值更低）。
   - **集成口径**：WeKnora 是"另一个 OpenOntologies 式外部服务"的正确候选——经其 MCP Server 独立接入、Agent 挂载工具，与平台内组件级知识库**并行不替代**（11 KB-3，P2 备选）。
3. **组件层是否换血**：不换。Qdrant（Apache-2.0、单容器、Eino 生态适配在核对清单 KB-O1）与 WeKnora 内部可插拔向量库选项（E4）重叠，能力满足 TopK 检索；sqlite-vec 可作为 SQLiteStore 的演进选项（当前余弦全扫在学习尺度下够用，不引入 C 扩展依赖）。
