## 1. 定位与学习目标

| 项 | 内容 |
| --- | --- |
| 模块定位 | 知识库是主平台内的**全局资源**（非外部服务）：库列表/库详情两栏视图，文档入库→切分→向量化→检索→对话注入的完整闭环。 |

| 实现基调 | 开源优先（Q-18 已定）：向量存储与检索优先使用开源组件；自研仅保留 SQLite fallback 作学习对照。选型结论与对比分析见 12《知识库_方案设计.md》§5。 |

### 3.1 知识库×本体交集治理五原则（M36/KB-13 固化，45 号 §6.4 承接）

> **判别句：层次关系可以嵌套，治理关系必须唯一；承载不等于拥有，展示不等于管理。**

| # | 原则 | 契约内容 |
| --- | --- | --- |
| P1 | 单一资产归属 | 一份数据只有一个 owner（KB KG 的 owner=知识库模块）；跨模块只共享只读视图，不共享写路径 |
| P2 | 展示位 ≠ 管理入口 ≠ 对接面 | 本体模块「消费与审计」KG 展示位允许保留，但标注数据来源=某知识库并给跳转；**治理（重建/审核/合并/别名）只在知识库侧提供入口**（已交付：审计页重建按钮退役 → 知识库图谱视图「重建 KG」+ 来源标注跳转） |
| P3 | 运行期单向，构建期离线 | 运行期只允许「本体→知识库」增强（KB-6③ 本体约束抽取词表注入即此方向）；「知识库→本体」只在构建期离线触发（REQ-108/M15 已如此）；**禁止运行期双向同步调用**——`internal/ontobuild` 独立成包避开 kb→chat 回环的教训即此规则的落地 |
| P4 | 交集处必须留可解释标记 | `degraded`（KG 抽取失败）、`provenance`（溯源链 chunk_id/doc#seq）、`source`（资产来自哪个库/哪个本体）、`strategy`（命中走了哪条路：vector/lexical/hybrid/rule） |
| P5 | 命名与契约单一真源 | 表名、端点、字段只在一处定义；实际表为 `kg_relationship`（迁移 010），历史文档写作 `kg_relation` 处一律以 `kg_relationship` 为准（I6 已回修 12 号与 35 号） |
