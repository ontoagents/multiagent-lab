# 需求登记

仅在需要判断立项、领号或维护需求队列时读取。项目规则见 [AGENTS.md](../../../../AGENTS.md) 纪律 1/3。

## 判断范围

- 新增产品能力、改变既定行为：先查相关需求是否已覆盖；已有 REQ 沿用，新需求再领号。跨模块不等于必然新增需求。
- 恢复既定行为的 bug 修复：沿已有 REQ 记录修复与回归；若修复实际改变需求，再补需求变更。
- 笔误、等价重构、测试补充、开发配置整理：不单独领号。治理规则变化在 [18 注册表](../../../../docs/18_REQ编号注册表.md) 治理节记录即可。

## 并发领号

1. `git fetch origin` 后核对远程 main 的最新注册表和归档册，以及本地在途登记；只整合本次需要的信息，不自动切分支或改历史。无法核实远程号段时可先完成方案和其他本地准备，暂不宣称已正式领号。
2. 序号取已分配最大值 + 1（包含已归档号），后缀用 `openssl rand -hex 2` 生成四位随机串；完整 ID 形如 `REQ-618-a3f9`，正式账本用完整串。同序号不同后缀合法；完整串碰撞才重新生成后缀。内容重复应复用已有需求，不靠换号规避。
3. 归属需求档：智能体 [01](../../../../docs/01_智能体_需求文档_PRD.md)、本体 [03](../../../../docs/03_本体_需求文档.md)、知识库 [11](../../../../docs/11_知识库_需求文档.md)。同轮写需求行、18 注册行和 [19 开放索引](../../../../docs/19_REQ状态索引.md) 六列行；状态枚举沿索引。
4. 批次/跨模块里程碑才新增 M 号，后缀与批主 REQ 一致；存量无后缀 ID 保持不变、完结 ID 不复用。

复杂设计需要独立方案时按 [文档导览](../../../../docs/README.md) 放入 research，在对应 handbook 模块导读添加完整路径。简单变更可直接在需求档说明，不为流程创建空方案。写共享账本前重读将编辑的段落和版本，保留并行更新。
