**背景与证据**：96 号对标给出硬证据——Open Ontologies 以 21 个 MCP 工具做到本体任务 F1 0.717，LLM 直读 OWL 仅 0.323；平台当时 facade 仅 6 个查询工具。O-1 的立项实质是把本体操作从「平台 UI/REST 专有消费」升级为「MCP 标准工具面智能体可消费」——外部 Agent 客户端与内部智能体共用一个面。

**取舍一：写路径纪律**。T2 的 spec CRUD（九件）**不经引擎直写**，全部走构建平面既有 PUT spec If-Match 版本门禁与校验管线——引擎里的图是投影，绕过门禁写图等于绕过整个质量体系；这条纪律换来了版本快照/overlay 提取/入库评分对 Agent 写入同样生效。

**取舍二：默认关+审批**。工具面对外全量注册可枚举（外部 MCP 客户端可用），但**平台内智能体**的 13 件扩展工具由 `agent.onto_ops` 能力开关默认关（存量零变化），写类 upsert/delete 入 danger 档审批——「对外开放」与「对内默认最小权限」是两层独立的门。

**后果**：O-5 多 Agent 协作流水线（REQ-370）得以直接用工具面承载建模与评审——领域专家/工程师/评审三角色在同一工具面上协作；这也解释了为什么工具面扩展被排在 96 号主线第一位：它是后续一切 Agent×本体深化（时序查询/评测联动/协作流水线）的工具基座。件数演进如实注记：REQ-366 交付时 facade 工具面 6→**19**（原 6 查询+13 扩展）；此后 REQ-368 companion_history（时序查询）追加为第 20 件；**2026-10-29 补记：第 21 件 check_answerable（REQ-415/M211，2026-10-24 交付）系本条演进链漏记，现行口径=21 件**——抽检修正注（2026-10-28）：本卡原题「6→20」系两轮交付口径混并。
