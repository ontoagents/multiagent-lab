**背景**：智能体的推理后端不止一种——平台内置管线之外，编码智能体生态（Claude Code/OpenCode/Aider/DSH）已是成熟的「可借用智能体」。是否接入、如何接入，决定平台是「单框架玩具」还是「多后端枢纽」。

**定案**：**注册表多后端矩阵**（internal/inference）——eino-adk 为内置默认（平台内进程管线，完整能力：审批/沙箱/hooks/事件全量）；claude-code/opencode/aider 为外部 CLI 适配器（stream-json/纯文本子进程协议）；dsh 走 ACP/SDK 双通道（31 号可行性批催生）。外部成员另有三通道：kind=cli 连接器、kind=a2a 远程智能体、kind=stdio MCP server（REQ-426~434 演进批）。探测结果 10min TTL 缓存，安装指引注册表驱动（REQ-450）。

**诚实边界（决策的一部分）**：外部 CLI 后端**旁路平台装配链**——不走 assembler/hooks/审批/沙箱，Harness 层配置对其不生效；能力降级在 Capabilities 里如实声明（如 Resume=false）。这不是缺陷没做完，而是刻意的边界：外部智能体的治理契约在其自身 harness 内，平台做的是协议转译+审计事件（external.audit）而非越权接管。

**后果**：代价=两套能力模型并存（内置全量/外部降级），文档与 UI 必须如实标注；收益=「任意外部智能体经协议即插即用」的多后端主张成立，且不被单一框架锁定。
