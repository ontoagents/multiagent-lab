## 0. 核心结论

**三个项目分别覆盖本体工程生命周期的不同阶段，构成「需求引出→从零构建→增量演化→治理运行」的完整方法链，且三者之间存在明确的方法互补关系**——OntoChat 管前段（需求→CQ→测试），OntoExtend 管后段（已有本体+CQ→增量扩展），Open Ontologies 管全域（构建+验证+治理+运行+对齐）。三项目共同验证的核心范式是：**LLM 参与本体工程的唯一可行方式是「生成→结构化验证→迭代修复」闭环**，单次生成不可用（Open Ontologies 论文实验：结构化 MCP 工具访问 F1=0.717 vs LLM 直读原始 OWL F1=0.323，甚至不如不给文件的裸 LLM 推理 F1=0.431）。[(arxiv 2605.09184)](https://arxiv.org/abs/2605.09184)

对本项目最直接的启示：**六路径已覆盖"构建"全域，但方法间的衔接（OntoChat 产出→OntoExtend 演化→质量门禁贯穿→运行面治理）尚未形成完整动线**。80 号已立项 REQ-337~340 着手解决这一断层。

## 1. Open Ontologies——全域本体工程与治理引擎

> 详细功能面与原理见 [65 号](08_调研预研/项目深度调研/open-ontologies/65_open-ontologies深度调研_功能全景与技术原理_20261008.md65_open-ontologies深度调研_功能全景与技术原理_20261008.md)；借鉴分层见 [66 号](08_调研预研/项目深度调研/open-ontologies/66_open-ontologies双轨退役与自研借鉴可行性_20261008.md66_open-ontologies双轨退役与自研借鉴可行性_20261008.md)。本段聚焦**构建与运行方法**。

### 1.1 定位与架构

Open Ontologies 是 Rust 实现的单二进制 MCP 服务器（v2.1.0，930★，MIT），基于 Oxigraph 内存三元组存储（pin 到 fork 0.5 版取 `Store::snapshot`），暴露 122 个 MCP 工具 + 10 个 tool profile，覆盖 9 个能力面。论文 arXiv:2605.09184（2026-05，Fabio Rovai）给出理论框架。[(github)](https://github.com/fabio-rovai/open-ontologies) [(arxiv)](https://arxiv.org/abs/2605.09184)

**架构核心是「证书即心脏」**：每条推理结果附带推导证书（两个 TSV：asserted + derivations），由独立形式化内核（Lean 4，15,288 行，无 Mathlib）证明健全性；另有 Isabelle、Rocq、Dafny 三个独立形式化做规范解读交叉验证。这套「引擎不可信→证书→独立内核复核」范式是全项目最值得借鉴的架构思想。

### 1.2 构建本体的方法

#### 1.2.1 工具面驱动的 LLM 构建闭环

Open Ontologies 的核心实验结论：**LLM 通过结构化 MCP 工具访问本体，效果远优于直接读原始 OWL 文件**——F1=0.717 vs 0.323（直读甚至不如裸 LLM 推理 0.431）。原因：原始 Turtle 语法的歧义性（属性 IRI 与类 IRI 混淆、语言标签不匹配、多行公理块遗漏）严重干扰 LLM 提取能力。

构建方法是一条**工具链闭环**：
1. **`onto_load`**：载入本体文件（Turtle/RDF-XML/等）
2. **`onto_validate`**：语法与结构校验
3. **`onto_reason`**：推理（rdfs/owl-rl/owl-rl-ext 三档 profile，前向链 29/78 条 OWL 2 RL 规则 + SHIQ tableaux）
4. **`onto_defects` / `onto_lint`**：本体自身质量检查（判数据之前先判本体自身：缺标签/注释/domain/range）
5. **`onto_shacl` / `onto_shacl_check`**：SHACL 形状验证
6. **`onto_cq_run` / `onto_verify_cq`**：能力问题批量运行+判定落库
7. **`onto_align`**：跨本体对齐（6 信号加权 + 用户反馈自校准）
8. **`onto_drift`**：版本漂移检测

LLM 在此闭环中扮演「生成+修复」角色：调用工具生成实体/公理→工具链验证→验证失败时工具返回结构化错误信息→LLM 修复→再验证。这条闭环在 Pizza 本体实验中 **5 分钟完成 91 类、96% 覆盖率**（手工约 4 小时）。[(arxiv 2605.09184)](https://arxiv.org/abs/2605.09184)

#### 1.2.2 数据管线（data profile）——结构化数据→本体

提供从数据表直接归纳本体的能力：
- **`onto_induce`**：「一表进，一本出」——从一张数据表归纳出 OWL 类 + 类型化属性 + SHACL 形状 + 装载映射，每行附证据。这是把"从零建本体"做成确定性管线的关键工具。
- **`onto_shape_induce`**：Kastor 式数据驱动 SHACL 形状归纳
- **`onto_ingest`**：CSV/JSON/NDJSON/XML/YAML/XLSX/Parquet → RDF 三元组
- **`onto_map`**：检视数据 schema + 已载本体 → 生成映射配置
- **`onto_extend`**（工具名）：一条龙 ingest → SHACL → reason

#### 1.2.3 质量门禁方法

Open Ontologies 的质量保障是**多层纵深**的：
1. **语法层**：`onto_validate`（RDF/OWL 语法校验）
2. **结构层**：`onto_lint`（缺标签/注释/domain/range）+ `onto_defects`（本体自身缺陷）
3. **语义层**：`onto_reason` 的一致性检查 + `onto_support_check`（图里的断言是否被支撑——unsourced-claim 率）
4. **形式化层**：Lean 证书体系——每条推理结果附带可独立验证的推导证书
5. **反馈自校准**：`lint-feedback`/`enforce-feedback`——同一告警被 dismiss 三次即抑制、accept 一次即钉住，教 lint/enforce 学习用户偏好

#### 1.2.4 设计模式强制与对齐

- **`onto_enforce`**：设计模式强制执行（`generic`/`boro`/`value_partition`/自定义 SPARQL）——确保本体遵循声明的建模模式
- **`onto_align`**：6 个加权信号（标签相似/属性重叠/父类重叠/实例重叠/限制模式/图邻域）的稳定匹配对齐，输出 `owl:equivalentClass`/`skos:exactMatch`/`rdfs:subClassOf` 候选
- **关键实验**：稳定匹配是对齐的决定性因素——OAEI Anatomy F1 从 0.182 提升到 0.832（P=0.963），信号权重变化 < 0.004 [(arxiv 2605.09184)](https://arxiv.org/abs/2605.09184)

### 1.3 运行与治理本体的方法

#### 1.3.1 Terraform 式变更生命周期

这是 Open Ontologies 最具工程创新性的部分——把 DevOps 的基础设施即代码范式引入本体治理：

```
plan → enforce → apply → monitor → drift → lineage
```

- **`onto_plan`**：声明期望态（Turtle 里没有的就被删），输出 diff + **blast radius**（变更影响范围）+ **risk score** + 锁 IRI。计划持久化在状态库（plan_id），跨会话可追溯。
- **`onto_enforce`**：在 apply 前强制设计模式合规
- **`onto_apply`**：两种模式——`safe`（写差量）/ `migrate`（加 `owl:equivalentClass` 桥接消费者）
- **`onto_monitor`**：SPARQL watcher + 阈值告警（动作：`notify`/`block_next_apply`/`auto_rollback`/`log`）
- **`onto_drift`**：版本对比 + 重命名检测（Jaro-Winkler 相似度）+ drift 速度 + 自校准置信
- **`onto_lineage`**：只追加审计轨迹

**保守性检查**：`check_conservativity: true` 才跑双向推理到不动点——**「缺失的块与干净的块对仪表盘长得一样」**，这是所有报告型接口的通病，项目显式处理。

#### 1.3.2 版本与包管理

- **`onto_version` / `onto_history` / `onto_rollback`**：命名快照 + 历史 + 回滚
- **`onto_pack` / `onto_unpack`**：可移植版本化包（排序 N-Triples + manifest + sha256 + lint 结果 + **证书联合的 content_sha256**）——unpack 时任一摘要不匹配即拒，并**在本机重跑 Lean 检查器**，「证书被拒则阻断装载；检查器缺席则报告"什么都没检"，而那不是通过」
- **`onto_conservative_check`**：加了这些公理，是否改变了本体已经说过的话？

#### 1.3.3 双时序（valid time / recorded time）

两个刻意独立的时钟——**VALID time**（陈述在世界上何时成立）与 **RECORDED time**（库何时开始持有它）。合并二者会丢掉两个核心问题——「当时什么是真的」与「当时我们信什么」。

实现：命名图承载断言 + 默认图描述有效期，区间半开 `[from, to)`（边界相接不算重叠）。**血缘是断言的、永不推断**：`temporal:supersedes`（命名被替换的图）与 `temporal:retracts`（命名被撤回且无替代的图）。[(65 号 §3.7)](08_调研预研/项目深度调研/open-ontologies/65_open-ontologies深度调研_功能全景与技术原理_20261008.md65_open-ontologies深度调研_功能全景与技术原理_20261008.md)

#### 1.3.4 RAG 切片蕴含保持

**核心洞见**：99% 覆盖率仍可能丢掉答案依赖的那一条三元组；且覆盖率朝错的方向动——**要的性质是"蕴含保持"，不是覆盖率**。

四象限诊断（`G`=全库, `P`=切片, `q`=答案依赖的 ground 正三元组）：

| `G⊢q` | `P⊢q` | 含义 | 修复方 |
| --- | --- | --- | --- |
| 是 | 是 | **preserved**——唯一能带证书的格子 | ✓ |
| 是 | 否 | 切片丢的 | 检索器 |
| 否 | 是 | 引擎不健全 | 引擎（永不是检索问题） |
| 否 | 否 | **`ungrounded_in_source`**——源里根本没支撑 | 生成器 |

**第四格是价值所在**：生成器编造与检索器漏取**修复方向相反**，把它们都报成"未保持"会把每次排查都送到错误的团队。[(65 号 §3.6)](08_调研预研/项目深度调研/open-ontologies/65_open-ontologies深度调研_功能全景与技术原理_20261008.md65_open-ontologies深度调研_功能全景与技术原理_20261008.md) [(arxiv 2605.09184)](https://arxiv.org/abs/2605.09184)

## 2. OntoChat——对话式本体需求工程框架

> 详细原理与实现见 [63 号](08_调研预研/项目深度调研/63_OntoChat深度调研_论文原理与开源实现_20261008.md63_OntoChat深度调研_论文原理与开源实现_20261008.md)。本段聚焦**构建与运行方法**。

### 2.1 定位与架构

OntoChat 是「**对话式本体需求工程（ORE）**」框架（Python/Gradio，MIT，33★），只覆盖本体工程生命周期的**前段**——需求引出→CQ 抽取→CQ 分析→本体测试。它**不生成 OWL 本体**，产出物是结构化的需求制品（用户故事 + CQ 集 + 覆盖性测试报告）。

论文：arXiv:2403.05921（ESWC 2024）+ arXiv:2408.15256（参与式提示改进版，AAAI-SS 2024）+ ACM TIST 2026（助手论文）。[(arxiv)](https://arxiv.org/abs/2403.05921) [(github)](https://github.com/King-s-Knowledge-Graph-Lab/OntoChat)

**设计依据**：N=23 语义网从业者调查——最需计算支持的任务：需求收集 86.4%、CQ 抽取 81.8%、本体测试 81.8%、需求分析 77.3%。

**理论谱系**：METHONTOLOGY(1997) → DILIGENT(2004) → NeOn/SAMOD/XD(2010s) → IDEA(2023) → **OntoChat(2024)**。CQ 是需求与实现/测试之间的枢纽——这也是本项目 REQ-248（CQ 一等公民）与 REQ-255（CQ→SPARQL 验收）的理论正当性来源。

### 2.2 构建本体的方法

OntoChat 的构建方法是**四模块对话工作流**，每个模块都有明确的算法、prompt 资产和评估口径：

#### 模块 1 · 用户故事共创（4 步）

| 步 | 名称 | 机制 |
| --- | --- | --- |
| 1 | LLM 角色定义 | 系统预置为「知识引出者」，一次只问一个问题 |
| 2 | 知识引出 | 用户逐步回答（Persona → Goal → Scenario）；未确认满意前不得进入下一问 |
| 3 | 故事生成 | One-shot learning：给范例→LLM 按同结构汇总草稿 |
| 4 | 精修 | 用户反馈→迭代精修至满意 |

**关键设计**：用户越级回答会被拒回；可回退到任意已完成步骤。10 条参与式提示模板（占位符 `**[必填]**` + `*[可选]*`）降低用户提示难度。

#### 模块 2 · CQ 抽取（4 步）

| 步 | 机制 |
| --- | --- |
| 1 | Few-shot 对齐：给「用户故事片段→CQ」成对示例 |
| 2 | 首次抽取：用户给故事→输出初始 CQ 列表 |
| 3 | CQ 净化（隐藏 prompt，两个关键算子）：①**拆非原子问题**（复合 CQ 拆为原子）；②**命名实体抽象**（去专名→通用问题模式） |
| 4 | 用户确认：CQ 数量/表述合理→满意为止 |

**核心增益**：CQ 抽取的两个净化算子（拆分复合问题 + 抽象命名实体）是相对朴素 LLM 抽取的关键增益——直接把「例子里的专名」收敛为「可复用的问题模式」。

#### 模块 3 · CQ 过滤与聚类

- **去冗余**：paraphrase identification（LLM 驱动，不依赖句向量）
- **聚类**：LLM 直接完成主题聚类（`{'cluster 1 topic': ['cq1','cq2']}`），论文反其道——IDEA/RevOnt 都依赖句向量+专用模型
- **产出**：带主题标签的 CQ 簇

#### 模块 4 · 本体测试（无 SPARQL 路径）

两步：
1. **本体口语化**（`verbaliser.py`）：把 OWL 本体转成纯文本（classes + named entities + relations 三段式）
2. **逐 CQ 独立判定**：用口语化文本，让 LLM 对每条 CQ 判定 Yes/No。**为保证独立性、防 prompt 泄漏，每条 CQ 单独调用一次**

### 2.3 运行与演化方法

OntoChat 本身不管理本体运行与演化——它的产出是需求制品，驱动下游工具（如 OntoExtend、LLM 本体生成器）进入构建阶段。但其**CQ 作为回归测试基准**的方法对运行阶段有直接价值：

- **CQ 即测试用例**：`onto_cq_run` + `onto_verify_cq`（Open Ontologies 的同名工具）可把 CQ 做成有判定的可回归基准——每次本体变更后跑一遍 CQ 验证，检测漂移
- **参与式提示的迭代**：arXiv:2408.15256 提出「由 LLM 根据当前用户故事主动建议下一步该改什么的定向 prompt」——这是引导卡自动推荐的论文级依据

## 3. OntoExtend——需求驱动的本体增量扩展框架

> 详细原理与实现见 [64 号](08_调研预研/项目深度调研/64_OntoExtend深度调研_论文原理与开源实现_20261008.md64_OntoExtend深度调研_论文原理与开源实现_20261008.md)。本段聚焦**构建与运行方法**。

### 3.1 定位与架构

OntoExtend 是「**需求驱动的本体扩展**」框架（Python，10★），管的是本体工程**后段**——本体已存在→增量维护。与 OntoChat（管前段需求引出）恰好互补。论文：arXiv:2607.17963（2026-07）。[(arxiv)](https://arxiv.org/abs/2607.17963) [(github)](https://github.com/dersuchendee/OntoExtend)

**核心创新**：**此前没有任何工作把「检索已有本体元素」内建进扩展流程**。成熟本体常有数百类/属性超出 LLM 上下文，即使塞得下也会被无关细节误导——检索出紧凑相关片段是关键。

### 3.2 构建本体的方法

#### 3.2.1 三段式管线

```
CQ + 输入本体
   │
   ▼
① Ontology Retriever  CQ → top-k 相关本体元素片段（向量检索）
   │
   ▼
② Ontology Extender   CQ + 片段 → LLM 生成缺失 TBox 片段 → 两阶段校验
   │
   ▼
③ Ontology Integrator 去重 + 拼接回输入本体 + 可选回灌重索引
```

#### 3.2.2 Retriever（检索器）

- **元素抽取**：遍历 OWL 实体（classes/object properties/data properties/annotations/SHACL shapes），为每个构建 `OntologyElement`（IRI/label/comment/domain/range/父类子类/verbatim Turtle 片段）
- **序列化**：管道符分隔字符串——`localName | label | comment | Type: {type} | Domain: {names} | Range: {names}`
- **索引**：向量 L2 归一化 → FAISS `IndexFlatIP`（内积=余弦）
- **查询**：CQ 同空间编码 → top-k（默认 20）
- **最佳配置**：`text-embedding-ada-002` + 管道符 + 含 comments（M_prod=0.23, M_w=0.63，12 组对照最优）[(arxiv 2607.17963 Table 3)](https://arxiv.org/abs/2607.17963)

#### 3.2.3 Extender（扩展器）

- **prompt 组装**：检索到的元素按来源本体分组渲染为 Turtle 片段（只读上下文）+ 统一 prefix 块
- **两套部署 profile**：
  - **工业本体 profile（SHACL 型）**：输出 `sh:NodeShape`/`sh:PropertyShape` + `sh:name`
  - **EU 本体 profile（OWL 限制型）**：要求 `rdfs:label`+`rdfs:comment`，鼓励 OWL restrictions
- **两阶段校验**：① Turtle 语法解析 ② 约束检查（domain/range 显式声明）——失败则重试或标记
- **prompt 关键约束**（从代码提取，可直接复用）：
  - 7 条 INSTRUCTIONS：分析 CQ 所需概念→映射到检索元素→优先语义相似度高者→仅 TBox→CQ 暗示时加限制→每个属性显式 domain/range→语法正确且自包含
  - 12 条 ImportantNotes（含 pitfalls 清单）：用 subClassOf/subPropertyOf 特化、已有则不重复、写 label/comment、避免命名不一致、不写 # 注释、仅 CQ 需要才加限制、需要时加具体化(reification)、无 A-Box、复用 prefix、追求高质量、只在有值时加 inverse

#### 3.2.4 Integrator（集成器）

极简设计：
1. **去重**（重复公理/类/属性/prefix）
2. **拼接**回输入本体
3. **回灌重索引**（可选）：把生成片段转发给 Retriever 索引——降低后续 CQ 处理时 Extender 重建相似元素的概率，促进跨片段一致性

**重要提示**：论文评估中回灌被关闭，链式一致性未经量化验证。[(64 号 §1.3)](08_调研预研/项目深度调研/64_OntoExtend深度调研_论文原理与开源实现_20261008.md64_OntoExtend深度调研_论文原理与开源实现_20261008.md)

### 3.3 运行与演化方法

OntoExtend 聚焦增量扩展，运行治理方法有限但其方法论对本项目有直接映射：

- **CQ 驱动演化**：每次新需求以 CQ 形式输入→检索→生成→校验→集成——天然的演化驱动模型
- **LLM 行为作为质量代理信号**（论文独到洞见）：若一组 CQ + 输入本体能让 LLM 系统性产出更高质量扩展，则该组合「更好」；反之系统性困难多半源于需求含糊/欠定义/隐藏建模假设——**LLM 行为可作为 CQ 与本体质量的新维度**
- **对 CQ 质量高度敏感**：工业 CQ（聚焦，专家+工程师共拟）Correctness 4.91~4.96；EU CQ（开放，决策留给工具）仅 3.66~3.69——**框架不能补救坏需求**
