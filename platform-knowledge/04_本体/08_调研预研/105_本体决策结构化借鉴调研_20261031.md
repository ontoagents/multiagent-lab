## 一、文章概要与主题判断

**文章性质**：一篇团队级工程实践复盘。商家财务团队三个月内在自建「Agent Room」中创建并完成 120+ 需求/工作项，实现从需求开发到数据订正、工单处理、业务运维的「工作全托管」——人只提需求 + 批 CF/CR 单（article.md:21,29-31）。

**证据等级说明**：文章全部效果主张（120+ 需求托管、模型/harness 换代后「输出稳定性没变」、「决策图越用越密」、「新任务多数判命中已有决策」）均为**单一团队自述**——无方法论、无对照、无法独立核实；文中截图导出时间戳（2026-08-13）与发布采集日（2026-10-30）之间亦有窗口期。本报告将此类内容一律按「文章自述」等级采信，用于说明**其主张与做法**，不作为其效果**已获证实**的依据；本报告对文章的引用如无「亲读/复核」标注的推断性概括，均为报告自身判断。

**核心主张三件套**：
1. **决策结构化**——把专家判断固化为含 `decision_question/trigger/start/required_slots/optional_slots/pre_route_evidence_plan/traversal/route_rules/reject_routes/output` 十字段的可执行 decision_function（article.md:84-97），文章自述与《金字塔原理》四原则「几乎是同构的」（article.md:78，img-08 复核）；
2. **四层 Ontology**——借鉴 Palantir 但加 Delivery/Governance 两层：Business/System/Delivery/Governance（article.md:121,129-136），知识链条 `Object/Property/Relation/State → Metric/Evidence → Logic/Decision → Action/Workflow → Audit/Feedback`（article.md:126）；
3. **碎片化沉淀**——不打包 Skill，每天把工作拆成 decision route / reject route / golden case 三类碎片受控写回（validate + 评审），自述「决策图越用越密」、知识沿图增长产生复利（article.md:213-225，img-18 亲读）。

**主题判断**：这是「本体作为 Agent 决策底座」主张的一份高完整度中文一线复盘（是否「最完整」无比较面支撑，不作断言）。它把本体的价值从「给人读的知识组织」推进到「驱动 Agent 取证-决策-交接的可执行资产」，核心论点：模型与 harness 都在被快速替换，业务知识层才是壁垒，而这一层文章自述「训练长不出来，也编排不出来」（article.md:243-247，img-22 复核）。

**与本项目的关系**：叙事高度同频——本项目定位即「以本体为知识底座的知识工作助手」，本文从重度实战侧为「本体工程=差异化知识底座」叙事提供了单团队自述级佐证（非独立审计，引用时须注明）。**场景错位**须警惕：文章是团队级工作全托管（有 Aone/O2/CR 发布链、CF/CR 审批单），本项目是单机自部署的个人知识助手——其「交付层门禁」「多 Agent 交接」部分不可照搬（见第四节）。文章对流程的口径与本项目 Q-23 诚实边界（「流程类场景」优势不作为已有能力主张）意外一致：其流程是**从决策长出来的**，不是预设的。

### 【可借鉴】按 P0/P1/P2（理由含契合度·成本·边界）

**P0-1 决策/规则/动作成为 spec 一等公民（decisions[] 可选层——知识形态半边）**
- 依据：B4/B7/A1。**定位修正（审读意见 3）**：文章价值支点=**可执行**决策结构（十字段中 trigger/route_rules/traversal/pre_route_evidence_plan 构成可执行语义，img-09 亲读）；本项目借鉴的是其**知识形态半边**——「判断是图上一等公民、可检索可审计」。契合度分档陈述：**知识形态契合=高**（判断成为可检索可审计资产，喂饱出题/审计/检索三条既有链）；**执行语义契合=0**（本批明确不做解释器，见不建议借鉴 2）。
- schema 草案（审读意见 8；沿 REQ-376 Restrictions 可选层先例——spec.go:25-29 注释、:169-192 Validate 校验、qualitygate.go:99-121 配套检查项，存量零迁移）：
```json
"decisions": [{
  "id": "dec_synonym_when_add",
  "decision_question": "何时应给概念补同义词？",
  "required_slots": [
    {"slot": "业务口语样本", "source": "relation:check_answerable 命中面", "missing_action": "先查缺口清单"}
  ],
  "reject_routes": [
    {"route": "把口语词直接改成概念名", "reason": "破坏既有引用与出题基线"}
  ],
  "proof_scope": "仅适用于 TBox 建模决策；不覆盖 KG 抽取口径"
}]
```
  Validate 新增（沿 restrictions 模式）：id 唯一、required_slots[].source 引用已定义关系/概念、required 字段非空；qualitygate 增 1~2 个 warning 级 checkDef（decision_question 缺失/required_slots 空）。**与 Axiom 的关系澄清（审读意见 6）**：现有五形态中 Axiom（disjoint_with/equivalent_class 两型，spec.go:121-125）是形式公理——承载 OWL 逻辑一致性、严格语义不由 LLM 生成（spec.go:118-120 注释亲核）；它不是「专家怎么判断」的业务知识，与决策节点互不替代。overlay 对象四类枚举（spec.go:412-417）不含 axiom 系既有口径，决策节点落地时须同批决定其 overlay kind 归属。
- 六舍字段去向（审读意见 3）：trigger/optional_slots/start/pre_route_evidence_plan **丢弃**（执行编排语义）；traversal **不另建**（facade 既有 neighbors/sparql_query 原语承担）；route_rules **留观察**（后续批次可作「槽值→建议动作」映射表，仍无执行语义）。保留四轻字段=decision_question/required_slots（描述性证据要求）/reject_routes/proof_scope。
- 冷启动与内容成本（审读意见 9）：文章飞轮前提=业务专家每天有真实决策可沉淀（article.md:225），本项目无等价决策流——这是本借鉴能否产生文章式复利的**根本变量**，也是最大不确定项。建议三来源起步：①**平台自举 dogfooding**——为本体工程域本体手写 3~5 条判断（如「何时补同义词」「何时跑 CQ 快筛」，REQ-500 快筛三态即现成证据源）；②**伴生晋升理由转提案**（承 REQ-529：确认实体时「为什么确认」的理由片段）；③**出题/批改缺口反哺**（承 REQ-524 mastery 薄弱概念→「待补决策」清单）。首批 3~5 条验证消费面，不追量；**内容成本不并入工程成本「中」的估计，单列评估**。
- 效果度量（审读意见 10）：建基线后比对——决策节点被 facade 检索命中数（ontology_hit 扩 node_kind 归因）、CqQuickScreen 三态分布与缺口命中率变化、回归门控第三信号开启后的拦截次数（详见五.7）。
- 成本：工程量中（schema+Validate+TTL round-trip+质量门+呈现）；内容成本另列（见上）；风险=77 号「不做 spec_json 全面 OWL 化」边界——决策节点是知识形态扩展非表达力 OWL 化，但须在 03 号立项行显式注边界防口径滑坡。

**P1-2 图谱工作台阅读面三件套（KEY HUBS 度数榜+规模统计卡+要素筛选增强）**（自 P0 降级，审读意见 4）
- 依据：C1/C3/C5/C7。
- 契合度：中高。03 资产面已有可视化 4 形态+REQ-363 跨视图选择总线「纯前端派生零后端」先例；SpecGraph 现有筛选仅要素级（rel/parent/instance links+showInstances+onlyWithInstances，`SpecGraph.tsx:102-205,342-345` 亲核），无度数枢纽榜/规模统计卡/搜索框。
- **降级理由与触发条件**：本项目资产量级（个人知识本体，数十~数百概念）远小于文章 770 节点，枢纽榜在当前规模非刚需；**升级触发条件**=单资产节点数持续 >300，或组装载/伴生图成为常态阅读对象。实现成本仍低（纯前端派生），可随任意本体轮顺带先行，不必占独立 P0。
- 口径注记（审读意见 11）：KEY HUBS 度数定义截图不可辨（入+出/仅语义边/是否排除 object_ref 等派生边均无标注）——实现需自定义口径并在 UI 注明；建议 v1=无向全边计数（与「连接度」直觉一致），后续可配。

**P1-3 证据槽/缺槽口语义接入消费与出题链**
- 依据：A3/D2——「缺哪个槽，就是一次补证任务」+隐含上下文四约束拆解。
- 契合度：高。REQ-500 CqQuickScreen 已有三态徽标+缺口清单直达钮（docs/03:854 盘点）；REQ-524 出题链诚实边界明写「check_answerable 覆盖度预检未接线」（docs/03:1180 亲核）。把缺口清单升级为「缺哪个概念/哪条关系/哪个同义词」的结构化槽位语义是既有两件的收窄而非新能力。
- 成本：低-中。主要在 check_answerable 返回结构细化（matched→missing 逐项）+前端呈现。

**P1-4 golden case 决策级回归：激活第三信号+gold 案例级扩展**
- 依据：E1/E2——golden case「用于回归校验后续变更会不会破坏原有判断」；受控写回必跑「案例回归」。
- 现状修正（审读意见 5，亲核）：**行为级对照接线已在位**——gateEvolutionCandidate 第三信号（REQ-382/M178）`with_benchmark` 显式开启时 base/patched 各跑一轮 cqbench 三率、gold 对齐率或白名单率回退计入门控回归（rest_evolution.go:150-156 注释、:213-219 双跑代码），默认关。本借鉴实际增量=①默认开启的时机与成本评估②gold 语义扩展为案例级（案例→期望命中概念集/期望不可答，沿 seeds/evaldata 单源惯例）③拦截事件留痕呈现。
- 成本：低-中（比原判更小——管线现成，扩语义+开闸即可）。

**P1-5 知识写回补「评审」半边：learning proposal 暂存区**
- 依据：E2/F1——写回=validate+**评审**双闸；「未验证的猜测、一次性日志、临时判断，一律不进 ontology」。
- 契合度：高。REQ-529 已打通出料口但直接 PUT 合并（docs/03:1179 亲核）；伴生链已有 confirm/reject 交互（与文章评审门同构）；approval.request/granted/denied 事件形态在位（`event_names.go:33-35`）。缺的是「提案→暂存→人批→入库」显式化+拒绝理由留痕（被拒提案即 reject route 素材）。
- 成本：低-中。暂存表+审批面复用 approval 形态；晋升端点改挂提案态；与 REQ-529 迭代表注明的「逐条勾选 UI 随伴生线 UI 轮」挂账合流。

**P2-6 proof_scope 结论边界透出与审计**
- 依据：A5/B7。项目消费归因（ontology_hit 带 profile_id，REQ-482）已记录「回答命中哪些本体」，未记录「结论适用边界声明」。前提=P0-1（decision 节点带 proof_scope 字段），单独做无承载。成本：低（字段+审计透出）。

**P2-7 layer/scope 分层组织约定（借范式不借引擎）**
- 依据：B1/B2。载体已在（多本体+组装载），缺组织范式。个人场景下 Delivery/Governance 两层不适用（不建议借鉴 1），但「知识本体 vs 来源系统登记本体」两层对「由知识库构建」「伴生晋升」链有真实价值。成本：低（约定+种子示例），随种子内容更新顺带，不单独立项。

### 【不建议借鉴】

| 项 | 理由 |
|---|---|
| 1. **Delivery 层与工作全托管叙事**（发布流水线/Aone 变更单/CR 门禁/120+ 需求托管效果主张） | 场景错位：交付对象依赖阿里内部发布链，本项目单机自部署无此实体；Q-23 诚实边界明确「流程类场景」优势不作为已有能力主张；且 120+ 托管系文章自述、无独立核实，照搬叙事会把本项目诚实边界打穿。其思想内核（门禁=对象化判断）已由 P0-1 覆盖 |
| 2. **decision_function 完整执行引擎**（槽位判满→遍历→路由的运行时解释器、insufficient_evidence 派 owner 补证的多 Agent 流转、next_owner 交接路由） | 这是文章的 harness/编排面：需常驻执行循环、任务派发与补证回路。本项目对话引擎（TurnLoop/delegate）面向单用户交互，不承载无人托管执行；强上会把产品拖向「迷你 Coze」式流程引擎——恰是 Q-23 已正式放弃的对标方向。**先以「决策知识可检索可审计」落地（P0-1/P2-6），执行化留触发条件**（例：用户开始用平台管理带审批流的个人事务、且伴生图积累到需要派发补证的规模——当前零证据支撑该触发） |
| 3. **Palantir 式企业级 Ontology 平台对标扩叙事** | 文章自言解决的不是企业数据分析而是 Agent 执行（article.md:121）；本项目用户画像为知识密集型专业个人。引用其 FDE 沉淀逻辑作调研素材可以，官网/README 不宜攀企业平台叙事 |
| 4. **key_states 重状态机建模**（发票 created/issued/valid/blue/red…） | 个人知识场景「对象生命周期状态」需求弱；Instance.attributes 自由键可承载轻量状态标注。留观察 |
