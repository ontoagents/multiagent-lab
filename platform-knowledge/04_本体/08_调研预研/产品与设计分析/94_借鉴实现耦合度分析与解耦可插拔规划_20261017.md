## 1. 耦合分级与可插拔判据

### 1.1 分级定义（沿 93 号底稿口径）

| 级 | 定义 | 摘除成本 |
|---|---|---|
| S0 | 独立：零被依赖或纯 build tag 测试消费 | 删目录即摘 |
| S1 | 旁路可摘：HTTP 边界或装配点集中 1–2 文件 | 断 1 处路由组+装配段 |
| S2 | 编译期依赖：≥2 文件 import 或挂进装配链 | 改装配+接口化，半天内 |
| S3 | 侵入主体核心：主链路 struct 直接持有具体类型+多方依赖网 | 结构性改造，随业务 REQ 顺带 |

### 1.2 可插拔四判据（本文新增，作为「可插拔」的验收口径）

借鉴实现 P 满足可插拔，当且仅当：

1. **边界独立**：P 位于独立包/独立进程/独立 go module，或经 HTTP 边界隔离（本体侧 12 包范式）；
2. **装配点集中**：主体接入 P 的位置 ≤2 文件（理想：api 装配层 server.go 一处，沿 companion/kg/ontobuild 现状）；
3. **抽象反转**：主体依赖接口而非 P 的具体类型——P 不可用时主体降级运行不编译失败（`chat.CompanionSource`/`CommunitySource` 接口反转范式，`runner.go:59-68`）；
4. **产物物理隔离**：P 的落库产物独立表/独立 artifact format，删除即整体摘除（qualitygate 质量报告 artifact 范式； REQ-274 P9 评测集进 evaldata 范式）。

四判据与低侵入三原则（旁路/默认关/可摘除，`qualitygate.go:3-8` 成文在先）的关系：**三原则是设计纪律，四判据是验收标准**——凡新借鉴落码，设计时对齐三原则，验收时过四判据。

## 3. 逐项耦合分析：S3/S2/渗透型/S1 各形态机制

### 3.1 吸附型 S3：kb（被依赖最广的借鉴实现）

**机制**：`chat.Service.KB` 为具体类型 `*kb.Service` 字段（`chat/runner.go:32`），对话主链路编译期调用（recallKB/graphrag/community 兜底/wiki 臂）；10 方非测试 import（cmd×2、api×4、chat×2、companion×2、ontobuild×1）。

**为什么它是债**：kb 同时扮演两个角色——①知识库产品功能（自有 API 面 L232-244）；②对话主链路的检索依赖。前者可插拔无争议；后者使「摘除 kb」=「对话降级」，编译期锁死。对比同链路的 companion/kg 均已接口反转（nil=未接入），kb 是唯一未反转的检索源。

**摘除成本实测（93 号底稿 §9）**：改 chat 结构体+装配+5 个 api handler+2 个 companion 文件——工作量半天~1 人日级，但**必须**随业务 REQ 顺带做（单独开批纯粹为架构美感不值得，见 §5 R4）。

### 3.2 编译期 S2×4：断点已收敛，缺的是最后一步抽象反转

| 包 | 反向依赖 | 断点位置（93 号底稿实测） | 距可插拔差什么 |
|---|---|---|---|
| companion | api 2 文件；chat 侧已接口反转（CompanionSource） | server.go L47-48 装配+L114-144 路由组+`Companion=nil` | **已达标**（四判据全过，收尾抽取挂 Run/Resume 时序属可接受的最小时序耦合） |
| kg | 4 方编译期；chat→kg 接口反转已做；**kg→chat 正向 import 3 文件** | main.go L74-86 注入+server.go L55+L255-269+companion/community.go L78 | kg 对 chat 的正向依赖应反转（GenerateStructured 主路径经接口/回调注入），否则 kg 单独摘除仍拖出 chat |
| ontobuild | api 2 文件 | server.go L56+L247-250+handlers_kb 构建流段 | 自依赖 chat/kb/store 四包——编排层身份使然，可接受；断点集中，达标 |
| ontology | 4 方编译期但仅 182 行纯代理 | cmd 两处构造+server.go 反代组+assembler L574-577 | 纯代理无业务逻辑，摘除成本低，**不动**（R4） |

### 3.3 渗透型：Helix 编辑三层系——无法插件化，只能纪律管未来

**机制**：借鉴实现不留独立包，直接以「修改主体核心模型」形态落码——overlay 表成为 spec 仓库数据模型一部分（迁移 043）、If-Match 成为 saveSpec API 语义、X-Onto-Triples 成为 backend↔runtime-manager 跨服务协议头。

**判定**：这**不是要清算的债**——编辑三层解决的是真实主线问题（机器写入覆盖人工编辑），且三层模型本身已成为主体的编辑语义。它揭示的是另一类风险：**未来的借鉴落码若继续以渗透形态进入，93 号这类扫描将无法识别借鉴边界（本次 HelixDB 即因无署名而漏判），摘除审计与来源追溯断裂**。药方见 §5 R3（署名纪律），而非改造存量。

### 3.4 S1 侧 12 项：可插拔已是既成事实

ontology-service 侧借鉴包的可插拔性由架构整体保证，非逐包努力的结果：同仓库独立 go module（跨模块 import=0）+ server.go L286-321 单一反代组挂载 + runtime-manager 对借鉴关键词全零（运行平面干净）。**拔除任一借鉴能力的动作=删反代路由行+删对应 internal 包**，主体零感知。ONTOCHAT 智能体工具化（REQ-354 P1）也在此边界内进行——工具包装消费 /api/ontochat/* REST，不引入新编译期耦合，方向正确。

### 3.5 前端契约耦合：唯一未成文的同步约定

web/src 对借鉴实现的耦合全是契约型（client.ts 端点族+types.ts 类型），无业务逻辑复制；但摘除面宽（ontochat 17 文件/companion 20 文件/graphrag 17 文件），且「后端摘除→前端同步收缩」目前靠执行者自觉。semantica 残留垫片即是该缺口的一次性产物。

## 4. 解耦资产盘点：基建已齐，缺纪律成文

**六种隔离机制已在代码中实战**（93 号底稿 §4）：

| 机制 | 实例 | 适用场景 |
|---|---|---|
| build tag | agenteval/eval/kbeval 共 7 处 | 评测/重依赖资产隔离出编译主路径 |
| tool.Registry 统一注册表 | SourceKind 四类+动态来源装配期并入 | agent 工具面插件化 |
| 接口反转 | chat.CompanionSource / chat.CommunitySource | 主体←借鉴包编译期依赖的解药 |
| 注入函数类型 | kb.KGExtractFunc / kb.WikiLLMFunc（nil=degraded） | 跨包回调防环 |
| 导出门面 | companion/evalfacade（零逻辑纯转发） | 评测等旁路消费者不触内部编排 |

**结论**：可插拔基建（机制+先例+实战验证）已全部就位；真正缺的只有两件——①两处存量债的最后一步（R1/R2）；②把隐性实践显性化为纪律（R3），使未来借鉴落码不产生新的渗透型与未收敛装配点。

## 5. 解耦可插拔规划（R1~R4 四档）

### R1｜kb 接口反转（清吸附型 S3 债）

- **动作**：`chat.Service.KB *kb.Service` 具体类型 → `chat.KBSource` 接口（沿 CompanionSource/CommunitySource 现成范式：chat 定义接口、kb 实现、api 装配层接线、nil=未接入降级）；kb 保持不 import chat（现状已满足）。
- **收益**：kb 从 S3 降 S2 并过四判据；对话主链路对检索源可替换（未来换检索实现/降级运行不再是编译事件）。
- **成本**：chat/api/companion/ontobuild 四处触点改接口引用，半天~1 人日。
- **时机**：独立小批（建议 REQ-355，P2 级），**不与业务 REQ 混批**——纯结构改动混进业务批会放大回归面。

### R2｜kg→chat 正向 import 反转（清 S2 债）

- **动作**：kg 三文件对 chat.GenerateStructured 的正向 import 改经注入（api 装配层把生成函数以回调/接口注入 kg，沿 kb.KGExtractFunc 注入函数类型先例）。
- **收益**：kg 摘除不再拖出 chat；kg 与 companion 一样成为「单向可摘」。
- **成本**：3 文件+装配段，半天内。
- **时机**：随 REQ-355 同批（同为接口反转机械动作，回归面同类）。

### R3｜解耦纪律成文（建议记 **D-O26**，防新债）——待拍板

新借鉴（论文/开源项目）落码四约定：

1. **独立落点+署名**：借鉴实现进独立包（或独立子目录），包注释署名来源项目/论文+调研档相对路径链接——这是耦合扫描能识别借鉴边界的前提（93 号底稿 §2 两表全靠包注释识别；HelixDB 无署名即漏判，实证署名价值）；
2. **独立迁移号+表前缀**：借鉴实现的存储产物独立 migration 与独立表名/artifact format，删除即整体摘除，禁止并入主体核心表；
3. **禁渗透**：不得以修改主体写路径/API 语义/跨服务协议的形态落码借鉴功能——确需动主体（如 Helix 编辑三层这类主线级能力）时，显式开 REQ 评审，把「借鉴来源、侵入面、可摘除性」写进需求行，接受架构审查；
4. **前端同步收缩**：摘除后端借鉴实现时，同一批收缩 client.ts/types.ts 对应段（含旧路由垫片清理），不让前端残留先于后端退役。

### R4｜不动清单：可插拔 ≠ 全部插件化

- **S0×4、S1×12 共 16 项不折腾**：旁路形态已达标，为「插件化」再抽象是纯税——插件抽象只在「预期替换或摘除」处值得支付；
- **internal/ontology 182 行纯代理不动**：摘除成本虽低，但它是对接面本身，动它无收益；
- **Helix 渗透型存量不动**：已成主体编辑语义，改造=推倒编辑模型，负收益；纪律只管未来；
- **ontobuild 自依赖四包不动**：编排层身份使然，断点集中已达标。
