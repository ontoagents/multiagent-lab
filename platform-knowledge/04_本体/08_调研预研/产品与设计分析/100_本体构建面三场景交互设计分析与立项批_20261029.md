## 一、结论摘要

**怎么做:不新增任何一条生成管线,把已经建成的深度透出到用户做决策的位置和动线断掉的地方。** 五条主路径与 Protégé 式树/画布/表单编辑均已交付,2026-10-27~28 五批治理已把交互痛点主体清账——剩下的差距集中在四处接缝:**构建流内没有结构化建模面**(S2 是裸 JSON,树/表单沉在资产详情第三层,`CustomBuildFlow.tsx:840` 注释自述「JSON 编辑+保存;版本/产物在资产栏」)、**反馈是关卡不是护栏**(校验分散四处靠手动触发,树上操作失败只有一行 toast,`HierarchyPane.tsx:681`)、**方法论与复用资产不在建模现场**(五卡硬编码在第五栏学习中心,`LearnPage.tsx:66-107`;词表联想 `vocabSearch` 仅 2 处消费)、**质量闭环断在呈现与预期**(CQ 覆盖自查只在两处「入库后」形态存在,完成/发布时点零检查;AI 精修只有整稿重生成一态)。

**优先级**:P0 三件(完成仪式+条目级缺口清单 R1、结构优先 S2 双形态 R2、常驻诊断条+失败明细与撤销 R3)先缝合断缝;P1 七件把小步提案(R4)、复用联想(R5)、边建边教(R6)、顺手声明(R7)、发布体检(R8)、材料起步(R9)、文案人话(R10)接到高频动线;P2 四件(推理对照 R11、研究留痕 R12、导入复用语义 R13、打卡挂钩真实动作 R14)触发成熟再领取。**全部建议零新管线、不触 Q-7 画布边界、不重启退役栈、不破「LLM=草稿生产者+人工确认+修复环≤3 轮」铁律(REQ-269)。**

## 二、根因诊断(两条主诉分开)

### 主诉一「没那么方便」:能力齐全,断的是接缝

**C1 动线断裂——结构化建模能力沉在资产详情第三层,构建动线内只有裸 JSON。** 实读 `CustomBuildFlow.tsx:843-929`:S2EditPane 主体是 `Input.TextArea`(:906-913),placeholder 即 spec JSON 模板(:912),分区标题就是「Spec JSON」(:891);而层级浏览/图形编辑/关系与属性/公理等 11 个分区全在 `AssetsPage.tsx:94-128` 的资产详情导航下。高频动作跨分区:`modals.tsx:109-127` 连线时声明关系为空,渲染禁用 Select+「先声明」,把用户踢去资产栏「关系与属性」分区,树/画布↔表格两次表单。树上操作钮 hover 才显隐(`HierarchyPane.tsx:721` 注释「树上快捷操作钮(hover 显隐…)」),元素级 REST 仅单条 upsert/delete/rename 三端点(`rest_elements.go:24-28`)。80 号 G1 判定的「六路径并列是路径陈列馆」在首页组织层已由 REQ-484~486 治理(docs/03:828-841,REQ-484「全页去 REQ/M 编号」✅ M283 实证),但**构建流内的编辑面未同步治理**。

**C2 反馈是关卡不是护栏——校验滞后、分散、失败反馈缩水,叠加平台方言认知税。** 实读 `HierarchyPane.tsx:672-685`:树上元素操作失败 catch 分支仅 `message.error(e?.message ?? '操作失败(校验明细见响应)')`(:681),而 :671 注释自认「400 校验明细如实回喂」——同一校验管线,`SpecEditorPane.tsx:383-395` 与 `CustomBuildFlow.tsx:914-926` 渲染 path+message 结构化明细表,树上只有一行 toast,两套反馈质量。就地诊断的技术可行性已被验证:`AssetsPage.tsx:337-344` save=false 静默跑分(注释「qualitygate 规则检查非 LLM、零副作用不落产物」)+ :353-358 列表态渐进预取,但都不进编辑视图。72 号判定「断层在呈现与闭环:结果被压成 toast/过程不可见」(docs/04:133)。术语层:`HierarchyPane.tsx:847` 分区名直写「Protégé 式树形导航(REQ-363)」、`AssetsPage.tsx:622` 「表达性签名(简化 DL 记号)」、`modals.tsx:53` 同义词帮助文案挂「REQ-419,check_answerable 预检消费」内部编号、`OntoChatFlow.tsx:894` 覆盖测试按钮 title 写「成本=N 次模型调用」——对非工程师画像每步一层认知税。

### 主诉二「建的本体不如意」:方法论不在场+质量闭环断层与预期差

**C3 方法论与复用资产不在建模决策点。** 13 号 G1 判定「AI 创建给结果、没有任何一处教怎么建模」是最大缺口(13 号:37-39 实读:「学习本体最大的门槛不是工具而是建模思维」);五张方法论卡内容质量高但硬编码在 `LearnPage.tsx:66-107` 组件内,构建动线零内联。复用侧:`vocabSearch`(client.ts:797-799,REQ-171 LOV/REQ-261 OLS,502 优雅降级在档)本轮 grep 实证仅 `OntoExtendFlow.tsx:172` 与 `ReferenceMaterialsPanel.tsx:58` 两处消费,树上/画布/声明表单的命名输入零接线——同义概念重复定义(OOPS P02/P07 类问题)在发生当下无处拦截。冷启动完全依赖用户自带建模思维,而 docs/01:73 明文「**冷启动建模成本是本定位胜负手**——『扔文件进来→LLM 辅助半自动建本体+KB』接近零努力的体验为一等需求方向」,对应 Q-23 衍生④仍 🧊 挂池(docs/19:69,触发条件=「定位落地首批需求」)。

**C4 质量闭环断层与预期差(修订版——本条 evidence 已按评审意见核实改写)。** 原草案「CQ 覆盖自查只在 OntoChat 路径手动触发」**不成立,已修正**:资产详情「校验与质量」分区早已有「覆盖测试站(快筛+SPARQL 精判双轨)」卡(实读 `QualityCardPane.tsx:694-764`:开始快筛钮 :709-710、逐条 Yes/No/Unknown 三态徽标表 :745-764、双轨精判 runDualTrack :332-368、cq-test-report artifact 持久化+版本超前「报告过期」标记 :714-724),经 `AssetsPage.tsx:933` 渲染,对任意来路(custom/KB/导入)入库后的本体均可手动触发——REQ-342 OC-2 交付在案(02_构建.md:21「质量卡『覆盖测试站』双轨并轨+三级覆盖量化」)。**修正后的真实缺口是时点与粒度**:①覆盖自查只存在于两处「入库后」形态(OntoChat 会话 test 站手动按钮+资产详情测试站卡手动按钮),**入库前动线(custom 构建流 S3 校验步/导入应用后)与完成/发布时点零覆盖**——本轮实读 `AssetsPage.tsx:697-730` 发布 Popconfirm 为纯快照动作(命名 Input+onConfirm 直接 `publishOntology`,零检查);②现有 verdict 表只有「能力问题/快筛/精判/解释」列,**无条目级缺口清单与「去补概念/加同义词」直达动作**;③custom 路径 AI 精修只有「整稿生成→接受/整稿重生成」两态(实读 `CustomBuildFlow.tsx:766-779` onOptimize=按 Findings 整稿 doAiDraft 重生成),且 job_id 为局部 const(:360-373),240s 超时后「任务仍在后台执行」但结果取不回(:373)。叠加预期差:LLM 被刻意约束为「草稿生产者+人评审」(02_构建.md:21 REQ-269 行「LLM 生成路径不产出公理(防幻觉)」),界面从未管理这个预期;CQ4OE 在档实证(15 号 T1-11:类 F1≈60% vs 属性≈32%、Full CQ Coverage 仅 2.1%;81 号登记注:Water 域全局 F1 70.6% 但 FC=0%)说明「全局分高≠单条 CQ 完整」,综合分数无行动价值——「一次成型」预期必然落空,而产品默认叙事没有把「生成→快筛→按缺口补」设为正途。78 号判定「发布关=publish 前质量检查为空白点(报告级不阻断)」(docs/04:111 实读)。

## 三、三场景需求与差距

### 学习场景

**典型任务**(三场景分析材料):读完材料内化为 5~15 概念的小本体;先写 CQ 再建模、建完自查;跟随七阶段路径边学方法论边建;从散落笔记归纳概念骨架。

**核心诉求**:冷启动零门槛、边建边教、反馈即时且是人话、「学会了吗」可检验、迭代有手感、术语不吓人、完成感小而快。

**关键差距**(均本轮实证):①第一步撞裸 JSON,S2 空态零引导(对照 `SpecEditorPane.tsx:350-358` 已有「从第一个概念开始」Alert——同一空态两种处理深度);②方法论停在第五栏;③覆盖自查是手动按钮且 title 挂成本警告(`OntoChatFlow.tsx:892-895`);④任务卡打卡是 localStorage 记账不校验真实动作(`01_学习中心.md:36` P-6 观察项在案);⑤AI 草稿只有整稿两态;⑥平台方言直接暴露。

### 工作场景

**典型任务**:业务台账→可查询资产;领域文档→可审计知识底座;已交付本体的增量演化(生产最重场景,REQ-339);对齐权威词表;「验收-发布」交付仪式。

**核心诉求**:改得放心(影响面可见+可回滚)、复用优先、就地反馈、结构化操作为主 JSON 兜底、交付有答案、全程留痕。

**关键差距**:①构建动线内没有结构化建模面(C1);②建模当下零就地反馈,元素操作失败仅一行 toast 无撤销入口(C2;注:draft 快照栈撤销已随 REQ-425 ✅ M221 交付,docs/03:705,但树上操作失败场景未接入其入口);③AI 精修整稿两态(C4);④连线跨分区两次表单(`modals.tsx:111-127`);⑤词表联想零接线(C3);⑥发布零体检(纯快照,`AssetsPage.tsx:697-730`);⑦改动影响面沉在「演化与影响」分区需专门前往(`AssetsPage.tsx:115-116` 分区表)。批量能力(REQ-423 B5)维持触发驱动,本轮不展开(见 §6)。

### 研究场景

**典型任务**:文献驱动的领域本体;对接权威词表并登记 external_refs/同义词;CQ 驱动的严谨建模与可验证交付;长周期演化与溯源。

**核心诉求**:严谨可验证(条目级缺口而非分数)、可溯源可审计、可复用可引用、可复现(推理开/关对照)、发布有仪式感、说研究语言。

**关键差距**:①CQ 验证不在建模动线与完成时点(修正后口径,见 C4);②推理对照无编排 UI——`RuntimePage.tsx:1002` 文案让用户「同本体建两套方案一开一关」手工拼环境,REQ-379② ◐ 在案(docs/03:115「②双栏对照 UI 留专项」);③发布关空白(78 号);④版本仅 v{N}+时间戳无命名承载(`VersionDiff.tsx:169` 实读 `label: v${v.version} · ${v.created_at}`,而 publish API 已带 version_name,client.ts:803-806);⑤元素级「为什么这么建」无挂点;⑥工程方言暴露(同 C2)。

### P0(先缝合断缝)
