# 本体测试数据集与基准测试模块必要性分析（2026-10-16）

> 状态：v1.0（分析档，不改代码）｜ 动因：开发者指令「分析当前项目本体模块将来是否有必要增加一个测试数据集模块用来管理用于评测本体的测试数据集，还要一个做 benchmark 测试的模块和能力」
> 关联：[81 号 CQ4OE](../项目深度调研/81_CQ4OE深度调研_CQ2Term与CQ2Onto原理与借鉴_20261016.md)、[83 号演进分析](83_OntoChat与OntoExtend路径演进分析_20261016.md)、[84 号 64 号蓝图评审](84_OntoExtend蓝图落地成熟度评审_20261016.md)、03 号 REQ-207/255/257/274/331/342/343/344、79 号产品定位

## 一、结论

**有必要，且缺口真实——但形态上不建议新起两个独立大模块。**

- 「测试数据集管理」是**当前本体评测链的最大瓶颈**：执行器与测试能力均已交付，唯独数据集缺位（CQ 基准集为 0），四处诚实遗留都指向它。真实增量 = **测试资产的统一落库与版本化**。
- 「benchmark 测试能力」的**骨架已经存在**（ontoeval build tag 基准 + REQ-255/274 产品内测试 + REQ-207 进化门控 + agenteval 完整执行器先例），且其核心演进（覆盖回归基准化、移除法+三维评估）**已被 REQ-342 OC-2 与 REQ-344 立项覆盖**。真实增量 = **基准执行从离线手动走向产品化动线与结果可比**。
- 建议按三档推进（§五），第一档并入已立项 REQ 领取批零新模块；第二档待 REQ-344 交付后评估是否占新号；明确不建议现在建数据集大 CRUD 模块。

## 三、缺口分析（对照两问）

### 3.1 「测试数据集管理」——真缺口，四处实锤

1. **REQ-255 诚实遗留**：「种子 spec 无 CQ 数据，ontoeval CQ 信号自动 N/A 留观察——待种子带 CQ 基准集」
2. **REQ-274 诚实遗留**：「P9 评估集（28 正 28 负 CQ）未落库，开源数据集本机不可达」
3. **REQ-333（NL2SPARQL，M133 📋）**：领取时需要 CQ→SPARQL 评测集才能验证生成质量，当前无集可测
4. **REQ-344/REQ-343**：移除法评估（OE-3）需要 39 CQ 式构造集，三段式 RAG 增益证明同样依赖

数据集现状是「散落且不成体系」：CQ 散在各本体 spec.cq、本体集内嵌在 build tag 测试文件、评估集只存在于调研档引用——**无统一存放、无版本、无来源与适用域标注、无与基准执行器的声明式关联**。81 号借鉴项 6 已前瞻指出：「Gold standard 构建方法论（四阶段标注+三人审核+E/I/R 分类）→ 评估数据集建设，为 REQ-331 提供 ground truth（P2）」。

### 3.2 「benchmark 测试能力」——骨架已有，缺两样

- **结果不可比**：ontoeval/质量卡每次独立出分，无版本对比（变更前后）、无渠道对比趋势（REQ-257 只有单次分组表）、无基准历史。生产化定位（79 号「教学 demo→生产工程化产品」+D-O22）下，回归护栏必须可比才有意义。
- **场景未覆盖全**：CQ 回归自动化（REQ-342 OC-2 承载中）、生成质量基准（REQ-344 承载中）、外部标准基准跑分（OAEI/CQ4OE，依赖 REQ-79/REQ-344）均未落地——但这些**已在立项管线内**，不是从零开始。

## 五、建议方案（三档，均不新起独立大模块）

### 第一档（P2，并入 REQ-342/REQ-344 领取批，零新模块）：CQ 基准集落库

- **目录化数据集**：沿 kb evaldata 先例建 `seeds/evaldata/ontology-cq/*.json`（数据集元信息+来源标注+适用域+gold SPARQL 判定集+rubric），版本随 git
- **给种子本体补 CQ**：Wine/AWO 等教学本体按 81 号借鉴项 6 方法论标注 CQ→term/axiom 映射（轻量版：教学本体规模小，二人标注+交叉复核即可，不必照搬三人审核全流程）
- **解除两处诚实遗留**：ontoeval CQ 信号从 N/A 变实——REQ-255/274 的「待 CQ 基准集」收口；REQ-333/344/343 领取时即有集可测

### 第二档（P3，REQ-344 交付后评估，可能占新号）：测试资产产品化

- **数据集管理面**：数据集清单（名称/版本/来源/适用域/规模）+资产详情「用基准集测我」动线（选数据集→跑覆盖/精判/门禁→出报告）；数据集 CRUD 轻量实现（JSON 导入+登记，不做多人协作编辑器）
- **基准报告可比化**：渠道对比（REQ-257 扩展为历史趋势）/版本对比（变更前后同数据集跑分对照）/与上次基准的 diff——进消费侧观测台（D-O19/D-O25 统一检索面）或质量卡扩展
- **Judge 基建复用**：agenteval judge.go 已预留本体侧复用注（ParseJudgeOutput+rubric 骨架），口语化判定/生成质量评分共享一套基建，不重写

### 第三档（触发驱动）：外部标准基准引入

- CQ4OE 数据集下载适配（HF/Zenodo→本地 JSON 化）进第二档数据集清单；OAEI 型对齐基准随 REQ-79 对齐能力立项后评估
- 触发条件：出现对外发布/论文级评估/与业界对比的真实诉求

### 明确不建议

- **独立「测试数据集管理模块」大 CRUD**：当前规模 10 份本体+数个 CQ 集，文件+目录+build tag 足够；多人协作数据集编辑、跨团队共享等诉求在本项目无场景。等产品出现真实多团队数据集共享诉求再升格，避免过度建设。
- **独立「benchmark 平台」**：执行器已分散就位（ontoeval/agenteval/质量卡/门控），收敛消费入口即可，不需要新建统一执行框架——那会与 REQ-207 门控、REQ-340 buildflow 形成第三套并行体系，违反管线收敛方向。
