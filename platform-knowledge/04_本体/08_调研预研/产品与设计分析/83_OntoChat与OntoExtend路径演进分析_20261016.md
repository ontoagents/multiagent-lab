| **OC-1** | **CQ 净化双算子落地** | 拆非原子问题+命名实体抽象（N1，06 号 §6）——63 号 §2.3 `functions.py` 注释代码可直接翻译；落到 REQ-272 CQ 抽取迭代 | **P1** | 复合 CQ 拆分率+专名抽象率人工核验（63 号 P9 的 56 条 CQ 集小样本）；中文语料有效性实证（63 号 §6.3 待验证项） |

### 2.3 演进中的价值跃迁

OC-2 完成后，CQ 从「构建产物」升级为「**回归基准**」：每次本体变更后自动跑 CQ 验证（OO `onto_cq_run` 同款范式，06 号 §2.3），检测漂移——这是 OntoChat 对**运行期**的间接贡献，也是两路径协同的枢纽（见 §4）。

### 2.4 诚实边界（沿 63 号 §6，不可回避）

1. 论文 87.5% 测试准确率是 56 条 CQ 二分类初步口径，**不宜当强基准**，只作方法示范；
2. 口语化判定对「可推断但不显式」的需求有**系统性乐观偏误**（3FP/4FN 实证）——快筛+精判双轨是必须的，不能只做口语化；
3. CQ 抽取幻觉/范围漂移未解（论文 2/8 范围外实体）——OC-1 净化算子缓解但不根治；
4. 中文语料下两算子与聚类标签有效性均待实证（63 号 §6.3）——OC-1/OC-3 验收必须含中文小样本。

## 3. OntoExtend 路径演进（对照 64 号 §4 蓝图）

### 3.1 核心判断

现路径（ODP+LOV）解决的是「**给本体补标准模式与词表**」；论文三段式解决的是「**按新需求（CQ）扩展已有本体的任意结构**」。二者互补而非替代——**演进主线是把论文三段式作为新能力落地，与现有 ODP/LOV 并列成双模式**（64 号 §4.4 明确：以新能力承载，**不复用现有 OntoExtend 路径 API 名**，避免语义混淆）。

### 3.2 演进项（OE-1~OE-5）

| # | 演进项 | 内容与依据 | 优先级 | 验收口径 |
| --- | --- | --- | --- | --- |
| **OE-1** | **论文三段式 RAG 扩展落地**（64 号 §4 蓝图 S1~S3） | ① 元素抽取器+检索器：spec→OntologyElement→管道符序列化→embedding→top-k（N2 检索口径直接采用 ada-002+pipe+comments M_w=0.63，无需重做对照实验；N4 序列化等价性先验证）；② 片段生成+两阶段校验：N3 prompt 双 profile+12 ImportantNotes+pitfalls 直接翻译进 Go prompt 库，复用 `/api/ontology-llm/generate` 异步 job+llmcreate 修复环；③ 集成器：去重→REQ-157 merge/preview→apply（版本快照） | **P2（核心）** | 39 CQ 式构造集上 CQ 验证覆盖+冗余 <2% 复现（中文语料对照 64 号 §5.3）；检索片段只读上下文不变式；校验失败必重试或标记不静默入库 |
| **OE-2** | **双模式演化动线** | REQ-339 已交付的演化入口下挂两模式：ODP 模式扩展（现）/ CQ 驱动 RAG 扩展（OE-1 新）；页面化（REQ-337）承载模式选择 | P2 | 演化路径页两模式可切换；新片段经 merge 审查入库 |

| **OE-5** | **CQ 质量预检** | N9：LLM 行为作质量代理信号——扩展前预检 CQ 质量（工业 CQ Correctness 4.91 vs EU 开放 CQ 3.66 的核心教训：**框架不能补救坏需求**）；开放/欠定义 CQ 给出预警 | P3 | 预检信号与人工判定相关度 |

### 3.3 诚实边界（沿 64 号 §5）

1. 两域小样本（Onto-DESIDE+Bosch）泛化未证；Bosch 19 CQ 不可复现；
2. 「CQ 验证 100%」系工程师写 SPARQL 判定非自动指标，含构造偏置；
3. 数据泄漏未排除（EU 本体公开）；仓库无 LICENSE——**只借鉴算法/prompt/口径，零代码引入**；
4. 中文 CQ+中文本体元素的召回质量待实证（64 号 §5.3）——OE-1 验收必须含中文对照。

## 4. 两路径协同：CQ 枢纽闭环

```
OntoChat（前段）                    OntoExtend（后段）
用户故事 ─→ CQ 净化抽取 ─→ spec.cq ─→ CQ 驱动 RAG 扩展（OE-1）
                │                │              │
                │           REQ-248 一等公民     ▼
                │                │        片段+两阶段校验
                ▼                ▼              ▼
          引导卡迭代        REQ-255 验收 ←── 覆盖测试/回归（OC-2）
                                  ↑
                        本体变更后自动跑 CQ 验证（漂移检测）
```

- **CQ 是两条路径的数据枢纽**：OntoChat 产出 CQ（spec.cq）→ OntoExtend 消费 CQ 驱动扩展 → REQ-255/OC-2 把 CQ 变成回归基准——这正是 06 号核心结论「方法间衔接动线」的落地形态；
- **REQ-340 六段管线编排是共同底座**：OntoChat draft 生成与 OntoExtend 片段生成同为「草稿→门禁→审查→入库」的参数化实例，两路径演进**不得绕开管线另建旁路**；
- **与 OO 借鉴横向衔接**：N5 四象限诊断（REQ-328 对账升级）、N7 判词纪律（所有报告型接口）、N10 反馈自校准（qualitygate 迭代）随两路径深化一并吸收。
