## 0. 结论速览

**判定：可行，且底座完备度为同类想法历史最高。** 三大底座全部就绪——①OntoChat 引擎已在构建平面完整自研交付（六阶段状态机+全套 REST+快照链+入库门禁，[docs/03](../../../../../docs/03_本体_需求文档.md) §2.30~§2.45）；②智能体工具机制现成（`Agent.Tools` 挂载 + `tool.Registry` 组装 + 内置工具组先例）；③导出回流链路已有先例（quality gate 门禁入库 + 伴生 TTL 导出）。

**真正缺的只有「最后一公里」**：智能体侧没有一组能把构建平面 `/api/ontochat/*` REST 包装成对话工具的胶水件（G1），以及指定智能体的能力配置与访谈引导模板（G2）、对话→构建页面的跨动线（G3，P2）、会话归属审计（G4，可选 P2）。

**新建面（硬指标 ≤3，实际 1+1 可选）**：
- 🆕 `backend/internal/tool/` 新增 OntoChat 工具组（1 个文件、3 个工具：start/turn/save），包装构建平面既有 REST——核心新建；
- 🆕 智能体 Instruction 引导段模板（纯文档形态，附录 A，零代码）；
- 🆕（可选 P2）构建平面 ontochat 会话表 ALTER 加 2 列（source/agent_id）审计映射。

**建议立项**：REQ-354「OntoChat 能力赋予智能体——对话式本体构建工具组与导出回流闭环」，P1 最小闭环 API 先行、无前端依赖；P2 跨动线价值兑现；P3 演进项验证后拍板。

**定位声明（防重复建设）**：本方案是 REQ-103 **模式 A（OntoChat 主动访谈式构建）的智能体化**，与已交付的 REQ-170 **模式 B（伴生本体被动旁路沉淀）** 互补不重复——伴生管「聊着聊着长出薄本体」，本方案管「专项访谈式结构化构建」（边界详表见 §5.5）。

## 2. 源资料摘要卡（S1）

### 2.1 KCL 版 OntoChat（本引擎的蓝本，已内化）

- **核心命题**：本体工程（OE）中多方交互造成系统性歧义与偏差，用对话式智能体承载需求工程四步（用户故事共创→CQ 抽取→CQ 过滤聚类→本体测试），可加速传统 OE 任务（[arXiv 2403.05921](https://arxiv.org/abs/2403.05921) §3；设计依据为 N=23 从业者调查：需求收集 86.4%、CQ 抽取 81.8%、需求分析 77.3%、本体测试 81.8% 被认为最需要计算支持）。
- **量化证据**（初步评估口径，作者自述 preliminary）：CQ 支持判定准确率 87.5%（P=88%/R=85.7%，56 条含 28 条人工构造负例，§4.2）；聚类 87.5% 有效分组、62.5% 认为交互直观；80%+ 用户满意用户故事生成，**仅 50% 满意数据示例生成**。
- **四模块算法与自研蓝图**：详见 [63 号](../项目深度调研/63_OntoChat深度调研_论文原理与开源实现_20261008.md) §3~§5；本项目已照论文算法自研内化（D-O23：不引入 Python/Gradio 栈），交付 REQ-271~275/306/308/312/337~340/342（六阶段状态机 story→cq→domain→draft→refine→done、双净化算子、覆盖测试站、质量报告环、引导卡 10 模板 25 追问）。
- **风险与诚实边界**：63 号 §6.2 八条（样本量小、测试准确率为二分类口径、口语化依赖注释质量、聚类无确定性保证、CQ 幻觉/范围漂移未解、temperature=0+seed 跨模型不可复现等）——本方案 §8 逐条映射对策。

### 2.2 zjunlp 版 OntoChat（ISWC 2024 demo，形态参照）

**未做一手核验**（GitHub README 被 robots.txt 拦截、独立论文号未确认；本轮仅获二手定位信息），故不登记入 [docs/15](../../../../../docs/15_开源项目及论文登记簿.md)，仅作形态参照使用，其可信信息为：以**多智能体流水线**（需求分析/术语提取/模式挖掘/评估四 agent 串联）实现对话式 OE、导出 Turtle/OWL。

**对本想法的价值**：它是「把 OE 流程做成智能体」的公开先例，形态与本方案同构——**引擎放服务侧、智能体只做对话壳与编排**。但注意其拆分四个专职 agent 的原因是单对话引擎能力弱；本项目引擎已在构建平面完整内化（算法、prompt、状态机、门禁均在），无需复制其多 agent 拆分（→ §5.1 选档论证，多 agent 拆分归 P3 观察）。

### 2.3 参与式提示演进（[arXiv 2408.15256](https://arxiv.org/abs/2408.15256)，AAAI-SS 2024）

- KCL 后续用户研究：纯自由对话访谈质量不稳，经研究者中介沉淀出 **10 预定义模板+25 追问**（persona/goal/scenario/sample data/data resources 五维），各项满意度 ≥4/5。
- 本项目已内化为引导卡机制（REQ-306，`story-templates` 端点）。
- **对本方案的两条直接启示**：①智能体对话中的访谈**不能靠裸 instruction 自由发挥**，必须显式引用引导卡与阶段纪律（§5.4 引导模板的依据）；②论文自认「模板机制可能抑制用户自由表达」——智能体 instruction 需允许用户随时跳出模板自由聊。

### 2.4 对三个子命题的直接回答（S1 结论）

1. **对话能承载六阶段工作流吗？** 能——OntoChat 的六阶段本质是「LLM 多轮对话+结构化后处理」，智能体对话天然是承载访谈的更自然界面；页面流程的表单/Steps 是对无对话引擎时代的补偿，对话侧反而更贴论文原意（「by interacting with a conversational agent」）。
2. **引擎可工具化封装吗？** 可——构建平面已提供全套无 UI 依赖的 REST（含 202+job 异步与轮询，REQ-271 设计即面向程序化调用）。
3. **闭环有先例吗？** 有——save 端点入库即过 REQ-267 quality gate；伴生侧 export-ttl（REQ-285④）证明「对话产物→TTL→资产」链路成立。

## 5. 方案设计（S4）

### 5.1 选档论证：标准档

三档对照（沿 63 号/83 号分档习惯）：

| 档 | 内容 | 前提 | 判定 |
| --- | --- | --- | --- |
| 轻量档 | 仅工具组（G1），挂载后靠智能体自由发挥 | 引擎+机制 ✅ | **不选**：访谈纪律无承载，质量不稳（§2.3：纯自由对话是论文证伪过的路径）；「指定智能体」缺产品身份 |
| **标准档（选）** | 轻量档 + Instruction 引导段模板（G2）+ P2 跨动线（G3） | 同上 | **对位**：与 D-O23 自研内化路线一致；低侵入三原则全过；P1 无前端依赖 |
| 重型档 | zjunlp 式多 agent 拆分（需求分析/术语提取/模式挖掘/评估四专职 agent+委派编排） | delegatetool ✅ | **不选（归 P3）**：引擎算法已在构建平面内化，拆多 agent 徒增 token/延迟/状态同步复杂度；zjunlp 拆分是对其单对话引擎弱的补偿，我们没有这个前提 |

### 5.2 低侵入三原则核对（可逐条验证）

| 原则 | 核对项 |
| --- | --- |
| ①旁路 | 工具组只发起对构建平面既有 REST 的调用，不进智能体 runner 主链路（不改 `chat/runner.go`/`assembler.go`）；不改 OntoChat 引擎任何行为；页面流程与智能体流程互不依赖 |
| ②默认关 | 工具组注册进 Registry 但**不进任何内置 agent 默认工具集**（沿 assistant 内置工具白名单惯例）；仅当用户在智能体配置 `Tools` 里显式勾选 `ontochat_*` 才生效；构建平面零行为变化 |
| ③可摘除 | 产物全部落在构建平面既有存储（ontochat 会话表+资产库，本来就独立于智能体侧）；摘除=智能体配置移除勾选+删 1 个工具文件，存量资产与会话零回归；P2 审计列为纯增列不动旧行 |

### 5.3 P1 工具组设计（🆕 核心新建，1 文件 3 工具）

落点 `backend/internal/tool/ontochat.go`（命名沿包内惯例），编译期 `Register` 进 Registry：

| 工具 | 入参 | 行为 | 返回 |
| --- | --- | --- | --- |
| `ontochat_start` | `topic`（领域主题，必填）；`mode`（story\|cq，默认 story） | `POST /api/ontochat/sessions`；story 模式顺取 `story-templates` 首卡 | `session_id` + 当前阶段 + 引导卡内容（供智能体直接转述开场） |
| `ontochat_turn` | `session_id`；`message`（用户本轮发言）；`action`（chat\|analyze\|test，默认 chat） | `POST .../turn`（202+job）；工具内部轮询 job 至 done（上限同 `ONTOCHAT_LLM_TIMEOUT` 300s）；analyze/test 走对应动作端点 | 阶段状态 + 助手消息 + 结构化产物（CQ 候选列表/story 文本/draft spec_json 摘要 + 质量报告卡三维分） |
| `ontochat_save` | `session_id`；`confirm_note`（用户确认说明，必填） | `POST .../save`（入 REQ-267 quality gate） | 成功：`asset_id` + 质量报告 + 入库摘要；失败：门禁明细逐条返回（不静默） |

实现要点：
- HTTP 客户端复用 backend 反代同源（REQ-103 模式 A 部署形态），错误口径沿 REQ-267 degraded 惯例：构建平面不可达时返回结构化提示（「构建平面暂不可达，请稍后重试或前往构建页面操作」），不伪造结果；
- 202+job 轮询封在工具内部，智能体与用户感知为一次同步调用（超时上限 300s，超时返回 job id 供续查）；
- `ontochat_save` 的工具描述（tool description）中写明**确认纪律**：调用前必须已向用户展示质量报告摘要与入库内容清单并获确认——配合 `Agent.ToolApproval`（all 档）形成双保险（§8 R2）；
- 不新增任何表；会话与产物状态全部由构建平面既有存储承载。

### 5.4 指定智能体配置（零新字段 + 附录 A 模板）

- **配置**：智能体编辑页 `Tools` 勾选 `ontochat_start/turn/save` 三件；Instruction 粘贴附录 A 引导段（或由管理员预置常用智能体模板）。
- **引导段职责**（依据 §2.3 参与式提示结论）：声明六阶段工作流与一次一问纪律；声明 CQ 候选必须列号呈现待确认；声明 save 前必须展示质量报告摘要+入库清单+征得确认；允许用户随时跳出模板自由表达（防模板抑制表达）。
- **项目下对话场景**：同一智能体在项目协作空间的会话中同样生效——工具与宿主无关，无额外工作（§1 已述）。

### 5.5 与伴生本体（模式 B）的边界声明

| 维度 | 本方案（模式 A 智能体化） | 伴生本体（REQ-170，模式 B） |
| --- | --- | --- |
| 触发方式 | 主动：用户发起专项本体构建任务 | 被动：对话过程中旁路自动抽取 |
| 产物形态 | 结构化 spec_json 本体（含 CQ/用户故事/质量报告） | 薄本体三元组候选（concept/relation/event） |
| 质量保障 | REQ-267 门禁+REQ-312 报告环+覆盖测试（REQ-342） | 人工逐条确认（pending→confirmed） |
| 入库路径 | save 直入资产库 | 会话图→export-ttl→导入 |
| 适用场景 | 「帮我建一个 XX 领域的本体」专项任务 | 日常聊天中顺带沉淀领域词汇 |

二者**互补不重复**：伴生适合长对话低打扰沉淀，本方案适合确定性交付；同一智能体可同时挂载（工具组与伴生绑定互不干扰，数据面隔离）。此声明随 REQ-354 写入 03 详设，防后续定位漂移。

### 5.6 数据模型最小化

- **P1 零新表零新列**：会话/快照/资产全部复用构建平面既有表；智能体侧不留任何状态（无状态胶水）。
- 溯源天然成立：对话消息本身留痕（session_id、asset_id、质量分都在消息流里），REQ-338 快照链保证草稿版本可回溯。
- P2 可选（G4）：构建平面 ontochat 会话表 ALTER 加 `source`（page\|agent_chat）、`agent_id` 两列——纯增列，旧行默认 page，满足审计与后续统计（哪个智能体产了多少本体）。
