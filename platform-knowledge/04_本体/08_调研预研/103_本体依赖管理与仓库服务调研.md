## 一、结论摘要（五问五答）

1. **本项目如何支持「本体引用本体」？** 形态是「**旁挂登记表 + 导出桥 + 运行面闭包**」：spec_json 资产模型**零跨本体引用能力**（写了即校验报错），跨本体语义唯一载体是 `external_refs` 旁挂表（import/alignment/reuse 三形态，D-O27 收敛单源），语义仅在 TTL 导出层物化（skos 映射 + owl:imports + rdfs:seeAlso），闭包展开只在运行面装载期（构建面全程不解析引用）。已交付闭环仅限**仓内引用**；远端拉取与联邦查询是 D-O27 拍板不做项。
2. **agent 如何使用有依赖的本体？**（动线系**机制推演**，仓内依赖尚无真实使用实例佐证——§4 开头诚实标注）内部自建：会话挂**一个**运行方案 → 方案多本体声明 + 装载期闭包补全 → union 查询 + 逐命中来源标注 + 装载期推理物化（仅 oxigraph）——**单方案组内语义完备，跨方案/会话级组合无通道**。外部公开本体：只能**整包导入为副本**或**登记外部 IRI**（定义在装载与查询期均不可见）——agent 对外部本体实际上只能「抄」不能「引」。
3. **是否值得开发镜像仓库式本体仓库服务？** **独立 registry 进程形态：不值得**（单机单用户无分发对象、仓库语义已被 D-O1 判给 ontology-service、OpenOntologies 退役护栏与 90 号 E4 触发前提双在、Ontohub 反面教训=仓库引擎不应比资产重）。**但「仓库能力面」中的真实缺口——引用版本 pin、发布快照、构建期依赖预览——值得以仓内功能形态分三步做**（§6.5）。
4. **业界怎么做的？** 标准线：OWL 2 imports 闭包（拉取式依赖 + 允许重定向本地副本=单机的标准依据）、版本 IRI 双标识 + OBO FP-004 发布冻结、RDF 命名图分区（非联邦）；平台线：BioPortal submission 版本 + diff、OLS 配置驱动最新版单点、OBO Foundry「git+CI+PURL」无服务器仓库语义（单机最强先例）；类比线：Schema Registry 注册即兼容门禁、npm/Cargo 声明+锁定两层、Helm 一个索引文件+静态工件的下限设计（§5）。
5. **推荐？** **方案 B「仓内依赖管理最小闭环」**：不做新服务，在 ontology-service 内补 external_refs 版本 pin + 发布不可变快照 + 构建期闭包只读预览三件；步骤一（版本 pin+发布快照）因痛点实锤可即领号，步骤二/三按判据触发驱动（§7.5）；备选中「维持现状」（A）漏掉已实锤的漂移风险，「独立 registry」（C）与「接入外部仓库平台」（D）违背定位，「联邦查询」（E）已被 D-O27 拍板排除（§7）。

## 二、问题定义与三个易混概念

「本体依赖管理」的讨论常把三件事混在一起，先拆开：

| 概念 | 含义 | 本项目现状 |
| --- | --- | --- |
| **引用（reference）** | 本体 A 的建模过程中指向本体 B 的概念/实体（对齐、复用、导入声明） | ✅ 已有：external_refs 三形态 + 导出桥 + 运行面闭包（D-O27/REQ-262/479~482） |
| **依赖版本管理（dependency versioning）** | 引用是否钉住被引方的具体版本；被引方演进后引用方是否感知、能否回滚 | ❌ 缺失：external_refs 无版本列，引用恒指头版本，漂移无兼容性感知 |
| **分发/仓库（distribution/registry）** | 资产的发布、发现、拉取基础设施（push/pull 协议、目录、镜像） | ❌ 无此面：唯一外部本体服务形态 OpenOntologies 已退役（REQ-100 ⛔）；D-O1 把「仓库」语义判给了 ontology-service 本身 |

问题③的「镜像仓库式本体仓库服务」属于第三层；但开发者真实痛点（§6.1 盘点）大概率落在第二层。这个区分是本档推荐结论的基础。

## 三、问题①：本项目对「本体间引用关系」的全链路支持现状（逐面 + 缺口）

### 3.1 构建面

**现状：旁挂登记表 + 导出桥，spec 资产模型零跨本体引用能力。**

- **spec_json 模型内没有任何跨本体引用字段**：`Spec` 只含 id/name/description/cq/concepts/relations/data_properties/axioms/instances（`pkg/ontology/spec/spec.go:128-140`，本轮实读核实）；Concept.Parents、Relation.From/To、Restriction.Property/Target 全部是**本体内裸名**；`Validate()` 只认本 spec concepts 名册，在他体概念名写进 parents/from/to/restriction.target 会直接报「定义域/值域引用了未定义概念」（`spec.go:155-167` 校验、`:220-225` 报错；上游勘察实跑临时测试确认三类写入均报错）。
- **跨本体引用唯一载体是旁挂登记表 external_refs**（REQ-262/M256，D-O27 三形态收敛单源）：`ontology-service/migrations/049_external_refs.sql:5-19`（本轮实读：12 列，**无版本列**）、ref_kind CHECK 约束限定 import/alignment/reuse（`:11`，v1.1 `grep -n CHECK` 裁决；初稿误写 :13）、alignment 用 SSSOM 词表五谓词（exactMatch 等，`internal/repo/external_refs.go:40-42`）、from_concept/to_concept 为裸名字引用（迁移注释明言「名字引用不 IRI 化」，`:4`）、to_onto_id 留空=外部词表/未导入资产的 IRI 登记态、本体级引用用哨兵源概念 `"(ontology)"`（`external_refs.go:38`）。REST 三端点在 `ontology-service/internal/rest/rest.go:112-114`。
- **跨本体语义只物化在导出层**（REQ-479/M279「桥长在导出层」）：TTL 导出读 external_refs——alignment 物化 `skos:*Match` 三元组、import/reuse 产出 owl:imports 头语句 + rdfs:seeAlso 概念段；被引方 IRI 按 `urn:o:{toOntoID}:concept:{name}` 构造，与对方自身导出同构造=union join 键（`ttlexport.go:141-196` planBridges/basePrefixOf，本轮实读核实；注释 `:337-338` 明言 join 键前提）。spec_json 模型零改动。实体 IRI 四形态 `urn:o:{ontoID}:concept|relation|instance|attr:{name}`（`ttlexport.go:200-203`），IRI 由名派生、同名即同 IRI（`merge.go:31` 原文）。
- **无版本化依赖机制**：external_refs 无版本列，引用经 GetArtifact 解析到**头版本**（`internal/repo/repo.go:266`）；本体自身有 ontology_version 快照版本史（BumpVersion/SaveVersion/RestoreVersion/Publish，`repo.go:329/448/426/391`；002_version.sql）但**与依赖完全解耦**。漂移防护仅有悬空检测两类：missing_ontology/missing_concept（`external_refs.go:132-168`）。
- **D-O27 拍板边界**（docs/03 §5 `:935`，本轮实读核实原文）：三形态收敛 external_refs 单源；**边界三分=远端闭包不做、仓内闭包（to_onto_id 非空、引用对象在本仓）装载期展开（REQ-480 兑现）、联邦查询不做**；身份统一双轨=import·reuse 被引方 IRI 原样出现 / alignment 物化 skos 映射。构建面 merge/校验/质量门禁全程不解析引用（qualitygate 包 grep external_refs 零命中；v2.10 交付注明言「不进 qualitygate.Check 纯函数」）。
- **KG 存储层无跨本体实体身份**：自研 KG 三表（kg_entity/kg_relationship/kg_claim）在 backend 主库按 kb_id 共表组织、无本体维度列；实体 uid=kb_id::name（`backend/internal/store/kg.go:67-71`，本轮实读）；一 KB 单本体绑定（knowledge_base.kg_ontology_id 单值，`backend/internal/store/knowledge.go:31/210-212`）；本体→KG 单向只读投影（I3，`backend/internal/kg/pipeline.go:7`），经 FetchSpecVocab 把 spec 词表注入抽取 prompt 白名单（`backend/internal/ontology/ontology.go:131-132`）。跨本体实体引用/对齐结果在 KG 存储层无承载。
- **LLM 辅助创建零跨本体上下文**（v1.1 补实读升级实证）：草稿 prompt 单源=领域描述+spec JSON Schema+可选种子范例，零仓内本体清单或可复用词表提示（`ontology-service/internal/llmcreate/llmcreate.go:27-33` SpecRolePrompt「请根据领域描述生成一个本体 spec_json」/FewShotHeaderPrompt/ClarifyPrompt）；扩展器仅带单目标本体复用指令（`internal/ontorag/extender.go:46`「请尽可能复用已提供目标本体中的元素」）；LOV/OLS 词表搜索为代理薄层——进程内缓存不落表（`internal/vocabsearch/vocabsearch.go:1-6/19-27`，REQ-171 底座+REQ-261/M259 OLS 第二通道），消费 REST 层无 external_refs 登记（v1.1 grep：external_refs 登记面=repo/external_refs.go+rest 资产面三文件+importer 三文件，`rest_consumption.go` 零命中）；选中术语入 spec 后与本地同名合并的具体行为未逐行复核（推断，沿上游勘察）。

**构建面缺口**（缺口 1~2/4 沿上游勘察事实清单实证；缺口 3 含 v1.1 修正；缺口 5 经 v1.1 补实读升级为实证，「同名合并」子行为仍系推断）：

1. spec 内无法直接引用他体概念——跨本体引用不进 spec 合并、质量门禁与图编辑器模型，只存在于旁挂表（编辑器可见性弱）。
2. 引用无版本 pin：被引本体演进后引用方无兼容性感知；悬空检测只覆盖「本体删除/概念不存在」两类，不覆盖语义漂移。
3. 构建面闭包不做：merge/preview、qualitygate 主链、导出阶段均不解析仓内引用，无法在**构建时**预览「解析后完整 schema」或**全量**跨本体依赖闭包图（闭包展开只在运行面）。**v1.1 修正**：REQ-278「变更影响分析」已于 M105 交付构建平面「影响报告」卡（两版本 spec 结构 diff+引用闭包波及面+风险分级「删除被引用概念=high」，诚实边界 v1=结构级波及面非语义级；docs/18A `:121`）——本缺口修正为「REQ-278 已覆盖版本 diff+引用波及面；**剩余缺口=全量依赖闭包图可视化+解析后 schema 预览+循环引用专项报告**」。
4. KG 层无跨本体实体身份机制：跨本体查询靠运行面 named graph union 而非 KG。
5. LLM 辅助创建/扩展无法建议复用或对齐既有本体（llmcreate.go:27-33 零仓内清单实证）；外部术语并入留不下来源（vocabsearch 不落表、消费链不自动登记 external_refs）。

> **一处表述勘误（上游勘察 partial 裁决，正文以此为准）**：旧口径「悬空检测只提醒不阻断」**已过时**——阻断在**运行面装载门禁**（REQ-480②，`closure.go:106-110`，docs/03 `:821`），提醒在**资产页质量门禁**（`external_refs.go:132-134`）；`external_refs.go:4/:132` 注释仍写「qualitygate 消费」属注释滞后。

### 3.2 运行面

**现状：从物理并排演进到单方案组内语义完备（REQ-480~482 批已收口）。**

**运行面缺口**（上游勘察逐条实证）：

1. **联邦查询完全不存在**（D-O27 维持不做）：跨运行方案、跨引擎端点间无任何查询通道——语义完备仅限单方案组内。
2. **两引擎推理能力不对等**：REQ-481 物化仅 oxigraph regular 启用；fuseki 无物化路径且其查询期推理与 per-graph 装载（逐本体独立命名图装载模式，与整库单图相对）结构性互斥——fuseki 多本体方案拿不到跨本体推断。
3. **闭包补全本体双缺**：经 imports/external_refs 自动装入、不在方案声明清单的本体，不可按自身 id 经 RunningByOntology 路由，也不进 lifecycle 版本漂移对比。
4. **更新无自动感知**：全靠面板 lifecycle plan 提示+人工 reload/apply；「更新后运行面自动换新版」无实现。
5. **版本概念薄弱**：仅 spec 版本 int 快照+generation 串；无语义化版本、无版本 pin/锁定、无「方案绑定不可变资产快照」——重载恒漂移到最新版，**无法回滚到历史版本装载**。
6. 推断图为方案级合并图，跨本体推断不可按来源本体归因；物化每次启动全量重算（owlrl N²~N³ 膨胀风险在案观察，docs/03 v2.43 注）；raw 图计数硬闸不覆盖推断图正确性。

### 3.3 消费面

**现状：运行平面强、平台消费链弱的分层格局。**

## 四、问题②：agent 如何使用相互之间有依赖的本体

> **诚实标注（v1.1，评审意见采纳）**：本节动线系**机制链路推演**——基于 §3 已核实机制与代码路径推演 agent 的使用方式，**非真实使用取证**；仓内依赖与外部本体两条路径目前均无真实会话实例佐证（使用证据全零，见 §3.4/§6.1 所引 90 号 §6 度量）。真实动线待使用证据积累后回填修订。

### 4.1 内部自建本体（仓内依赖）——agent 的机制动线（推演）

以「本体 A 引用本体 B（import 登记）」为例，agent 视角的端到端动线：

1. **构建态**（人/LLM 在构建平面）：A 在资产页「关联本体」登记 external_refs（REST 三端点 `rest.go:112-114`）；A 的 spec_json 本身不写 B 的概念名（写了校验报错，§3.1）。
2. **部署态**：开发者把 A（或 A+B）配进某运行方案的 ontology_ids；**若只配 A，装载期闭包自动补全 B**（BFS 沿登记边，`closure.go:83-140`）；B 缺失/悬空则**阻断启动**，错误文案为人话且含修复指引（v1.1 实读 `closure.go:107-109`：「装载门禁阻断（REQ-480② 悬空引用）……悬空引用须先修复或摘除（资产页『关联本体』）」）。
3. **语义态**（仅 oxigraph regular）：A+B 全集并置跑 OWL 2 RL 物化，跨本体推断（如 A 实例经 A 概念 ⊑ B 概念〔⊑=子类关系符〕的分类）落 urn:inferred:assembly 合并推断图（REQ-481）。
4. **查询态**（agent 工具面）：agent 在会话中（挂该方案）经 facade onto_* 工具消费——get_concept/get_instance/list_instances/neighbors 按 label **跨方案内全部本体匹配**并标注来源本体；sparql_query 默认图=全部 raw 图（+推断图）union，可跨本体 join（IRI 同构 `urn:o:{oid}:concept:{name}` 为 join 键、alignment 的 skos 映射为桥），结果携 scope 块告知本体清单与 GRAPH 限定线索（REQ-482）。
5. **消费审计态**：答案 cited 归因到本体级命中行（REQ-530，target 名粒度）。
6. **运维态**：B 发布新版本后——运行面**不会**自动感知；面板 lifecycle plan 提示 loaded_versions 漂移 → 人确认 reload → 整方案重装载（恒取 B 头版本，无法钉旧版）。

**能力小结**：仓内依赖在「单方案组内」已是**语义完备**（装载闭包/推理物化/组查询/来源标注四件齐），短板集中在**版本维度**（无 pin、无自动感知、无回滚）与**组合维度**（会话单方案、跨方案无通道）。

### 4.2 外部公开本体（FOAF/schema.org 等）——两条路径，均非「引用」

| 路径 | 机制 | agent 实际可见性 |
| --- | --- | --- |
| **导入为仓内副本** | REQ-316 catalog fetch → 导入管线 → 仓内 spec 资产 | 可见可用；但**是快照拷贝**，与上游无版本关联追踪，上游演进无感知 |
| **登记外部 IRI** | external_refs to_onto_id 留空（LOV/OLS 搜索并入同此，且为本地拷贝不自动登记） | 导出层物化 skos 映射段/seeAlso（IRI 字面）；**定义与实例在装载与查询期均不可见**（远端 IRI 不拉取，D-O27） |

**结论**：agent 对外部公开本体实际上**只能「抄」（导入副本）不能「引」（活体依赖）**。这不是实现缺陷而是 D-O27 拍板边界（单机自部署不做远端网络依赖）；改变它需要决策反转+触发证据，见 §7 备选 E。

| 场景 | 能/不能 | 载体 |
| --- | --- | --- |

### 5.1 标准与协议线

1. **OWL 2 owl:imports 与 imports 闭包**〔已复核：W3C owl2-syntax §3.4/3.2 + ROBOT + ODK〕——本体级依赖声明唯一的 W3C 级标准件。要点：imports 指向本体文档 IRI，直接导入的传递闭包即 imports closure；**允许循环导入**；**规范级许可「工具 MAY 将导入 IRI 重定向到本地副本（缓存/file:）」**——单机自部署用本地资产库替代远端拉取有标准依据；安全约束 SHOULD NOT：闭包内同系列不同版本共存、owl:incompatibleWith 命中。工程工具链：ROBOT mirror/merge、ODK dynamic imports 工作流。**对本项目**：闭包做成**发布期/装载期一次解析的产物**、运行时零网络依赖——现行运行面闭包已是此形态的正确实例。
2. **RDF 1.1 数据集/命名图 + SPARQL 1.1 Federation（SERVICE）**〔部分复核：rdf11-mt §10 逐字核实；修正两条——QLever 实已支持 SERVICE（「缺 SERVICE」说法过时）、Oxigraph issue #926 实为本地 join 模式排序慢查询而非联邦 join，引它证「联邦易慢」属错置〕——要点：**命名图无标准语义**（「The semantics does not require…that graph names…refer to the graph they name」），只是打包+GRAPH 寻址约定；SERVICE 为跨网络设计（整体派发子模式、SILENT 失败降级、VALUES 下推仅 informative、变量 endpoint 无正式语义）。Oxigraph 自称实现 Federated Query 但优化器朴素、无推理（#130 开放）。**对本项目**：多本体共存查询的正解是**单库命名图分区+union/GRAPH**——现行 raw/inferred 双图隔离与 REQ-482 union 语义正是此正解；联邦是跨网络能力，单机用不上且引入远端失败面。
3. **本体 IRI 版本化（version IRI / owl:versionInfo / dct:replaces）+ OBO FP-004**〔已复核：owl2-syntax §3.1/5.5、OWL2 New Features §2.6.4、FP-004 逐条、DCMI terms〕——要点：**本体 IRI 标识「本体系列」、version IRI 标识具体版本**；导入本体 IRI 解析到系列当前版（浮动），导入版本 IRI 钉死具体版（pin）；owl:priorVersion / backwardCompatibleWith / incompatibleWith 版本链接；OBO FP-004 版本纪律=官方发布 MUST 有唯一版本 IRI、日期 ISO-8601、**发布文件内容 MUST NOT 修改**（bug 进新版本）。**对本项目**：「系列标识+版本标识双轨、引用可浮动可钉死、发布即冻结」可直接映射到 spec_json 资产——与本项目「迁移文件只增不改」纪律同构。
4. **OBO PURL/ID 解析体系**〔未复核（非关键条目）〕——IDSPACE（本体命名空间唯一短码，如 GO/UBERON）唯一分配+CURIE（紧凑 URI，「前缀：本地名」形式，如 GO:0008150）展开+「当前版固定入口+不可变版本路径」双层入口+重定向配置集中托管。可借鉴「解析层与存储层解耦、引用不烂换存储不换 ID」思想；单机形态=PURL 退化为进程内路由（一张 IRI→版本映射表）。
5. **ROBOT release 管线与 imports 模块化构建（+ODK）**〔已复核：robot.obolibrary.org 全命令链 + ODK README/project-schema〕——典型发布链：mirror→extract（SLME 三档〔SLME=基于语法局部性的模块抽取算法，STAR/TOP/BOT 三档按保留逻辑蕴含强度递减〕/MIREOT〔=Minimum Information to Reference an External Ontology Term，按层级边界抽取外部术语的保层级算法〕）→merge→reason→materialize→reduce→verify（QC 违规即失败退出）→annotate（写版本 IRI）→report/diff。**核心思想=依赖闭包在构建期物化、产物自包含、发布前 QC 门禁**。不适配：ROBOT 是 Java 11+、ODK 依赖 Docker，与 Go 全栈+一条命令启动（D-O15 精神）冲突——**只能复刻管线形态，不能复用工具**。
6. **本体模块化研究线（SLME/MIREOT/ODP）**〔未复核（非关键条目）〕——逻辑模块性/保守扩展需要 OWL 推理器，Go 生态无成熟实现，整体过重；可迁移的只有「按 seed 词表抽取子图」朴素思想。ODP「可复用建模模板」与 LLM 辅助建模+种子 spec 有结合点（推断，门户一手来源未抓到）。
7. **SHACL 跨本体校验**〔未复核（非关键条目）〕——shapes 图/数据图分离+跨图复用+severity 分级，是多本体共存后一致性兜底的标准形态；但成熟实现集中在 Java/Python/JS，**Go 无成熟 SHACL 处理器**（检索未见反例）——只宜自研受约束子集（targetClass/基数/值域/closed）并诚实标注，不能引 pySHACL（D-O15）。

2. **EBI OLS / OLS4**〔部分复核：GitHub API 实测 pushed_at=2026-10-29 活跃、README「single point of access to the latest ontology versions」；出入=ols-config.yaml 属 OLS3 旧方案，OLS4 配置已换代为 JSON〕——「**配置文件声明仓库内容+单点查询最新版**」是单用户自部署可平移的最小仓库模型；现行 ontology-service 已有 SQLite 资产库（v1.1 实数迁移建表 **13 张**：ontology/ontology_artifact/ontology_version/external_refs/pipeline_profile/ontochat_session/ontochat_draft_version/ontochat_job/evolution_candidate/ontology_quality_score/async_job/schema_migrations/ontology_object_overlay），语义上已是它的特例（配置=仓内资产表）。初稿「SQLite 三表」系与 backend 主库自研 KG 三表（kg_entity/kg_relationship/kg_claim）混淆的笔误，v1.1 订正。
3. **Ontohub**〔已复核（v1.1 升级：GitHub API 实测 pushed_at=2017-08-21T11:34:03Z、archived=false、description="A web-based repository for distributed ontologies"；上游 commits feed 口径 2017-04-03 系 staging 分支 feed，取 API 为准）〕——Git 仓库式多逻辑本体仓库引擎，**最后 push 2017-08、实质停更约九年且无归档声明**。反面教训入档：**仓库引擎不应比被托管资产更重**（Ruby+Hets 栈本身即高门槛）；fork/PR 协作面单用户无意义。
4. **LOV（Linked Open Vocabularies）**〔未复核（非关键条目）〕——策展型目录：准入四硬门槛+Bot 每日自动巡检上游变更+逐版本留存（原文件消失仍有备份）。可轻量复制三件：准入检查单、cron 巡检上游、逐版本快照入库——「自动巡检+版本留存」对单机资产防腐烂直接适用。
5. **OBO Foundry 发布工程（PURL+ROBOT/ODK+GitHub）**〔已复核：purl README、COB ReleaseWorkflow、FP-003〕——**无中心仓库平台**，靠 git 仓库+CI 发布（release=带日期 tag 的不可变工件，vYYYY-MM-DD）+PURL 稳定 URI 重定向（每本体 YAML 生成 RedirectMatch，URI 永不变、物理目标可变）三件套达成完整仓库语义，数百本体在用（config/ 实数 235 份 YAML、注册表 191 active）。**对本项目最强先例**：「release=不可变工件+稳定 ID 解析到当前版」完全可在 Go+SQLite 内实现（版本表=tag、稳定 URI→当前版本=进程内路由），**不需要任何仓库服务器进程**。

### 5.3 类比工程线（非本体域的依赖管理机制）

1. **Confluent Schema Registry**〔已复核：官方 SerDes 文档+config 页+OpenAPI spec 逐项〕——模式按 subject 归组、subject 内版本递增；**注册即门禁**：七档兼容模式（BACKWARD/FORWARD/FULL/三 TRANSITIVE/NONE），不兼容注册返回 409 Conflict，另有 dry-run 兼容性预检。**对本项目最可平移的机制**：spec_json 入库/发布轮做向后兼容判定，不兼容提交拒绝并给人话错误；subject 作用域=按本体作用域。不需要其 Kafka 存储层与序列化器集成面。
2. **OCI Distribution Spec**〔未复核（非关键条目）〕——blob 以 sha256 digest 内容寻址（不可变、去重、可验证完整性），tag=可变名→digest 映射。digest 思想 Go 标准库数行可落（本项目 KB-20 维度登记、uid 确定性派生已有同思想先例）；网络协议面单机不需要。
3. **Helm Chart 仓库**〔未复核（非关键条目）〕——「**一个 index.yaml+一堆静态 tgz**」的下限仓库设计，无需专用服务器软件。可直接抄：SQLite 一张表当 index、本地文件树当工件库。
4. **npm / Cargo / Maven 依赖解析**〔均未复核（非关键条目）〕——共同结构=「**声明层（范围/意图）+锁定层（现实/解析结果）**」两文件分离（package.json+lockfile / Cargo.toml+Cargo.lock）；Cargo 兼容规则 left-most non-zero 最清晰；Maven 最近优先仲裁确定性弱、单用户不必引入。**对本项目**：单用户可直接简化为**只存锁定版本**，范围声明层仅在多项目共享本体时才需要（推断）。
5. **联邦查询三件（GraphDB FedX / Stardog Virtual Graphs / Neptune SERVICE）**〔均未复核（非关键条目）〕——共同点=多端点/多源**消费面增强**，不是仓库机制，与本档主线正交；其约束清单（只读联邦+单可写成员、只读 SERVICE、join 下推/超时调参成本）可抄为未来若做联邦的设计边界。D-O27 已把联邦拍板排除，此线仅存档。

### 5.4 业界盘点的四条可迁移结论

1. **依赖闭包做成发布期/装载期一次解析的产物，运行时零网络依赖**（OWL 2 imports + ROBOT/ODK 管线思想）——本项目运行面闭包已是正确实例，缺口在构建面预览与版本维度。
2. **「系列标识+版本标识」双轨 + 发布即冻结 + 引用可浮动可 pin**（OWL 2 version IRI + FP-004 + Schema Registry 门禁）——直接补 external_refs 无版本列的缺口。
3. **仓库语义可无服务器达成**（OBO 三件套 + Helm 下限设计）——「release 工件+稳定 ID 路由+一个索引」在 Go+SQLite 内是功能子集级工作量，**不需要独立 registry 进程**。
4. **跨本体一致性与共存查询靠命名图分区+装载期校验，不靠联邦**（RDF 1.1 + SHACL 思想）——现行 union 语义方向正确，增强点在 SHACL 受约束子集（远期，触发驱动）。

## 六、问题③：是否值得开发镜像仓库式的本体仓库服务（承 §五盘点作答）

### 6.1 先看需求真实性：当前痛点盘点

从 §3 缺口清单提炼，与「依赖/仓库」直接相关的实锤痛点按证据强度排序：

| # | 痛点 | 证据 | 强度 |
| --- | --- | --- | --- |
| P1 | 引用无版本 pin：被引本体演进后引用方无感知，重载恒漂移头版本、无法回滚装载 | 049 迁移无版本列；manager.go:687-699 恒取头版本；lifecycle 仅提示 | 实锤（机制缺失） |
| P2 | 构建面无**全量**依赖视图：无法预览解析后 schema/全量闭包依赖图/循环引用专项报告 | qualitygate 零命中；闭包仅在运行面；REQ-278 影响报告卡已覆盖版本 diff+引用波及面（docs/18A:121，v1.1 查证） | 部分已覆盖（剩余缺口实锤） |
| P3 | 闭包补全本体不可路由、不进漂移对比 | 上游勘察运行面缺口 3 | 实锤（机制缺失） |
| P4 | 外部本体导入副本与上游无版本关联、无自动巡检 | §4.2；LOV 对照 | 实锤（但属外部同步面） |
| P5 | LLM 辅助创建零跨本体上下文，无法建议复用/对齐 | v1.1 补实读：llmcreate.go:27-33（prompt=领域描述+JSON Schema+种子范例，零仓内清单）+extender.go:46+vocabsearch.go:1-6 | 实证（本档自证指针，非循环引用） |
| P6 | 会话单方案、跨方案无通道；KB/伴生链单本体 | models.go:165-166 等 | 实锤（但属消费组合面，未必属仓库面） |
| P7 | 对外发布/社区分发（E4 模板库） | 90 号 `:130-138` | **愿景，无使用证据**（90 号 §6 全零） |

**关键观察**：实锤痛点全部集中在**版本维度（P1~P3）与体验维度（P5）**——它们都是「仓库能力面」的缺失；而「镜像仓库**服务**」（独立进程、push/pull、多消费者）对应的 P7 恰恰是唯一没有使用证据的。**痛点指向的是依赖管理，不是分发基础设施。**

### 6.2 做镜像仓库服务的利（诚实列出）

1. 版本 pin/发布快照/依赖门禁一旦以 registry 形态立起，语义最完整（subject/版本/兼容门禁/digest 一应俱全，Schema Registry 全套可平移）。
2. 为 90 号 E4（本体模板库/权威本体目录）预留了直接地基，若未来开源演进到 E4 可平滑升级。
3. 对 P4（外部本体镜像+自动巡检）有自然承载（LOV Bot 思想）。
4. 若未来出现第二台机器/第二消费者（团队化、多机同步），registry 是**最完整的可扩展形态之一**（v1.1 修正：初稿「唯一」与本档 §5.2-5 相抵——OBO 先例证明 git 远端+CI 发布同样可承载多机分发，数百本体在用即证，§5.4-3 同口径）。

### 6.3 弊（与单机自部署定位的张力）

1. **没有分发对象**：单机自部署、单用户（Q-5）意味着 push/pull 协议、索引缓存同步、多客户端互操作全部没有第二端——registry 的核心价值（分发）在本场景为空转。这是定位级论据，非实现级。
2. **仓库语义已被占据**：D-O1 明文「构建平面管仓库，仓库是唯一事实源」——ontology-service **就是**本项目的本体仓库；再立一个 registry 进程=同一语义两层承载，违背「小而快、摘除便宜」纪律（66 号退役论证的核心理由链）。
3. **反面教材在案**：Ontohub（仓库引擎比资产重而死；停更 v1.1 GitHub API 实测坐实，§5.2-3）、Foundry「引入却用不到的能力面」警醒（D-O24 原文「作为后续任何引擎/能力面引入评估的对照项」，docs/03 `:933`，v1.1 补指针——初稿轮 sed 实读已覆盖该行）——镜像仓库服务正是典型的「引入时能力面 > 使用面」候选。
4. **退役护栏与触发纪律**：OpenOntologies 双轨（唯一先例=外部本体服务形态）刚于 2026-10-08 退役，护栏明令不重启已退役外部栈；66 号 §4 自研路线留作**触发驱动**重评底稿；90 号 §7「不为开源而开源……触发驱动，不预设排期」；E4 跳序明令禁止。**现在做仓库服务=在三条触发纪律上同时抢跑。**
5. **维护面**：独立服务=独立进程/端口/存储/健康检查/文档面，单人维护下的腐烂风险正是 66 号取证实证过的模式（oo-worker 休眠腐烂）。
6. 本项目已有明确的服务进程预算约束意识（构建/运行/主平台三服务 + 双引擎子进程），再加常驻进程与单机一条命令启动（run-dev.sh 零 venv、验收 22）的简洁性诉求相悖。

### 6.4 判断

**「镜像仓库式的本体仓库服务」作为独立服务进程：不做。** 它解决的是 P7（无证据），而 P1~P3/P5 这些实锤痛点**不需要 registry 形态即可解决**——业界先例（OBO Foundry）恰好证明完整仓库语义可以**无仓库服务器**达成。

**但「仓库能力面」的最小闭环值得做**，形态=**ontology-service 内的功能增强，不是新服务**：

> **「发布（release）+ 依赖账本（manifest）+ 门禁（gate）」三件，全部长在现有 ontology-service 进程与 SQLite 里。**
> - **发布**：本体 Publish 时生成不可变发布快照工件（spec_json+TTL+内容 sha256 digest+版本号），版本表即 tag（OBO/OCI 思想）；
> - **依赖账本**：external_refs 增加版本维度（浮动=头版本 / pin=某发布版本，OWL 2 双 IRI 语义），发布快照自带依赖清单 manifest；
> - **门禁**：构建/发布轮做兼容性预检（受约束判据：概念删除/关系改签名=破坏性）与悬空/漂移检测（Schema Registry 思想）；运行面装载按 pin 解析快照而非恒取头版本。

这与 D-O1（仓库=ontology-service）完全同构——只是把仓库从「资产当前态存储」升级为「资产版本化存储」，不新增任何进程。

### 6.5 如果做：分几步（草案，均须走正规立项）

- **步骤一（修痛点 P1+P3；版本维度最小件，预估 2~4 人日**〔推断，未排期〕**；可即领号，触发口径见 §7.5）**：external_refs 加 `pin_version` 列（空=浮动头版本）；Publish 生成发布快照工件+digest 落库；运行面 FetchTTL 按 pin 解析对应快照、无 pin 维持现状；lifecycle plan 对账扩展「pin 版本 vs 头版本」漂移提示；闭包补全本体进漂移对比与路由（修痛点 P3）。验收锚点=「B 升级后 A 的方案重装载仍取 pin 版本，显式刷新才漂移」。
- **步骤二（修痛点 P2 剩余面+P5；构建面依赖视图，预估 2~4 人日**〔推断〕**；触发驱动，判据见 §7.5）**：把运行面 expandClosure 算法前移为构建面**只读预览**端点（全量依赖闭包图+解析后 schema 预览+循环引用专项报告，不回写不阻断——D-O27「构建面闭包不做」指的是不做装载语义，只读预览与之不冲突**〔推断，立项时须在需求档显式裁决这一口径〕**）；**与 REQ-278 的关系=扩面衔接而非新功能**——REQ-278 已交付影响报告卡（版本 diff+引用波及面，docs/18A:121），本步骤补全量依赖闭包图与解析后 schema 预览，立项时在 REQ-278 行或新号行互注；LLM 辅助创建注入仓内本体清单+可复用词表提示（FetchSpecVocab 先例扩面，修痛点 P5）。
- **步骤三（对应痛点 P4/P7；触发驱动，对外分发面）**：导出「本体包」（manifest+依赖清单+digest，Helm index 思想）+导入整包时自动登记 external_refs（补 REQ-511 单点选择的缺口面）；外部本体源自动巡检（LOV 思想）挂触发。**仅当**出现真实第二消费端（多机/社区/官网种子 spec 分发需求，即痛点 P7 证据）时，才评估是否升格为 90 号 E4 目录面——届时按 E1→E4 顺序走，不跳序。

### 7.3 推荐

**方案 B「仓内依赖管理最小闭环」；推进节奏=步骤一（痛点 P1 实锤）可即领号立项，步骤二/三按 §7.5 判据触发驱动；A 作为 B 未立项期间的默认态。**

理由三条：

1. **痛点-形态匹配**：实锤痛点（P1~P3/P5）全部落在版本与视图维度，B 以最小形态全覆盖；registry 形态（C）多出来的分发协议面对痛点零贡献（§6.1 关键观察）。
2. **业界最强先例支持同构做法**：OBO Foundry 证明「release 不可变工件+稳定 ID 路由+依赖闭包发布期解析」可在无仓库服务器前提下达成完整仓库语义〔已复核，§5.2-5〕；Schema Registry 证明门禁机制可独立于分发基础设施存在〔已复核〕。B 恰是这两条在 Go+SQLite 里的最小实例。
3. **与全部已拍板决策同向**：不违 D-O1（仓库仍在 ontology-service）、不违 D-O27（仓内边界）、不违退役护栏与 90 号触发纪律（无新进程、E4 不跳序）、符合 D-O5/D-O15（开源思想借鉴+Go 自研）。

### 7.4 为何不选备选

- **A（维持现状）**：P1 漂移风险已实锤且正在发生（每次 reload 恒取头版本、无回滚），「挂触发」对已成立的机制缺失不成立；A 只适合作为 B 立项前的默认态，不适合作为终态。
- **C（镜像仓库服务）**：§6.3 六条弊，核心是「分发无对象+语义双层承载+三处触发纪律抢跑」；且其能解决的 P1~P3 子集 B 以小得多的成本同样解决。**若未来 E1 使用证据成立、出现真实第二消费端，C 的评估入口是 90 号 E4 而非本档**——届时 B 的发布快照/manifest/digest 恰好是 C 的地基，投入不浪费。
- **D（接入外部仓库平台）**：OntoPortal Appliance 全家桶（Ruby+Solr+专用三元组库）与零重运维约束直接冲突（D-O15 同理）；其增量价值（跨库检索/annotator/recommender）全是多租户社区面，单用户为零；且引入外部栈违背退役护栏精神。OLS 自托管则与 ontology-service 现有仓库语义完全重复。
- **E（远端活体引用+联邦）**：D-O27 于 2026-10-28 复审后**仍拍板维持不做**——重启需新证据驱动的显式决策反转，本档未见该证据（单机场景无跨网络消费需求）；且 Go 生态无成熟联邦层（v1.1 检索佐证：Go 侧仅 garsue/sparql、knakk/sparql 等端点客户端库，无 SPARQL 1.1 Federated Query 引擎实现；联邦实现集中在 Comunica〔JS〕与 GraphDB/Virtuoso/Neptune 等非 Go 栈；来源 github.com/garsue/sparql、github.com/knakk/sparql、w3.org/TR/sparql12-federated-query）——自研联邦等于在失败面（超时/下推/缓存）之上再加引擎工程，单机是纯负债。
