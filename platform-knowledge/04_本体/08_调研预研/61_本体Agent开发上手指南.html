// GUIDE FOR DEVELOPERS · 2026

本体（Ontology）× Agent 开发上手指南

写给「完全没接触过本体、但要动手做本体 + Agent 项目」的开发者。不讲哲学史，只讲你写代码时需要知道的概念、工具和最短落地路径。

30 秒结论：本体就是一份机器可读的、带逻辑约束的领域数据字典（有哪些类、类之间什么关系、什么字段合法）。它在 Agent 项目里的核心价值是：给 LLM 的知识抽取和检索立规矩——不让模型自己发明 part_of / PartOf / part-of 三种关系，让多跳推理和结果溯源成为可能。最短落地路径：Protégé 学概念 → rdflib 写本体 → SPARQL 查询 → 把查询包成 tool 给 LLM 调用，一个周末可跑通。

01本体是什么

一句话定义

本体（Ontology）源于哲学，在计算机科学里的工程定义是：对一个领域中有哪些类型的东西、它们有什么属性、彼此之间允许什么关系的形式化、显式、机器可读的规范。

用开发者最熟悉的类比：

  • 它像 数据库 schema + 一套更严格的业务规则，但用图（三元组）而不是表来组织；
  • 它像 TypeScript 的类型定义，但类型之间可以声明逻辑关系（传递、对称、互斥、等价…），机器能据此自动推理出新事实；
  • 它像 一份带 URI 全局唯一 ID 的数据字典，任何系统引用同一个 URI 就指同一个概念，天然支持跨系统互操作。
turtle · 一个最小本体长这样（以生信数据集领域为例）
# bio_ontology.ttl —— 本体文件就是文本，Turtle 是最常用的人类可读格式
@prefix bio:  <http://example.org/bio#> .
@prefix rdf:  <http://www.w3.org/1999/02/22-rdf-syntax-ns#> .
@prefix rdfs: <http://www.w3.org/2000/01/rdf-schema#> .
@prefix owl:  <http://www.w3.org/2002/07/owl#> .
@prefix xsd:  <http://www.w3.org/2001/XMLSchema#> .

# —— TBox：概念层（"类型定义"）——
bio:Dataset a owl:Class ; rdfs:label "数据集" .
bio:Sample  a owl:Class ; rdfs:label "生物样本" .
bio:SequencingFile a owl:Class ; rdfs:label "测序文件" .

# 对象属性：类与类之间的关系
bio:hasSample a owl:ObjectProperty ;
    rdfs:domain bio:Dataset ; rdfs:range bio:Sample .

# 传递属性：A derivedFrom B, B derivedFrom C ⇒ A 也 derivedFrom C（推理机自动得出）
bio:derivedFrom a owl:ObjectProperty , owl:TransitiveProperty ;
    rdfs:domain bio:SequencingFile ; rdfs:range bio:Sample .

# 数据属性：类到字面值的字段
bio:fileFormat a owl:DatatypeProperty ;
    rdfs:domain bio:SequencingFile ; rdfs:range xsd:string .

# —— ABox：实例层（"数据行"）——
bio:ds001 a bio:Dataset ; rdfs:label "肝癌队列2026" ;
          bio:hasSample bio:s01 .
bio:f01  a bio:SequencingFile ;
         bio:derivedFrom bio:s01 ; bio:fileFormat "FASTQ" .

本体 vs 你已知的东西

概念回答的问题和本体的关系
分类法 Taxonomy谁是谁的子类？（is-a 树）本体的一个子集。只有层级树，没有属性和逻辑约束
数据库 Schema表、列、外键长什么样？本体 ≈ schema 的"图逻辑增强版"：支持多值、多继承、推理、开放世界，且每个术语有全局 URI
知识图谱 KG具体实体和关系的数据是什么？本体是 KG 的 schema（TBox），KG 里按本体填充的实例数据是 ABox。先有本体再建图，图才不会长歪
JSON Schema / SHACL数据合不合法？SHACL 是 RDF 世界的校验约束语言，相当于"针对图数据的 JSON Schema"，用来验收 LLM 抽取结果
向量库 RAG哪些文本块语义相似？本体/图谱回答"关系和结构"，向量回答"相似性"。生产中常混合使用，不是二选一

三个必须建立的思维模型

  • 三元组（Triple）：一切知识都是 主 — 谓 — 宾。(bio:f01, bio:fileFormat, "FASTQ") 就是一行知识。谓语（属性）本身也有 URI，也是一等公民。
  • TBox vs ABox：TBox 是术语层（类、属性、规则 = 类型定义），ABox 是断言层（具体个体 = 数据）。TBox 要稳、要少改；ABox 天天增。
  • 开放世界假设（OWA）：数据库默认"没写进表里的就是不存在"（封闭世界）；本体默认"没说的不等于没有，只是还不知道"。这意味着 约束的写法和 SQL 思维不同——你要显式声明不相交、基数限制，而不是靠"查不到"来判断。
WHY IT MATTERS FOR AGENTS

Agent 场景里本体最实际的三个作用：① 约束 LLM 抽取——实体和关系只能用本体里定义的词汇，输出可校验；② 支撑多跳/传递推理——向量 RAG 第一跳就断链的问题，图遍历天然解决；③ 三级溯源——每个答案都能定位到具体三元组，幻觉可度量。参考 ontorag 的同题基准：向量 RAG 在传递推理题上断链，而图方案可做到三元组级引用（ontorag）。

02核心技术栈：W3C 语义网全家桶

不用全学，先知道每样东西在链路里干什么，用到再查：

技术角色（类比）你需要知道的
RDF数据模型（JSON）主谓宾三元组，一切的基础。一切皆 URI
RDFS基础类型系统定义类层次 subClassOf、属性的 domain/range
OWL / OWL 2强类型 + 逻辑等价类、互斥类、基数限制、传递/对称/函数属性等，推理机靠它推出新事实。三个性能档位：OWL2 EL（大规模术语）、QL（查询重写）、RL（规则）
SPARQL查询语言（SQL）图上的 SQL，模式匹配三元组。Agent 最常自动生成/执行的就是它
SHACL数据校验（JSON Schema）定义"形状"约束，校验 RDF 数据合不合法——验收 LLM 抽取结果的关键
SWRL业务规则"如果…那么…"式规则，配合推理机使用（如：基金经理有处罚记录 ⇒ 基金标高风险）
Turtle (.ttl)序列化格式最常用的人类可读格式，本体文件基本都长这样；另有 RDF/XML、JSON-LD
推理机 Reasoner逻辑执行引擎HermiT、Pellet（全功能 OWL DL）、ELK（EL 档位，快）。Protégé 和 Owlready2 都可挂载
PRAGMATIC NOTE

做 Agent 项目 90% 的情况用 RDFS + 少量 OWL（传递属性、定义域值域）+ SPARQL + SHACL 就够了。复杂 OWL 限制和 SWRL 主要出现在医疗、金融合规等强监管场景。别一上来啃完整 OWL 规范。

03如何构建一个本体

本体工程（Ontology Engineering）有成熟方法论，斯坦福 Protégé 团队的短课把它浓缩为标准流程（Protégé Short Course）。开发者视角整理为七步：

七步建模法

1

定领域与范围

写清这个本体覆盖什么、不覆盖什么。例：「覆盖测序数据集、样本、文件、物种；不覆盖分析流程和临床诊疗」。范围控制是本体项目成败第一要素。

2

写"能力问题"（Competency Questions）

用自然语言列出这个本体必须能回答的问题，它们既是需求也是验收测试：

  • 「这个数据集里有哪些 FASTQ 文件？」
  • 「某样本最终产出了哪些下游文件？」（需要传递属性）
  • 「哪些数据集用了人类样本但没签伦理协议？」（需要约束推理）

答不上来的问题，说明类或属性缺了——回头补。

3

枚举领域术语

从文档、数据库表、和领域专家聊天中收集名词（类候选）和动词（关系候选），先不纠结结构，能列多少列多少。

4

定义类与类层次

把名词组织成 is-a 树。原则：子类是父类的严格子集（"样本"是"材料"的子类 ✓；"数据集"是"项目"的子类 ✗，那是整体-部分关系，要用对象属性表达）。

5

定义属性

对象属性连两个类（Dataset —hasSample→ Sample），数据属性连字面值（fileFormat → string）。给每个属性写清 domain/range，并标注传递、对称、函数型等特性。

6

加约束（Cardinality / 限制）

如「每个 Dataset 至少有 1 个 Sample」（存在限制 ∃）、「文件格式只能是 FASTQ/BAM/VCF 之一」（枚举）。需要数据级校验时同步写 SHACL 形状。

7

填实例 + 跑推理机 + 用能力问题验收

灌几条真实数据，启动推理机（HermiT/Pellet）看它推出的隐含关系对不对，逐条回答第 2 步的能力问题。推理结果不符合预期 = 建模错了，这是本体独有的"编译期查错"。

REUSE FIRST

先复用，再自建。通用概念有成熟本体可直接 import：Schema.org（通用实体）、FOAF（人/组织）、SKOS（词表/分类）、Dublin Core（元数据）；生信领域有 EDAM（数据类型/格式/工具）、SIO、OBI、SO（序列本体）。复用能省掉一半建模工作，还自带互操作性。

建模工具

  • Protégé（斯坦福，免费桌面端）：本体界的 IDE，可视化建类、属性、限制，一键挂推理机看推理结果。入门必装，跟着经典 Pizza 教程走一遍（Pizza 教程仓库、从零建本体 Hands-On），2~3 小时即可建立完整直觉。官网：protege.stanford.edu。
  • 纯代码流：熟悉概念后，工程里用 rdflib（Python 基础库）或 Owlready2（面向对象风格操作 OWL，内置 HermiT 推理）直接写 .ttl，可 Git 版本管理、可 CI 校验。
  • LLM 辅助建模：2025 年起出现多 agent 本体工程流水线（如 OntoGenix：schema 生成 → OWL/Turtle 代码 → rdflib 自校验修复 → 知识图谱物化，OntoGenix；CoA-Text2OWL 用多 agent 分块从文档抽取本体，论文）。可以用，但 LLM 产出的本体必须过推理机和 SHACL 校验，不能直接上线。

04本体 × Agent 的四种结合模式

这是本指南的核心。目前业界"本体 + Agent"的玩法收敛为四种模式，按落地难度递增：

模式 A

本体当 Schema 的 GraphRAG

// 最主流，先做这个

本体作为知识抽取和图谱构建的顶层约束：LLM 按本体定义的类/属性把文档抽成 RDF 三元组 → 存图数据库 → 检索时向量+图遍历混合召回 → 喂给 LLM 生成答案。

文档 → LLM 抽取(受本体约束) → SHACL 校验 → 知识图谱 → 向量召回 + 多跳图遍历 → LLM 生成(带三元组溯源)

适合：企业知识库、科研文献、运维手册这类需要跨文档综合回答的场景。关键工程要点：抽取前先有本体，否则 LLM 会在五篇文档里发明三种写法的同义关系，图直接报废（Decoding AI · Agentic GraphRAG）。

模式 B

Agent 直接查图（Ontology-as-Tools / MCP）

// 开发者最易实现

不把图内容塞进 prompt，而是把图操作包成工具给 LLM function calling：get_schema() 看本体词汇、find_entities() 找实体、sparql_query() 执行查询、traverse() 多跳遍历。Agent 自己决定查什么、怎么查，返回结构化 JSON。

用户提问 → LLM → 调用本体工具(get_schema / sparql_query / traverse) → Fuseki/rdflib → 结构化结果 → LLM 作答

适合：需要精确查询、可审计答案的场景。参考实现 ontorag（Apache Jena Fuseki 后端，实测图遍历只增加约 1.5% 延迟，瓶颈在 LLM）；工程上推荐把工具挂成 MCP server，search_memory / write_memory 两类工具让 Agent 既能查也能写，形成持续记忆（Modern Data 101 · Agentic GraphRAG 统一记忆层）。

模式 C

符号推理机兜底（Hybrid Reasoning）

// 高可信/合规场景

LLM 负责理解自然语言、把问题转成查询意图；确定性推理交给推理机（HermiT/Pellet/GraphDB 执行 OWL/SWRL 规则），LLM 不参与事实判断。例如"基金经理有处罚记录 ⇒ 产品自动标记高风险"这类规则，推理机给出的结论 100% 可复现、可解释。

自然语言 → LLM(意图解析) → SPARQL/规则 → 推理机(OWL/SWRL 确定性推理) → 合规过滤 → LLM(组织语言)

适合：金融合规、医疗、制造故障诊断等"错了要担责"的领域。架构参考：基于图谱的 Agent 思路（CSDN）。

模式 D

用本体描述 Agent 自身（Agent 即知识）

// 前沿方向，了解即可

把 Agent、任务、目标、工具、工作流模式本身建模成本体（如 ESWC 2025 的 AgentO：用 OWL/RDF 标准化描述 agentic 模式，已验证可把 AutoGen/CrewAI/LangGraph 的工作流双向编译——代码转 KG、KG 再生成可执行代码，实现跨框架互作，AgentO 项目）。类似的还有 AJAN：Agent 的行为树用 RDF/SPARQL 定义，可热更新、可语义查询（AJAN 论文）。

适合：做多 Agent 平台、需要 agent 资产跨框架复用/审计时研究。新手不用从这里起步。

怎么选

你的情况推荐模式
第一次做，想周末跑通模式 B：rdflib + 3 个查询工具，最短路径
有大量文档要问答、要溯源模式 A：本体约束抽取 + GraphRAG
金融/医疗/合规，答案不能错模式 C：推理机承载确定性规则
做 agent 平台/跨框架编排模式 D，关注 AgentO / AJAN 演进

05最小可跑 Demo：周末五步法

目标：一个能回答「数据集里有哪些文件、什么格式、来自哪个样本」的本体 Agent。技术栈：Python + rdflib + 任意 LLM function calling，零外部服务依赖。

1

建立概念（2~3 小时）

装 Protégé，跟完 Pizza 教程：建类、建属性、加存在限制、启动 HermiT 推理机看类被自动重分类。做完你就理解了本体 80% 的概念。

2

用代码写你自己的小本体

pip 安装 rdflib，把第 1 章那份 bio_ontology.ttl 存盘（或直接用代码建），写入几条实例：

python · 建图 + 写实例
from rdflib import Graph, Namespace, RDF, RDFS, Literal

BIO = Namespace("http://example.org/bio#")
g = Graph()
g.parse("bio_ontology.ttl")          # 加载 TBox

# 写 ABox 实例（等价于 insert）
g.add((BIO.ds001, RDF.type, BIO.Dataset))
g.add((BIO.ds001, RDFS.label, Literal("肝癌队列2026")))
g.add((BIO.ds001, BIO.hasSample, BIO.s01))
g.add((BIO.f01, RDF.type, BIO.SequencingFile))
g.add((BIO.f01, BIO.derivedFrom, BIO.s01))
g.add((BIO.f01, BIO.fileFormat, Literal("FASTQ")))
3

跑通 SPARQL 查询

python · SPARQL = Agent 未来的"取数接口"
q = """
PREFIX bio:  <http://example.org/bio#>
PREFIX rdfs: <http://www.w3.org/2000/01/rdf-schema#>
SELECT ?dataset ?file ?format WHERE {
  ?dataset a bio:Dataset ;
           rdfs:label ?dlabel ;
           bio:hasSample ?sample .
  ?file bio:derivedFrom ?sample ;
        bio:fileFormat ?format .
}"""
for row in g.query(q):
    print(row.dataset, row.file, row.format)

数据量上来后把 .ttl 换成 Apache Jena Fuseki（起个 SPARQL HTTP 服务）或 Neo4j + neosemantics，代码逻辑不变。

4

把图包成工具给 LLM（核心一步）

这就是模式 B。只暴露两个工具，Agent 就能自主查图：

python · function calling 工具定义
TOOLS = [
  {
    "name": "get_ontology_schema",
    "description": "获取本体的类、属性和层次结构。查图前必须先调用，用这里的词汇构造查询。",
    "parameters": {"type": "object", "properties": {}}
  },
  {
    "name": "sparql_query",
    "description": "对知识图谱执行只读 SPARQL SELECT，返回结构化结果。",
    "parameters": {
      "type": "object",
      "properties": {"query": {"type": "string",
                   "description": "SPARQL SELECT 语句"}},
      "required": ["query"]
    }
  }
]

def execute_tool(name, args):
    if name == "get_ontology_schema":
        return schema_summary(g)   # 返回类树 + 每个属性的 domain/range
    if name == "sparql_query":
        return [str(r) for r in g.query(args["query"])]

系统提示词里告诉模型：「回答前先 get_ontology_schema 了解可用词汇，需要事实数据时写 SPARQL 查询，只能使用本体中存在的类和属性」。一个查图 Agent 就成型了。

5

加抽取管道，让图自己长大

再给 Agent 一个 ingest_text 工具：LLM 按本体把文档/对话抽成三元组 → SHACL 校验通过才写入。至此闭环完成：本体立规矩 → LLM 抽数据 → 校验入库 → Agent 查图作答 → 新对话再回流。这正是 MCP 统一记忆层的思路。

SECURITY

sparql_query 工具上线前：只允许 SELECT（禁 INSERT/DELETE/LOAD）、加查询超时、限制返回行数。LLM 生成的 SPARQL 永远当不可信输入处理。

07三周学习路线 + 避坑清单

建议节奏

  • 第 1 周 · 建立建模直觉：Protégé + Pizza 教程；自己动手为你的业务领域画类层次和属性；写 10 条能力问题。
  • 第 2 周 · 代码化：rdflib 读写 .ttl、写 SPARQL；试 Owlready2 跑一次推理机看隐含三元组；用 pyshacl 写一个 SHACL 形状校验数据。
  • 第 3 周 · 接 Agent：按第 5 章做模式 B 的查图 Agent；跑通后加 ingest_text 抽取管道；最后评估要不要上图数据库。

新手高频坑

坑 1 · 一上来建"宇宙本体"

第一个本体控制在 15~25 个类，用能力问题驱动。本体是迭代出来的，不是设计出来的。

坑 2 · 用 is-a 表达一切

"数据集包含样本"是整体-部分，不是子类关系，要用对象属性 hasPart。子类关系必须通过"is-a"测试（A 是一种 B 吗？）。

坑 3 · 让 LLM 自由抽取不校验

没有本体约束时，LLM 会为同一关系生成 part_of / Part Of / part-of 多个变体，图直接不可用。本体约束 + SHACL 验收是抽取管道的必备环节。

坑 4 · 拿向量 RAG 的思维硬套

单实体事实查找，向量 RAG 又快又好；多跳关系、传递推理、需要逐条溯源才是图的主场。成熟做法是混合检索：向量找入口实体，图遍历补关系（混合检索 + 查询改写实验显示模式感知的改写能把覆盖率从 27.5% 拉到 81.2%）。

坑 5 · 忽视开放世界假设

"查不到三元组"不代表事实不存在。需要"必须有/只能有"的语义时，显式写基数限制和不相交声明，或在应用层做封闭世界处理。

坑 6 · TBox 频繁变动

TBox 一改，历史数据和抽取 prompt 全要跟着动。前期多花时间在能力问题和复用标准本体上，让 TBox 尽快稳定。
