## 1. 为什么用 spec_json——五点设计动机（考古）

spec_json 是本体的**中枢建模形态**：三要素（concepts/relations/instances）+可选层（cq/data_properties/axioms，D-O22 逐批增设）。选它而非 OWL 全栈做仓库与编辑形态，是五点叠加的取舍：

1. **LLM 生成契约的可靠性**（最核心）：AI 生成是本平台第一公民路径——生成-校验-回喂循环要求 LLM 能**可靠输出**目标 schema。OWL 全表达力（类表达式/基数/属性特征/公理组合）下 LLM 生成错误率不可控；spec_json 的简单 schema 让 GLM/DeepSeek 生成-修复循环 3 轮内收敛成为现实（REQ-171 门禁、REQ-271 异步环）。**表达力每加一档，LLM 契约可靠性就折损一分**——这是 D-O22「表达力升级按需分批」而非一次到位的根本原因。
2. **单机零依赖仓库层**：SQLite 直接存 JSON——不需要 RDF 三元组库/OWL 推理机做仓库；查询与推理下放到引擎侧（构建/运行解耦 D-O1），运行时**不走 spec_json**。
3. **教学最小核心**：概念/关系/实例三要素是本体建模教学的最小完备集（REQ-90 方法论锚点）；JSON 直读可写，学习曲线平缓。
4. **前端统一结构**：SpecGraph/GraphEditor/Graph3D/详情页/质量门禁（三维评分/查重/悬空检查）全部确定性地作用于三要素——复杂结构会让质量评分与编辑器双双不可计算。
5. **双形态保真设计**：多形态资产从第一天就是「**original 永不失真 + spec_json 归一化投影**」并存——有损只发生在结构化操作面，不在运行面（见 §2）。

## 2. 有损的精确边界：丢什么、保什么、哪里有损

**sidecar 投影现状**（REQ-69 细则 + REQ-235/268/269 三轮升档后）：

| OWL 构造 | 投影行为 |
| --- | --- |
| rdfs:label / skos:prefLabel·altLabel | ✅ name/label（pref/alt 优先） |
| rdfs:comment / skos:definition | ✅ definition |
| rdfs:subClassOf / skos:broader·narrower | ✅ parents（未注册目标逐条 warning 丢弃） |
| owl:NamedIndividual + 属性断言 | ✅ instances（对象属性→关系、datatype→attributes） |
| owl:DatatypeProperty 声明 | ✅ data_properties（M77；domain 未注册留空不悬空） |
| owl:disjointWith / owl:equivalentClass | ✅ axioms（M78；双端注册才入） |
| **匿名类表达式**（someValuesFrom/allValuesFrom/unionOf/intersectionOf…） | ❌ **逐条 warning 丢弃**（「匿名父类（限制/公理）丢弃」含 n3 片段） |
| **属性公理**（FunctionalProperty/InverseOf/Transitive/Symmetric） | ❌ 丢弃+warning |
| 其余类级公理/注解细节/多语言标签/版本与 imports | ❌ 丢弃+warning |

**关键澄清——有损的适用范围**：以上丢失**只影响 spec_json 侧**（结构化编辑/LLM 再生成/质量评分）；**运行与查询完全无损**——运行方案挂载时 FetchTTL 直取 original 原文装引擎，SPARQL 查询、REQ-255 owlrl 推理检查全部作用于完整语义。即：**「导入有损」=「建模子集投影有损」，不是「本体语义丢失」**——original 永不失真，且导入报告已按**逐项**粒度列明丢弃构造（12 处 warning 点，非总数口径）。

## 3. 是否可以优化——分级结论

**先说不需要优化的部分**：①「丢弃项透明度」已达逐项粒度（REQ-235 定案），无需重做；②运行无损是架构保证，无需优化；③「spec_json 全面 OWL 化」**明确不建议**——会摧毁 LLM 生成契约可靠性（§1.1）与质量门禁可计算性（§1.4），65 号对 oo 全栈的判定同构。

**P1（低成本诚实性补强，建议随下个前端轮顺带）**：
- **双形态能力说明卡**：导入报告与本体详情页各加一行口径卡——「original=完整语义（运行/查询/推理无损）；spec_json=建模子集（结构化编辑/LLM 生成/质量评分作用面）」；权威本体库（REQ-316）条目详情预告「大型 OWL 本体的投影丢弃项会较多，导入报告逐项列出」——预期管理。

**P2（触发驱动，真实需求出现再立项）**：
- **未投影公理透传 sidecar**：导入时把无法投影的公理**序列化存档**（artifact 侧，不动 spec_json 结构），导出 TTL 时拼接还原——「三要素编辑无损 + 高级公理透传」的组合让 round-trip 趋近无损。**触发条件**：REQ-316 权威本体引入后「编辑→再导出→外部使用」的真实频次出现（当前引入本体多作参照/运行，编辑再导出场景弱）。**风险**：透传公理引用的 IRI 若被改名→dangling，需 dangling_axiom_ref 检查扩展；编辑语义一致性成本中高。
- **表达力续批（D-O22 后续）**：基数约束档/属性特征档——按教学与生成场景需求逐批，每批先过「LLM 生成可靠性不折损」评估。

**明确不做**：编辑回写 original 的完整 round-trip（65 号口径「不引入」，工程量与收益不成比例）；OWL 推理机引入仓库层（违背 D-O1 解耦与单机零依赖）。

## 4. 判定口径沉淀

「为什么用有损中间格式」类问题的回答结构：①先讲正向动机（契约可靠性/依赖成本/可计算性）——有损不是妥协的偶然，是**双形态保真设计的半边**；②精确划界「哪里有损哪里无损」（本项目：运行无损、建模面有损）——多数质疑源于把两者混为一谈；③优化排序先透明度后能力（逐项报告→能力说明→透传 sidecar→表达力续批），**能力扩展永远以 LLM 契约可靠性为闸门**。
