## 1. 理念

把"构建本体、运行本体服务、对接 agent"看作一条**七阶段流水线**。每个阶段业界都有多个主流开源方案；学习平台提供**工具链配置页**，学习者为每个阶段挑选工具，形成定制工具链——同一份本体换不同工具跑全流程，差异看得见，这是选型学习最有效的方式。

**平台内角色三态**（每个候选工具归属其一）：

| 模式 | 含义 | 平台做什么 |
| --- | --- | --- |
| **builtin 内置** | 平台自身功能 | 直接可用 |
| **guided 引导执行** | 外部开源工具 | 生成执行指引（安装/启动命令、数据交接点、入口链接）+ 学习者逐项打卡 |
| **managed 自动编排** | 运行段专属 | Runtime Manager 真实拉起进程/容器（已有能力，REQ-84~86） |

## 2. 七阶段定义与数据交接契约

| 阶段 | 名称 | 目标 | 输入 → 输出 |
| --- | --- | --- | --- |
| **S1** | 本体来源 | 从 0 获得本体 | 无 → spec_json / original |
| **S2** | 编辑管理 | 修改完善本体 | spec_json ⇄ spec_json |
| **S3** | 校验 | 保证正确性 | spec_json / original → 校验报告 |
| **S4** | 可视化浏览 | 理解结构 | spec_json / original / endpoint → 交互视图 |
| **S5** | 运行时引擎 | 让本体"活"起来 | spec_json 或 original → 运行中的数据服务 |
| **S6** | 服务化接口 | 标准化访问 | 运行中引擎 → SPARQL endpoint / MCP / REST |
| **S7** | 对接 Agent | 被智能体消费 | MCP endpoint → Agent 对话能力 |

**三形态交接契约**（复用 D-O2 多形态资产设计）：

- `spec_json` —— 平台归一化形态（编辑/内置工具用）
- `original` —— 原始形态（OWL/TTL 等不可变存档，RDF 工具用）
- `endpoint` —— 运行中的服务端点（SPARQL / MCP / REST）

任何工具只要声明"吃什么形态、吐什么形态"即可插入流水线——**这是工具可插拔的技术基础**。

## 3. 各阶段主流开源方案清单

### S1 本体来源

| 方案 | 许可 | 模式 | 说明 |
| --- | --- | --- | --- |
| 手写 spec_json（表单 + JSON 编辑器） | — | builtin | 平台默认（REQ-61） |
| 文件导入 spec/csv/graphml/OWL/TTL | — | builtin | 平台默认（REQ-80/69/72） |
| AI 辅助生成 | — | builtin | Eino 生成-校验循环（REQ-82，P2 功能） |
| Protégé 桌面版 | BSD | guided | 业界标准桌面建模器；导出 OWL/TTL 回流导入 |
| WebProtégé | Apache-2.0 | guided | 在线协作建模，可自托管；导出 OWL |
| OWLAPY | MIT | 对照参考 | Python LLM 构建框架，借鉴提示词与循环设计 |
| open-ontologies `load`（实例数据快速灌装） | MIT | guided | CSV/XLSX/JSON→RDF 数据装载（双轨 oo-worker 托管，§4.7）；数据留双轨 data-dir，不进 spec_json 体系 |

### S2 编辑管理

| 方案 | 许可 | 模式 | 说明 |
| --- | --- | --- | --- |
| 平台内置编辑器（JSON + 图形化双形态） | — | builtin | React Flow + RJSF（REQ-71），spec_json 往返 |
| WebProtégé | Apache-2.0 | guided | 完整 OWL 编辑能力；导入→编辑→导出往返体验 |
| Protégé 桌面 | BSD | guided | 同 S1，编辑视角 |
| ROBOT | Apache-2.0 | guided（进阶） | 命令行本体处理：template 模板批量生成、merge、subset |

学习要点：spec_json 图形编辑（低门槛）vs OWL 编辑器编辑（表达力强）的**往返一致性**是核心体验点。

### S3 校验

| 方案 | 许可 | 模式 | 说明 |
| --- | --- | --- | --- |
| 内置 Schema + 引用完整性校验 | — | builtin | JSON Schema（santhosh-tekuri）+ 引用检查（REQ-63） |
| Jena rule reasoner | Apache-2.0 | guided | RDFS/OWL 逻辑一致性检查 |
| ELK / HermiT（经 Protégé） | LGPL | guided | OWL 推理器：ELK 快（EL 片段）、HermiT 全量表算法 |
| pySHACL / Jena SHACL | Apache-2.0 | guided | SHACL 约束校验（shapes 语言） |
| OOPS! (Ontology Pitfall Scanner) | Apache-2.0（Java CLI 可本地跑） | guided | 本体建模陷阱扫描（G8 零代码登记，v0.2）：34 类常见错误检测（如误用 domain/range、不对称关系），输出可读报告；OOOPS CLI 离线可用，适配"引导执行"模式 |
| open-ontologies `validate` / `reason`（语义校验/推理） | MIT | guided | RDFS/OWL-RL 物化推理 + SHACL 校验 + 不一致检查（双轨 oo-worker 托管，§4.7）；Eats=[turtle] Gives=[report] |

学习要点：三层校验对应三种工具——**结构正确性**（Schema）→ **逻辑一致性**（推理机）→ **业务约束**（SHACL）。

## 4. 配置页功能草案（REQ-75/76 对应）

- **工具链配置（pipeline_profile）**：为某本体创建配置——七阶段纵向步骤条，每阶段展开候选卡片（名称/许可/模式/输入输出形态/学习要点），选中即保存；支持复制为新工具链、重置为默认。
- **引导清单（checklist）视图**：按当前配置生成逐项指引（guided 工具的安装/启动/交接点），学习者完成打卡；状态记录在配置上。
- **S5 段特殊渲染**：managed 模式直接内嵌运行方案选择/创建入口（复用运行方案页能力）。
- **默认工具链**：每阶段预置 builtin 默认项，配置页打开即是可用的完整流程，配置只是"换工具"。
- **学习任务卡视图（v0.2 新增，REQ-91）**：StageTool.Learning 从单行要点扩展为任务卡引用（`learning_task_id → seeds/learning/tasks/*.json`）；任务卡含阶段/标题/目标/前置/步骤/验收问题/关联工具/难度，打卡走 checklist 的 `task:<id>` key 空间（与 `tool:` 工具打卡分列）；进度视图按阶段聚合双序列（工具打卡 + 任务打卡）。任务卡数据资产与示例本体清单见《04_本体_方案设计.md》§4.8.3。

数据模型与 StageTool 接口见《04_本体_方案设计.md》§4.6。

## 5. 与现有架构的关系（重要：新增代码量可控）

| 阶段 | 现状 | 新增工作 |
| --- | --- | --- |
| S1~S4 内置项 | 构建平面已有功能（导入/编辑/校验/Explorer） | **零**——功能不变，纳入阶段叙事与清单数据化 |
| S5 | Runtime Manager 三引擎 | **零**——pipeline_profile 引用 runtime_profile_id |
| S6/S7 | facade + 主平台接入 | **零** |
| 配置层 | 无 | pipeline CRUD + 候选清单 tools.json + 配置页 + checklist 视图（薄层，P2） |

核心洞察：**七阶段模型是对现有功能的重新组织 + 一个薄配置层**，不是新子系统。P1 只需落实 REQ-74 的阶段映射与默认工具链；配置页（REQ-75/76）排 P2。
