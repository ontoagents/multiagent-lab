## 3. 核心架构：十一模型完整体系与六大设计理念

### 3.1 十一模型体系（L0–L6 分层）[13]

| 编号 | 模型 | 核心职责 | 层级 |
|---|---|---|---|
| MM | 对象-数据表映射模型 | 对象到数据库表的持久化映射 | L0 持久化映射层 |
| M1 | 对象模型 | 实体、属性、关系、约束 | L1 领域对象层 |
| M2 | 行为模型 | 领域原子行为、触发条件、前后置约束 | L2 原子能力层 |
| M3 | 规则模型 | 跨对象/跨行为的业务决策规则 | L3 解耦决策层 |
| ME | 事件模型 | 业务事件、生产者/订阅者、事件链路 | L3 解耦决策层 |
| M4 | 场景模型 | 跨对象事件协同的业务语义链 | L4 编排协同层 |
| M6 | 流程模型 | 端到端协同流 + 审批流 | L4 编排协同层 |
| MI | 接口模型 | 系统边界的接口契约 | L5 集成边界层 |
| MU | UI 模型 | 屏幕、界面元素、导航、调用链 | L6 交互入口层 |
| M5 | 主体模型 | 参与者、角色、权限边界 | 横切层 |
| M7 | 查询统计与报表模型 | 跨对象查询、统计分析、固定报表 | 旁路层 |

MM 和 MI 的位置极具深意：**映射与接口被单独建模，这是"业务/技术隔离"的制度化**——对象模型不碰表，接口模型不碰行为执行，各自可以独立变更[13]。

### 3.2 六大设计理念[9][13]

1. **正交分解**：对象（What）、行为（How）、规则（Why）、场景/流程（When）四维独立建模、独立演进；
2. **事件解耦**：通过事件链替代长事务，避免强耦合同步调用链（早期版本以 ME 模型承载，v9 收敛为同步联动）；
3. **流程分离**：端到端流程/审批流独立于原子行为建模（SOA 服务编排的现代演绎）；
4. **读写分离**：查询统计报表走旁路模型（M7），不混入领域行为；
5. **可追溯**：每个实现单元都能溯源到具体的本体模型元素；
6. **可管控**：模型可静态校验（引用完整性、无环检测）、可评审、可做变更影响分析（图遍历）。

### 3.3 与既有路线的对应关系[13]

- **DDD**：M1 直接使用聚合根/实体/值对象分类，聚合边界即事务边界；
- **经典本体论**：M1 对应 OWL/OWL2 的实体-属性-关系-约束；M3 把表达力从 OWL 简单约束扩展到 SWRL/SHACL 级复合规则；
- **Palantir**：对象 ≈ Object Type、行为 ≈ Action Type、规则 ≈ Function。Palantir 官方将本体定义为"语义元素（对象/属性/链接）+ 动力元素（动作/函数/动态安全）"，是组织的数字孪生[14]，其核心主张"**规则和行为建模才是本体核心**"被这套规范全盘继承；
- **SOA/EDA**：事件模型用消息中间件解耦行为；场景模型是服务编排的当代形态。

## 4. v9 七模型规范精读（以真实 YAML 范例为据）

v9 规范要求每个业务域产出七个 YAML 元文件 + 一个 `manifest.json`。以下结合仓库黄金范例（销售合同执行管理）逐一拆解[3][6][7][8]。

### 4.1 M1 对象模型（OBJECT）

描述**业务对象而非数据库表**——这是整套隔离原则的基石[13]。

```yaml
model_type: OBJECT
version: "1.0"
domain: "客户管理"
aggregates:
  - id: AGG-CUSTOMER-001
    name: 客户
    alias: Customer
    aggregateType: AGGREGATE_ROOT        # DDD 分类：聚合根
    lifecycle: [草稿, 待客户经理审批, 待部门总经理审批, 已通过, 已驳回]  # 状态机
    attributes:
      - name: customerNo
        label: 客户编号
        type: String
        required: true
        unique: true
      - name: customerType
        label: 客户类型
        type: DictionaryRef              # 数据字典引用（驱动下拉框）
        dictionaryRef: { dictionaryId: DICT-CUSTOMER-TYPE, typeCode: CUSTOMER_TYPE }
data_dictionaries:                       # 数据字典：驱动下拉选项与白名单
  - id: DICT-CUSTOMER-TYPE
    types: [{ typeCode: CUSTOMER_TYPE, items: [{code: PERSONAL, label: 个人客户}, ...] }]
```

关键约定：聚合根主表 + 子实体从表、值对象字段平铺/JSON 列、聚合间关联存 FK、每个表含 **5 个默认字段**、业务编号按"**三位前缀 + 四位流水号**"自动生成[4][5]。M1 驱动数据库 DDL、DTO、表单字段、查询字段、外键关系与 SQL 白名单[5]。

### 4.2 M2 行为模型（BEHAVIOR）

领域行为，不是逐表 CRUD。每个行为声明**前置条件、后置状态变更、引用规则、同步联动**四要素[13][8]：

```yaml
behaviors:
  - id: Receipt_Record                    # 「对象_行为」命名法
    name: 录入合同收款
    ownerEntity: AGG-RECEIPT-001
    behaviorType: COMMAND                 # COMMAND | QUERY
    triggerType: USER_ACTION              # USER_ACTION | SYSTEM
    preconditions: ["对应开票已批准且未作废", "累计有效收款不超过开票金额"]
    postconditions:
      - field: receipt.status
        setValue: "已登记"
    appliedRules: [RULE-INVOICE-REMAIN-RECEIPT-QUOTA, RULE-RECEIPT-CONTRACT-CONSISTENT]
    requiredPermissions: [PERM-RECEIPT-RECORD]
    syncTriggers:                         # 行为成功后同步触发的下游行为
      - behaviorRef: Invoice_UpdateReceiptStatus
        description: 收款登记后同步更新开票收款状态
```

v9 的一个重要转变：早期版本的"行为→事件→行为"异步链（EDA）在 v9 中收敛为 `syncTriggers` 同步联动 + M6 流程编排，并配套**聚合事务纪律：一个行为只改一个聚合，跨聚合联动靠 syncTriggers 或流程**[4]。这是为"AI 一次生成可运行系统"做的工程妥协——同步联动在单体 SQLite 架构中可确定性生成，异步事件则引入了生成难度与排错成本。

### 4.3 M3 规则模型（RULE）

规则独立建模、**可复用**（同一规则被多个行为 `reusedBy` 引用），分验证/推导/计算三类：

```yaml
rules:
  - id: RULE-CONTRACT-APPROVAL-LEVEL
    name: 合同审批层级判定
    ruleType: VALIDATION                  # VALIDATION | DERIVATION | COMPUTATION
    inputParams:
      - { name: totalAmount, type: Decimal, sourceField: Contract.totalAmount, required: true }
    outputType: Boolean
    expression: |
      totalAmount >= 1000000
    reusedBy: [Contract_Submit, Contract_Resubmit, Contract_ApproveFinance]
```

`sourceField` 强制规则输入绑定到 M1 对象字段，`expression` 采用受控伪代码（运行时由 `simpleeval` 规则引擎执行，违反规则给中文提示）[4]。这相当于把 SHACL/SWRL 的"约束与推理"角色降维成"可执行的业务校验"——牺牲逻辑推理能力，换取 AI 与人都能读懂、运行时零依赖。

### 4.4 M5 主体模型（ACTOR）

横切层：参与者→角色→权限三级，权限绑定到行为并支持数据范围：

```yaml
permissions:
  - permissionId: PERM-CONTRACT-QUERY-LIST-OWN-DEPT
    targetType: BEHAVIOR
    targetRef: Contract_QueryList
    dataScope: DEPT                       # ALL | DEPT
    abacCondition: "actor.departmentId == resource.departmentId"   # RBAC + ABAC
```

### 4.5 M6 流程模型（FLOW）

分 `COLLABORATION`（端到端协同）与 `APPROVAL`（审批子流程）两类；活动类型覆盖 START / USER_TASK / SYSTEM_TASK / APPROVAL_TASK / BEHAVIOR_CALL / GATEWAY / SUB_FLOW_CALL / END；网关分支支持条件表达式或规则引用（`ruleRef`）；审批任务声明 `approvalOutcomes: [APPROVE, REJECT]`。强制校验：**SUB_FLOW_CALL 调用图无环、所有 roleRef/behaviorRef/ruleRef 引用必须存在**[4][8]。

### 4.6 M7 查询报表模型（REPORT）

旁路层：每个固定查询/报表与**唯一的 M2 QUERY 行为双向一对一绑定**（M2 侧 `queryReportRef` ↔ M7 侧 `behaviorRef`），杜绝"界面查询无行为承接"或"行为无报表定义"的悬空[4][8]。这实质是 CQS（命令查询分离）原则在模型层的制度化。

### 4.7 MU UI 模型（UI）

```yaml
application:
  menus:                                  # 菜单树 → screenRef
    - { menuId: menu-customer-apply, name: 客户申请, screenRef: frmCustomerApply }
screens:
  - screenId: frmCustomerApply
    screenType: SINGLE_FORM               # SINGLE_FORM | MASTER_DETAIL | QUERY_LIST | APPROVAL
    elements:
      - { id: cboCustomerType, type: COMBO, label: 客户类型, required: true,
          dataBinding: Customer.customerType }        # 控件类型由 M1 属性类型决定
    actions:
      - { actionId: actSubmit, name: 提交, actionType: SUBMIT, behaviorRef: Customer_Submit }
```

布局有硬性规范：单表一行 2 控件、主从表主区一行 3 控件+从表表格化、查询区 3 控件+结果表格分页；枚举/字典→下拉框、聚合根引用→跳选框；**带审批的功能界面必须提供"保存草稿/提交"双按钮**[4][5]。

## 5. 工程化落地：从需求到可运行系统的完整管线

这套规范不只定义"模型长什么样"，还定义了**完整的交付管线与机器可执行的门禁**[3][4]：

### 5.1 三阶段管线（强顺序 + 人工门禁）

```
阶段一 需求探索（8 个子阶段，逐段硬暂停等人确认）
   总体理解 → 业务对象 → 功能规则 → 跨对象联动 → 端到端/审批流
   → 查询报表 → 角色权限 → UI 原型（可选）
   产出：<业务域>-需求规格说明书-V9.md（含附录 C 七模型建模输入基线）
        [门禁] 47 项自检全通过、附录 B 无 [待确认] 才能标记"完整"
阶段二 本体建模
   输入附录 C 基线 → 产出七模型 YAML + manifest.json
   建模顺序：M1 → M5 角色 → M3 → M2 → M7 → M5 权限 → M6 → MU
        [门禁] 引用完整性 / M7↔M2 一对一 / M6 无环 / 可追溯
阶段三 应用构建（10 步流水线）
   写 YAML → 生成 DDL → 字典注册 → 行为+规则服务 → 权限种子
   → 流程引擎 → 菜单页面路由 → 强制实现右侧 AI 对话框 → 全链路联调 → 验收
```

### 5.2 运行时架构：模型驱动的 AI 原生应用[5]

技术底座 code-paas（Flask + SQLite + React/TS 单体）遵循六层架构，核心机制：

1. **Ontology Registry 语义注册表**：启动时解析全部 YAML，构建 16 类索引（聚合、行为、规则、角色、权限、流程、报表、界面、API 能力、AI 工具、SQL 白名单等），作为运行时唯一语义中枢；
2. **AI 编排层**：意图路由优先级为"行为 API → 查询 API → 规则能力 → 只读动态 SQL（NL2SQL）→ 语义解释"；系统提示词强制注入需求概述 + 本体语义 + API 清单 + 下划线命名的真实表结构；
3. **Hybrid UI**：固定界面（MU 驱动）+ AI 动态界面（text/table/chart/action 四种渲染协议，SSE 六事件流式推送）；
4. **安全边界**：AI 对话默认只读，动态 SQL 强制 SELECT + 白名单表/字段 + LIMIT + 超时 + 审计日志。

这一层的设计印证了本体的"三重角色"：业务建模载体、程序生成基础、**AI 运行时推理知识底座**[5]。

## 6. 与经典本体工程体系的对照分析

### 6.1 与 W3C 语义网标准（RDF/OWL/SHACL/SKOS）

| 维度 | sharptoolbox 规范 | W3C 语义网栈 |
|---|---|---|
| 载体 | YAML（人机共读、整块进上下文、diff 友好） | RDF 三元组 / Turtle / JSON-LD |
| 类型系统 | 聚合根/实体/值对象 + 业务类型 | rdfs:Class / owl:Class 层级 |
| 约束与规则 | 伪代码表达式 + 运行时规则引擎 | OWL 公理（推理）+ SHACL 形状（校验，2017 W3C 建议） |
| 世界假设 | **封闭世界**（继承数据库/工程传统：缺省即否定） | OWL 开放世界（缺省=未知）；SHACL 封闭世界[16] |
| 推理 | 无 DL 推理机；靠静态引用校验与图遍历 | Pellet/HermiT/ELK 等 reasoner 分类与一致性检查 |
| 目标 | **驱动代码生成与运行时** | 知识表示、互操作与逻辑推理 |

本质区别：OWL 2 是"知识表示语言"（其 13 个规范文档含 EL/QL/RL/DL/Full 五档 profile[15]），而这套规范是"**软件建模与代码生成规范**"——它借用了本体的概念骨架（显式/形式化/共享，Gruber 1993[13]），但把"机器可推理"置换成了"机器可执行 + LLM 可理解"。这是务实的选择：企业业务系统的正确性靠编译器与测试保障（封闭世界），而非开放世界推理。

### 6.2 与上层本体 / 学术方法论

- **上层本体**：BFO（ISO/IEC 21838-2，Continuant/Occurrent 二分，亚里士多德实在论）、DOLCE（描述论、认知对齐）、UFO/OntoUML（概念建模导向）构成 ISO 认可的三大基础本体[18][19]。sharptoolbox 规范**没有对齐任何上层本体**——它的"本体"停留在领域层（对象/行为/规则），缺少 Endurant/Perdurant、刚性/依赖等哲学级判据。代价是与 FIBO/SNOMED CT 等标准本体生态无法互操作；收益是建模门槛大幅降低，业务专家可直接评审。
- **方法论**：METHONTOLOGY（规范/获取/概念化/形式化/实现五阶段）、NeOn（9 场景 55 活动）、OntoClean（同一性/统一性/刚性/依赖元性质校验）、Ontology 101 均以 **Competency Questions（能力问题）**为需求锚点[20][21][22]。本规范的需求探索八阶段 + 47 项自检实际上扮演了同样角色，且比经典方法论**多了硬性人工确认门禁**——这与 LLM 幻觉直接相关：模糊输入不会让 LLM 报错，只会让它"自信地答错"[13]，因此用门禁把歧义消灭在建模之前。这与 2023 年以来兴起的 LLM 增强本体工程管线（LLM 起草 + 人工/reasoner 硬门禁[22]）思路一致。

### 6.3 与 Palantir Foundry Ontology

| Palantir 概念[14] | 本规范对应 | 差异 |
|---|---|---|
| Object Type / Property / Link | M1 对象/属性/关联 | Palantir 基于数据集映射，本规范面向从零建模 |
| Action Type | M2 行为 | Palantir 声明"可提交的变更集"，本规范附规则与联动 |
| Function | M3 规则 | Palantir 是服务端代码逻辑，本规范是声明式表达式 |
| Roles | M5 主体 | 本规范细化到 ABAC 数据范围 |
| Workshop/UI | MU 界面 | 本规范 UI 也模型化，可全量代码生成 |
| 商业闭环平台 | 开源 YAML 规范 + code-paas 底座 | 部署形态：SaaS 重平台 vs 轻量单体 |

可以说，这套规范是"**Palantir 本体思想的开源化、轻量化与 LLM 原生化**"：把 Palantir 的"可执行业务语义层"从数百万美元的平台拆解为七个 YAML 文件 + 一个 Flask 底座。

## 7. 批判性评估

### 7.1 突出优势

1. **为 LLM 时代重新发明了建模规范**：几十 KB 的 YAML 一次性进入上下文，给 agent 全局视角；模型可静态 lint（悬空引用、无环检测）、可做变更影响图遍历——这些是"代码为真相源"模式做不到的[13]；
2. **人工门禁 + A/B 类内容分级**直击 AI Coding 最大失败模式（凭空补全业务规则）；
3. **双层体系务实**：十一模型是完备性上限，v9 七模型是单系统入场券，避免"一次性建完整体系"的经典大坑[13]；
4. **模型→实现多对多**：同一套模型可落成传统应用、低代码配置、Skills 技能包、MCP Server 或纯知识问答[13]；存量数据库可逆向建模、旧代码可逆向工程，为遗留系统知识资产化提供了通道；
5. **一致性与可追溯是硬约束而非口号**：M7↔M2 一对一、M6 无环、聚合事务边界等都有明确门禁条款。

### 7.2 局限与风险

1. **非标准、单源维护**：规范为私有约定，无 W3C/ISO 背书；与 RDF/OWL 生态（SPARQL、reasoner、FIBO 等）无互操作路径；
2. **规则表达力受限**：伪代码表达式无形式语义，不能像 SWRL/SHACL 那样做逻辑推理与机器验证一致性——"可校验"目前主要是引用完整性级别；
3. **v9 的同步化倒退是有代价的**：ME 事件模型在收敛版中被 syncTriggers 取代，长事务、跨系统解耦、数据反向驱动业务等 EDA 能力弱化（作者在 v2.0 时代曾明确以"行为→事件→行为"链为卖点[9][11]）；
4. **模型/代码双向同步未解决**：单向"模型→代码"会随迭代漂移，规范尚无代码逆向建模的自动化工具（cnblogs 将其列为五个坑之一：不做则"隔离三个月内名存实亡"[13]）；
5. **版本演进快、文档体量大**（v6 达 221KB），六版本并存对学习者构成认知负担；"人月聊IT"系列文章散落于公众号/腾讯云/博客园，缺统一入口；
6. **底座定位轻量**：SQLite + 单体 + 简化 RBAC（MVP 阶段登录即全权限[5]），适合原型与中小系统，企业级高并发/分布式场景需另行论证。

### 7.3 适用性判断

| 场景 | 建议 |
|---|---|
| 中小规模管理类 BS 系统 + AI 辅助开发 | **高度适配**（合同/供应链/电商分析等案例已验证） |
| 遗留系统知识资产化（存量库/代码→语义模型） | 适配，需补逆向工程工具 |
| 跨组织语义互操作、金融/医疗标准化 | 不适配，应选 OWL/FIBO/SNOMED 路线 |
| 大规模分布式、复杂事件驱动 | 需恢复 ME 事件模型并重估底座 |
| 快速验证 | 参考其"两周验证法"：第 1 周建一个非核心域的 YAML 模型，第 2 周让 AI 生成实现只评审模型，第 3 周做变更演练——**判断标准：需求变化时，你是先改模型还是先改代码？**[13] |

---

## 8. 结论

sharptoolbox 的本体建模规范是 2026 年"本体 + AI 原生应用"浪潮中**完成度最高、工程闭环最完整的中文开源方法论**之一。它的价值不在于发明了新理论——模型体系处处可见 DDD、Palantir、OWL/SHACL、SOA/EDA 的影子——而在于**收敛**：把四条既有路线收敛成大模型能直接读、静态可校验、门禁可执行、代码可生成的 YAML 规范，并用"需求探索→本体建模→应用构建"三阶段管线把抽象方法论变成了可复制技能包。

从本体工程的学术视角看，它是"降维"的（放弃开放世界推理与上层本体对齐）；从 AI 工程的实践视角看，它是"升维"的（把建模从文档活动升级为运行时语义中枢与代码生成的唯一真相源）。这套"哲学上不纯粹、工程上很彻底"的取向，恰恰是它在 LLM 时代最有生命力的原因。
