# 本体模块：开源复用与自研边界分析

> 版本 v0.2 ｜ 2026-09-20 ｜ 分析输入：《03_本体_需求文档.md》v0.4、《04_本体_方案设计.md》v0.6、三份开源调研报告
> 结论先行的原则：**开源占比进一步扩大，自研收缩为 1 个学习核心（Runtime Manager）+ 7 个业务薄层；OWL/RDF 解析与内存图引擎均已确定不自研。**

---

## 1. 分析框架

将本体模块按 03 需求 + 04 方案拆成 13 个可分析单元，按四档归类：

| 档位 | 含义 |
|---|---|
| **A 直接复用** | 引入即用，零或近零开发 |
| **B 集成复用** | 需要配置、预转换或适配胶水，但不改其核心 |
| **C 参考借鉴** | 不引入运行时，借鉴其设计/实现/提示词 |
| **D 自研** | 本项目编写代码 |

## 3. 开源复用清单明细

### 3.1 直接复用（A）

| 组件 | 角色 | 许可 | 备注 |
|---|---|---|---|
| **Oxigraph** | RDF 运行时引擎（SPARQL） | MIT/Apache-2.0 | Rust，吃 original OWL/TTL，Docker 部署；**P1 唯一引擎**（D-O5 v0.4） |
| **Jena Fuseki** | RDF 运行时引擎（推理） | Apache-2.0 | 唯一轻量推理路径，吃 original |
| **rdflib** | RDF/OWL 解析与序列化（Python sidecar） | BSD-3 | 全格式覆盖（OWL/RDF-XML/Turtle/JSON-LD）；承担导入解析 + spec_json→TTL 导出 + 可选 pySHACL |
| **WebVOWL** | TBox 可视化 | MIT | 自托管静态服务 |
| **OWL2VOWL** | OWL → WebVOWL JSON 预转换 | MIT | 构建管线一步，导入成功时预生成 |
| **LodLive** | ABox 可视化 | MIT | 直连 SPARQL 端点，零适配 RDF 型方案 |
| **mcp-go** | MCP 协议层（Server） | MIT | Go 栈推荐，facade 与后续智能体侧共用 |
| **Eino** | LLM 结构化生成框架 | Apache-2.0 | 主平台已用，REQ-82 生成入口 |
| **Hertz** | HTTP 框架 | Apache-2.0 | 构建/运行平面 REST |
| **santhosh-tekuri/jsonschema** | JSON Schema 校验 | MIT | spec_json 校验器核心 |
| **modernc.org/sqlite** | SQLite 纯 Go 驱动 | MIT | 仓库元数据存储，无 CGO |
| **gopsutil** | 进程/系统监控 | BSD-3 | Runtime Manager 健康检查辅助 |
| **React Flow + RJSF + dagre** | 前端图形/表单/布局 | MIT | 编辑器与方案管理 UI 组件层 |

### 3.2 集成复用（B）

- **rdflib sidecar 链路**：Python 子进程/HTTP 服务，Go 主服务调用——①导入解析（original→spec_json + 导入报告，REQ-80/69）②spec_json→Turtle 导出（自建本体进 RDF 引擎的必经路径，O1）③（可选）pySHACL 业务约束校验。需处理 Python 运行时依赖的安装引导。
- **WebVOWL 链路**：导入成功时调用 OWL2VOWL 预转换 → 静态托管 → 前端 iframe/跳转。需处理"非 OWL 资产无 TBox 可视化"的降级展示。
- **LodLive 链路**：仅对运行中的 RDF 型方案可用（需要 SPARQL 端点）；P2 若引入内存图方案，走 OntologyExplorer 资产对接 spec_json（自有代码改造）。
- **Cayley fork 嵌入链路（P2 可选）**：aperturerobotics/cayley（v0.15.0，Apache-2.0）作为 Go 库嵌入（`NewMemoryGraph`），外面包一层薄的语义适配层（概念/实例/关系业务 API），facade 契约不变。

### 3.3 参考借鉴（C，不引入运行时）

| 源 | 借鉴什么 | 用于 |
|---|---|---|
| **Open Ontologies**（Rust，39 工具） | MCP 本体工具的入参/返回 schema 设计、错误码语义 | facade 路由层（#11） |
| **OWLAPY**（Python） | LLM 构建本体的提示词模板与生成-校验循环设计 | LLM 创建闭环（#5） |

> Cayley（aperturerobotics fork）原列于此档（仅借鉴迭代器设计），v0.2 升级为 **B 档直接引入候选**（P2 内存图，见 §4-C）。

## 4. 自研项清单与开源替代评估（核心章节）

> 开发者的问题三：每个自研项都认真回答一次"有没有可用开源"。
> v0.2 立场（开发者两次拍板后）：**能不开源就不自研**——解析与内存图均已确定走开源。

### A. 本体仓库存储 —— 有没有可用开源？**没有更优的，SQLite 是正解**

- 候选质疑：能否用 Oxigraph 嵌入式替代？→ Oxigraph 官方 binding 仅 Rust lib / Python / JS，**无 Go binding**；且仓库要存的是"多形态文件 + 元数据 + 版本 + 导入报告"，本质是资产库而非三元组库，用 RDF 库反而把多形态设计（D-O2）做窄了。
- **结论：自研薄 CRUD（SQLite + 文件系统），规模约 1-2 天。** 开源件 modernc.org/sqlite 已覆盖存储层，业务模型是唯一自写部分。

### B. OWL/RDF 导入解析 —— **不自研，走 Python rdflib sidecar（v0.2 定案）**

- 现状（2026-09 验证）：Go 生态没有成熟维护的 RDF/OWL 解析库；knakk/rdf 等多年未更新，无 OWL 语义支持。RDF/OWL 工具链集中在 Python（rdflib、owlready2）和 Java（Jena）。
- **开发者拍板（2026-09-20）：避免自研，优先 Python 方案** → 路线② rdflib sidecar 升为 P1 定案：

| 路线 | 做法 | 状态 |
|---|---|---|
| ① 自写受限解析器 | Go 只提取所需模式，遇不支持构造进告警 | ~~原 P1 推荐~~ **已否决**（开发者拍板不自研；保留作对照记录） |
| **② rdflib sidecar（✅ P1 定案）** | Python 子进程/HTTP 服务做格式转换，Go 主服务调用 | 全格式全覆盖；顺带承担 spec_json→TTL 导出与可选 pySHACL |
| ③ Jena CLI | rdfparse 做预转换 | 备选（引入 Java 依赖，仅当 sidecar 模式受阻时评估） |

- Sidecar 一体化收益：O1 的 **spec_json→TTL 导出器同样由 rdflib 实现**（构建 RDF 图 → Turtle 序列化，比 Go 手写序列化更稳）；S3 校验的 SHACL 层也可复用同一 sidecar（pySHACL）。一个 Python 进程承担三个 RDF 相关职责，引入 Python 依赖的成本一次摊薄。
- 关键缓冲不变：**RDF 型运行方案（oxigraph/fuseki）直接吃原始文件，完全不经解析器**——两平面 + 多形态设计（D-O1/D-O2）把解析器的影响面限制在"构建平面入库"一处。
- **结论：sidecar 模式定案（O1 引入），O-9 的"①→②切换时机"问题随之关闭。**

### C. memory_graph 引擎 —— **不自研，直接用开源（v0.2 定案）**

> **⚠️ 2026-09-20 更新一（D-O5 v0.3）**：自研必要性不足，P1 唯一引擎改为 Oxigraph，memory_graph 延后为 P2 可选学习项。
> **⚠️ 2026-09-20 更新二（D-O5 v0.4，开发者拍板）**：**彻底避免自研**——P2 若需要轻量内存图，直接集成开源引擎；LG-12（手写图引擎）学习目标取消，学习点转为"开源引擎集成 + 语义适配层设计"。

- 可用开源（本次验证）：Cayley 上游 2020 年起停更（近 12 个月 0 commit）；但 **aperturerobotics/cayley fork 活跃**（v0.15.0，2026-07 发布，Apache-2.0），支持 Go 库嵌入（`NewMemoryGraph`），Apache-2.0 与本项目兼容。
- **结论：不自研。** P2 引入时直接 import Cayley fork 作图存储与查询核心，外面包一层薄的语义适配层（把 quad/path 迭代器封装成概念/实例/关系业务 API，约 1-2 天）；若届时 fork 也失活，后备评估其他嵌入式图库或干脆不引入（Oxigraph 已覆盖 P1 全部场景，内存图方案纯属可选增强）。
- 原自研方案（map + 倒排索引 + path 迭代器，参照 Cayley 设计思想）不再实施，记录保留供学习对照。

### D. Runtime Manager —— 有没有可用开源？**没有贴合的，这正是学习点**

逐个排除候选：

| 候选 | 为什么不贴合 |
|---|---|
| supervisord | Python 写的进程管理器，无"运行方案"业务模型，难嵌入 Go 服务 |
| Docker Compose / Docker API | 编排的是容器，要求用户机器有 Docker；本机教学场景过重 |
| Nomad / K8s | 严重过重，单机平台用不上 |
| systemd | Linux 绑定，无业务 API，Windows 开发环境不可用 |

- 核心差距：候选都是**通用进程/容器管理器**，而 Runtime Manager 的本质是"**运行方案**业务状态机（created→starting→running⇄stopped/error）+ profile 持久化 + 健康检查 + 日志采集"的组合，业务模型是本项目的领域资产。
- 进程原语部分：Go 标准库 `os/exec` + signal 足够，监控用 gopsutil。
- **结论：自研（P1，里程碑 O2），无可用整体开源；gopsutil 等零件开源。这是全项目唯一保留的"学习核心"自研项。**

### E. MCP facade 路由 —— 有没有可用开源？**协议层有，业务路由自写（薄）**

- mcp-go 覆盖 MCP 协议全部（Server 能力、工具注册、JSON-RPC）→ 直接复用。
- 路由逻辑（按 profile 分发到引擎、onto_* 契约实现、降级时带 profile_id 提示）是业务层，约 300-500 行，自写。
- **结论：自研薄层（P1，里程碑 O2）；Open Ontologies 作 schema 设计对照。**

### F. LLM 辅助创建闭环 —— 有没有可用开源？**Go 侧没有，Python 参考实现可借鉴**

- Eino 结构化生成 + 主平台模型连接（REQ-98）→ 开源/已有能力复用。
- 生成-校验-修复循环（≤3 轮）+ 人工预览确认：自写薄层；OWLAPY（Python）的提示词模板与循环设计可直接参考。
- **结论：自研薄层（P2，里程碑 O5），无 Go 侧现成方案——该领域本身很新。**

## 6. 结论（v0.2）

> **⚠️ 2026-09-20 更新一（D-O5 v0.3）**：memory_graph 从"自研核心"调整为 P2 可选，P1 唯一引擎 = Oxigraph（+spec_json→TTL 导出器）。
> **⚠️ 2026-09-20 更新二（开发者拍板，v0.2 定案）**：**OWL/RDF 解析与 memory_graph 均确定不自研**——解析走 Python rdflib sidecar，内存图直接集成开源（Cayley fork 候选）。自研清单最终收缩为：**1 核心（Runtime Manager）+ 7 薄层**（仓库 CRUD、业务格式解析、校验、LLM 闭环、facade 路由、REST、前端）。

1. **开源优先成立且进一步加重**：13 个模块中，运行时引擎（Oxigraph/Fuseki/Cayley fork）、解析（rdflib）、可视化（WebVOWL/LodLive）、协议层（mcp-go）、框架层（Eino/Hertz/React 生态）全部开源复用；Go 生态的 RDF 短板用 Python sidecar 化解而非自研补齐。
2. **自研 = 1 核心 + 7 薄层**：Runtime Manager 是唯一学习核心（LG-13）；其余 7 块是"业务胶水"，各 1-3 天。原 LG-12（手写图引擎）学习目标取消，转为开源引擎集成与语义适配。
3. **原唯一技术缺口已闭合**：Go 生态无成熟 RDF/OWL 解析库的问题，以"rdflib sidecar（导入解析 + TTL 导出 + SHACL 三合一）"定案解决，O-9 关闭。
4. **所有自研项都有后备路线**，最大风险项（Runtime Manager）的 fallback 不破坏 MCP 契约（facade 屏蔽），学习目标失败的代价可控。

### 遗留到方案评审的决策点

- ~~O-9（已登记）：OWL 解析路线①→②的切换时机~~ **已关闭**（v0.2 直接定案路线②，O1 引入 sidecar）。
- Runtime Manager 后备路线里"容器化降级"是否预留实现位（建议：引擎适配器接口天然支持，无需额外设计）。
- sidecar 的交付形态（CLI 子进程 vs 常驻 HTTP 服务）在 O1 动工前定（建议 P1 用 CLI 子进程，零常驻、按需调用，部署面最小）。
