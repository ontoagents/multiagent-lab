# 本体间关联引用方案调研（开源方案与论文）

## 0. 结论速览

**问题**：当前每个本体是独立资产（spec_json 归一化形态，概念间纯名字引用），复杂场景需要多个本体之间表达关联引用。

**业界方案五档全景**：

| 档 | 方案 | 代表实现/标准 | 耦合度 | 本项目适配性 |
| --- | --- | --- | --- | --- |
| 1 | owl:imports 依赖链 | W3C OWL 2 标准 | 强（公理级合并） | ❌ 不适配（spec 无 IRI 无公理；REQ-262 已明确不上全量语义） |
| 2 | 本体模块化（拆分/组织） | MOMo/ODP、ROBOT module | 中（单本体内） | 方向不同（组织方式≠跨本体引用）；MOMo 理念有启发 |
| 3 | **声明式映射档（映射外挂）** | **SSSOM + SKOS matching 词表** | **弱（本体保持独立，关联独立成档）** | **✅ 推荐主档**——与「本体独立个人」定位精确对位 |
| 4 | 对齐自动生成 | OAEI 生态：LogMap/AML/BERTMap/OntoAligner/LLM-Oracle | 弱（产物=映射档） | ✅ P2 引入：LLM 辅助对齐候选（不引 Java 工具） |
| 5 | 运行时联邦查询 | SPARQL 1.1 Federation/FedX/Ontop | 强（IRI 化+端点+查询改写） | ⏸ 观察池（依赖 IRI 化，非当前形态） |

**推荐路线**：以 **REQ-262 既有口径为骨架、SSSOM/SKOS 语义为内核**做细化——引用登记外挂（不进 spec.Concept、不 IRI 化），ref_kind 三分类映射到业界标准语义；P1 登记闭环 → P2 LLM 辅助对齐+SSSOM 导出 → P3 消费侧联动观察池。

**与既有资产关系**：REQ-262（多本体模块化轻量步，2026-10-02 立项）是本方案的**既有落点**——本档不新占需求号，而是给 REQ-262 补数据模型与业界依据；REQ-79（本体对齐）远期方向由 P2 的 LLM 辅助对齐承接。

## 1. 业界方案全景（开源方案与论文）

### 1.1 档 1：owl:imports 依赖链（W3C 标准）

- **机制**（[OWL 2 Structural Specification §3.4](https://www.w3.org/TR/2008/WD-owl2-syntax-20081008/)）：本体 O 声明 `Import(u)` 直接导入 O′；`imports` 关系是 `directlyImports` 的**传递闭包**；import 闭包不应包含同系列不同版本（owl:incompatibleWith 冲突检测）；版本管理配套 owl:backwardCompatibleWith（旧版本标识符语义不变承诺）。
- **语义代价**（[OWL Reference](https://www.w3.org/TR/2003/WD-owl-ref-20030221/)）：被引本体的含义**被视为导入本体含义的一部分**——推理器处理 imports 的方式是**物理合并公理**（axiom closure），必须获得被引本体的完整公理集。
- **耦合代价的学术证据**（Grau & Motik《Importing Ontologies with Hidden Content》,[牛津 CS 存档](http://www.cs.ox.ac.uk/files/4545/Grau_Motik.pdf)）：imports 强耦合导致「想复用概念却必须物理分发全部公理」，为此学术界提出 import-by-query（oracle 接口下做子包含/可满足性推理）——侧面证明**标准 imports 对复用场景过重**。
- **对本项目**：spec 模型概念间是名字引用（`Concept.Parents []string`），无 IRI 无公理，无推理闭包可合并；且 [REQ-262 立项原文](../../docs/03_本体_需求文档.md)已明确「不上 OWL imports 全量语义」。**判定：整体机制不适配，但其传递闭包/版本冲突检测思想可在 P2 质量门禁借用（循环依赖检测、跨本体改名失效检测）。**

### 1.2 档 2：本体模块化（MOMo/ODP、ROBOT）

- **MOMo（Modular Ontology Modeling）**（[Hitzler 学派教程](https://people.cs.ksu.edu/~hitzler/pub2/2020-mom-tutorial.pdf)、[LLM 加速 KG 工程](https://arxiv.org/html/2411.09601)）：本体由 ODP 设计模式实例化成模块再拼装；模块可重叠可嵌套，无精确边界规则，「模块提供人类专家概念化与数据现实之间的概念桥梁」；OPLa 注解语言让模块可编程识别（GeoLink/Enslaved.org 案例实践）。
- **模块化维度框架**（[UCT 实证研究](https://pubs.cs.uct.ac.za/id/eprint/1048/1/AO15modulesPaper.pdf)）：模块化五维度（use-case/type/technique/property/evaluation），Borgo 三分类（单本体模块/多本体模块/通用模块）。
- **ROBOT**（构建工具链先例见 66 号 §2②）：merge/filter/module 操作做物理拆分合并。
- **对本项目**：模块化是「**一个本体内部的组织方式**」，不是「多个独立本体间的关联引用」——方向不同。但 MOMo 两条理念直接吸收：①模块间松耦合、通过设计模式桥接（对应本项目「本体独立+引用外挂」）；②模块边界允许重叠嵌套（对应 ref_kind=reuse 的复用语义）。**判定：不作为主方案，理念吸收。**

### 1.3 档 3：声明式映射档（SSSOM + SKOS matching 词表）✅ 推荐主档

- **SSSOM 标准**（[官网](https://mapping-commons.github.io/sssom/)、[Database 期刊论文](https://academic.oup.com/database/article-pdf/doi/10.1093/database/baac035/43831757/baac035.pdf)）：
  - **核心模型**：mapping = `<subject, predicate, object>` 三元组 + **映射元数据**（provenance 作者来源/confidence 置信度/justification 判定依据——expert review、exact lexical match 等）；mapping set 集合可带元数据（license、描述）。
  - **predicate 词表**：`skos:exactMatch`（可互换）/ `skos:closeMatch`（高度相关）/ `skos:broadMatch` / `skos:narrowMatch`（包含关系）/ `skos:relatedMatch`（相关）/ `owl:equivalentClass`。
  - **设计哲学**（论文原文）：「flat 简单性」——表格式（TSV/CSV）可进数据科学管线不用解析本体；把映射的**不精确性显式化**（等价还是仅相关？宽还是窄？怎么判出来的？）——「映射缺乏元数据导致错误假设，难以组合与调和使用人工与自动映射」。
  - **双序列化**：TSV 表（人可读）+ RDF Turtle（Linked Data 生态），LinkML schema 定义。
- **OxO2 映射服务**（[arXiv:2506.04286](https://arxiv.org/pdf/2506.04286v2.pdf)）：基于 SSSOM 的跨本体映射浏览器，用 Datalog 规则引擎（Nemo）做**链式推导**（A↔B、B↔C 推导 A↔C）并保证逻辑健全（如 exactMatch∘exactMatch→exactMatch，broadMatch 只能与同向组合）——**映射组合的合法性规则**可直接借鉴为 qualitygate 检查项。
- **对本项目**：三个精确对位——①「本体保持独立、关联独立成档」= 「每个本体是独立的个人」的业界标准形态；②映射元数据（confidence/justification/author）与项目 PROV-O 审计习惯（D-O15 沉淀）同构；③TSV/RDF 双序列化与 rdflib sidecar 导出器（REQ-78）兼容。**判定：主方案语义内核。**

### 1.4 档 4：对齐自动生成工具生态（OAEI 社区）

- **OAEI 年度评测**（[2024 Anatomy 赛道](https://oaei.ontologymatching.org/2024/results/anatomy/index.html)）：LogMap（2011 起常驻，Java，10 万级本体可扩，lexical+structural+逻辑一致性，12 秒跑完 Anatomy F=0.881 P=0.917）、ALIN（P=0.984 精度最高）、Matcha、AML（AgreementMakerLight）、MDMapper。
- **新兴方向**：
  - **OntoAligner**（[arXiv:2503.21902](https://arxiv.org/pdf/2503.21902v1)）：2025 模块化 Python 框架，pip 安装，集成轻量方法与 LLM 方法，对比 DeepOnto（Java 依赖重）安装友好。
  - **LLM-as-Oracle**（[arXiv:2508.08500](https://arxiv.org/html/2508.08500v2)）：LLM 替代人工 Oracle 过滤 LogMap 的不确定映射候选（ℳ_ask）——交互式对齐的人工环节由 LLM 兜底，OAEI 2025 interactive 赛道实证。
- **对本项目**：LogMap/AML 是 Java 栈，与 Go 主线+「不引外部服务栈」纪律（D-O23 先例）不符；**LLM 辅助对齐候选**（两本体 vocab 表对照→LLM 判定 predicate+confidence→人工确认落档）与 REQ-271~275 LLM 工作流同构，成本低。oo 的 6 信号 stable matching 细节存 65 号 §2⑥ 可随时取用。**判定：P2 引入 LLM 辅助候选生成，不引入 Java 工具链。**

### 1.5 档 5：运行时联邦查询

- **SPARQL 1.1/1.2 Federated Query**（[W3C 规范](https://www.w3.org/TR/sparql12-federated-query/)）：`SERVICE` 关键字把子查询路由到远程端点再合并结果。
- **FedX/RDF4J**（[GraphDB 文档](https://graphdb.ontotext.com/documentation/10.0/fedx-federation.html)）：多端点虚拟联合为单一端点，透明联邦+查询优化。
- **对本项目**：需要 IRI 化+独立端点+查询改写三前提，当前 spec 名字引用形态与 Oxigraph 单机形态均不具备；且 D-O19 已定「KG 检索限定本体 TTL 装载来源」——多本体消费侧的正确路径是**装载时同图分 graph（本体 ID 命名）+映射桥接**，非运行时联邦。**判定：观察池，P3 之后视场景。**

## 3. 方案设计（S3 映射 + S4 约束与数据模型）

### 3.1 选档论证

**选档 3（声明式映射档）为主档，档 4 的 LLM 辅助生成做 P2 增强**。理由：与「每个本体是独立的个人」的产品定位精确对位（本体不合并、语义不强耦合、关联独立可管理可审计）；与低侵入默认约束（旁路/默认关/可摘除）逐条可核对；REQ-262 占位口径正是档 3 的内嵌版——**细化而非推翻**。

ref_kind 三分类与业界标准语义的对齐关系：

| ref_kind（REQ-262 既有） | 业界标准语义（建议向此靠拢） | 含义 |
| --- | --- | --- |
| import | owl:imports 轻量版（仅登记依赖，不拉公理） | 「本本体设计时参考/依赖对方概念体系」 |
| alignment | skos:exactMatch / closeMatch / broadMatch / narrowMatch / relatedMatch | 「两个概念间语义对应」（predicate 细分） |
| reuse | dcterms:source + prov:wasDerivedFrom 混合语义 | 「直接复用对方概念（含定义），来源留痕」 |

### 3.2 数据模型（最小化，种子冻结+溯源字段从一开始就留）

**🆕 新建 1 张外挂表**（唯一新建，data_properties 先例：可选层零存量迁移）：

```
external_refs（跨本体引用登记表）
├─ ref_id           唯一 ID
├─ from_onto_id     源本体
├─ from_concept     源概念名（名字引用，不 IRI 化）
├─ to_onto_id       目标本体（可指向任意已存本体）
├─ to_concept       目标概念名
├─ ref_kind         import / alignment / reuse
├─ predicate        对齐细分（exactMatch/closeMatch/broadMatch/narrowMatch/relatedMatch；import/reuse 时留空）← SSSOM 词表
├─ confidence       置信度（人工确认=1.0；LLM 候选=模型给出）← SSSOM
├─ justification    判定依据（expert_review / lexical_match / llm_candidate…）← SSSOM
├─ created_by       责任人 ← PROV-O 惯例
├─ created_at       时间戳
└─ note             备注
```

**映射原则逐行标注**：
- ✅ 已有：名字引用模型（不 IRI 化）、LLM 工作流模式、rdflib sidecar、qualitygate 挂靠点、详情页资产区块模式（「关联本体」区块沿资产详情既有布局）
- 🆕 新建：external_refs 表（1 张，≤3 达标）
- ⏸ 后置：SSSOM TSV/TTL 导出（P2）、LLM 对齐候选（P2）、消费侧多 graph 装载+映射桥接（P3 观察池）、imports 传递闭包分析（P3，若出现深层引用链）

### 3.3 约束原则（低侵入三原则逐条核对）

1. **旁路**：external_refs 独立表只读 spec 概念名做存在性校验，不进 spec.Concept/Relation 主链路；spec_json 结构零改动。
2. **默认关**：引用能力以「登记即显式动作」存在——不登记不生效；LLM 对齐候选（P2）以显式按钮触发（沿 REQ-274 默认关先例）。
3. **可摘除**：表物理隔离，摘除=drop table+详情区块隐藏，存量本体零回归。

### 3.4 风险与对策（业界风险→本方案对策）

| 风险（来源） | 对策 |
| --- | --- |
| imports 传递闭包版本冲突（W3C §3.4：同系列版本不得共存） | to_onto_id 锁定本体资产版本；目标本体删除/概念改名→悬空引用检测（P1 qualitygate 新检查项「失效引用提醒」，只提醒不阻断） |
| 映射缺元数据导致误用（SSSOM 论文动机） | confidence/justification/created_by 从 v1 就留（3.2 模型） |
| 映射组合逻辑不健全（OxO2 链式推导课题） | v1 不做链式推导（映射只作展示与检索线索）；P2 若做推导先抄 OxO2 合法性规则（exactMatch∘exactMatch→exactMatch 等）入 qualitygate |
| LLM 对齐幻觉（OAEI LLM 方案通病） | LLM 只产**候选**（confidence<1.0，justification=llm_candidate），**人工确认后**才落生效映射——沿 REQ-170 候选确认模式 |
| 循环引用（A→B→A） | P2 质量门禁检测循环 import 链（借鉴 imports 传递闭包思想；alignment/reuse 循环无害不检） |
| 跨本体名字冲突（概念同名不同义） | 名字引用始终带 to_onto_id 限定（限定名），前端展示「本体名:概念名」消除歧义 |

### 3.5 分阶段路线（S5）

| 阶段 | 内容 | 依赖 |
| --- | --- | --- |
| **P1 最小闭环** | external_refs 表 + 引用登记 API（增删查+存在性校验）+ 详情页「关联本体」区块 + qualitygate 失效引用检查——API 先行无前端强依赖，登记→展示→失效提醒端到端 | REQ-262（既有占位，本方案细化其实现口径） |

## 7. 场景追加分析（2026-10-13 开发者追问，v1.1）

**追问场景**：项目后期同时支持①导入外部现成本体（完整 OWL/RDFS 形态：有 IRI、有公理、文件内自带 imports 声明）②自建本体（spec 名字引用形态）③一个智能体同时使用多个本体。

**逐档再评估**：

| 档 | 新场景下角色 | 变化 |
| --- | --- | --- |
| 1 imports | **仅装载侧子集**：导入外部本体时，装载器须解析其文件内 imports 声明并连带装载依赖本体（否则导入即残缺）；自建互引仍不用 imports | REQ-262「不上全量语义」边界不破——imports 只是装载能力，不是自建互引机制 |
| 2 模块化 | 不变（理念吸收） | — |
| 3 映射档 | **仍为主方案且更重要**：外部本体只读不可改，映射档是自建↔外部唯一合理关联方式（外部概念有稳定 IRI，桥接目标明确） | 桥接对象从「自建↔自建」扩展为「自建↔外部 IRI」 |
| 4 对齐 | **价值上升建议提级**：外部本体动辄数千概念，人工逐条映射不现实，LLM 候选+人工确认在「自建↔外部」比「自建↔自建」更刚需 | 原 P2 建议提前至导入能力落地时 |
| 5 联邦 | **仍不需要**：智能体多本体使用走「同库分区」——所有本体装载进同一 Oxigraph 不同 graph（一本体一分区），一条 SPARQL 跨 graph 查询；跨本体等价概念在装载时把映射档物化为 skos:exactMatch 三元组进图，查询自动接通 | 消费侧口径=D-O19 边界内（KG 检索限定本体 TTL 装载来源），多 graph 为其自然扩展 |

**结论**：组合拳、主轴不变——映射档（档 3）主方案延伸到「自建↔外部」；新增最小件=外部本体装载器的 imports 解析（仅装载侧）；智能体多本体使用=同库多 graph+映射物化桥接，不引入联邦运行时。

**落点建议**：①REQ-262 细化范围增补「to_onto 支持外部本体资产类型+to_concept 支持外部 IRI 定位」；②外部本体导入能力立项时（若尚未立项）应含 imports 解析子项；③消费侧多 graph 装载与映射物化挂消费侧演进（D-O19 扩展，P3 观察池维持）。
