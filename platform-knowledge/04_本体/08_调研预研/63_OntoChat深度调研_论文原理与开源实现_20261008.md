## 0. TL;DR（12 条）

1. **论文定位**：OntoChat 是「**对话式本体需求工程（ORE）**」框架，只覆盖本体工程生命周期**前段**——需求引出（用户故事）→ CQ 抽取 → CQ 分析（去重/聚类）→ 本体测试。它**不生成 OWL 本体**，产出物是**结构化的需求制品**（用户故事 + CQ 集 + 覆盖性测试报告）。
2. **设计依据是一次 N=23 语义网从业者调查**：最需计算支持的任务 = 需求收集 86.4%、从文本需求抽 CQ 81.8%、本体测试 81.8%、需求分析 77.3%（≥75% 正向的「强证据」口径）。
3. **理论谱系**：METHONTOLOGY（1997）→ DILIGENT（2004）→ NeOn/SAMOD/XD（2010s）→ **IDEA**（2023，de Berardinis，前身工具）→ **OntoChat**（2024）。OntoChat 明确 building upon IDEA。
4. **四模块算法全部成立**：① 用户故事共创（4 步，一问一答 + one-shot 生成 + 迭代精修）；② CQ 抽取（4 步，few-shot + **拆非原子问题** + **命名实体抽象**）；③ CQ 过滤与聚类（**paraphrase 去重 + LLM 聚类**，论文主张纯 LLM、不依赖句向量）；④ 本体测试（**本体 verbalisation → 逐 CQ 独立 Yes/No 判定 + 解释**）。
5. **评估数字**：用户故事 N=6 音乐领域专家（>80% 满意、仅 50% 满意示例数据）；CQ 抽取 N=8 本体工程师（2/8 报范围外实体、仅 50% 认为能减少作者偏差）；聚类（62.5% 认为交互直观、87.5% 认为簇有意义）；本体测试**准确率 87.5%（P=88%、R=85.7%），混淆矩阵 25TP/24TN/3FP/4FN（共 56 条 CQ = 28 正 + 28 负）**。
6. **实现栈**：Python 3.11 + Gradio（4 tab）+ OpenAI API。仓库当前 `config.py` 为 **`gpt-4o` + temperature=0 + seed=1234**（论文评估时用 gpt-3.5-turbo / gpt-3.5-turbo-16k）——**确定性采样**是其工程选择。
7. **诚实边界（实现现状）**：仓库 `app.py` **仅启用 2 个 tab**（Set API Key、User Story Generation），CQ 抽取/分析/测试三个 tab 代码仍在但**被注释**；旧版 CQ 生成走 HF Space 的 `/cq_generator` 端点（见 `cq_generator_ontochat_app.py` 的 `gradio_client` 调用）。故 **CQ/聚类/测试模块是「论文 + 遗留源码级」资产，不是当前线上主线**。
8. **可白嫖资产**：① 需求引出访谈**系统提示全文**（`functions.py` 的 instructions）；② `OntoChat_Backend_Prompts.md`（分 4 节访谈脚本）；③ **参与式提示 10 条模板全文**（`User_Needs_...md` / `functions.py`）；④ CQ 抽取/拆分/实体抽象 prompt（`functions.py` 注释 + `ontolib.py`）；⑤ 聚类 prompt（`analysis.py`）；⑥ 测试 prompt（`ontolib.py` 的 `cqt_prompt_a/b`）。
9. **参与式提示（2408.15256）的核心洞见**：普通用户**不会写有效 prompt** → 引入「研究者中介」把用户诉求转写为 prompt 模板 → 归纳出「用户故事 5 段（Persona/Goal/Scenario/Example Data/Data Resource）× 模板」体系，占位符语法 **`**[必填]**` + `*[可选]*`**。这是自研引导卡机制的直接蓝本。
10. **对本项目最大价值**：我们的 `ontochat` 实现（REQ-103 模式 A）目前只有 `cq→domain→draft→refine→done`，**等价于论文工作流的「中间一段切片」**——缺上游「用户故事需求引出」、缺下游「CQ 分析（去重聚类）与本体测试」。论文给了这三块的**完整算法 + prompt + 评估口径**，可直接作为自研的**理论依据与实现参照**。
11. **与现有能力的衔接**：CQ 抽取 → 直连 REQ-248（CQ 一等公民，`spec.cq`）；CQ 聚类/测试 → 直连 REQ-255（CQ→SPARQL 验收闭环 + owlrl 推理检查档）；引导卡机制 → 复用 REQ-246（素材可达）与 REQ-247（生成质量透明）的既有形态。
12. **不引入项**：Python/Gradio/sentence-transformers 栈（与本项目 Go 栈 + D-O15 边界冲突）；只取**算法、prompt、评估口径、交互范式**。

## 一、论文原理层（arXiv 2403.05921 · ESWC 2024）

### 1.1 研究问题与调查证据（RQ1）

- **RQ1**：哪些本体工程活动最需要计算支持？→ 通过 Google Forms 在线问卷（不收集个人信息），5 分 Likert 量表（1 完全不同意 → 5 完全同意，3 中立），面向语义网从业者，回收 **N=23**。
- **样本构成**：60.8% 自评有强 OE 专业知识；用过的 OE 方法论 NEON 47.4%、Ontology 101 47.4%、eXtreme Design 42.1%、Linked Open Terms 42.1%、METHONTOLOGY 31.6%、SAMOD 5.3%。
- **强证据口径**：因样本量小，作者采用「≥75% 正向（4-5 分）」作为结论门槛。
- **最需计算支持的活动**（本档核心数据）：

| OE 活动 | 正向比例 |
| --- | --- |
| 本体需求收集（collection of ontology requirements） | **86.4%** |
| 从文本需求抽取 CQ（extraction of CQs from textual requirements） | **81.8%** |
| 本体测试（ontology testing） | **81.8%** |
| 需求分析（analysis of ontology requirements） | **77.3%** |

- **RQ2**：LLM 如何支撑一个对话式 OE 框架去支持这些活动？→ 用**对话式工作流 + prompt 驱动功能**，让**不同角色（stakeholders / domain experts / ontology engineers）各自独立与环境交互**，产出中间制品与文档。

### 1.2 设计原则与理论谱系

```
METHONTOLOGY(1997) ─┬─ 需求引出(源于 Uschold&King 1995) + 概念化/实现/维护
DILIGENT(2004)     ─┤  引入多利益相关方
NeOn / SAMOD / XD  ─┤  敏捷迭代；XD 强测试驱动、给出需求引出指南
  └ IDEA(2023, de Berardinis) ─ NLP 驱动的 CQ 迭代引出与改进（OntoChat 的直接前身）
       └★ OntoChat(2024) ── 把 IDEA 扩成「用户故事→CQ→分析→测试」全链对话框架
```

- **用户故事三要素**（论文引用 `polifonia-project/stories`）：**persona**（典型用户：姓名/职业/技能/兴趣）+ **goal**（该 persona 的目标）+ **scenario**（当前如何达成目标，用以凸显与待建资源的差距）。
- **CQ 的中心性**：CQ 是「结构化查询的自然语言对应物」，是 KG 应能回答的问题（溯源 TOVE，Gruninger & Fox 1994/1995）。CQ 用于**收集需求 → 驱动实现（XD 中映射为 ODP）→ 用于测试**三处。
- **关键立场（对我们的启示）**：CQ 是**需求与实现/测试之间的枢纽**。这也是 REQ-248「CQ 一等公民化」与 REQ-255「CQ→SPARQL 验收」两条线的共同理论正当性来源。

### 1.3 四模块算法（逐模块拆解）

#### 模块 1 · Assisted persona and story creation（用户故事共创，4 步）

| 步 | 名称 | 谁在动 | 机制 |
| --- | --- | --- | --- |
| 1 | LLM 角色定义（back-end） | 系统 | 把 LLM 预置为「知识引出者（knowledge elicitator）」，目标是从用户处收集每个故事成分：persona / goal+scenario / 数据示例 |
| 2 | 知识引出（user） | 用户 | 系统**一次问一个问题**（如「用户的姓名、职业、技能、兴趣是什么？」）；用户答得不全/部分回答时，**继续追问直至信息齐备**（不是一次列出所有问题） |
| 3 | 用户故事生成（back-end） | 系统 | **One-shot learning**：给 LLM 一个**用户故事范例**，要求按同结构把引出到的信息汇总成草稿 |
| 4 | 精修（user） | 用户 | 呈现草稿 → 用户给反馈 → **迭代精修直至用户满意**（可勘误/补充/删除无关细节） |

- **实现细节**：模块 2 的「不许先进下一题」是硬约束——用户没确认当前问题满意，**下一题的回答会被拒绝并要求先答当前题**；且用户可**回退到任意已完成步骤**。

#### 模块 2 · Competency question extraction（CQ 抽取，4 步）

| 步 | 名称 | 机制 |
| --- | --- | --- |
| 1 | 指示 LLM 抽取（back-end） | 提供「用户故事片段 → 期望 CQ」的**成对示例**（few-shot），对齐本体工程师期望 |
| 2 | 首次抽取（user） | 用户给出一段用户故事（可手工写，或来自模块 1）→ 输出初始 CQ 列表 |
| 3 | CQ 精修（back-end，隐藏 prompt） | **3.1 拆非原子问题**：few-shot 判断每个 CQ 是否复合，复合则拆——例：数据「Penny Lane 有 baroque pop、psychedelic pop 两个 genre/style」生成「What genres/styles are associated with Penny Lane?」→ 拆成两条「What genres…?」「What styles…?」<br>**3.2 命名实体抽象**：去掉 CQ 中的真实世界实体——「…associated with Penny Lane?」→「…associated with the musical work?」 |
| 4 | 用户确认（user） | 询问 CQ 数量与表述是否合理；不合理则用步 3 的能力**重复精修直到满意** |

- **要点**：CQ 抽取的两个「净化算子」（**拆分复合问题** + **抽象命名实体**）是 OntoChat 相对朴素 LLM 抽取的关键增益，直接把「例子里的专名」收敛为「可复用的问题模式」。

#### 模块 3 · Competency question filtration and analysis（CQ 过滤与聚类）

- **两个子能力**：① **paraphrase identification**（去等价 CQ）② **CQ clustering**（同类需求分组）。
- **去冗余的两点收益**（论文引 RevOnt）：减轻前序步骤引入的噪声与伪影；减少呈现给工程师的 CQ 数量。
- **关键立场差异**：OntoChat **反其道**——IDEA/RevOnt 都依赖**句向量 + 专用模型**，而 OntoChat **完全用 LLM** 完成去重与聚类（依据：LLM 具备聚类能力，引 Aharoni、Zhang (ClusterLLM)、Viswanathan (few-shot clustering)）。
- **聚类 prompt 骨架**：`Clustering the competency questions into clusters based on their topics. Keep the granularity of the topic in each cluster at a similar level. Return in JSON format, such as: {'cluster 1 topic': ['cq1','cq2']}`；可选指定簇数。
- **当前版本此步不需用户监督**（自动执行）。
- **产出形态**：带**主题标签**的 CQ 簇（论文 Appendix Listing 1 给出 Music Meta 真实产物：Music Artists / Musical Pieces and Composers / Music Ensembles / Musical Performances and Recordings …）。

#### 模块 4 · Ontology testing support（本体测试）

- **本体测试三方法论**（论文引 Blomqvist 2012）：**CQ verification**（验证需求被正确实现）、**inference verification**（验证推理）、**error provocation**（找本体应失败之处）。传统做法是把 CQ **形式化为 SPARQL**。
- **OntoChat 的「无 SPARQL」路径（两步）**：
  1. **Ontology verbalisation（本体口语化）**：把 OWL 本体转成**纯文本**——按描述性方式记录 classes、properties、named entities 及其关系。方法遵循**简单算法过程**，且**假设本体注释良好（well commented）**才能产出有表现力的口语化。
  2. **Prompt-driven CQ unit testing**：用口语化文本，让 LLM **对每条 CQ 判定覆盖与否（Yes/No）**。**为保证独立性、防 prompt 泄漏，每条 CQ 单独调用一次**。
- **论文测试 prompt（两版）**：
  - `cqt_prompt_a`：`…infer if the ontology described before can address the following competency question: "{cq}" Valid answers are: Yes, No.`
  - `cqt_prompt_b`：`…Only reply: 'Yes', 'No' and provide an explanation after a comma.`（要求**附带解释**）
- **评估口径**：把 28 条人工 CQ（正样本，应被支持）**扩增等量 28 条负 CQ**（本体尚不支持的伪需求）→ 二分类任务。

### 1.4 评估体系与结果

| 组件 | 评估者 | 方法 | 关键结果 |
| --- | --- | --- | --- |
| 用户故事共创 | **N=6** 音乐领域专家（Polifonia 项目） | 5 分 Likert 问卷（10 题） | 生成故事抓住意图与需求、**始终提供相关信息**；>80% 喜用、认为结构良好易理解；**仅 50% 满意示例数据**；4/6 认为能加速（2 中立）；5/6 愿以之替代人工 |
| CQ 抽取 | **N=8** 本体工程师 | 问卷（8 题） | CQ 全面、反映本体范围、易理解；**2/8 报抽取到故事范围外实体**；**仅 50% 认为能减少作者偏差**；6/8 满意、**8/8 一致认可有前景** |
| CQ 聚类 | 同上 N=8 | 问卷 | **62.5%** 认为交互直观；**87.5%** 认为簇是有意义的归类；省时但**不能单独支撑完整分析** |
| 本体测试 | 实验（56 条 CQ） | 二分类 | **准确率 87.5%（P=88%、R=85.7%）**；混淆矩阵 **25 TP / 24 TN / 3 FP / 4 FN**；常附解释与示例 |

- **案例基准**：复刻 **Music Meta Ontology**（Polifonia 项目）的工程过程。选它三理由：OE 投入大且曾是歧义来源；有高质量金标材料（用户故事/CQ/文档/查询）；作者能触达领域专家池。
- **完整数据集**：`data/music_meta_cqs.txt`（**28 条正 CQ**）+ `data/music_meta_cqs_neg.txt`（**28 条负 CQ**）——**开源可复现的二分类评估集**。

### 1.5 局限（作者自述）

- LLM 在专门领域知识**有限或过时**；
- **persona 创建存在偏差**；
- 尚未提供**实施成本与工期**的洞察；
- 需量化**用户监督与参与度**（达成满意产出的交互次数、反馈具体度 vs 全人工）；
- 未来工作：增强**用户故事中的示例数据生成**、**CQ 创建中的命名实体范围界定**、**扩展分析支持**。

### 2.3 模块逐文件实现要点

#### （a）`functions.py` — 用户故事共创引擎

- **系统提示（instructions）**：一份「本体工程师访谈领域专家」的角色设定 + 分节脚本（Persona → Goal → Scenario → Create User Story），规定：
  - **一次只问一个问题**，每问必附「示例答案 + 应使用的 prompt 模板名」（如 `Use template **[Create Persona]** to answer`）；
  - 当前引出**未被确认满意前，不得进入下一问**（用户越级回答会被拒回）；
  - 用户可**回退到任意已完成步骤**；
  - 回答不对题时**温和提醒并引导**；
  - 精修请求**只给一条、一句话、聚焦当前答案**；
  - **拒绝回答与任务无关的提问**。
- **一轮对话 = 一次 `chat_completion`**：`instructions + build_messages(history) + 本轮用户输入`（**全量历史**随每轮重发）。
- **10 条「参与式提示」预置模板**（`current_preidentified`）：Domain / Persona / User Goal / Actions / Keywords / Current Methods / Challenges / New Methods / Outcomes，占位符 `**[必填]**`、`*[可选]*`；前端 `gr.Dataset` 以按钮形式供用户点击填入输入框。
- **会话状态**：`gradio.Chatbot(type="messages")` 持有 `history`（`[{role, content}]`），`build_messages` 直转 OpenAI messages —— **无服务端持久化**。

#### （b）`analysis.py` — CQ 分析（**双路线**）

- **`preprocess_competency_questions`**：按 `\n` 切分 → 折叠多空行、去 tab、规整分号。
- **路线 1 层次聚类（无 LLM）**：`SentenceTransformer("all-MiniLM-L6-v2")` 编码 → **L2 归一化** → `sklearn.cluster.AgglomerativeClustering(n_clusters?, metric="euclidean", distance_threshold?)` → 用 `children_/distances_/counts` 手工构造 linkage matrix → `scipy.cluster.hierarchy.dendrogram` 画树状图（转 PIL 图返回）。
- **路线 2 LLM 聚类（论文主张）**：
  - 可选先做 **paraphrase detection**：`Perform paraphrase detection for the following competency questions: {cqs}. Return a Python list of duplicate competency questions.` → 得到重复项后从计数中减去；
  - 再 `Clustering the competency questions into {n} clusters based on their topics. Keep the granularity of the topic in each cluster at a similar level. Return in JSON format, such as: {'cluster 1 topic': [...]}`；
  - 用 `ast.literal_eval` 解析回复（`response_parser`），失败则回空。
- **注**：论文正文只说「纯 LLM」，而仓库**同时保留了句向量路线**；`app.py` 的旧描述称「从经验看 **LLM 聚类表现最好**」。

#### （c）`verbaliser.py` — 本体口语化（模块 4 的前半）

`verbalise_ontology(path, onto_about, onto_desc)`：

1. `rdflib.Graph().parse(path)`；
2. 建 `label_dict`（`rdfs:label`）与 `comment_dict`（`rdfs:comment`）；**无 label 时取 URI 末段**；
3. **类**：取所有 `rdf:type owl:Class` → 每类输出 `「标签 (subconcept of 父类…): 注释」`（父类来自 `rdfs:subClassOf`）；
4. **命名实体**：`NE_QUERY`（SPARQL 取 `owl:NamedIndividual` 及其类型）→ 每实体输出 `「X is an instance of class Y.」`；
5. **关系**：取所有 `owl:ObjectProperty` → 每属性输出 `「标签 (subproperty of …): 注释 The domain of this relation can be: … The range … can be: …」`（domain/range 来自 `rdfs:domain`/`rdfs:range`）；
6. `collate_verbalisations` 拼成三段式纯文本：`Ontology description: …` + `The main classes…` + `The main named entities (individuals)…` + `The main relations…`。
   - **注意**：`rdfs:subClassOf`/`subPropertyOf` 有「子项未在类/属性集合中出现就 `raise NotImplementedError`」的**强约束**（要求本体良好注释且层次闭合）。

#### （d）`ontolib.py` — CQ 抽取与测试（模块 2/4 的内核）

- **`ChatInterface`**：封装 `OpenAI` 客户端，默认 `config.DEFAULT_MODEL / SEED / TEMPERATURE`，`chat_completion(messages, **kwargs)` 支持逐调用覆盖 model/temperature。
- **`extract_competency_questions`**：`onto_verbalisation + cqe_prompt_a` → 系统提示「You are an ontology expert.」→ **`model="gpt-3.5-turbo-16k"`** 产出 CQ 列表。
  - `cqe_prompt_a` = `You are asked to provide a comprehensive list of competency questions describing all the possible requirements that can be addressed by the ontology described before.`（**从本体反向生成 CQ** 的 prompt）
- **`test_competency_questions`**：**逐条 CQ 循环**，每条拼接 `cqt_prompt_a/b` 单独调用（**防泄漏 / 保独立性**），正则 `^(Yes|No)(.*)` 提取判定 + 解释，聚成 `{cq: (Yes/No, explanation)}`。
- **`split_cq_test_data`**：Yes→1 / No→0，非 Yes/No 抛错——**直接支撑二分类评估**。

#### （e）`cq_generator_ontochat_app.py` — 批处理 API（FastAPI）

- 定位：把 **CSV（含 Scenario / Competency Question 列）** 批量转 CQ。按 **unique Scenario（或 dataset 列）分组**，每组只发**一次**请求：
  ```
  Here is a user scenario for ontology engineering:
  """{scenario}"""
  Please generate up to five competency questions for this scenario
  and return them on one single line, separated by a semicolon (;).
  ```
- 生成路径：优先 `gradio_client.Client("b289zhan/OntoChat").predict(..., api_name="/cq_generator")`；失败则 **OpenAI `gpt-4o-mini` 兜底**（temperature=0.4, max_tokens=120）。
- 产出：逐行 `{gold standard, generated}` + 聚合结果，落 `results/*.json|csv`。
- **本文件价值**：证明「**按场景聚合 → 批量产 CQ → 与金标对照**」的**评测流水线形态**，对 REQ-255 的 CQ 验收有直接参照意义。

#### （f）`chatbot.py` / `config.py` / `queries.py`

- `chatbot.py`：`chat_completion` 捕获 `APITimeoutError / APIConnectionError / AuthenticationError / RateLimitError` 并**转为人类可读字符串**返回（不抛出）；`build_messages(history)` 直转。
- `config.py`：**`DEFAULT_MODEL="gpt-4o"`、`DEFAULT_TEMPERATURE=0`、`DEFAULT_SEED=1234`**（确定性优先）。
- `queries.py`：`NE_QUERY` 取 `owl:NamedIndividual` 及其非 `owl:NamedIndividual` 的类型。

## 三、后续演进论文（自研设计的重要补充）

### 3.1 参与式提示（arXiv 2408.15256，AAAI-SS 2024）

- **动机**：初版 OntoChat 期望用户**自己写 prompt** 来驱动生成，**初步评估发现用户做不到**（不会有效提示）。
- **方法（participatory prompting）**：引入「**研究者中介**」——用户表达诉求 → 研究者按**预定义提示策略**转写为 prompt → 模型生成 → 用户反馈再来一轮。**三阶段**：Step 1 故事描述 → Step 2 Prompt 开发 → Step 3 故事评估。
- **产出**：面向用户故事 **5 段**（Persona / Goal / Scenario / Example Data / Data Resource）的**预定义 prompt 模板**（对应 P3，本档 §2.4）。
- **关键设计洞见（对我们极重要）**：
  - 用户问句 → prompt 的**增补规律**：常需**追加一句「解释为什么」/「对齐 persona 的兴趣与技能」**才能得到满意结果（例：`Could you improve the goal by providing a more detailed description, including keywords…？` + `Explain why these goals are important and align them with the persona's interests and skills.`）。
  - **占位符语法**：`**[必填项]**`、`*[可选项，如 简洁/生动、要点/段落/层级]*`。
  - 未来工作提出：**由 LLM 根据当前用户故事主动建议「下一步该改什么」的定向 prompt**（用户可直接采纳或个性化后再提交）——**这正是我们要做的「引导卡自动推荐」的论文级依据**。
- **诚实记录**：即便用参与式提示，**产出有效 prompt 仍耗时且需多轮迭代**；且「每个新问句都会被正式转为 prompt」使参与者变得谨慎，可能**漏掉一些想法**。→ 提示我们**不要让模板机制成为用户的认知负担**。

### 3.2 ACM 2026 助手论文（DOI 10.1145/3810943）

- 标题：*OntoChat Assistant for User Story Generation in Ontology Engineering*（ACM TIST，2026-04）。
- 定位：**首个经设计验证的「提示引导框架」**；形成性研究 **N=10** + 知识工程师评估 **N=24**（一手仅得 README 引文，正文未读）。
- 与本项目关联：REQ-82（多轮引导会话）、REQ-91（任务卡）。

### 3.3 Bench4KE 评测（README 声明）

- README 明确 CQ 生成用 **Bench4KE**（`fossr-project/ontogenia-cini`）对照金标，做**词法 + 语义**指标。→ 我们做 CQ 质量评测时可参考其指标口径（词法重叠 + 语义相似度），避免只看「像不像」。

## 五、自研 OntoChat 实现蓝图（理论依据落地）

> 原则：**不搬 Python 栈**，只搬**算法、prompt、交互范式、评估口径**；全部落在现有 Go 服务 + 前端形态内（复用 `llmcreate` / 平台 LLM 代理 `/api/ontology-llm/generate` 异步 job）。

### 5.1 目标状态机（扩展 REQ-103 模式 A）

```
story ──→ cq ──→ analyze ──→ domain ──→ draft ──→ refine ──→ test ──→ done
 ↑用户故事共创  ↑CQ抽取   ↑去重聚类    ↑补全      ↑生成草稿   ↑修正     ↑覆盖测试   ↑入库
 （新）        （增强）   （新）        （现有）   （现有）     （现有）   （新/REQ-255）
```

- `story` / `analyze` / `test` 为新增阶段；`cq` 增强为「**可从 story 自动抽 CQ**」；其余沿用。
- 阶段间**制品流转**：`story → (抽取) → cq → (分析) → clusters → (生成) → draft → (测试) → test report`。

### 5.2 数据模型变更（最小侵入）

`ontochat_session` 增列 / 复用：

- `stage` 枚举扩展（`story|cq|analyze|domain|draft|refine|test|done`）；
- `context_json` 增字段：`story{persona,goal,scenario,exampleData,resources}`、`draft_story`（one-shot 汇总稿）、`cq_clusters[]`、`test_report{passed,failed,details[]}`；
- 可选新表 `ontochat_cq`（`session_id, cq, cluster_label, test_verdict, explanation`）——若要与 REQ-248/255 打通，优先进 `spec.cq` 而非新表。

### 5.3 模块设计

| 模块 | 输入 | 处理 | 输出 | 复用点 |
| --- | --- | --- | --- | --- |
| **A 需求引出（story）** | 用户逐轮回答 | 9 段访谈脚本（Persona/Goal[Actions/Keywords]/Scenario[Before/Challenges/During/After]）逐轮一问 + 「未确认不进下一题」硬规则 + one-shot 汇总 | 结构化用户故事 | P1/P2/P3/P4 |
| **B CQ 抽取（cq↑）** | 用户故事 或 已有本体口语化 | few-shot 抽 CQ → **拆非原子** → **抽象命名实体** | CQ 列表 | P5/P8 |
| **C CQ 分析（analyze）** | CQ 列表 | paraphrase 去重 → 主题聚类（可选簇数）→ 标签 | `cq_clusters` | P6（+可选并行句向量） |
| **D 本体测试（test）** | 本体（口语化）+ CQ | 逐 CQ 独立 Yes/No + 解释；与 REQ-255 SPARQL 结果**互校** | 覆盖报告 | P7/P8/P9 |

- **A 的交互不变式（论文硬规则，务必照搬）**：① 一次只问一个；② 未确认当前不满不进下一题；③ 可回退；④ 偏题温和纠回；⑤ 精修只给一句；⑥ 拒答无关问题。
- **D 的独立性不变式**：**每条 CQ 单独一次调用**（防泄漏）；同时保留「批量」选项用于吞吐。

### 5.4 引导卡机制（参与式提示落地）

- 把 P3（10 模板）+ P4（25 追问）做成**可点选引导卡**（复用 REQ-246 素材面板与 REQ-247 的质量透明形态）；
- 占位符语法统一为 `**必填**` / `*可选*`，面板内高亮；
- **进阶（论文未来工作）**：由 LLM 依当前用户故事内容**主动推荐「下一步该改哪里」的模板**——这是「引导执行（D-O7）」的论文级落点。

### 5.5 与现有资产衔接

- CQ 抽取/分析产出 → 写入 **`spec.cq`（REQ-248）**，成为一等公民数据；
- 覆盖测试 → 与 **REQ-255** 的 CQ→SPARQL 验收**并轨**：口语化判定作**快筛**，SPARQL 作**精判**，通过率统一入质量卡；
- 用户故事 → 可选**归档为「需求制品」**，供学习中心/任务卡援引（呼应 REQ-91）。

| --- | --- | --- | --- |

## 六、不采纳项与诚实边界

### 6.1 明确不引入

| 项 | 理由 |
| --- | --- |
| Python/Gradio/sentence-transformers 栈 | 本项目 Go 栈；**D-O15**（semantica 退役同理：不引入重运行时依赖） |
| `rdflib` 口语化实现 | 我们有 spec/TTL/OWL 多形态与 sidecar（python3+rdflib，已存在但用于导入导出）；口语化可在此基础上做，**不新增服务** |
| Gradio 内存态会话 | 我们已有 SQLite 持久化（**优于原实现**），无需回退 |
| HF Space 的 `/cq_generator` 外部依赖 | 生产不可依赖第三方在线服务 |

### 6.2 诚实边界（逐条）

1. **论文模块 ≠ 线上能力**：OntoChat 线上只活跃「用户故事」模块，CQ/聚类/测试是**论文 + 遗留源码**级——自研须照**论文算法**实现，勿假设其线上可复刻。
2. **样本量小**：N=23 调查 / N=6 / N=8 评估 / 56 条测试 CQ——**结论为「初步（preliminary）」**，作者自述为初步评估；数字（87.5% 等）**不宜当作强基准**引用，只作**方法示范**。
3. **测试准确率的口径**：87.5% 是 **56 条 CQ 的二分类**结果（且 28 条负 CQ 是**人工构造**），不代表真实开放域表现；3 FP / 4 FN 中有「potentially plausible」误判（如「Does a music algorithm favor a specific genre?」被判 Yes 但实际不支持）——说明**口语化判定对「可推断但不显式」的需求有系统性乐观偏误**。
4. **口语化依赖注释质量**：论文自述「假设本体注释良好」；`verbaliser.py` 对未闭合的 subclass/subproperty 会直接 `NotImplementedError`——**本体注释差则口语化不可用**。
5. **聚类评价不高**：仅 62.5% 认为交互直观、论文承认**不能单独支撑完整分析**；纯 LLM 聚类**无确定性保证**。
6. **CQ 抽取的偏差问题未解**：2/8 报范围外实体、仅 50% 认为能减少作者偏差——**幻觉/范围漂移仍是已知未解**。
7. **`gpt-4o + temperature=0 + seed=1234`**：仓库追求确定性，但**跨版本/跨模型仍不可复现**；自研需自行记录模型版本与参数。
8. **参与式提示的成本**：即便有模板，**有效 prompt 仍费时且多轮**；模板机制本身可能**抑制用户自由表达**（论文 Discussion 明言）。

### 6.3 待验证项（后续可实证）

- 我们 spec_json 形态下的**口语化适配**：把 spec（概念/关系/实例）渲染成论文式三段文本的**最优粒度**与 token 预算；
- 口语化快筛 vs SPARQL 精判的**一致率**（用 P9 的 56 条 CQ 做小规模对照）；
- **拆非原子 / 抽象命名实体**两个算子在中文语料下的有效性；
- LLM 聚类在**中文 CQ**上的标签质量（论文全英文）。
