## 一、项目全貌（v0.2.1 现状）

OpenBKN 自我定位是**面向企业 AI Agent 的开源本体平台**（Open-Source Ontology Platform），Palantir Foundry Ontology 的开源对标物。4 仓 composition（star 为 v1 调研时快照）：

| 仓库 | 语言 | Star | 职责 |
|---|---|---|---|
| [bkn-foundry](https://github.com/openbkn-ai/bkn-foundry) | Go 为主 | 521 | 后端基座：本体引擎 BKN、上下文装载 Context Loader、数据虚拟化 VEGA、执行工厂 Execution Factory、治理 BKN Safe、证据链 BKN Trace |
| [bkn-studio](https://github.com/openbkn-ai/bkn-studio) | TypeScript / React | 204 | Web 控制台，独立于 Foundry（Foundry 严禁含 UI） |
| [bkn-sdk](https://github.com/openbkn-ai/bkn-sdk) | TypeScript + Python | 16 | 统一 SDK + `openbkn` CLI + 3 个 Agent Skill 包（openbkn / create-bkn / create-skill） |
| [bkn-samples](https://github.com/openbkn-ai/bkn-samples) | — | 14 | 可导入的知识网络样例（world-cup / supply_ontology / order-basics / exchange-recovery） |

**背景（v1 考证）**：2026-05 前后从 `kweaver-ai/kweaver-core` fork 并重品牌化，遗留中文硬编码 i18n 基线 2605 条等包袱；Agent 与人类混合提交已是其默认工作方式（v1 时 issue/PR 编号已到 #1722）。

**v0.2.1 服务拆分**（较 v1 调研时的单块描述已演进）：

```
bkn-foundry/
├── adp/
│   ├── bkn/
│   │   ├── bkn-backend/        # 构建+建模服务（端口13014）：CRUD/校验/导入导出/概念索引/Cypher编译器
│   │   └── ontology-query/     # 运行查询服务（端口13018）：实例查询/子图/行动执行/指标
│   ├── context-loader/         # Agent 检索中间层：MCP 工具面 + 检索/排序（agent-retrieval，ranker 在此）
│   └── execution-factory/      # 工具执行面：toolbox/tool/MCP/sandbox 函数
├── bkn-safe/                   # 访问控制（行过滤策略、权限）
├── bkn-trace/                  # 证据链/Agent 可观测（conversation/interaction/operation + spans）
├── vega/                       # 数据虚拟化引擎（catalog/resource/dataset/索引构建）
├── comm-go/                    # 公共库

```

依赖栈：MariaDB 11.4+/达梦 DM8（元数据）、OpenSearch 2.x（倒排+KNN 向量）、VEGA（数据虚拟化，下推 MySQL/PG/HTTP 等连接器）、model-factory（embedding 默认 768 维/rerank/LLM）。纯后端无 Web UI，唯一入口是 CLI `openbkn` 与 REST/MCP。

## 二、核心设计理念

1. **本体是语义层，不是数据仓库**。对象类型只定义 schema（键、属性、数据源绑定），实例数据留在业务源系统，查询时经 Vega 虚拟化下推访问。平台不搬数据、不建图库——与 67 号 Helix Foundry「数据说话自动推断」解法相反，但**共识相同：本体放在应用层工程产物里，不让数据库承载语义**（与 62 号 K5、我们 D-O1 三方互证）。
2. **"对象-关系-行动-风险"四合一建模**（Object / Relation / Action / Risk）+ ConceptGroup（检索作用域）+ Metric（声明式聚合）。比一般本体多两类一等公民：Action（可执行操作，带触发条件/工具/审批）和 Risk（风险类型，挂在对象/关系/行动上）。
3. **定义即代码（BKN Lang）**。全部本体以 `.bkn` 文件（YAML frontmatter + Markdown 正文表格）组织成定义树，与 SKILL.md 同目录，支持 tar 打包、CHECKSUM、diff、upsert 导入——本体可版本化、可评审、可离线编辑。
4. **Agent 是一等公民**。知识网络自带 SKILL.md；平台暴露完整 MCP 工具面；业务问答强制"受管会话"（conversation/interaction ID 门禁）+ bkn-trace 证据链。
5. **自建可执行栈 vs W3C 可推理栈的取舍**（v1 判断，v2 维持）：没有 OWL/RDFS/SHACL 和推理机，换来「一张 Markdown 表 = 一个可映射到真实 API 的对象视图」。企业场景要的是 **executable** 而非 **reasonable**。这也是 REQ-91 建模方法论卡片与 T2-3「要不要用 OWL」的现成对比案例。

## 三、本体构建链路（如何构建）

### 3.1 定义格式：BKN Lang v2.0.1

规范全文：`bkn-sdk/skills/create-bkn/references/SPECIFICATION.llm.md`（LLM 优化的规范，约 660 行）。要点：

- **根文件 `network.bkn`**：`type: knowledge_network`，YAML frontmatter（id/name/description/version）+ Markdown 正文。目录约定自动发现：`object_types/`、`relation_types/`、`action_types/`、`concept_groups/`、`data/`，目录名是硬约定。
- **5 种类型实体**，每种一个 `.bkn` 文件：
  - `object_type`：ID 规则 `{name|snake}_{ot}`；Data Properties（表格 DSL：名/显示名/类型/语义/备注/映射字段）+ **Keys 三类**（Primary=业务键、Display=唯一显示键、Incremental=DB 自增主键）+ **Logic Properties**（动态属性：`source: metric|tool`，带参数绑定和"分析维度"标记）+ Data Source（Vega resource 绑定，可留 `{{*_RES_ID}}` 占位符待 push 后绑定）。
  - `relation_type`：两种实现——`direct`（Mapping Rules：源对象键=目标对象键的 join 规则）与 `indirect`（Backing Resource + 双向 mapping，中间表物化视图型，push 时自动在 VEGA 建 `vega_bind`）。
  - `action_type`：ID 规则 `{verb}_{object}`；Bound Object + Trigger Condition（entries_conditions，声明式状态机守卫：`object_type_id/field/operation/value`）+ Pre-conditions + **Impact Contracts**（事前声明"这次行动会新增/变更什么对象"，v1 考证）+ Tool Configuration（`tool:|mcp:`，平台工具箱工具名）+ Parameter Binding（property/input/const 三种来源）+ Schedule（FIX_RATE/CRON）+ `risk_level/requires_approval`。
  - `concept_group`：对象类型分组（branch 维度），作用域限定检索。
  - `risk_type`：风险类型定义与绑定（四段结构见 5.1）。
  - `metric`（v1 考证，样例目录还有 `metrics/*.bkn`）：声明式聚合——condition/aggregation/group_by/order_by/having 全 YAML 表达。
- **同目录 SKILL.md**（agentskills.io 标准）：知识网络的 Agent 技能入口。
- **显式设计**：无 patch 模型，导入=按 ID upsert；删除走 delete API；大小写敏感；ID 稳定不可改（改 ID=新实体+旧实体删除，关系重定向）。

实例（`examples/k8s-network/object_types/pod.bkn` 节选）：

```markdown
---
id: pod_ot
name: Pod
type: object_type
description: 集群内可调度与可观测的容器负载实例
primary_key: uid
display_key: name
incremental_key: row_id
data_source:
  type: vega
  resource: "{{POD_RES_ID}}"
  dataset: "{{POD_SET_ID}}"
---

# Pod

## Data Properties

| Name | Display Name | Type | Semantic | Notes |
|------|--------------|------|----------|-------|
| uid | 对象ID | STRING |  | Kubernetes UID |
| name | 名称 | STRING | title | Pod 名称 |

## Logic Properties

| Name | Display Name | Type | Source | Params | Analytical |
|------|--------------|------|--------|--------|------------|
| restarting | 是否重启中 | BOOLEAN | metric | metric_id=`{{metrics/restarting.yaml}}` | Y |
```

**BKN Lang 为什么聪明（v1 判断，v2 复核成立）**：人机双写、LLM 双读（业务专家直接改 Markdown，LLM 生成 Markdown 成功率远高于嵌套 JSON Schema）；天然 Git 友好（行级 diff，对比图序列化是数量级优势）；"定义以全文形式存放在数据库字段"规避迁移地狱；弱 Schema 配强工具链（parser/validator/serialize/checksum/differ 五件套把格式松散的代价转移到 SDK 层）。**代价**：Markdown 表格对列数变化、单元格内 `|`、多表同义脆弱，类型演进比 Protobuf/Avro 痛苦，CHECKSUM+validator 是补丁不是根治（对应 C 类第 17 条）。

### 3.2 三条构建路径

官方手册（`help/en/manual/bkn.md`）+ samples 实证：

| 路径 | 流程 | 适用 |
|------|------|------|
| **A. Agent 生成** | 自然语言 → `create-bkn` skill（规范+模板+示例驱动 LLM 产出定义树）→ `openbkn bkn validate` → `openbkn bkn push` | 从零建模、快速原型。这是官方推荐主路径（prompt-driven，Claude Code/Codex 直接跑） |
| **B. 数据源生成** | Vega Catalog 表发现 → `openbkn create-from-catalog`（表/字段→对象类型骨架、外键→关系骨架）→ 人工语义增强 | 从已有库表起步。world-cup 示例即"由生成脚本按 CSV 外键推导 27 对象类型+29 关系骨架" |
| **C. 人工/CLI CRUD** | `openbkn object-type create/update/...`、`relation-type ...`、`action-type ...` 逐实体维护 | 增量调整、联调 |

### 3.3 校验与推送：SDK 解析 → 平台导入的完整链

**本地校验**（SDK 侧，纯静态）：`openbkn bkn validate <dir>` 由 `bkn-specification/bkn` Go 包执行——`loader.go`（目录发现）→ `parser.go`（frontmatter+表格 DSL 解析为 models.go 结构）→ `validator.go`（ID 规则/引用完整性/键配置/参数绑定校验）。

**推送导入**（服务端 `bkn-backend/server/driveradapters/bkn_handler.go`）：

```
openbkn bkn push
  → SDK 侧 tar 打包（network.bkn + 各类型目录 + SKILL.md）
  → UploadBKN (multipart)
  → bknsdk.LoadNetworkFromTar + Checksum 校验
  → bkn_convert.go: ToADP* BKN定义树 → 平台内部模型
     （含 indirect 关系 → vega_bind 物化视图准备、
      concept_group → 反向填充 object_type.ConceptGroups）
  → 分类型 Validate：KN / Object / Relation / Action / ConceptGroup / Risk（strict 可选）
  → detach 策略：处理"绑定但不存在"的外部依赖
  → importService.CreateKN(mode: overwrite|skip + strict)
  → Capability 绑定导入：声明式引用 SKILL/tool/MCP（缺失不阻断，导入报告列出 skipped）
  → 操作审计（import history）
```

**包化与版本化**（v1 起持续强化）：`pack_tar.go`/`tar_loader.go`（定义树 ⇄ tar，自动生成 SKILL.md、CHECKSUM 与目录结构说明）、`checksum.go`（内容指纹，等价容器镜像 digest）、`differ.go`（`DiffNetworksFromTar` → Creates/Updates/Deletes 三分类+引用影响统计，导入前 diff 审查）；pull/export 可从平台导回定义树，形成"本地编辑 → push → 平台"的 git-like 双向流（samples 的 `dataset.lock`、`releases/` 即此模式产物）。**v1 判断保留：这是拿容器镜像/包管理的心智模型治理知识资产。本体从不是一次性建模而是持续演化；没有 diff 就无法评审、灰度、回滚。大多数本体项目做到"能建模"就停了，很少把"本体变更管理"当一等工程问题。**

**导入后自动生效**：`worker/concept_syncer.go` 后台 worker 周期同步，为每类概念构建**全文向量索引**——向量化文本 = `OTName + Tags + Comment + BKNRawContent(原始 .bkn 全文)`，embedding（默认 768 维）→ 写入平台自建概念 dataset（`ontology_init.go` 启动时向 VEGA 注册 `BKN_CATALOG/BKN_DATASET`，底层数据落 OpenSearch），docid=`(KNID, module_type, 实体ID, branch)`。**这是"定义存储为全文、按需动态加载"语义搜索的实现底座：本体定义本身即被向量化的语料**。另有 `proxy_sync_worker`（每网络 proxy 账号同步）与 `schedule_worker`（行动调度）。

## 四、本体运行链路（如何运行）

### 4.1 存储分层（运行时三处数据）

| 数据 | 存储 | 说明 |
|------|------|------|
| 本体元数据/定义 | MariaDB/DM8 | 平台内部模型（bkn_convert 转换后的 ADP 结构） |
| 概念索引（语义） | VEGA 概念 dataset → OpenSearch（knn 向量） | 原文全文 embedding，支撑语义搜索与概念召回 |
| **实例数据** | 留在源系统 | Vega 虚拟化 + proxy 账号直连/下推，本体查询时翻译执行 |

### 4.2 查询链路（四类查询，全部无实例搬运）

1. **语义搜索**（`context-loader/agent-retrieval` → `bkn-backend`）：查询词 embedding → 概念 dataset KNN → 召回对象/关系/行动/风险/概念组类型定义 → ranker 精排（六维静态信号 + 标签/组/关系加权 + score-based 截断）。这是 Agent 找"该用哪个本体概念"的入口。**v1 判断保留：「先 schema 后 instance」两段式（search_schema→kn_search）本质是把 Text-to-SQL 里"先给表结构再写查询"的经验，提升成受本体约束的正式协议。**
2. **结构化实例查询**（`ontology-query/server/logics/object_type_service.go`）：按对象类型查询实例行，条件 DSL（conditions/logic/search_after）→ property_access_plan/row_filter_plan（行级权限计划）→ 转换为 OpenSearch/VEGA DSL；knn 子条件查询词向量化带**单请求 memoize**（同词同模型只算一次向量）；游标分页（query_cursor.go）。
3. **Cypher 图查询**（核心亮点，`bkn-backend/server/logics/cypher/`）：完整 Cypher 子集实现——`parser.go`/`ast.go`/`parse.go` 解析，`binder.go` 把标签绑定到对象类型、关系绑定到 join 规则，`plan.go` 出执行计划，`sqlgen.go` 生成 **MySQL 方言 SQL 提交 vega-backend 翻译下推**（Postgres 方言已预留），`row_filter.go`/`visibility.go` 做权限注入。设计原则写在 `kncypher/index.go` 注释："**compiler lives where the model lives**"——编译器在 schema 所在地（bkn-backend），context-loader 只转发请求、原样带回编译器的拒绝信息与构造名。多跳图查询在源数据上直接执行，实例永不搬家。
4. **子图遍历**（`ontology-query driveradapters/knowledge_network_handler.go` GetObjectsSubgraph）：起点+方向+路径长度扩展子图；indirect 关系走 vega_bind 物化视图。

另有 **Logic Property 解析**（`knlogicpropertyresolver`）：metric/tool 型动态属性在查询时按对象实例参数调用指标引擎或工具计算；**knrunsql** 提供经权限的 SQL 直查出口。

### 4.3 行动执行链（Action 运行时）

```
ActionType（触发条件+预条件+工具+参数绑定+schedule+审批）
  → ontology-query action_scheduler（条件触发/定时）
  → execution-factory（toolbox: function/HTTP/MCP 工具；sandbox 函数）
  → action_logs（执行日志）→ bkn-trace（operation 级证据）
```

带 `risk_level` / `requires_approval` 的行动在执行前走审批（BKN Safe）。

### 4.4 Agent 消费面（运行侧最有特色的部分）

**MCP 工具面**（context-loader `agent-retrieval/server/logics/`）：

| 工具/能力 | 作用 |
|-----------|------|
| `bkn_start_interaction` / `bkn_finish_interaction` | **受管会话门禁**：每轮问答必先 start（携带 question/agent_name/conversation_mode），业务工具必须逐字携带返回的 conversation_id/interaction_id，结束后 finish 提交——否则越权/无审计 |
| `kn_search`（semantic） | 概念召回+精排 |
| `run_cypher` | 只读 Cypher 图查询（bkn-backend 编译执行） |
| subgraph / logic-property / run_sql / metrics / resources | 各查询面 |
| `kn_skills` / `kn_tools` | 调用平台上注册的 SKILL.md 技能包与工具箱工具 |
| `permissionguide` | 面向 Agent 的权限自解释（告诉 agent 能查什么、怎么补救） |

**SKILL.md 双层结构**（samples 实证）：
- 网络级：`kn/SKILL.md` 与 network.bkn 同目录，作为本体的"agent 使用说明书"（world-cup 示例：目录清单+校验命令+对象/关系 ID 表）。
- 技能包级：`skills/<name>/SKILL.md` 把**业务分析规则编译成 agent 可执行剧本**（supply chain 示例的"总可售量"技能：参数解析顺序→MCP 调用→逐层 BOM 扣减规则→确定性覆盖判定→报告字段），并明确禁止 agent 读 CSV/数据库复制计算。
- v1 考证的 exchange-recovery SKILL.md 补充：工作流状态机 `Accident Request → Think → Risk Evaluate → Plan → Act → Report`、每阶段决策规则、风险等级矩阵（"不确认则终止"）、以及**反 LLM 惯性的负向约束**（"每次恢复请求都是独立的恢复操作，不应查询或依赖历史恢复记录"）。价值在：**本体不再是给数据库用的 schema，而是给 LLM 用的 operating procedure**——绝大多数本体项目缺的正是这一跳。

**BKN Trace 证据链**（v1 精读细节保留，契约仍有效）：三级实体 **Conversation → Interaction → Operation(attempt)**，重试申请新 attempt；`PayloadEnvelope` 固定 1 MiB（阈值内 inline、超限 `omitted/payload_too_large`、序列化失败 `omitted/serialization_failed`——不因记录而放大存储）；**Receipt 收据机制**（看 `receipt_status` 而非返回值判终态）；CLI `openbkn context tool-call --receipt` 返回 `{value, bkn_receipt}`；**兜底铁律写死在契约**："Trace 终态写入失败不能覆盖已经产生的业务结果或异常"。第三方 Agent 的 trace 可拉 spans、用"符号规则 + LLM rubric"诊断、构建 eval-set（`openbkn trace ...`）。

### 4.5 治理面

BKN Safe：RBAC（org/user/role）+ 行过滤策略（row_filter，在查询计划层注入）+ proxy 账号隔离（每知识网络独立账号访问源数据）+ 审计。受管会话 + 证据链 + 权限自解释构成"Agent 可信访问"三件套。

## 五、工程治理与许可证（v1 精华，v2 复核仍有效）

### 5.1 Risk Type 一等公民（比多数同类项目更成熟的地方）

`risk_types/production_data_overwrite.bkn` 完整结构四段：**Control Scope**（适用边界）/ **Control Policy**（按条件分级，高风险"必须用户确认"）/ **Pre-checks**（声明式校验表：Object|Check|Condition|Message，如 `recovery_task/property:recovery_destination/== production/必须用户确认`）/ **Risk Mitigation + Rollback Plan + Audit Requirements**（缓解动作如"执行前自动创建快照"、回滚步骤、审计要求含"日志至少保留 180 天"）。把"风险"做成与对象/关系同级的建模原语，意味着**权限策略、人工审批、审计留痕可被统一推导**——给企业 Agent 系统做设计时的必选项。

### 5.2 AGENTS.md 分层规则系统与 Agent 硬规矩

根目录 `AGENTS.md` 是入口而非全集：Agent「进入任何子目录前，逐级读取从根到目标目录的每一个 AGENTS.md，深者优先」，规则外挂 `rules/{WORKFLOW,CONTRIBUTING,ARCHITECTURE,DEVELOPMENT,TESTING}.md` + `.github/CODEOWNERS`。Agent 硬规矩可执行化：先 diff 后外部写（呈现 diff 前不得 commit/push/建 PR）、review 反馈需重新授权、Issue 准入制（只领 `agent-ready` 标签，验收标准需人类 `ac-approved`）、风险操作熔断（部署/删数据/schema 迁移/生产配置一律改提交「做什么/影响半径/回滚方案」三段式确认打 `awaiting-confirmation`）、红线（不得 approve/merge PR、不得跳过 CI）、卡住就交还（`needs-human`）。标签体系 `agent-ready / ac-approved / awaiting-confirmation / owner-confirmed / by-agent / needs-human` 构成完整的人机权限分层流水线。

### 5.3 架构规则可执行化 + CI 非典型检查

`rules/ARCHITECTURE.md` 全部可用 CI 检验：Foundry 严禁含 UI、依赖单向（产品→Foundry 禁反向）、禁止页面级 BFF（新建后端前 4 问全"否"则不许）、**服务预算硬约束（后端微服务 < 5 个，CI 自动计数）**、可选组件必须可关（禁用后仍能启动优雅降级）、API 三级制（Public/Internal/Experimental，跨组件只依赖 Public）、兼容性定义到字段级（请求侧不得 optional→required；响应侧只增不删不改；行为语义不得同名异义）、**Skill 也算契约**（`name` 发布不改；`input_schema` 只增可选字段；破坏性变更走新 version+废弃窗口）。CI 亮点：**i18n 棘轮机制**（`ci-i18n-hardcoded.yml` 扫描硬编码中文，baseline 2605 条只降不升——"允许存量、绝不允许新增"是还技术债唯一现实做法）、`lint-no-ee-import`（阻断开源仓引入商业版代码）、迁移/分支名/提交信息全链路卡点、AI review 进流水线。

### 5.4 许可证（引用必读）

`LICENSE-OPENBKN.txt` = **modified Apache 2.0 + Additional Conditions**，只适用于源码头注释明确引用它的模块（BKN Safe、BKN Studio 等）；upstream kweaver-ai 组件纯 Apache 2.0（NOTICE 逐组件明细）；**bkn-sdk 纯 Apache 2.0**。实质限制：允许单客户实施/集成/部署与二次开发（不需要商业订阅）；**禁止（需书面授权）共享/多租户服务、把 Licensed Modules 做成托管平台、白标/OEM 竞品**；前端 Logo 与版权声明不得去除；贡献条款（提交的代码 OpenBKN 可任意商用再许可）；条款可调整不溯及既往。**结论：借鉴思想+重实现完全没问题；fork BKN Studio/BKN Safe 做产品对外服务不行。**

### 5.5 文档与交付一致性（v1 考证）

中英文档成对、VERSION/NOTICE/LICENSE 三件套（NOTICE 逐组件授权明细）、`preflight.sh` 三态退出码+`--list-fixes` 预览 → `deploy.sh` → `onboard.sh` 幂等可重入、OpenAPI 3.1 契约+redocly+版本化文档站、per-service CHANGELOG。另有 bkn-studio `AGENT_COMPOSITION_CHARTER.md`（智能体整合章程）：**页面不是复用单元，scene 才是**；契约先于实现；`module.manifest.ts` 机器可读能力清单（可暴露场景/输入摘要/权限依赖/后端依赖/是否支持嵌入，显式给人**和 Agent**读）；禁止深层 import 其他模块私有文件；**未来的消费方一半是 Agent，模块边界必须机器可读**。

### D. 明确不采纳（v1 结论 + v2 复核）

- **整体引入/独立栏集成**：平台级重叠（学习型 vs 企业型）+ OpenBKN License 限制 + KWeaver fork 包袱；**借鉴思想+重实现没问题，fork 其 Licensed Modules 做产品不行**。
- **放弃 spec_json/TTL 换 BKN Lang**：BKN Lang 服务"可执行"，本项目服务"可推理+教学"（D-O5 已定 W3C 栈）；Markdown 形态只作为 LLM 交互层与教学资产形态。
- **README 性能数字**（准确率 93%/Token 省 50%/TCO 降 70%）：无可复现基准，当营销口径，勿引用。
- **Markdown 表格承载强类型 Schema**：演进成本高，务必先 validator+migration 工具。
- v2 复核补充：纯后端无 UI（依赖 CLI+agent 生态，与我们前端优先的学习平台诉求相反）；面向 B 端复杂度极高（组织/账号/审批齐全）。

## 七、给"自己构建本体"的最小落地路径（v1 保留）

1. **先定义 DSL**：一个实体类型 = 一个 `.md` 文件，frontmatter 放 `id/name/tags`，正文 Data Properties（含 Mapped Field）+ Keys 两张表起步。**不要一开始上 Relation/Action/Risk 全套。**
2. **同步做 parser + validator + checksum + differ**（Go/Python 均可）。没做这步先别写编辑器，否则模型资产很快失去可控性。
3. **加 concept_groups 控制召回作用域**——控制 LLM 上下文成本最便宜的手段。
4. **选一个窄业务切片**（参考 exchange-recovery：8 对象+7 行动+2 风险跑完整闭环），坚持"从业务切片渐进"，别做大而全本体。
5. **产出 SKILL.md**：工作流、决策规则、负向约束、风险矩阵写进去。做完这步本体才真正"能跑"。
6. **最后才做 Trace/Safe**：Conversation→Interaction→Operation(attempt) 三级 + PayloadEnvelope + 追踪失败不覆盖业务结果；权限下沉到对象/行动粒度。
7. **配套治理**：AGENTS.md 分层、Issue 标签流水线、i18n 棘轮——零成本、早引入收益最大。
