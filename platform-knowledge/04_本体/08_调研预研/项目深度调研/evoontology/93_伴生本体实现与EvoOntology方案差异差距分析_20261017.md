# 伴生本体实现方案 × EvoOntology 方案：差异差距分析（2026-10-17，待拍板）

> 触发：开发者指令「分析当前项目伴生本体的实现方案和 EvoOntology 的方案的差异差距」。
> 分析基准：[31 号 伴生主事实源 v2.37](../../../02_智能体/01_运行时动态本体/31_动态薄本体_可行方案.md)（REQ-170/194/211/216/286/296/297~303 全交付态）+ [43 号 EvoOntology 深度研究](./43_深度研究_EvoOntology与BI-Agent_自进化本体.md) + [40 号开源项目分析](./40_EvoOntology_开源项目分析.md) + docs/03 §2.13/§2.15（REQ-170 P1~P2 交付、REQ-207/M43 交付）。代码事实沿 31/35 号代码级盘点，本轮未重新逐行核码。

## 一、结论

1. **两线不在同一问题域，"差距"要拆开看**：项目伴生本体 = 「对话记忆式薄本体」（从对话流**被动伴生沉淀**，治智能体跨会话隐式召回失败，MLSys 2026 报告轻量档落地）；EvoOntology = 「数据任务语义层 + 自进化」（从 workload **主动探针构建**，治 agent–data gap，本体层是"可训练的 agent 状态"）。路线不同，承重件天然不同。
2. **EvoOntology 的方案核心项目并非没有——REQ-207（M43 已交付）已把四个最承重的件吸收到"本体进化线"**：四步循环（诊断→归因→补丁→配对门控）、候选 vN-cK 状态机（不覆盖正式版）、Evidence 锚定、轮次预算 + ontoeval 双信号基准。差距的真实形态是：**这些件建在 spec 侧进化线，伴生线（REQ-170）一侧尚未接入**——而 43 号立项注记早已预留"门控机制与伴生本体的共享边界待两线一期落地后评估"，两线一期（M34/M43）均已落地，现在正是评估时机。
3. **伴生线五项真实可收敛差距**（按价值排序）：①自动入图无"效果对比"门控（只有置信阈值+批内分位，不看图变好还是变坏）；②证据锚定弱（溯源只到消息 ID，无原文 span / 探测实证，EvoOntology 消融中 Evidence 家族 −8.7、Mappings −13.4 是最大承重）；③消费方式是"每轮检索注入"而非"按需语义查询"（缺 browse/resolve 式工具，agent 主动查伴生图只能写 SPARQL）；④评估协议单薄（evaldata Recall@5 仅测召回环节，且因 embedding 连接未配置**基准数字至今未落档**）；⑤伴生图无版本化（confirm 即生效，靠 invalidAt 失效化留痕）。
4. **项目反向领先的维度也如实列出**：抽取管线工程化（分窗/游标/对齐/别名/归并/矛盾检测/事件可视）、实体消解工具链、治理操作（行级编辑/挖掘/清理/合并）、三级召回链、PROV-O+失效化历史保留、成长可视化、低侵入集成——这些 EvoOntology 论文均未覆盖或仅有雏形。
5. **不建议吸收**：主动探针构建（与被动伴生定位冲突）、无人值守自动循环（REQ-207 一期已定人触发，一致）、每模型独立演化（教学平台成本不划算）。

## 二、定位差异：两条路线的根上不同

| 维度 | 项目伴生本体（REQ-170 线） | EvoOntology |
|---|---|---|
| 理论源头 | MLSys 2026《Ontology-Guided Long-Term Agent Memory for Conversational RAG》轻量档 | 人大 ruc-datalab arXiv:2609.15779，方法论借鉴 SkillOpt |
| 核心问题 | 隐式召回失败：对话沉淀的知识后续会话召回不到（Recall@10 0.61→0.28 场景） | agent–data gap：Agent 对数据的结构与语义事先不知，靠探测盲猜 |
| 本体角色 | 智能体的概念级记忆（D-O19 第三来源） | 可训练的 agent 状态——"不训练模型，训练知识资产" |
| 服务对象 | agent 长期多会话对话记忆与检索增强 | 数据分析任务（text-to-SQL / BI / 多源研究） |
| 构建触发 | Run/Resume 收尾自动伴生（事件驱动+游标续抽），被动 | Builder agent 对 workload 主动发探测查询构建 v0；进化=阈值触发「检测+提醒」，**人触发** |
| 数据来源 | 对话消息流（只读 message 表） | 数据库/文件/文档（经领域工具访问） |
| 演化对象 | **抽取管线与治理工具**（170→194→211→216→286→296→303 一路是"人诊断→立项→修管线"） | **本体数据本身**（四步循环直接改本体状态并门控） |

> 关键洞察：项目伴生线的演进史本身就是一个人肉版"诊断→补丁"循环——但**循环进化的是管线代码，不是伴生图数据**；EvoOntology 把这个循环下沉到数据层并加门控。这不是项目"漏做了"，而是 D-O19 有意切分（伴生解决「新增实体入图」、REQ-207 解决「已有本体的受控进化」）；差距在于 REQ-207 的机制目前只覆盖 spec 本体，伴生子图作为"本体"的一种（REQ-216 资产化后）尚未挂进进化面。

## 三、六维对照

### 3.1 数据模型与证据锚定

| | 伴生线 | EvoOntology | 差距判定 |
|---|---|---|---|
| 模型 | 种子 5 骨架类（bot:Concept/Relation/Event/Source/Agent）**冻结 schema、仅实例填充** | Content（Terms/Mappings/Constraints/Evidence 四节点家族+5 语义边+结构引用边）/ Schema（对象模型）/ Tool 三层 | 结构性差异：伴生走"薄"是报告轻量档的刻意取舍，词表爆炸风险结构性免疫 |
| 证据 | bot:extractedFrom（消息 URI）+ confidence + prov:wasGeneratedBy；REQ-227 confirmCount 印证计数 | **Mappings 钉物理字段（−13.4）+ Evidence 探测实证（−8.7）为最大承重家族**；"概念必须钉到物理字段、必须有探测实证，不能只写自然语言描述" | **可收敛**：伴生证据粒度=「从哪条消息抽的」，缺「原文支撑片段」；候选/入图 schema 加 evidence span 成本低 |

### 3.2 获取路径（构建与抽取）

- 伴生线（被动沉淀）：逐窗 LLM 单遍抽取（≤16 条/8k/≤3 窗）→ 剪枝 → 候选落库 → 自动入图（阈值+分位）或人工确认；对齐清单注入（REQ-194①）、别名机制（REQ-286 B3）、关系挖掘补抽（A2）。**弱点**：单遍无精炼（35 号 Q3）、跨轮重复候选（Q2）、窗边界切断语义（Q1）——REQ-303 P2/P3 池已列未做。
- EvoOntology（主动探针）：builder agent 从 workload 推导候选概念→对原始源验证→发布 v0；**没有对话抽取管线**（它不处理对话流）。
- 判定：**结构性差异**。伴生线的抽取工程化程度在"对话流→本体"这个子问题上超过 EvoOntology 论文粒度； EvoOntology 的探针构建与伴生定位冲突，不吸收。

### 3.3 门控与质量保障（最大可收敛差距）

| | 伴生线 | EvoOntology | 差距判定 |
|---|---|---|---|
| 入图门控 | 置信阈值 + 批内分位 ≥0.5 自动入图；人工三桶确认流；矛盾语义二分类（REQ-194⑤） | **配对门控：Parent vs Candidate 同验证集同预算对比，改进 ≥τ 才保留；消融 w/o Gate −11.2 为最大承重墙**；"更选择性而非更迭代" | **可收敛（核心）**：伴生自动入图只看抽取置信，不看"图对下游检索是否变好"。REQ-207 配对门控已建成（真机 gate 98.95 案例），机制在平台内存在，未接到伴生线 |
| 留档 | reject 留候选三桶；编辑审计 onto_decision | **Reject 留档防重复无效更新**（rounds.jsonl+归因+problem map）；状态机 running/accepted/incomplete | 部分对应（REQ-207 候选态机已实现 proposed→accepted/rejected 留档），伴生侧 reject 无归因留档 |
| 版本化 | 伴生子图无版本（confirm 即生效；invalidAt 失效化保历史） | vN-cK→vN+1 不覆盖正式版；active.json 指针；可回滚 | **可收敛**：REQ-239 发布状态机已建（spec 侧），伴生子图快照机制已有（REQ-216 增量轮结果集快照），缺"候选版→正式版"语义接线 |

### 3.4 消费方式（注入 vs 按需查询）——范式上最尖锐的差异

- 伴生线：**检索注入**——每轮对话 recallCompanion 三级召回（向量主+词法兜底+2 跳邻域）→ ≤5 实体+定义+活跃边注入 System；外加 facade sparql_query `graph=companion` 供 agent 主动查（SPARQL 门槛高）。
- EvoOntology：**MCP 按需查询 + 极简 manifest**——manifest 是唯一进 prompt 的本体内容，其余 browse_semantics（语义检索 top-n）/resolve（取记录及链接对象）按需取；论文实测：**同一份语义画成静态图全量塞 prompt，Claude-Sonnet-5 上 −15.0pp**。
- 判定：伴生注入的是检索结果而非全量（≤5 实体），不等于论文批评的"死图全注入"，但 EvoOntology 数据支持的更优形态是"按需查询"；项目 agent 主动查伴生图缺**自然语言语义检索工具**。**可收敛**：把伴生图消费升级为 browse/resolve 式语义检索工具（自然语言→语义匹配→实体+邻域），与 92 号《OntoChat 能力赋予智能体可行方案》的工具赋予线天然衔接（其 S2 盘点已点名 CompanionOntologyID 绑定在位）。40 号 §3 亦已确认 EvoOntology 与本项目"本体暴露为 MCP 服务"方向同构、有可直接跑的开源实现。

### 3.5 进化闭环

- 伴生线：**无数据层进化**——schema 冻结、实例只增；治理=人工点状工具（挖掘关系/检查清理/人工合并/行级编辑）。图"长歪"（离散/重复/矛盾）靠人发现、人立项修工具。
- EvoOntology：**四步循环直改数据**——诊断（从轨迹提取反复失败签名）→ 归因（Content/Tool/Schema 三层之一，−6.3 承重）→ 局部补丁（每候选只动一层）→ 配对门控；Tool-only 单层增益最大（+13.2，增益占比 57%）。
- 判定：**可收敛（中期）**。伴生图规模尚小时人工治理够用；到"多 agent 长期运行、图质量衰减"阶段，REQ-207 的候选补丁机制可扩展到伴生子图（诊断信号=检索 miss 事件/矛盾候选率/孤立实体率——这些事件伴生线已在产出）。D-O19 边界允许"门控共享评估"，不需要推翻切分。

### 3.6 评估协议与成本意识

| | 伴生线 | EvoOntology | 差距判定 |
|---|---|---|---|
| 基准 | evaldata：种子会话 3 段+问题 15 条，Recall@5 三组对比（词法/向量/向量+2 跳）——**诚实边界：embedding 连接未配置，跑分器 Skip，数字至今未落档**（31 号 §11.7/§12.6/§14.7 三轮挂账） | 互逆双折 70/30（A→B+B→A 取均值）、留出折冻结隔离、无 GT 用 LLM Judge 匿名 A/B、完整消融、成本账（总 token −20%） | **可收敛（第一步成本最低）**：先配置 embedding 把 evaldata 跑出数字——这是证明"伴生本体带来检索收益"的唯一在库手段，也是后续一切门控阈值校准的前提（31 号 §11.5 原话：完整门控"待评估基准落地后才有校准依据"） |
| 收敛/停止意识 | 无（触发由对话驱动） | 4~5 轮收敛、Terms 61→80 自然上限、每元素增长 <5%/轮停 | 观察项，伴生为持续伴生无"轮"概念，映射为"图规模增速监控" |
| 跨骨干 | 伴生图绑定 agent **不绑定模型**——换模型共用同一图 | **本体有骨干个性：Jaccard<0.62，跨骨干迁移至少 −6.6 分** | 已知边界：伴生图是记忆性质（实体/事实）而非 prompt 优化性质（manifest 表述），受影响预计小于论文场景；列为观察项，暂不动作 |

## 四、反向差距：项目领先 EvoOntology 的维度（公平对照）

| 维度 | 伴生线已有 | EvoOntology |
|---|---|---|
| 对话抽取管线 | 分窗+游标续抽+断点恢复+增量 IO（REQ-303 E1）+剪枝+事件族可视+异步 job | 无此管线（不处理对话流） |
| 实体消解 | 名称对齐注入/label 规范化/bot:alias 别名/向量归并 ≥0.8/人工合并/印证聚合 | 论文未展开实体消解机制 |
| 治理工具链 | 行级编辑（迁移式改名）/挖掘关系（异步分批）/检查清理（六检查项）/整体摘除 | 无（治理靠进化循环重新生成） |
| 检索 | 三级召回链+2 跳邻域注入+match 诚实标注 | browse 向量检索+resolve，无邻域注入设计 |
| 溯源与历史 | PROV-O 全链+invalidAt 失效化保历史可查 | 版本层可回滚，图内无失效化语义 |
| 可视化 | 成长图 3D/多形态/搜索聚焦/空边诚实提示 | /evo-visualize 基础可视化 |
| 集成纪律 | 低侵入三原则（主链路 0 改动/开关默认关/整体摘除） | Claude/Codex 插件形态（不同维度不可比） |

## 五、差距收敛路径（待拍板，未立项）

**P1（低成本高确定性）**：
1. **配置 embedding 连接并跑落 evaldata 基准数字**（治 §3.6 最大的"未闭合挂账"）——一切门控/归并/召回优化的量化前提；
2. **Evidence span 升级**：抽取候选 schema 增原文支撑片段字段，入图落 bot:evidenceText（provenance 事实不可编辑边界内）——对齐 EvoOntology Evidence 承重件，成本低；
3. **伴生语义检索工具**：把伴生图消费升级为 browse/resolve 式工具（自然语言→语义匹配→实体+邻域，挂 facade 工具面），接 92 号工具赋予线。

**P2（机制接入，需先有 P1① 数字）**：
4. **伴生自动入图接入门控**：以 evaldata 扩展（候选注入前后 Recall@5 对比）作为"图改动效果"度量，自动入图从"置信阈值"升级为"阈值+基准门控"——即 REQ-207 配对门控思想在伴生线的最小落地（43 号预留的"门控共享评估"正式收口）；
5. **伴生子图候选版本语义**：沿 REQ-239/207 状态机把伴生快照升级为 vN-cK→正式版（伴生场景可简化为"日快照+确认点"）。

**观察项（不立项）**：图规模增速监控、跨骨干共用伴生图的影响实测、reject 归因留档。

**明确不吸收**：主动探针构建（与被动伴生定位冲突，构建侧已有六路径）；无人值守自动循环（与 REQ-207 一期"人触发"定案一致）；每模型独立演化（成本不划算）。

## 六、局限

- 代码事实沿 31/35 号既有盘点（最近一次代码级核验 2026-10-12/14），本轮未重新逐行核码；
- EvoOntology 侧数据均来自论文/仓库公开材料（43/40 号），其消融结论在对话记忆场景的外推有效性未验证——特别是"Tool 增益占比 57%"基于数据任务轨迹，伴生场景工具面（检索工具质量）是否同为主导杠杆待实测；
- §五 P1~P2 为分析建议，未拍板未立项；若拍板建议沿 18 号注册表分配新 REQ，门控接入项应与 43 号预留注记正式闭环。
