## 0. TL;DR（12 条）

1. **论文定位**：OntoExtend 是「**需求驱动的本体扩展**」框架——把新需求以**能力问题（CQ）**形式输入，从**已有（输入）本体**中 RAG 检索相关元素，交由 LLM 生成**缺失片段**，再**集成**回本体。它管的是本体工程**后段**（本体已存在 → 增量维护），与 OntoChat（63 号，管前段需求引出）恰好互补。
2. **核心创新点（一句话）**：**此前没有任何工作把「检索已有本体元素」内建进扩展流程**。成熟本体常有数百类/属性超出 LLM 上下文，即使塞得下也会被无关细节误导——检索出**紧凑相关片段**是 OntoExtend 的关键。
3. **三段式架构**：**Ontology Retriever**（CQ → top-k 相关本体元素片段）→ **Ontology Extender**（CQ + 片段 → LLM 生成缺失 TBox 片段 + 两阶段校验）→ **Ontology Integrator**（去重 + 拼接回输入本体 + 可回灌重索引）。
4. **检索实现**：每个 `OntologyElement` 序列化成**管道符分隔字符串**（`localName | label | comment | Type: object property | Domain: X | Range: Y`）→ 稠密句向量 → **L2 归一 + FAISS `IndexFlatIP`（内积=余弦）**；查询 CQ 同空间编码，返回 **top-k（默认 20）**。
5. **最佳检索配置（RQ1）**：12 组对照（3 模型 × 4 文本风格）中 **`text-embedding-ada-002` + 管道符分隔 + 含 comments** 最优（M_prod 0.23 / M_w 0.63；M_w = 0.7·P@3 + 0.3·P@20，人工判相关）。
6. **两套 prompt/部署 profile**：工业本体用 **SHACL 型**模板（输出 NodeShape/PropertyShape + `sh:name`）；EU 本体用**通用限制/复用类策略**模板（要求 `rdfs:label`+`rdfs:comment`，鼓励 OWL restrictions）。**prompt 与管线解耦**，可换公司/用例而不改底层。
7. **校验器**：生成片段先过**两阶段**——Turtle 解析器验语法 + 约束检查器验建模约定（两个 profile 均要求对象/数据属性显式 `rdfs:domain`+`rdfs:range`；**这是可配置治理约束，非普适正确性判据**）。
8. **集成器极简**：仅**去重（repeated axioms/类/属性/prefix）+ 拼接**；并把每个片段**回灌 Retriever 重索引**（使后续 CQ 站在更早片段之上，促跨片段一致）——但**论文评估中该回灌被关闭**，以便逐 CQ 独立评。
9. **评估数字**：**39 CQ**（EU 项目 Onto-DESIDE 20 + Bosch 工业 19）。结构：语法错误 0%（EU）/2.5%（工业），**OOPS! 无新增严重/重要陷阱**（仅少量 minor：P02 同义词当类 1 例、P04 孤立元素 ≤1、工业 P08 缺注释 ~3.7 次/CQ）。功能：**CQ 验证 100% 建模**、**冗余元素 <2%**（对比前人 [16] 约 30%）。用户：**N=6 本体工程师** Correctness/Completeness 5 分制——工业 4.91/4.56（o1-preview）、4.96/4.54（GPT-5）；EU 3.69/3.11、3.66/2.94；Fleiss Po 0.80~0.98。
10. **RQ2 结论**：**GPT-5 与 o1-preview 表现相当**（提供检索上下文后），证明收益主要来自**检索增强**而非模型换代。
11. **最关键的产品结论**：OntoExtend 是**「起草助手（drafting assistant）」**——生成**完整扩展模块**，用户只需**轻量审核 + 定向精修**（工业场景「少量至中等修订」）；把人力从**手工写公理**转为**快速验证**。且**对 CQ 质量高度敏感**——工业的**聚焦 CQ**（专家+工程师共拟，高层建模决策已定）得分远高于 EU 的**开放 CQ**（决策留给工具）。
12. **LLM 行为可作质量代理信号（论文独到洞见）**：若一组 CQ + 输入本体能让 LLM 系统性产出更高质量扩展，则该组合「更好」；反之系统性困难多半源于**需求含糊/欠定义/隐藏建模假设**——**LLM 行为可作为 CQ 与本体质量的新维度**。

## 一、论文原理层（arXiv 2607.17963 · 2026-07）

### 1.1 问题陈述与研究问题

**问题陈述（论文 Introduction 原文要点）**：LLM 已用于本体生成（从需求构建）与本体评估，但**没有先前研究**考察「LLM 如何通过**复用已有本体元素**来**扩展现有本体**以建模新 CQ」。该任务的三大挑战：

- 输入本体常含**数百类/属性**，**超出 LLM 上下文**；
- 即便塞得下，**无关细节会误导** LLM 产出**离题或不一致**的输出（[24]）；
- 本体扩展本质是**面向新功能需求的系统性增强**，需要能**增量维护本体模块**。

**四个研究问题（RQ）**：

| RQ | 问题 |
| --- | --- |
| RQ1 | 哪种 **embedding 配置**最适合构建「抽取与给定 CQ 最相关的紧凑本体片段」的检索模型？ |
| RQ2 | 哪种 **LLM** 最能有效扩展检索到的片段以正确建模 CQ？ |
| RQ3 | 评估生成片段质量需要哪些**评估准则**？ |
| RQ4 | OntoExtend 产出的扩展本体有哪些**优势与不足**？ |

**三项贡献**：① OntoExtend 框架（代码/实验数据/CQ 开源）；② 两真实用例上的**检索与提示策略对照实验**；③ 一套评估**结构有效性 + 功能充分性**并含**用户研究**的评估方法。

### 1.2 相关工作谱系与定位（论文 Table 1）

论文自述：LLM 本体扩展（亦称 ontology enrichment）相对其他 LLM 辅助知识工程任务仍处**早期**，方法从交互工具到自动化富集系统；**共性约束** = 可复现性、依赖交互工具、复杂公理支持有限、需求引出与验证仍需人工。**关键空白**：无人聚焦**从基线本体检索已有元素**，且多数工作**几无形式化评估**。

Table 1 在 10 个维度上对比（**Symbols: Y=yes, P=partial, N=not reported**）：

| 工作 | 思路 | 亮点/局限 |
| --- | --- | --- |

**谱系定位**：本体扩展研究尚在早期；**OntoExtend 是"RAG 检索内建 + 多维评估"的首个完整工作**。

### 1.3 三段式架构（逐模块拆解）

```
                     新 CQ + 输入本体（待扩展本体，同时被索引）
                            │
                            ▼
① Ontology Retriever  预处理：解析本体 → 逐 OWL 实体构建 OntologyElement 记录（IRI/label/comment/
                      domain/range/父类子类/verbatim Turtle 片段）→ 管道符串 → 句向量 → FAISS(IP)
                     查询：CQ 同空间编码 → top-k（默认 20）最相似 OntologyElement
                            │
                            ▼
② Ontology Extender  组装 prompt（按来源本体分组渲染 Turtle 片段作只读上下文 + 统一 prefix 块）→
                     LLM 生成候选 TBox 片段 → 两阶段校验（Turtle 解析 + 约束检查 rdfs:domain/range）→
                     失败则重试或标记
                            │
                            ▼
③ Ontology Integrator  去重（重复公理/具名类/属性/prefix）+ 拼接回输入本体 →（可选）把片段回灌 Retriever 重索引
```

> 术语约定：**input ontologies = reference ontologies**（用户想扩展的本体，同时被 Retriever 索引）；**fragment（片段）**= 为**单个 CQ** 检索或生成的自包含 RDF/Turtle 公理集合。

#### 3.1 Ontology Retriever

- **预处理**：解析用户指定的每个本体文件，遍历所有声明的 OWL 实体——**classes、object properties、data properties、annotations，以及（若有）SHACL shapes**。为每个实体构建 `OntologyElement`：**IRI、人类可读 label/comment、domain/range 声明、父/子类（或父/子属性）关系、捕获实体规范声明的 verbatim Turtle 片段**。
- **序列化**：每个元素序列化为**管道符分隔字符串**，拼接 **URI local name + label + comment + 元素类型 + domain/range**：
  `hasMaterialComponent | has material component | … | Type: object property | Domain: Material | Range: MaterialComponent`
- **索引**：向量 **L2 归一化**后存入 **FAISS**，配置**内积相似度**（归一后=余弦），以支持大集合高效近邻检索。
- **查询**：用户 CQ 编码到同空间 → 检索 **top-k（默认 20）** 最相似元素——**这一步是促进复用已有本体元素的关键**。

#### 3.2 Ontology Extender

- **prompt 组装**：检索到的元素**按来源本体分组**渲染为 Turtle 片段，作为**只读上下文**注入 prompt；另构造**统一 prefix 块**，合并所有输入本体的命名空间声明，**让任何来源的元素 IRI 在生成输出中正确解析、无命名空间冲突**。
- **prompt 可配置**：允许本体工程师配置不同 prompt 模板，运行时按需选择。
- **两阶段校验器**：片段被接受前——① **Turtle 解析器**验语法；② **约束检查器**验生成属性是否满足所选用例的**建模约定**（两个 profile 中=显式 `rdfs:domain`+`rdfs:range`；**这是可配置治理约束，非普适正确性判据**）。**失败片段要么重试、要么被标记**。
- **prompt 变体与部署 profile**：
  - **工业本体 profile（SHACL 型）**：指示 LLM 输出 **SHACL `sh:NodeShape`/`sh:PropertyShape`** 定义，遵循特定命名约定、含 `sh:name` 标签——**下游合规工作流消费 SHACL 产物所必需**；建模指导大体止于要求合适的 domain/range。
  - **EU 本体 profile（通用限制/复用类策略）**：要求每个新引入的类/属性都标注 `rdfs:label` 与 `rdfs:comment`。
  - **两者都施加强复用约束**：指示 LLM **复用已有本体元素而非重新声明**。
- **可外置**：这些 prompt 配置被**外置**，系统可在**不改底层组件**的情况下切换公司/用例。

#### 3.3 Ontology Integrator

- **仅两步**：**去重**（移除重复公理、具名类、属性、prefix）→ **把清洗后片段与输入本体拼接**。
- **回灌重索引**：把每个生成片段**转发给 Retriever 索引**，**降低后续 CQ 处理时 Extender 重建相似元素（类/属性）的概率**；使每个片段成为后续 CQ 的参照，**促进跨片段一致性**。
- **评估中关闭**：论文评估中**该回灌被关闭**，以便**每个 CQ 片段被独立评估**。

### 1.4 实验设置

**数据集构造（四步，含"系统性移除"法）**：

1. 从本体中**随机选取类集 C**；
2. 对每个类 `c`，**移除 `c`**，并把**所有 domain 或 range 引用了 `c` 的属性**加入集 P；
3. **迭代扩展**：把被移除类的**所有子类**加入 C，并把这些子类引用的属性加入 P，重复直至无新子类；
4. 针对 C 与 P **构造 CQ 集**——每个 CQ 问「对应类及其属性在原本体中本意代表/完成什么」。

> **要点**：该步骤系统性探测**被移除的本体组件**，使评估能有效检验 OntoExtend 能否**从 CQ 重建它们**。

**数据集统计（Table 2，token 用 GPT-4o tokenizer 计）**：

| 本体片段 | Size (tokens) | Axioms | Classes+Properties |
| --- | --- | --- | --- |
| EU-project — part 1 | 75 000 | 2920 | 405 |
| EU-project — part 2 | 22 000 | 958 | 242 |
| EU-project — part 3 | 25 000 | 1172 | 270 |
| EU-project — part 4 | 6 000 | 228 | 54 |
| Industry use case（Bosch） | 22 000 | 979 | 134 |

> EU 项目（Onto-DESIDE，循环经济数据互操作）**四模块合并为 1 个 setting（20 CQ）**；Bosch 工业本体（制造业 profile）**19 CQ**。输入本体转 Turtle + **紧凑 prefix 声明**以减小体积。

**检索配置调优**：在**小开发集**上对比 **3 个 OpenAI embedding 模型**（`text-embedding-3-small`/`text-embedding-3-large`/`text-embedding-ada-002`）× **4 种元素文本风格**（分隔符 `|` vs `\n`；含/不含 comments），用**不在测试数据中的 5 个 CQ** 人工判相关，计算 **P@3 与 P@20**。主选指标 **M_w = 0.7·P@3 + 0.3·P@20**（强调 top 排名质量=最可能被 LLM 消费的部分）；辅以 **M_prod = P@3 · P@20**（惩罚只在一处 cutoff 好的配置）。**两指标对最优配置一致**。

**Table 3：embedding 配置对照（前列配置）**

| Embedding model | Separator, Comments | M_prod | M_w |
| --- | --- | --- | --- |
| text-embedding-3-small | Newline, with Comments | 0.22 | 0.62 |
| text-embedding-3-large | Newline, without Comments | 0.20 | 0.54 |
| **text-embedding-ada-002** | **Pipe, with Comments** | **0.23** | **0.63** |

→ **胜出并选定主实验**：**`text-embedding-ada-002` + 管道符 + 含 comments**（12 组中最优）。

**LLM 与 prompt 选择**：选 **`o1-preview`**（前人 [16] 报告本体生成最优）与 **`GPT-5`**（OpenAI 最新）；**未选其他模型族**（前人报告相对 o1-preview 表现更低）。**prompt 调优同检索流程**：先在**与主评估集不相交的小开发集**上评估多个 prompt 变体，初始 prompt 紧贴 [16]，**补充"不得出现"的已知陷阱清单**，再由**两名本体工程师**逐轮检查反复出现的问题并调整措辞与约束。

**最终 prompt 组成**：① 通用模板（任务 + 输出格式）② 插入 Retriever 元素的 section ③ 给定 CQ 占位 ④ **指示期望建模形式（formalism）的 directive**。框架自动填充各组件；**style directive 可由用户提供**以约束输出风格（EU 要求用 OWL restrictions；工业**禁用 OWL restrictions、只要求 SHACL shapes**）——**两用例不应解释为测试同一 OWL 表达力层级**。

### 1.5 评估体系（多维）

**结构指标**：OOPS!（Ontology Pitfall Scanner）+ **Pellet 推理机** + **RDFLib** 语法检查。**做法**：对**集成生成扩展前后**的输入本体各跑一次 OOPS!，**对比陷阱报告**，记录扩展**新引入**的问题；再对集成后本体跑 Pellet **一致性检查**。

**功能指标**：
- **CQ 验证（CQ verification）**：判断某 CQ 是否真被本体表示——**尝试写出能检索该 CQ 答案的 SPARQL 查询**，写不出=未建模。**两名本体工程师独立验证 + 交叉核对 + 讨论裁决**（沿用 [14] 流程）。
- **冗余元素（superfluous elements）**：论文对 [16] 的定义做了**更精确修订**——一个具名类或属性是冗余的，当且仅当：**① 在验证 SPARQL 中未被提及**，**且 ② 未通过 `subClassOf`/`subPropertyOf` 与查询中的组件相连**。因此**层级亲属不算冗余，真正断连的具名类/对象属性才算**。

**用户调查（Survey）**：招募 **6 名来自学术界与工业界的本体工程师**评估扩展后本体；准则**改编自 Monka et al. [19]**（原用于评 SPARQL 生成的 Correctness/Completeness 两维），5 分 Likert：

- **Correctness**（**孤立看**片段的语法+语义质量）：1=生成失败（如超 token 限制）/2=语法错误片段/3=语法正确但语义错（如分类不当）/4=语法语义正确但**不完全满足 CQ 意图**/5=语法语义正确且**完全契合 CQ 意图**。
- **Completeness**（片段**并入输入本体后**的充分性，反映工程师**使其可用所需工作量**）：1=无用需完全重做/2=重大修改（**25~40%** 需改）/3=中等修改（**11~25%**）/4=轻微修改（**1~10%**）/5=与输入本体结合后**完整正确**。

另计算 **Fleiss 加权观测一致度 Po** 量化评估者间一致性。评估者可自由用 Protégé/TopBraid EDG/VSCode 等可视化产物。

### 1.6 结果

**结构评估**：生成片段**几乎无 Turtle 语法问题**；OOPS! 显示**集成后未引入任何新的 critical/important 陷阱**，仅在特定用例见少量 minor：
- EU 本体：**P02（把同义词当类）** 仅出现于**单个** EU 项目（每个生成扩展贡献 1 个 P02 实例）；**P04（孤立本体元素）** 仅在**4 个 EU 用例中的 2 个**检出（每次扩展至多加 1 个 P04）。
- 工业本体：OOPS! 报 **P08（缺注释）**——**很可能因输入本体"无注释"风格，OntoExtend 按 prompt 复现了该风格**；**平均约 3.7 次/CQ 扩展（两个 LLM 皆然）**。
- 与既有生成工作 [6,13,16]（彼等显示相当多 important/critical 陷阱）相比，OntoExtend **仅少量 minor**——**结构上可接受、不系统性引入新缺陷、少量问题易修**。

**Table 4：结构+功能评估汇总**

| Use case | OOPS! P2,P4&P8 (o1-prev, GPT-5) | CQ-verification (o1-prev, GPT-5) | Syntax errors (o1-prev, GPT-5) | Superfluous elements (o1, GPT-5) |
| --- | --- | --- | --- | --- |
| **EU-Project** | 13 (7, 6) | **100% (100%, 100%)** | 0% (0%, 0%) | 2% (3.8%, 0%) |

- **冗余对比**：本工作片段 **<2% 冗余**，而 [16] 报告约 **30%**（用 [16] 原定义约 35%）——**显著改进**。

**工程师指出的系统性缺陷**：
- **EU 片段**：① 片段内**孤立元素**（本应经 `subClassOf` 等连到输入本体却未连）；② **类命名不佳**（如**过度具体**的名字）。
- **模型特异性**：**GPT-5** 常**漏掉新属性的显式 domain/range**、施加**错误语义限制**（如滥用 `allValuesFrom`/`complementOf`）、**名字过度简化**；**o1-preview** 常**重定义已有类**、含**语法错误公理**（结构评估工具未显）、**给部分属性错误 domain**、**创建比单个 CQ 显得过于具体的对象属性**。
- **工业片段**：少数情况**只加 SHACL property shape 而无对应对象属性 + `rdfs:domain`/`rdfs:range`**、缺 `sh:datatype`、**漏 `rdfs:subClassOf` 公理**、**缺类/属性注释**；o1-preview 特有——**引入大量 CQ 回答不需要的 Property shape/对象属性**；两条评论担心**扩展未从 CQ 或输入本体获得 grounding**（LLM 纯依输入本体已有模式**预判**扩展）。

### 1.7 讨论与局限

**总体**：OntoExtend 在两域**可靠产出高质量扩展**——语法几乎总有效、仅少量 minor OOPS!、正确建模所有 CQ、**<2% 冗余**，工程师判为**至多"少量至中等"编辑**。**实践中作"起草助手"**：生成完整扩展模块，用户通常只需**审核 + 轻改**，把人力从**手工写公理**转为**快速验证 + 定向精修**，**显著降低领域专家扩展本体的门槛**。

**CQ 表述与质量对结果的影响（论文核心洞见）**：
- 两种使用场景：**① 高度具体、预定 CQ**（工具=写公理助手）；**② 较泛/开放 CQ**（工具须做**实质性建模决策**）。
- **工业 CQ 刻意聚焦**（领域专家+本体工程师共拟，高层建模决策已定，每个 CQ 主要要求生成一个缺失类或一小组属性）；**EU CQ 定义更开放**（作者多为领域专家，**许多建模决策留给工具**）。
- → EU 场景 LLM 产出**结构合理但工程师判为不够完整**（需额外人工精修对齐完整规范的建模选择）；**EU 较低的 Correctness/Completeness 反映的是 CQ 定义局限（缺期望清晰度与上下文细节），而非框架缺陷**。

**LLM 行为作为隐式质量度量（独到洞见）**：**若一组 CQ + 输入本体系统性产出更高质量扩展、更少建模错误，则该组合"更好"**；反之系统性挣扎**多半源于输入的含糊、欠定义或隐藏建模假设**。→ **LLM 行为可作为本体与需求质量的"工具中心"新维度**。

**实践影响**：把 **~75k token 的大型本体片段直送 LLM** 会导致**端到端响应更长、API 成本更高**；OntoExtend **只送紧凑子集**，**大幅降低往返时延与传输/成本**。

**局限**：① 仅两域用例，泛化性待验；② 仅少量 LLM 配置，跨模型/厂商系统对比不足；③ **数据泄漏风险**（LLM 预训练可能见过相似本体/CQ——EU 本体公开但 CQ/覆盖材料非公开，工业本体未公开）；④ **需求（CQ）质量对结果影响大**，未来应显式分析与改进 CQ 质量（半自动生成 CQ 或映射到 CQ 模板，见 Keet et al. [11]）。

**`OntologyElement`（Pydantic 模型）**：`uri`、`element_type`（class/object_property/data_property/annotation_property/node_shape/property_shape/restriction）、`source_ontology`、`label`、`comment`、`domain[]`、`range[]`、`super_classes[]`、`sub_classes[]`、`additional_info[]`、`snippet`。

**`get_searchable_text()`（管道符序列化，与论文一致）**：`localName | label | comment | "Type: {element type}" | "Domain: {names}" | "Range: {names}" | additional_info…`（`" | "` join；`element_type` 下划线转空格）。

**`PrefixManager`**：`collect_prefixes_from_files` 解析各本体收集命名空间（跳过标准 & xml，清洗非法字符，冲突自动加序号）；`build_prefix_block` 输出 `@prefix` 块——**先默认命名空间，再 38 条 `REQUIRED_PREFIXES`（rdf/rdfs/owl/xsd + bosch-*/brick/csvw/dc*/dcat/foaf/geo/odrl/org/prov/qb/schema/sh/skos/sosa/ssn/time/vann/void/wgs 等，含 Bosch 企业专用前缀硬编码）**，最后补本体自定义前缀（排序去重）。

**`OntologyExtractor`**：`_extract_single` 遍历 `owl:Class` / `owl:ObjectProperty` / `owl:DatatypeProperty` / `owl:AnnotationProperty` / `sh:NodeShape` / `sh:PropertyShape` / 具名 `owl:Restriction`（**跳过空节点**）；`_collect_snippet(depth=1)` 生成**深度 1 的空节点闭包 Turtle 片段**（含 `owl:Restriction` 的 `onProperty` 追踪）；`_extract_shacl_shape` 抽 targetClass/targetObjectsOf/property/path/datatype/class_/minCount/maxCount；`_extract_named_restriction` 抽 onProperty/someValuesFrom/allValuesFrom/hasValue/各种 cardinality。

**`FaissVectorStore`**：`faiss.IndexFlatIP(dim)`（内积；配合向量 L2 归一=余弦）；`seen_uris` 去重；`search` 返回 `(element, score)` 列表。

**`PromptBuilder`**：`_format_relevant_elements` **按来源本体分组**渲染（`## From {stem} ontology:`）——每条先 `- {searchable_text}`，再附其 ```` ```ttl ```` snippet；`build` 填入 `USER_TMPL`。

**校验**：`TurtleValidator.validate_ttl`（rdflib 解析）；`PropertyConstraintValidator.ensure_domain_range`（**遍历 ObjectProperty/DatatypeProperty，任一缺 `rdfs:domain` 或 `rdfs:range` 即 `raise ValueError`**——对应论文"两阶段校验器"的第二段）。

**`OntologyCombiner`**：`remove_prefixes_from_fragment`（剥掉片段内 `@prefix`/`PREFIX` 行）+ `combine`（拼**头部注释**〔参考本体/生成时间/片段数/`owl:Ontology` 声明〕+ 逐片段带 `# ── Fragment i ──` 分隔）。

**`OntologyRAG`（编排）**：`_build_store`（抽元素→索引→可选载入缓存片段→建 prefix 块）；**`_retrieve_relevant(cq, k=20)`**（CQ 编码→检索→**按来源白名单过滤**〔reference+session(+可选 cache)〕）；`_generate_fragment`（建 prompt→`llm.complete(system=SYS_PROMPT)`→正则抽 ```` ```ttl ```` 代码块）；`run_single_cq` / `run_csv`（逐 CQ 处理，成功写 `individual_ontologies/`、回灌 `session` 重索引、失败按 `Invalid Turtle`/`ValueError` 记日志）。

**系统与用户 prompt 全文（可直接复用）**：

```
SYS_PROMPT =
"You are an ontology engineer. Reuse elements from the provided core ontology when possible.
 If you must create new elements, append '# GENERATED' as a comment.
 Return only Turtle/TTL syntax inside one markdown code block."
```

`USER_TMPL`（要点摘录）：声明任务=「基于 CQ（需求）与 OS（上下文/本体故事），生成建模 CQ 的本体片段，**存在 SPARQL 可抽答案**」；要求**优先复用 RELEVANT ONTOLOGY ELEMENTS 中的元素**、非必要不新建；给 `{prefix_block}`；**禁 A-Box、仅 TBox**；**7 条 INSTRUCTIONS**：①分析 CQ 所需概念/关系 ②映射到检索元素 ③优先语义相似度高者 ④仅输出 TBox Turtle ⑤**CQ 暗示时加限制；参考本体用 OWL restrictions 则只用 OWL，只用 SHACL 则只用 SHACL** ⑥**每个对象/数据属性显式 `rdfs:domain`+`rdfs:range`** ⑦语法正确且自包含；**NOTES**：不用外部本体、复用命名空间、**NodeShape IRI 与所塑类同名**（`<prefix>:<ClassName> a sh:NodeShape`）、**PropertyShape 命名 `<ClassName>-<PropertyName>`**、用 `rdfs:label` 作 `sh:name`、不新建 `owl:Ontology`。

**日志四件套（CSV）**：`ontology_elements.csv`（timestamp/uri/type/source/label/comment/domain/range/super/sub）、`cq_processing_log.csv`（cq_index/cq/success/elements_used/source_ontologies_used/processing_time/error）、`generation_runs.csv`（total/successful/failed/success_rate/总耗时/均耗时/output_file）、`token_cost_log.csv`（per-CQ per-model prompt/completion/embedding tokens + cost_usd）。→ **可直接对齐我们"抽取运行元数据"需求**。

**CLI**：`cq --cq "…" --onto a.ttl b.ttl [--top-k 20] [--include-cache]` / `csv --file cqs.csv --onto-dir dir [--limit N] [--top-k 20] [--include-cache]`。

### 2.5 分解式提示原型（Decomposed Prompting）

`OntoExtender/Prompting Techniques/` 下：`DecomposedPrompting.py`（`SplitUnit` 分解 → `CallLLMUnit` 求解 → `MergeUnit` 拼接）+ `MemoryUnit`（CoreOntology/Tasks/SolvedTasks 状态）。两份 prompt 模板：

- **`DecomposedPromptingLong.py`**：**12 条 ImportantNotes**（用 `rdfs:subClassOf`/`subPropertyOf` 特化、已有则不重复、写 label/comment、避免 `hasName` vs `has_name`、不写 `#` 注释、**仅 CQ 需要才加限制**、**需要关系自身有身份/属性时用具体化〔reification/association class〕**、无 A-Box、复用 prefix、追求高质量、**只在有值时加 inverse**）+ **3 条 pitfalls**（禁循环 `subClassOf`、每类/属性/个体至少 label+comment、勿误用已有对象属性 domain/range）。
- **`DomainOntoGen.py`**：**one-shot 示例**（AquaticResource 观测 CQ → 完整 OWL 片段，示范 `owl:qualifiedCardinality`/`owl:onClass`/`owl:onDataRange` 用法）。

4. **示例数据偏 Bosch**：`REQUIRED_PREFIXES` **硬编码 Bosch 企业前缀**（`bosch-meta-o`/`bosch-metadata-o`/`ssmo` 等）——通用化须剥离。

6. **requirements 与 pyproject 不一致**：requirements 钉 `openai==0.27.8`（旧版同步 API）与 `faiss_cpu`/`ollama`，pyproject 用 `openai>=1.108`/`azure-identity`/`sentence-transformers`/`langchain-openai`——**两套依赖口径并存**，跑通需自行消歧。
7. **评估口径的构造性**：39 CQ 由**"系统性移除类+子类+相关属性"反向构造**（离开放域真实表现有距离）；工业本体未公开，**不可完整复现其 19 CQ 场景**。
8. **回灌重索引评估中关闭**：论文的**链式一致性**能力**未经量化验证**。

## 三、与本项目实现的对照（⚠️ 关键：同名不同物）

### 3.1 澄清：「OntoExtend 路径」≠ 论文 OntoExtend

| 维度 | 本项目「OntoExtend 路径」（REQ-171 P2② / M-O14 / `internal/ontoextend`） | 论文/开源 OntoExtend |
| --- | --- | --- |
| 触发输入 | **无 CQ**；用户选目标本体 + 选 ODP 模式 | **以 CQ 为唯一需求输入** |
| 素材 | **人工精选 12 个 ODP**（`curated` 编译期内嵌）+ **LOV 词表搜索**（REQ-171 P1） | **从目标本体 RAG 检索相关元素**（向量检索） |
| 生成 | **无 LLM 生成**——`ontoextendDraft` 直接把 ODP 的 spec **拷贝**成草稿（`draft.Name = odp.Name + " 扩展片段"`） | **LLM 生成缺失 TBox 片段**（带两阶段校验） |
| 集成 | 走**通用** merge/preview→apply（REQ-157） | **专用 Integrator**（去重+拼接+回灌重索引） |
| 后端 | `GET /api/ontology/ontoextend/odps` + `POST /api/ontology/ontoextend/draft` | Retriever/Extender/Integrator 三段式管线 |

> **结论**：本项目复用「OntoExtend」之名承载的是**「模式/词表驱动的本体扩展」**（重用既有模式），**与论文「CQ + 检索 + LLM 生成的增量扩展」是两回事**。项目里所有 `OntoExtend 流程/路径/ODP/LOV` 的表述都是**前者**；本档其余「自研蓝图」讨论的是**论文语义的 OntoExtend**（若采纳，宜以**新路径/新能力**承载，避免与现有路径混淆）。

### 3.2 现有可复用底座（论文 OntoExtend 落地所需的原料）

| 论文环节 | 本项目已有可复用资产 | 差距 |
| --- | --- | --- |
| Retriever · 元素抽取 | `pkg/ontology/spec`（概念/关系/实例）+ `importer`（TTL/OWL→spec） | 无「元素级 RAG 索引」（现有检索在 KB 侧，本体侧无） |
| Retriever · 向量检索 | KB 侧已有向量层（REQ-206 embedding 连接、召回增强）；`qualitygate` 词表 | **本体元素向量化缺失**；`spec` ↔ 向量 无桥 |
| Extender · prompt | 平台 LLM 代理 `/api/ontology-llm/generate`（**ai-draft-async 202+job 异步**）+ `llmcreate`（含生成-校验回喂 ≤3 轮） | 无「片段生成」形态 prompt；无 prefix 块合并 |
| Extender · 校验器 | `spec.Validate` + `qualitygate` 11 项三维评分（strict 门禁） | **domain/range 治理约束**、Turtle 语法独立校验可加 |
| Integrator | merge/preview→apply 三策略（replace/merge-overwrite/merge 重命名并入+引用改写，REQ-157） | **去重/回灌重索引**未做（apply 有版本快照） |
| 需求输入 | `spec.cq`（REQ-248 一等公民）+ CQ→SPARQL 验收（REQ-255） | 已是 CQ 驱动，天然契合 |
| 运行元数据 | 质量报告 artifact、版本快照 | **token/成本/检索日志**未落（论文四 CSV 可对标） |

### 3.3 一句话结论

本项目**已有论文 OntoExtend 所需的绝大部分"接口级"底座**（CQ 一等公民、LLM 异步代理、生成-校验环、merge 审查、质量门禁、版本快照），**唯独缺"本体元素级 RAG 检索"这一论文核心创新点**与"专用的去重/回灌 Integrator"。**若采纳，增量集中在 Retriever（元素向量化+FAISS/内积等价）与 Integrator（去重+链式重索引）两处，其余可复用**。

## 四、自研实现蓝图（理论依据落地）

> 原则：**不搬 Python 栈**（`faiss`/`rdflib`/`openai` 旧 SDK/langchain/sentence-transformers 均不引入，**D-O15**）；只搬**算法、prompt、交互范式、评估口径**，落进现有 **Go 服务 + spec 多形态** 之内。

### 4.1 目标管线（三段式 → Go 栈映射）

```
输入本体（spec/TTL）+ 新 CQ（spec.cq）
   │
   ▼
① Retriever   抽取 OntologyElement（类/对象属性/数据属性/父类/domain/range/snippet）→
              管道符串 → embedding（复用现有向量连接）→ 内积检索（top-k 默认 20，按来源过滤）
   │
   ▼
② Extender    CQ + 检索片段 + 统一 prefix 块 → /api/ontology-llm/generate（异步 job）→
              抽 ```ttl``` 代码块 → 两阶段校验（Turtle 语法 + domain/range 治理约束）→ 失败重试/标记
   │
   ▼
③ Integrator  去重（公理/类/属性/prefix）→ 走 REQ-157 merge/preview 审查 → apply（版本快照）→
              （可选）把新片段回灌 Retriever 重索引（链式，默认关以保独立评估）
```

### 4.2 数据模型（最小侵入）

- **`OntologyElement`（新，Go struct）**：`URI/element_type/source/label/comment/domain[]/range[]/super[]/sub[]/snippet`；`SearchText()` 复刻管道符格式（**先 localName，再 label/comment，再 `Type:/Domain:/Range:`**）。
- **`OntologyFragment`（复用 spec 形态）**：生成片段既可为 **TTL 串**（对接现有 importer），也可为 **spec 片段**（对接现有 merge）——**推荐后者**，直接进 REQ-157 审查底座，零新表。
- **检索日志（可选新表或 artifact）**：对标论文四 CSV——`elements_used / source_ontologies / token(cost) / retrieval_log`，**优先落服务日志或 artifact**，不新增核心表。

### 4.3 模块设计

| 模块 | 输入 | 处理 | 输出 | 复用点 |
| --- | --- | --- | --- | --- |
| **A 元素抽取器** | 输入本体（spec/TTL） | 遍历类/对象属性/数据属性（+可选 SHACL 形态）→ `OntologyElement` + snippet（空节点闭包深度 1） | 元素集 | `importer`（TTL→spec）、`pkg/ontology/spec` |
| **B 检索器** | CQ + 元素集 | `SearchText()`→embedding→**内积/余弦 top-k（默认 20）**→按来源过滤 | 相关片段 | 现有 KB 向量层（REQ-206 连接）、embedding 缓存 |
| **C 前缀管理** | 输入本体集 | 收命名空间→清洗→标准前缀 + 自定义前缀去重 | `prefix_block` | 现有 spec 命名空间 |
| **D 片段生成器** | CQ + 片段 + prefix 块 | 组装 prompt（**翻译论文 SYS/USER + 两 profile**）→异步 LLM job | 候选 TTL/spec 片段 | `/api/ontology-llm/generate`、`llmcreate` 生成-校验环 |
| **E 两阶段校验器** | 候选片段 | ① Turtle/spec 语法校验 ② **domain/range 治理约束**（可配） | 合格/重试/标记 | `spec.Validate`、`qualitygate` |
| **F 集成器** | 合格片段 + 输入本体 | 去重 → merge 审查 → apply →（可选）回灌重索引 | 新版本本体 | **REQ-157 merge/apply**、版本快照 |

- **不变式**：① 检索片段**作只读上下文**（不许 LLM 改写已检索元素）；② **prompt 与管线解耦**（profile 可换）；③ 校验失败**要么重试要么标记**，不静默入库；④ 集成**必经 merge 审查 + strict 门禁**（不自建旁路）。

### 4.4 与现有资产衔接

- **需求入口**：CQ 直接取 **`spec.cq`（REQ-248）**；覆盖性判定与 **REQ-255（CQ→SPARQL）** 并轨（可加论文式**冗余元素**统计：`subClassOf/subPropertyOf` 亲属不算冗余）。
- **fork 扩展（REQ-83，P2）**：论文三段式是 **fork 扩展的直接参考架构**——按新需求检索已有本体片段（而非整本塞 prompt）→ LLM 生成 → 校验集成。
- **审查与门禁**：集成**复用 REQ-157 merge/preview→apply**（去重可作 preview 前置）；质量用 **qualitygate 三维评分 + strict 开关**。
- **可观测**：token/成本/检索日志轴对齐论文四 CSV，补「本体命中→回答贡献度量缺失」（与 62 号 K/G 借鉴同族）。
- **区别于现有路径**：建议以**新能力（如"CQ 驱动增量扩展"）**承载，**不复用现有 `OntoExtend 路径` 的 API 名**，避免与 ODP/LOV 语义混淆。

### 4.5 分阶段实施建议

| 阶段 | 内容 | 优先级 | 说明 |
| --- | --- | --- | --- |
| S1 | **元素抽取器（A）+ 检索器（B）**：spec→OntologyElement→向量→top-k | P2 | **论文核心创新点**；依赖现有向量连接，最小增益最直接 |
| S2 | **片段生成器（D）+ 校验器（E）**：翻译两套 prompt + 两阶段校验 | P2 | 复用 `/api/ontology-llm/generate` 异步 job + `llmcreate` 环 |
| S3 | **集成器（F）**：去重 + merge 审查 + 回灌重索引 | P2~P3 | 复用 REQ-157；回灌默认关（保独立评估），可配开关 |
| S4 | **评估口径**：39 CQ 式"移除法"造集 + 冗余元素/CQ 验证/OOPS! 三维 | P3 | 落 `internal/evaldata`（build tag 手动跑，沿 M34④ 先例） |
| S5 | **运行元数据**：token/成本/检索日志 | P3 | 对标四 CSV，落 artifact/日志 |

- 评测：引入 ada-002+pipe+comments 的**检索口径**与论文**三维评估**（结构 OOPS!/语法/一致性 + 功能 CQ 验证/冗余 + 用户 Likert Correctness/Completeness）。

## 五、不采纳项与诚实边界

### 5.1 明确不引入

| 项 | 理由 |
| --- | --- |
| Python 栈（faiss/rdflib/sentence-transformers/langchain/owlready2） | 本项目 Go 栈；**D-O15**（不引入重运行时依赖） |
| `openai==0.27.8` 旧 SDK 同步调用 | 已有平台 LLM 代理 + 异步 job，无需自建 SDK 层 |
| Bosch 企业前缀硬编码 / `corporate-openai` Azure 分支 | 企业私有配置，与通用平台无关 |
| 直接复用仓库代码 | **仓库无 LICENSE**（§2.7-1），仅借鉴**算法/prompt/口径** |
| 分解式提示骨架（`CallLLMUnit` 占位） | 未实现实体，无复用价值 |

### 5.2 诚实边界（逐条）

1. **两域小样本**：仅 Onto-DESIDE + Bosch 两用例，**泛化性未证**；工业本体未公开，**其 19 CQ 不可复现**。
2. **39 CQ 是构造集**：由"系统性移除"反向造出，**离开放域真实需求有距离**。
3. **"CQ 验证 100%" 的口径**：系**两名工程师写 SPARQL 判定**，非自动指标；易受"被移除元素恰是 CQ 所指"的构造偏置影响。
4. **冗余 <2% vs 30%** 的对比是**修订定义后**（把层级亲属排除），**跨定义比较需谨慎**。
5. **模型对比有限**：仅 o1-preview / GPT-5，**同厂两代**；论文自述"少量 LLM 配置"是局限。
6. **数据泄漏未排除**：EU 本体公开，论文承认存在预训练泄漏风险。
7. **回灌重索引未验证**：论文评估中**关闭**该能力，链式一致性**无量化证据**。
8. **对 CQ 质量高度敏感**：开放/欠定义 CQ 下 Correctness/Completeness 显著下降（EU 场景 2.94~3.69），**框架不能补救坏需求**。
9. **仓库工程完成度低**：无 LICENSE、README 仅图、依赖两套口径不一致、分解式提示为骨架（§2.2/2.5/2.7）。

### 5.3 待验证项（后续可实证）

- 我们 **spec_json 形态**下的元素序列化（类/关系/domain/range）与管道符格式的**等价性**与检索质量；
- 复用**现有向量连接**（中文）对**中文 CQ + 中文本体元素**的召回质量（论文全英文）；
- 两阶段校验中**domain/range 治理约束**（论文 profile 特有）是否适配我们质量门禁口径；
- **去重 + 回灌重索引**在中文/多版本场景下对**跨片段一致性**的实际收益。
