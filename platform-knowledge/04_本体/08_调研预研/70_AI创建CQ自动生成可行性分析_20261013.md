## 1. 诉求还原与现状盘点

**诉求**：AI 创建路径的 CQ（能力问题）目前要用户完全手写——写好 CQ 是专业工程，而本体效果又很依赖 CQ 质量。设想：由大模型先要求用户输入必要信息，再由大模型生成足够的 CQ。

**现状（关键事实）**：

| 能力 | 现状 | 所在 |
| --- | --- | --- |
| CQ 手写框（AI 创建） | 「能力问题（CQ）引导（可选，每行一个）」纯手写，非专家写不出好 CQ | S1Source AI 创建 Tab |
| **CQ 自动抽取** | **已存在**：`ExtractCQs`——领域材料→LLM 生成 CQ 候选（63 号 P5 蓝本中文适配+两净化算子〔拆非原子问题/命名实体抽象〕+解析失败回喂重试+既有 CQ 去重），产候选经**人工确认卡**（勾选/逐条编辑/删行/手动添加）写回 | REQ-272/M81，`internal/ontochat/cq.go` |
| CQ 材料组装 | `buildCQMaterial(sess)` = 用户故事（如有）+领域描述+逐轮补充 Hints——**与 AI 创建的「描述+澄清轮 hints」一一对应** | 同上 |
| 「LLM 要求用户输入必要信息」 | **已存在**：REQ-306 A1 澄清轮——`ai-clarify` 输出范围复述+五维缺口清单（概念覆盖/关系与层级/属性/实例来源/约束规则）+逐轮补充 | M110，`llmcreate.ClarifyPrompt` |
| CQ 回写 | DraftWithCQ 的 cqs 入参→spec.CQ 入资产（REQ-248 闭合，AI 创建已接线） | llmcreate |

**结论先行**：开发者设想的两个环节——「LLM 要求用户输入必要信息」与「LLM 生成 CQ」——**平台都已各自存在**（澄清轮与 ExtractCQs），只是没有接到 AI 创建路径的 CQ 环节上。本方案可行性=高，本质是一次**能力接线**而非新能力研发。

## 2. 开发者方案可行性评估

设想流程：「LLM 反问用户必要信息 → 用户回答 → LLM 生成足够 CQ」。

- **可行性：成立**。反问机制（澄清轮）与生成机制（ExtractCQs）都是已交付能力，接线上无技术风险。
- **但有一个交互设计上的次优点**：**为 CQ 单独再做一轮「LLM 反问」是多余的**——①澄清轮的五维缺口清单已经承担了「引导用户补必要信息」的职责，且清单口径（概念覆盖/关系与层级/属性/实例来源/约束）恰好就是 CQ 生成的原料维度；②CQ 生成**不需要用户先回答什么专业问题**——CQ 是「本体要回答什么问题」，从领域描述+补充材料直接抽取是 63 号 P5 的标准做法（论文路径：用户故事/领域描述→CQ），用户的领域知识已经在描述和补充材料里了；③多一轮专门反问=多一次交互成本，且 LLM 自由反问的质量不会优于已定稿的五维清单口径。
- **角色转换洞察（更佳方案的核心理由）**：非专家写不好 CQ 的根源是「不知道什么是好 CQ」——让用户**生产** CQ 不如让用户**评审** CQ。LLM 生成候选+人工勾选确认，用户只需判断「这是不是我想问的」，门槛从专业建模降到常识判断。

## 3. 更佳方案（推荐）：CQ 候选生成+人工确认，直接消费澄清轮产出

**交互流（AI 创建路径内闭环）**：

```
领域描述（必填）
  → 材料单薄？自动进澄清轮（REQ-306 已交付：五维缺口清单+逐轮补充）
  → CQ 区新增「AI 生成 CQ」按钮：调 ExtractCQs（描述+澄清轮累积 hints 为原料）
  → CQ 候选确认卡（沿 REQ-272 形态：勾选/逐条编辑/删行/手动添加）
  → 确认后的 CQ 并入生成入参（capability_questions → DraftWithCQ → spec.CQ 回写，REQ-248 链路已通）
  → 生成草案
```

**设计要点**：
1. **不做 CQ 专属反问轮**——材料不足时澄清卡的五维清单自然引导补充，CQ 生成直接消费其累积材料；材料足够时用户可以跳过澄清直接生成 CQ。交互最少路径：填描述→点「AI 生成 CQ」→勾选→生成。
2. **生成材料复用**：`buildCQMaterial` 的三源（故事/描述/Hints）中，AI 创建路径使用「描述+澄清轮 hints」两源；参数化解耦 `sess`（小重构，纯函数化）。
3. **人工确认步保留**（REQ-272 定案口径）：LLM 候选不自动全采——用户勾选/编辑后才并入生成；诚实边界随行（生成质量上限=领域材料质量）。
4. **去重与净化免费获得**：ExtractCQs 自带两净化算子+既有 CQ 去重+回喂重试（REQ-272 已交付），无需重做。
5. **与澄清轮的顺序自由**：先补材料再生成 CQ（推荐，原料更足）或直接生成（描述够好时）——不强设顺序。

**与开发者设想的对齐度**：设想中「LLM 要求用户输入必要信息」由**已交付的澄清轮**承担（且口径更结构化）；「LLM 生成足够的 CQ」由**已交付的 ExtractCQs**承担；省掉的是设想中的「专门为 CQ 再反问一轮」——以更少交互达到同一目标。

## 4. 实现落点预估（拍板后细化）

| 项 | 落点 | 成本 |
| --- | --- | --- |
| ExtractCQs 解 sess 化 | `buildCQMaterial(description, story, hints)` 纯函数化+无会话抽取入口（ontochat 导出） | 小 |

| 前端确认卡 | AI 创建 CQ 区「AI 生成 CQ」按钮+候选确认卡（沿 OntoChatFlow REQ-272 卡形态；组件抽共享或形态复制，设计轮定） | 中 |

| 手写保留 | 手写框保留（LLM 生成与手写共存；手动添加在确认卡内也有） | 零 |

**批次建议**：P1=上表全部（一次交付闭环）；观察项=CQ 覆盖度自检轮（生成后 LLM 对照五维清单查漏提示——ExtractCQs 已有两净化，边际价值待观察）。

## 5. 口径校准与诚实边界

- **「本体效果完全依赖于 CQ 的质量」需校准**：CQ 是建模锚点之一（REQ-90/REQ-248：先列 3~5 条再动手、spec.CQ 入资产可追溯），但生成质量同样取决于领域材料完整性与生成链路（few-shot 种子范例+生成-校验-质量门禁循环）。CQ 好而材料差的草稿一样泛化。
- LLM 生成 CQ 的质量上限=领域材料质量——材料单薄时先走澄清轮（这正是澄清轮存在的意义），但**不强制**（描述足够好可直接生成）。
- 候选必须人工确认，不自动全采（REQ-272 定案口径延续）；「生成足够的 CQ」的「足够」由用户在确认卡中裁定，系统不设数量门槛。
- 手写入口不退役：专家用户/教学场景（方法论卡「先列 CQ 再动手」）仍可直写。

## 6. 判定口径沉淀

「XX 要完全自己写太专业」类诉求的拆解顺序：①先查平台是否已有该能力的自动生成+人工确认形态（多半在另一条路径已交付——本例 ExtractCQs 在 OntoChat）；②用户角色从「生产者」转「评审者」是降门槛的第一杠杆，LLM 反问补充材料是第二杠杆（且常已被澄清轮覆盖）；③生成类交互的确认卡是质量闸门，不自动全采。
