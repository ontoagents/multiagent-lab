# 本体专业概念手册（构建·运行·使用全景）

> **定位**：本体模块涉及的全部专业概念参考册——回答「这个术语是什么、和谁有关系、在本项目哪里用到」。实现细节看 [90_本体_底层实现原理](90_本体_底层实现原理.md)，产品语义看 [00_本体模块](00_本体模块.md)；本文是**概念层横切参考**，按分层架构组织，支持从任一层切入查阅。
> **阅读方式**：先看 §1 分层地图建立全局，再按需跳章节；每个概念含「定义 → 关系 → 本项目落点」三要素。跨章节引用用 §x.y 锚点。

## 1. 概念分层总地图

W3C 语义网技术栈在本项目的映射，自下而上八层（下层是上层的基础）：

```
┌─ L8 方法论层    CQ / ODP / 七阶段 / 六路径构建          ← 怎么做出好本体
├─ L7 治理溯源层  PROV-O / 版本化 / 模块化 imports / SSSOM ← 谁改的、从哪来
├─ L6 运行时层    三元组库 / 属性图 / Endpoint / Oxigraph·Fuseki ← 存在哪、怎么跑
├─ L5 推理层      RDFS 语义 / OWL RL / 推理机             ← 能推出什么新事实
├─ L4 查询层      SPARQL 1.1 / Update / Endpoint 协议      ← 怎么查、怎么改
├─ L3 约束校验层  SHACL / ShEx / 质量门禁                 ← 怎么判对错
├─ L2 词汇建模层  RDFS / OWL / SKOS / 词表复用            ← 怎么定义类与关系
└─ L1 数据模型层  RDF / IRI / Literal / Turtle·JSON-LD    ← 万物的基础表示
```

**两句话抓住全局**：L1 的 RDF 定义了「事实如何表示」（三元组）；L2 的 RDFS/OWL 在其上定义「概念与约束的词汇」；L3 的 SHACL 检查数据合不合规矩；L4 的 SPARQL 查询；L5 的推理机从已有事实推新事实；L6 是承载这一切的数据库与协议；L7/L8 是工程化与方法论。本项目自研的 spec_json 是 L2 的轻量替代形态（见 §9 平台映射）。

## 2. L1 数据模型层：RDF 家族

### 2.1 RDF（Resource Description Framework）

- **定义**：W3C 万物表示的标准数据模型。一切知识拆成**三元组** `<主语 Subject, 谓语 Predicate, 宾语 Object>`——如 `<张三, 就职于, 华为>`。全图 = 三元组的集合。
- **关系**：所有上层概念（RDFS/OWL/SHACL/SPARQL）都以三元组为共同底座；谓语必须是 IRI（§2.2），宾语可以是 IRI、字面量或空白节点。
- **本项目落点**：「TTL 即 KG」的 T；本体资产 TTL 导出经 rdflib sidecar 装载进 RDF 引擎（90 号 §1）。

### 2.2 IRI / URI / URL

- **定义**：IRI（Internationalized Resource Identifier）= 允许非 ASCII 字符的 URI，是 RDF 中**标识万物**的唯一 ID；URL 是 URI 中「可定位」的子集。RDF 1.1 起统一用 IRI。
- **关系**：本体中的每个类、属性、实例都由 IRI 命名——IRI 的命名空间设计（§8.2）是本体工程的第一决策。Helix Foundry 的 `logicalId=digest(typeId+":"+key)` 确定性身份键（67 号 B5、对口 REQ-249 同名歧义）就是「IRI 命名稳定性」的工程化答案。
- **本项目落点**：spec→TTL 导出时 IRI 回写（attr: 命名空间与实例属性断言同 IRI，90 号 §1）。

### 2.3 Literal（字面量）与 xsd 数据类型

- **定义**：三元组宾语中的「值」——字符串、数字、日期等。RDF 字面量可带**数据类型**（`"42"^^xsd:integer`）与**语言标签**（`"张三"@zh`）。
- **关系**：数据类型来自 XML Schema（xsd:）——`xsd:string/integer/decimal/boolean/date/dateTime/double` 最常用。与 IRI 的区别：IRI 标识资源，Literal 是资源上的属性值。
- **本项目落点**：数据属性声明层（REQ-268/M77）的 range 即 xsd 类型；LLM 生成与 CSV 灌装时的类型一致性靠质量门禁检查（§4.3）。

### 2.4 空白节点

- **定义**：没有全局 IRI 的匿名资源（记作 `_:b1`），用于表示「存在某物但不需要命名」——如复合值、匿名类限制。
- **关系**：是 OWL 复杂公理（匿名节点限制）的载体；对 diff/合并不友好，工程实践倾向少用。
- **本项目落点**：导入边界——匿名节点限制与复杂公理**丢弃计 lossy warning**（90 号 §1，D-O22 表达力边界）。

### 2.5 序列化格式：Turtle / N-Triples / RDF/XML / JSON-LD

| 格式 | 扩展名 | 特点 | 本项目使用 |
| --- | --- | --- | --- |
| **Turtle (TTL)** | `.ttl` | 人类可读首选：`@prefix` 前缀缩写、分号续同主语、逗号续同谓语 | ✅ 主格式：TTL 导出/源码视图/SPARQL 工作台对照 |
| **N-Triples** | `.nt` | 一行一三元组、无缩写，机器友好 | 导入支持（sidecar） |
| **RDF/XML** | `.rdf/.owl` | W3C 最早官方格式，真实世界 OWL 资产多为它 | ✅ 导入（OWL-RDF-XML，sidecar 子进程） |
| **JSON-LD** | `.jsonld` | JSON 形态的 RDF，Web API 友好 | ✅ 导入识别（REQ-235/M62） |
| **TriG** | `.trig` | Turtle 扩展，支持 Named Graph | 导入支持（sidecar） |

- **关系**：同一 RDF 图可有多种序列化，**信息内容等价**——「导入即保留原始形态」是本项目硬要求（90 号 §1）。
- **本项目落点**：`internal/importer` 多格式导入分层 + spec→Turtle 导出（经系统级 python3+rdflib sidecar，无 venv，D-O15）。

### 2.6 Named Graph 与 RDF Dataset

- **定义**：一组三元组可打上一个 IRI 标签（图名）——「图中的图」。RDF Dataset = 默认图 + 多个命名图。
- **关系**：是 SPARQL Update、联邦查询（SERVICE）、数据集隔离的基础；三元组库多按命名图做多本体隔离。
- **本项目落点**：多本体装载进引擎的隔离机制（运行方案 = 引擎 + 本体集合，00 号 §运行）。

## 3. L2 词汇建模层：RDFS / OWL / SKOS

### 3.1 RDFS（RDF Schema）

- **定义**：RDF 的**轻量词汇扩展**，提供最基础的建模原语：`rdfs:Class`（类）、`rdfs:Property`（属性）、`rdfs:domain/range`（属性定义域/值域）、`rdfs:subClassOf/subPropertyOf`（层级）、`rdfs:label/comment`（人读标签/注释）。
- **关系**：是 OWL 的子集与基础；其层级声明本身就有推理语义（§5.1）。够用时不必上 OWL。
- **本项目落点**：伴生 SPARQL 查询与 KG 处理中的 `rdfs:` 前缀词汇（backend/internal/companion/sparql.go）。

### 3.2 OWL（Web Ontology Language）2

- **定义**：表达力远超 RDFS 的本体语言——类公理（等价/不相交）、属性特征（传递/对称/逆）、基数限制、存在/全称量化。分三档**配置**（profile）适配不同场景：

| 配置 | 定位 | 典型场景 | 推理代价 |
| --- | --- | --- | --- |
| **OWL 2 EL** | 大规模类层次 | 生物医学本体（SNOMED CT） | 多项式时间，快 |
| **OWL 2 QL** | 查询改写友好 | 数据库之上加语义层 | 查询重写即可，不需物化 |
| **OWL 2 RL** | 规则引擎可实现 | 企业数据推理 | 可换算成 if-then 规则，可物化 |

- **关系**：核心词汇 `owl:Class / owl:ObjectProperty / owl:DatatypeProperty / owl:NamedIndividual / owl:equivalentClass / owl:disjointWith / owl:inverseOf / owl:TransitiveProperty / someValuesFrom / allValuesFrom`。**与 SHACL 的分工**：OWL 管推理（从已知推未知，开世界假设 OWA），SHACL 管校验（查违规，闭世界 CWA）——见 §4.1。
- **本项目落点**：公理保留层（REQ-269/M78）捕获 `owl:disjointWith/equivalentClass` 入 `Spec.Axioms`；数据属性捕获 `owl:DatatypeProperty`（REQ-268/M77）；qualitygate 的 `reasoning_owlrl` 推理档检查（REQ-255）；复杂公理（匿名节点）有损丢弃——**轻量 spec_json 与完整 OWL 的表达力边界**是项目刻意保留的教学点（90 号 §1）。

### 3.3 SKOS（Simple Knowledge Organization System）

- **定义**：表示**叙词表/分类法/受控词表**的 W3C 标准：`skos:Concept`（概念）、`skos:ConceptScheme`（概念集）、`skos:prefLabel/altLabel/hiddenLabel`（首选/别名/隐藏标签）、`skos:broader/narrower/related`（层级/相关）、`skos:inScheme`。
- **关系**：与 OWL 的分工——**OWL 建形式化类（可推理），SKOS 建人读概念组织（分类导航）**；大型本体常用「OWL 管顶层类 + SKOS 管实例化术语」混合。本项目 KB/伴生检索的别名（altLabel）召回即 SKOS 思想。
- **本项目落点**：`sidecar_skos_test.go`——SKOS 导入识别（REQ-235/M62）；伴生检索定义文本向量 + 别名回溯（REQ-287）。

### 3.4 本体 / 词表 / 分类法 / 叙词表——概念层级对照

| 概念 | 形式化程度 | 代表 | 与本项目关系 |
| --- | --- | --- | --- |
| **Ontology（本体）** | 最高：类公理+推理 | OWL 本体 | 本模块主角 |
| **Vocabulary（词表）** | 中：类+属性声明 | FOAF、DCTERMS | 复用来源（OntoExtend 路径 LOV 词表） |
| **Taxonomy（分类法）** | 低：纯层级 | 图书分类 | SKOS broader 链 |
| **Thesaurus（叙词表）** | 低-中：层级+相关+等价 | GND、MeSH | SKOS 全套 |

### 3.5 复用词表生态：FOAF / DCTERMS / LOV / ODP

- **FOAF**（Friend of a Friend）：人员-组织关系的经典词表——本平台组织人员示例本体的建模参照（00 号相关资料）。
- **DCTERMS**（Dublin Core）：文献元数据词表。
- **LOV**（Linked Open Vocabularies）：可复用词表索引——OntoExtend 流程（构建路径 5）的词表来源。
- **ODP**（Ontology Design Pattern）：**本体设计模式**——成熟可复用的建模套路（如 part-whole、event）；OntoExtend 流程的「ODP 精选模式」即此（00 号 §六路径）。

## 4. L3 约束校验层：SHACL / ShEx

### 4.1 SHACL（Shapes Constraint Language）

- **定义**：W3C 2017 推荐的 RDF **数据约束校验**语言。核心三件套：**Shape**（约束模板 `sh:NodeShape`）、**PropertyShape**（属性约束 `sh:path` + `sh:minCount/maxCount/datatype/pattern`）、**Target**（约束作用对象 `sh:targetClass`）。校验产出标准化**验证报告**（`sh:conforms` + 违规明细）。
- **关系**：与 OWL 的本质区别——

| | OWL | SHACL |
| --- | --- | --- |
| 语义 | **开放世界**（OWA）：没说的不代表错，还能推出新事实 | **闭世界**（CWA）：没说的/说错的就是违规 |
| 用途 | 推理（§5） | 校验（查违规、出报告） |
| 失败语义 | 不一致（inconsistent） | 违规（violation） |

  二者**互补不互斥**：主流工程实践 = OWL 管语义推理 + SHACL 管数据质量门禁。
- **本项目落点**：**自研轻量替代**——qualitygate 16 检查项数据驱动门禁（`internal/qualitygate`，REQ-171）+ `dangling_dataprop_domain / undeclared_attribute_key / dangling_axiom_ref` 检查 + 三维评分（完备 .35/一致 .45/可维护 .20）= SHACL「形状约束→验证报告」思想的 spec_json 平面实现（90 号 §2）；oo Data Pipeline 的 `map→ingest→shacl` 管线思想已在 ontobuild.go 注释留档。**教学点**：为什么不用真 SHACL 引擎——spec_json 主形态下结构校验只有一条（Spec.Validate），引入 pyshacl 会重蹈 semantica venv 覆辙（D-O15 教训）。

### 4.2 ShEx（Shape Expressions）

- **定义**：与 SHACL 同期竞争的校验语言（社区标准），紧凑的 DSL 语法描述节点形状。
- **关系**：与 SHACL 解决同一问题；SHACL 胜出为主流（W3C 推荐 + 工具链广）。知道存在即可。

## 5. L4 查询与操作层：SPARQL

### 5.1 SPARQL 1.1 查询

- **定义**：RDF 的标准查询语言（对标 SQL 之于关系表）。四种查询形态：

| 形态 | 用途 | 例子 |
| --- | --- | --- |
| **SELECT** | 查变量值（最常用） | `SELECT ?name WHERE { ?p foaf:name ?name }` |
| **ASK** | 存在性判定（布尔） | 覆盖测试快筛的逐 CQ 精判（REQ-274） |
| **CONSTRUCT** | 查询结果重建新三元组 | 数据转换/子图抽取 |
| **DESCRIBE** | 返回资源的子图描述 | 快速看某实体全貌 |

- **关键语法**：`PREFIX` 前缀声明、WHERE 三元组模式（变量用 `?x`）、`FILTER`（表达式过滤）、`OPTIONAL`（左连接）、`UNION`（并）、**property path**（属性路径：`/` 串联、`|` 或、`^` 反向、`+/*` 任意深度——递归查询利器，对照 74 号 Snowflake 递归 CTE L1 学习素材）、聚合（`COUNT/SUM/GROUP BY/HAVING`）、`ORDER BY / LIMIT / DISTINCT`。
- **本项目落点**：SPARQL 工作台（Yasgui）；`onto_sparql_query` facade 工具（只读 SELECT 白名单 + 10s 超时 + 200 行上限，D-O17/REQ-151）；onto_* 翻译透视（REQ-94）——每个 facade 调用都可看到翻译后的 SPARQL。

### 5.2 SPARQL Update

- **定义**：SPARQL 的**写操作**扩展：`INSERT DATA / DELETE DATA`（直接增删）、`INSERT {…} WHERE {…} / DELETE {…} WHERE {…}`（条件改写）。
- **关系**：查询只读、Update 可写；运行时层 endpoint 分别暴露 `/query` 与 `/update` 端口。
- **本项目落点**：对 Agent 的契约**刻意只读**（5 个 onto_* 工具零写操作）——「受控固定工具 vs 任意查询通道」的取舍是教学点（00 号 §运行）。

### 5.3 SPARQL Protocol（Endpoint）

- **定义**：SPARQL over HTTP 的标准协议——查询引擎暴露 HTTP 端点，`GET/POST ?query=…`（Content Negotiation 返回 JSON/XML/CSV）。
- **关系**：是「运行方式」的统一抽象——无论底层 Oxigraph 还是 Fuseki，Agent 与工作台只见 HTTP endpoint。
- **本项目落点**：运行方案端点查看（运行栏）；Runtime Manager 统一编排引擎与方案启停（90 号 §0）。

## 6. L5 推理层

### 6.1 RDFS/OWL 推理

- **定义**：从已有三元组按语义**推出新三元组**——`A subClassOf B` + `x type A` ⇒ `x type B`；`domain` 传播、逆属性、传递属性等。RDFS 推理最轻，OWL 2 RL 可完全规则化物化。
- **关系**：与查询的关系——推理结果可**物化**（提前算好存回库，查询快）或**按需**（查询时现算，省空间）。
- **本项目落点**：Fuseki 推理对照引擎——同一查询并排 diff「有无推理」的结果差异（00 号 §运行），是理解推理价值的**最直观教具**；qualitygate `reasoning_owlrl` 检查项做一致性预筛（REQ-255）。

### 6.2 推理机（Reasoner）

- **定义**：执行 OWL 语义推理的引擎。代表：**HermiT / Pellet**（完整 OWL DL）、**ELK**（EL 配置极速）、Jena 内置规则推理机。
- **关系**：Fuseki（Jena 系）自带规则推理；独立 reasoner 常挂 Protégé 使用（S2 编辑阶段工具链，07 号七阶段清单）。

### 6.3 TBox / ABox

- **定义**：描述逻辑经典二分——**TBox**（Terminology）= 类与属性的**模式层**（What can exist）；**ABox**（Assertion）= 个体实例断言层（What does exist）。
- **关系**：本体文件通常承载 TBox；知识图谱（§7.3）= TBox + ABox 的合称。spec_json 的三要素对照：Concept/Relation 偏 TBox，Instance 偏 ABox。

## 7. L6 运行时层：图数据库与生态

### 7.1 三元组库（RDF Store）vs 属性图（LPG）

| 维度 | RDF 三元组库 | 属性图 LPG |
| --- | --- | --- |
| 数据模型 | 三元组+IRI+标准化 | 节点/边直接挂键值属性 |
| 查询语言 | SPARQL（W3C 标准） | Cypher（Neo4j）/ Gremlin |
| Schema | 显式本体（RDFS/OWL） | 隐式/可选 |
| 推理 | 标准推理语义 | 无标准，靠插件 |
| 交换 | RDF 全家桶格式 | GraphML / GEXF 等松散格式 |
| 适合 | 语义互操作、跨源集成 | 图算法、高性能遍历 |

- **本项目落点**：**P1 唯一引擎 = Oxigraph**（D-O5 避免自研）；GraphML 作为导入格式之一是两世界的桥（90 号 §1）；Cayley 占位（P2 可选）是属性图对照位。

### 7.2 引擎生态一览

| 引擎 | 栈 | 定位 | 本项目角色 |
| --- | --- | --- | --- |
| **Oxigraph** | Rust | 轻量嵌入式 SPARQL（单二进制/内嵌库） | ✅ P1 默认引擎 |
| **Jena Fuseki** | Java | 全功能 RDF 平台（含推理） | ✅ 推理对照引擎 |
| **Virtuoso** | C | 企业级大规模三元组库 | 了解即可 |
| **GraphDB**（Ontotext） | Java | 企业级 + 强推理 + 语义搜索 | 了解即可 |
| **Stardog** | Java | 商业知识图谱平台（虚拟图） | 对照 Snowflake 语义层（74 号） |
| **Cayley** | Go | 轻量图数据库 | 占位 P2（D-O5 另议） |

- **本项目落点**：运行栏引擎分组（Oxigraph/Fuseki/引导/Cayley 占位）——「引擎可替换、契约不变」的运行抽象（D-O17 facade 5 工具）。

### 7.3 知识图谱（KG）与本体的关系

- **定义**：**本体 = 概念模型（TBox，Schema）**；**知识图谱 = 本体 + 实例断言（ABox，Data）**的合称——工业语境常混用。
- **关系**：本平台的分层实践——本体资产（TTL）装载即 KG（「TTL 即 KG」）；另有 LLM 抽取文本建 KG 的独立来源（SQLite 三表 kg_entity/kg_relation/kg_claim，claim 带 chunk_id 溯源，90 号 §4）。

### 7.4 GraphRAG

- **定义**：**图增强检索生成**——检索时经知识图谱扩展关联实体（一跳/多跳），把结构化关系注入 LLM 上下文，缓解纯向量检索的语义漂移（微软 2024 提出范式）。
- **关系**：向量检索（语义相似）+ 图扩展（结构关联）+ 生成三者组合；是 KG 在 AI 时代最重要的消费形态。
- **本项目落点**：GraphRAG 三步检索（向量命中 → KG 一跳扩展 → 汇出关系与 claims）；伴生检索三臂 RRF k=60（FTS5 兜底 + 定义文本向量 + 图臂，REQ-287）+ 社区摘要（REQ-288）= GraphRAG 的轻量自研实践；对照 OntoFlow 写入侧聚合（42 号）与 Snowflake Flattened GraphRAG（74 号 REQ-313）。

## 8. L7 溯源与治理层

### 8.1 PROV-O（Provenance Ontology）

- **定义**：W3C 溯源本体的 RDF 词表——核心三角 **Entity**（产物）/ **Activity**（活动）/ **Agent**（责任者），关系 `wasGeneratedBy / used / wasDerivedFrom / wasAssociatedWith / wasAttributedTo` + 时间戳。
- **关系**：回答「这条数据/这个结论从哪来、谁在何时用什么做的」；是决策审计的标准化语言。
- **本项目落点**：审计表决策链 → **PROV-O Turtle 导出**（Go 原生模板，零 Python 依赖，消费与审计栏，90 号 §5）；KG claim 的 chunk_id 溯源是同一思想的数据层实现。

### 8.2 命名空间设计与常见前缀

本体工程第一决策：IRI 命名空间划分。常用前缀速查：

| 前缀 | IRI | 用途 |
| --- | --- | --- |
| `rdf:` | http://www.w3.org/1999/02/22-rdf-syntax-ns# | RDF 原语（type/type/first…） |
| `rdfs:` | http://www.w3.org/2000/01/rdf-schema# | RDFS 词汇 |
| `owl:` | http://www.w3.org/2002/07/owl# | OWL 词汇 |
| `xsd:` | http://www.w3.org/2001/XMLSchema# | 数据类型 |
| `sh:` | http://www.w3.org/ns/shacl# | SHACL |
| `skos:` | http://www.w3.org/2004/02/skos/core# | SKOS |
| `prov:` | http://www.w3.org/ns/prov# | 溯源 |
| `foaf:` | http://xmlns.com/foaf/0.1/ | 人员组织 |
| `dcterms:` | http://purl.org/dc/terms/ | 文献元数据 |
| `attr:` | 项目内部命名空间 | spec 数据属性（TTL 导出，90 号 §1） |

- **关键工程点**：IRI 稳定性 > 可读性；改 IRI = 破坏所有下游引用（对照 REQ-249 同名歧义、67 号 B5 确定性身份键）。

### 8.3 版本化 / 模块化 / 映射——多本体协作三件套

- **版本化**：本体演进快照策略。本项目「保存即新版本 + diff 三集合统计 + 候选状态机」（REQ-207 vN-cK）。
- **imports 模块化**：`owl:imports` 声明依赖其他本体，装载时合并。68 号五档方案调研的档一。
- **SSSOM 映射**：标准化本体间**术语映射**格式（同一概念的跨本体对齐）。68 号调研已收口为「模块化引用 + SSSOM 映射档」拍板（REQ-262 细化待拍板）。
- **本体间对齐工具生态**：LogMap/AgreementMakerLight 等自动匹配系统（68 号）。

## 9. L8 方法论层：从需求到本体

### 9.1 CQ（Competency Questions，能力问题）

- **定义**：本体建模的需求载体——「这个本体必须能回答的问题清单」。建模前先写 CQ（如「某设备当前由谁维护？」），本体交付时逐条验证（理想验证 = 转 SPARQL 可执行）。
- **关系**：CQ 是连接业务需求与形式化模型的桥；是 OntoChat 四步工作流的核心环节；「CQ→SPARQL 验收」是本体质量的形式化检验。
- **本项目落点**：`spec.CQ` 字段；OntoChat 流程 CQ 抽取（REQ-272 人工确认卡）→ CQ 分析聚类去冗余（REQ-273）→ 覆盖测试快筛（REQ-274 口语化 + Yes/No 判定 → 存疑转 SPARQL 精判）→ REQ-255 验收链路——**完整 CQ 方法论教学闭环**。

### 9.2 七阶段与六路径（本项目教学框架）

- **七阶段**（REQ-74）：S1 来源 → S2 编辑 → S3 校验 → S4 可视化 → S5 运行 → S6 服务化 → S7 对接 Agent——本体资产全生命周期的概念化骨架，与本文 L1~L7 分层**正交对照**（阶段是时间维，分层是技术栈维）。
- **六路径构建**（00 号 §设计原理）：自定义/OntoChat/由知识库构建/~~oo~~/OntoExtend/~~semantica~~——同一 spec_json 收敛，殊途同归。

### 9.3 建模方法论参照卡（S1~S4 阶段）

学习中心五模块方法论卡片（REQ-90/91）的原理索引：自顶向下（领域驱动）vs 自底向上（数据驱动）vs 中会合；Helix Foundry 数据驱动推断（67 号）与 Snowflake Autopilot（74 号）是自底向上自动化的两个当代样本。
