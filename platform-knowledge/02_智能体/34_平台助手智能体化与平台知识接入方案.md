## 1 目标与范围

**一句话**：把设置中配置的内置「平台助手」升级为智能体界面的**内置对话智能体**——具备平台知识（能答"怎么用/为什么"）、能查系统状态、能对低危配置**提案修改**（diff 确认后执行）；同时把 `platform-knowledge/`（42 md/715K）抽为**可检索的知识库**，作为其知识底座。

**做：**
1. 平台助手对话化：智能体列表内置卡片 + 专用对话端点（多轮、SSE、工具循环）；
2. 平台知识 KB 化：目录扫描 → chunk → 导入 → 增量同步 → 检索工具化；
3. 分级工具面：L0 只读全开 / L1 写提案白名单（diff 确认两段式）/ 删除类不做。

**不做（明确排除）：**
- 高危配置直写（模型连接增删改、Agent 配置改）——不进首批白名单；
- 任何无确认的写操作、任何删除操作；
- 知识图谱化（KG）——不做，留待触发条件（见 §8）；
- 悬浮泡泡形态（REQ-168 独立保留；其"操作指令执行+解释回答"意图由本方案的内置卡片承接，泡泡入口是否还需要，P3 开发前开发者拍板）。

## 3 后端设计

### 3.1 对话端点与 Agent 组装

- **新增** `POST /api/assistant/chat`（SSE 流式）：入参 `{"conversation_id", "message"}`；会话持久化复用 chat 包既有会话/消息表，agent 标识固定 `builtin-assistant`（与用户 Agent 会话隔离）；
- Agent 组装复用 `chat/assembler.go`：`newChatModelAgent(ctx, "平台助手", description, instruction, maxIter, cm, tools)`（L594）+ `assembleTools` 装配模式（L383）；
- 指令与模型参数：读 `assistant_config`（id='default'）——提示词微调/模型覆盖/temperature 语义完全复用；`assistantDefaultPrompt` 重写为对话角色（平台使用答疑/状态查询/配置提案/内容优化四职责，附 platform-knowledge 目录树索引，约 1.5K tokens，三级注入 L1）；
- 工具循环迭代上限沿用 chat 包默认（max_iteration），60s 工具超时沿用 REQ-167 口径。

### 3.2 工具面定义（分级白名单）

| 级别 | 工具名 | 实现 | 风险控制 |
| --- | --- | --- | --- |
| L0 | `doc_read` | 包装 `docRead` 白名单逻辑（platform-knowledge/ + docs/，仅 .md，fsutil 防越界） | 只读 |
| L0 | `list_model_connections` / `list_agents` / `list_kbs` | 包装既有列表端点（脱敏：不返回 API Key） | 只读 |
| L0 | `get_assistant_config` | 读 assistant_config | 只读 |
| L0 | `search_platform_kb` | KB 向量检索 topK=5（见 §4） | 只读 |
| L1 | `propose_assistant_config` | 产出**配置提案 JSON**（system_prompt/model_conn_id/temperature 三字段内的 diff）→ 前端 diff 预览 → 用户确认 → 后端才执行 PUT assistant_config | 两段式：确认前不落库 |
| L1 | `propose_kb_import` | 提案导入/重建索引某文档 → 前端确认 → 执行 | 两段式 |（✅ 交付裁决 2026-09-29：以 sync_platform_kb 增量对账工具覆盖其诉求——平台知识为 repo 派生内容，同步幂等且无破坏面，无需提案制；本行保留为设计留痕）

**执行模型（安全基石）**：L1 工具只产出**提案**，不直接执行；确认动作由用户在前端完成，后端收到确认回调（或前端直接调既有 PUT 端点）才生效——LLM 幻觉/误操作被确认环节拦截。交互复用 REQ-167 diff 预览组件心智。

**明确不开放**：模型连接写、Agent/项目/本体/技能任何写、KB 删除、全部 DELETE 类。

### 3.3 权限与身份

- 平台助手无用户身份概念（内置），工具面即权限面（白名单硬编码于助手装配处，不进通用工具注册表）；
- `tool_approval` 机制（agent 表字段）不适用（不落表）；确认交互在助手前端会话内实现。

## 4 平台知识 KB 化设计

### 4.1 同步管线（新增任务，非服务）

- **建库**：启动时/手动确保存在专用知识库「平台知识」（名称固定，来源标记 `source=platform-knowledge`）；避免与用户自建 KB 混淆；
- **同步任务** `syncPlatformKnowledge`（backend/internal/kb/ 新增，命令式任务非常驻）：
  1. 遍历 `platform-knowledge/**/*.md`（42 份）；
  2. 增量判定：文件 mtime + git commit hash 对比 KB 文档元数据（`knowledge_docs` 扩 `source_path`/`source_hash` 两字段或等价 KV）；
  3. 变更文档：切 chunk（复用 split）→ `KB.Import(ctx, kbID, title, content)` 走既有管线（embedder/qdrant 现成）；
  4. 删除文档：**标记隔离**（从检索索引摘除，KB 记录保留）——不物理删除；
- **触发**：后端启动时全量对账一次 + 手动触发端点（设置页平台助手分区加"同步平台知识"按钮）；
- **REQ-171 P2⑤ 关系**：本方案承接「平台知识入库」这一具体子集并先行落地；P2⑤ 的通用管线增强（分块策略/质量评估等）仍独立排期，互不阻塞。

### 4.2 检索工具

- `search_platform_kb`：POST 内部调用既有检索路径（等价 `previewKBSearch` 的 service 层入口），topK=5，返回 chunk 文本+来源文档路径（供 doc_read 二次精读与前端引用展示）；
- 前端对话消息中检索命中显示来源徽标（文档名，点击可打开平台知识阅读抽屉——复用 REQ-169 DocViewerModal）。

### 4.3 三级注入汇总

| 级别 | 机制 | 本方案落点 |
| --- | --- | --- |
| L1 提示词 | 目录树索引写入 assistantDefaultPrompt | §3.1 |
| L2 精读 | doc_read 工具按需读全文 | §3.2 |
| L3 泛搜 | search_platform_kb 语义检索 | §4.2 |

## 5 前端设计

1. **智能体列表内置卡片**：列表头部独立"内置"小节（分区展示，不与用户智能体混排）；固定徽标「内置 · 平台助手」；点击进入对话页（ChatWindow 复用，顶部显示助手说明与配置入口链接）；卡片不可编辑/删除/复制；
2. **对话页**：复用 ChatWindow + SSE 链路；输入区不带模型/温度 chips（配置走设置页）；
3. **diff 确认交互**：复用 REQ-167 优化预览组件——L1 工具提案以 JSON diff 卡片呈现，「确认执行 / 忽略」两按钮；确认后调既有 PUT/POST 端点；
4. **设置页平台助手分区增强**：新增「同步平台知识」按钮 + 最近同步时间/文档数显示。

## 7 分阶段交付与验收

| 阶段 | 内容 | 验收 |
