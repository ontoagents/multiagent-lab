# 工作区领域层（垂直分层）可行性与落地方案

**判定：可行但有条件** — 垂直分层（工作区=领域容器、项目=执行容器）在现有代码上可行：关键在「创建时继承」写时复制——工作区默认 KB/方案在 CreateConversation store 层默认值填充段一次写入，运行期装配链/recallKB 单库门禁/retrieval 事件契约零改动。落地=M1 实体+继承（后端小件先行）→M1b 工作区页（模块内页签，导航项不动不触 REQ-111）→M2 项目可选归属与继承→M3 记忆作用域随衍生②立项。前置拍板一项：本方案的工作区是「项目之上的新实体」，与已落档的「工作区=项目显示层别名」（01 §3.15③、REQ-495 拍板②语境）是实体指称反转，属语义级需求变更，须先落档再动工。

## 二、数据模型
- workspace 表（迁移编号动态领取：撰写时点 migrations 目录最大 078 共 76 文件，但 079 已被在途 REQ-545 占用=quiz_item.coverage_verdict〔docs/19:42、18:115 实读〕、080 有 REQ-546 提案占用——工作区轮开工当日以 `ls migrations/` 取 max+1 为准，下同）：id TEXT PK / name / description / default_kb_id TEXT（无 FK）/ default_profile_id TEXT（无 FK；主平台对 runtime-manager 的引用 id 字符串，与 conversation.runtime_profile_id 同构 O-6）/ default_agent_id TEXT（无 FK；工作区直挂对话默认运行目标，可空=前端回落内置助手）/ created_at / updated_at。全部可空=未设默认
- conversation 加列 workspace_id TEXT NULL REFERENCES workspace(id) ON DELETE SET NULL（同迁移）——直挂对话 scope 保持 'agent'、agent_id 必填（Assemble 要求 agent 非 nil，assembler.go:233-235；store 层 :110-111 已有 scope=agent 必带 agent_id 校验）。删工作区 SET NULL（对话回落智能体页，消息资产保留）而非 CASCADE（project 现状 CASCADE 见 projects.go:98-108，但对话含消息资产，保守取向），终归开发者拍板
- 互斥校验（新增，初稿缺失）：CreateConversation store 层加「project_id 非空时拒绝 workspace_id 非空」（400），位置=conversations.go:107-113 既有 scope 互斥校验旁；无 schema 级 CHECK（避免重建表），应用层单点守卫即可覆盖唯一写入口（handlers_conversations.go:31-47 decodeJSON 直传）

## 三、上下文解析链
- 设计原则：工作区只提供「会话创建时的默认值」，不新增运行时覆盖层级——运行期装配链（recallKB/MountOf/审批/context_mode/伴生）零改动，合并序叙事维持现状，仅新增一段创建期求值
- 覆盖域仅两项（存储层纯会话级、agent 表无同名字段）：①KB 默认库（对位 conversation.kb_id/enable_kb）②本体运行方案（对位 conversation.runtime_profile_id/ontology_enabled）。措辞修正（红队核验）：agentCols 实为 39 列（sed -n 78p | tr ',' wc -l=39），物理表 40 列含被 agentCols 排除的遗留列 companion_ontology（021 加入、REQ-216 退役为派生）——两口径下均无 kb_id/runtime_profile_id，承重结论不变；另「本体域已有 agent 级默认先例」如实标注=companion_ontology_id（REQ-302 两层化），KB/方案与之不同处在于语义属场景供给而非智能体能力
- 创建期求值链（优先级从高到低）：请求显式参数 > 项目默认（M2，仅继承转发不加覆盖面）> 工作区默认 > 零值。现状修正（红队 obj-6 采纳）：前端建会话从不带 kb_id——AgentsPage.tsx:58/98 两处 createConversation 均只传 {scope:'agent', agent_id, title:'新对话'}，KB/方案是建后经 chips patchConv 写入（ChatWindow.tsx:621-643）——故求值链第一层在 M1 是前向兼容位（现状无调用方传参），如实标注为死代码而非既有行为；单点函数 ResolveConvDefaults 落 backend 一处，落档为方案档 §上下文解析
- 降级与失效（写死口径）：①默认库被删→config 列无 FK 不级联，ResolveConvDefaults 求值校验存在性，失效即回落零值；②默认方案失效（runtime-manager 方案停止/删除）→既有 ontology.unavailable 单次降级不阻断（assembler.go:1074-1082 先例）。M1 降级提示=静默回落+chip 态可见（会话行即最终态，KB/本体 chip 显示未开启与手动新建无异）——不扩 createConversation 响应契约（响应是会话 JSON，加 warnings 字段属新契约且无前端消费项，初稿设计撤销）
- 显式关闭语义天然成立（写时复制核心收益）：会话创建后行内 kb_id/enable_kb 即普通会话级配置，chip 关闭（patchConv 现有通路）即真正关闭，不被工作区默认复活
- 存量与归属变更兼容：工作区改默认不影响已建会话；批量刷新走 M2「应用到现有会话」显式动作，幂等补齐只覆写仍处继承值的行（沿迁移 031 MigrateBindingsToOntologies 幂等先例），不做 SQL 裸回填
- 前端生效透出：ConvSettingsPanel「生效配置总览（合并序：会话>智能体>全局）」（ConvSettingsPanel.tsx:75）M2 增「继承自工作区」来源行；M1 不动总览，chip 显示当前生效值已够
- 对比窗格零改动：PaneConfig 空值=继承对话当前配置（runner.go:167-176 注），读会话行——写时复制后行内已含继承值，窗格继承链自动获得工作区默认
- 装配分流不变：工作区直挂对话 scope='agent' 走 assembleSingle（assembler.go:255-257 scope!=='project' 分支），无项目加载/协作编排介入；文件能力继承 REQ-336 智能体面（见 ia 节修正）
