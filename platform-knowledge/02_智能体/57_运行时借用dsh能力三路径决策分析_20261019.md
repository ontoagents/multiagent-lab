# 运行时借用 dsh 能力：三条路径决策分析（57 号）

## 一、差距归因：先拆因子，再谈路径（现状分析之一）

`Agent = Model + Harness`（41 号，dsh 官方公式）。「平台跑复杂任务不如 dsh/zcode」的感知差距由三个因子叠加，**必须拆开量化，否则任何路径决策都建立在误判上**：

| 因子 | 内容 | 平台现状 | 与运行时路径的关系 |
| --- | --- | --- | --- |
| **模型因子** | dsh 官方基准=DeepSeek-V4-Pro（max 思考档、Minimal 模式）；zcode=GLM-5.3（OX Alpha 智能体编码后训练、1M 上下文）。模型与 agentic 后训练差异与运行时无关 | 平台 agent 可配任意推理后端与模型；若未用同级模型/思考档，此部分差距必然存在 | **换任何运行时都无法消除**；选模型可消除 |
| **Harness 因子** | 36 号十层对照中本地弱项：状态真源/上下文工程/工具广度/多智能体纵深 | **大头已按 38 号路线借鉴交付**（REQ-201~204/210/224/231/232 ✅，53~56 号域档承接）；残留：token meter 单点计价、KV-cache 前缀保持、终端 PTY/后台任务工具、subagent continuation（REQ-208） | **路径②的领地**；沿既有 REQ 增量，无需新运行时 |
| **场景因子** | dsh/zcode 是编码 harness（真实文件系统+终端+仓库），编码任务是其甜区；平台是多租户通用平台 | 平台任务谱系远宽于编码 | 部分差距是场景匹配度，非能力缺陷 |

**可证伪实验（关键）**：REQ-223 agenteval 已支持 `AGENTEVAL_AGENT_A` / `AGENTEVAL_AGENT_B` 两个存量 agent 各跑全量 12 任务出对照（LLM Judge + build tag `agenteval`）。同模型、只切 `inference_backend`（eino-adk vs dsh-acp）跑一轮 → harness 因子被单独量化，模型因子同步可比。**零代码，仅配置两份 agent**。见 §七 T1。

## 二、现状分析之二：接入面盘点（底座已具备什么、真正缺什么）

- **运行链路**：`backend/internal/inference/`（后端注册表：eino-adk 默认 + 外部 CLI 探测）→ `backend/internal/chat/{runner,external}.go`（进程内 / 外部桥接双轨）→ agent 装配链（hooks/审批/verify/沙箱/事件契约，53 号代码地图）。
- **dsh 对接现状**：headless 通道（M24，cliAdapter）+ **ACP 主通道**（REQ-206 S1+S2：`streaming.go` streamingProc + `acp.go` acpClient）。2026-10-12 真机四项翻正：①会话延续（服务端 UUID 映射 `data/acp_sessions.json`）；②MCP 挂载直通（`type:"http"`+headers 必填规则）；③`DSH_PERMISSION_MODE=read-only` → 平台 approval.request 审批闭环；④事件形态勘误落档。能力等级 **L3（标准语义级）**，31 号 §5 矩阵为权威。
- **五层借鉴现状**：Context（REQ-201 ✅ 预算三档/压缩/剪枝/轮次保全）、Harness（REQ-202/231/232 ✅ hooks/重试/审批三档）、Loop（REQ-204 ✅ checkpoint/续跑/todo.md）、Graph（agent_as_tool 推荐，REQ-205 编排未启动）、Model（后端可插拔 ✅）。
- **边界约定**：D-O5 开源优先不重复造轮子；D-O15 不引 Python/Node 运行时进主链；36 号两项「不推荐」（换掉 adk 自研循环 / 全面插件化 Cordis 化）。
- **结论**：底座已具备「对接通道 + 五层借鉴框架 + 评测武器（agenteval）」；真正缺的不是新运行时，而是 **①差距的量化归因（未做过）②触发驱动项的领取时机判断 ③外部后端使用策略（路由+诚实标注）**。

## 三、路径一：直接借用 dsh 能力——已建成，残余损失与增量空间

### 3.1 已建成部分（引用 31 号，不重复展开）

headless（M24）+ ACP（REQ-206 S1/S2 ✅）双通道；会话延续/MCP/权限审批/事件落 `run_event` 四项真机翻正；风险台账（SDK 无版本协商、ACP 仅本机 stdio 无鉴权、锁版本 0.1.5-rc.3）已在 31 号 §13。

### 3.2 残余能力损失（该形态的固有上限，非待修缺陷）

| # | 损失 | 根因 | 缓解 |
| --- | --- | --- | --- |
| 1 | AgentAsTool/Workflow 不映射 | dsh 内部 subagent（maxDepth=1）与平台 Graph 编排是两套语义 | 平台侧编排继续走 agent_as_tool（56 号推荐轨） |
| 2 | 平台技能降级为 instruction | dsh 原生 Skills 是其自有文件形态；平台技能的知识文件/工具白名单无法变成 dsh skill | 技能内工具经 MCP 挂载可直通（见 3.3-A2） |
| 3 | 事件面只有标准语义更新 | ACP 协议面 13 调用，无内部轨迹全量 | REQ-206 S3（SDK `session.event` 全量，可选待领取） |
| 4 | 单 workspace | dsh 会话绑定单目录 | 平台多项目文件世界不做多根映射，选 work_dir 挂载 |
| 5 | 无 transcript 回放 UI | dsh web UI 特性不经 ACP 暴露 | 平台自有调用轨迹面板（REQ-217/284）已覆盖 |
| 6 | **外部后端旁路平台装配链** | `inference_backend` 为外部 CLI 时，平台 hooks/审批三档/work_dir/verify 全不生效（53 号开放问题 5）——治理责任移交 dsh 自身 harness | 治理面 UI 诚实标注（53 号 W5，REQ-206 扩注归属）；dsh 侧权限模式已可配（read-only→审批闭环已翻正） |

### 3.3 还能做的增量（全部小件，无新立项）

- **A1 后端路由策略**：复杂任务 agent 默认/建议选 `dsh-acp` 后端——纯配置层 + 产品引导，随 W5 标注一起落（REQ-206 扩注）。
- **A2 平台工具 MCP 挂载复用**：平台 `/mcp` HTTP 端点 × dsh `mcpCapabilities.http=true` 已真机直通——本体工具（onto_*）/连接器工具可挂进 dsh 后端 agent，把平台资产带进 dsh 世界（31 号 §12.4②）。
- **A3 REQ-206 S3**：SDK 全量事件审计（调试/合规场景按需领取）。

## 四、路径二：借鉴方案与代码——不新增运行时，沿既有 REQ 演进

### 4.1 事实：这条路径的主体已经走完

「借鉴 dsh 实现新增本项目运行时能力」≠「新增一个运行时」。平台五层运行时（54~56 号域档）自 REQ-201 起就是按 dsh 借鉴路线增量演进的：

| dsh 能力 | 平台承接 | 状态 |
| --- | --- | --- |
| 上下文工程（compaction/pruner/spill/token meter） | REQ-201：tool 轮次保全/预算三档/LLM 压缩持久化/准入链/剪枝（54 号） | ✅ M37（token meter/KV 前缀保持未含，见 4.3） |
| 工具流水线/hooks/verify/重试 | REQ-202 + REQ-224/231/232：HookChain/失败合成/审批三档/hooks 可配（53 号） | ✅ M38/M52/M58 |
| 渐进披露/上下文预算 | REQ-203 | ✅ M38 |
| Loop 闭环（checkpoint/续跑/todo） | REQ-204 + REQ-210 | ✅ M39/随 201 |
| 事件契约/Trajectory 审计 | REQ-217/224/284 调用轨迹面板 | ✅ |
| 会话持久化（JSONL 单写者） | 平台 SQLite 会话+run_event 双写（36 号指出的真源弱项，治理已收敛） | ✅（形态不同） |
| subagent continuation / 多提供方 | REQ-208 可继续子 Agent | 📋 M42 触发驱动 |
| 工作流编排 | REQ-205 | 📋 M40 触发驱动 |
| 沙箱纵深（PTY/后台任务） | REQ-225 | 📋 M53 触发驱动 |
| MCP 工具清单装配缓存 | REQ-356 | 📋 M156 待领取 |

**结论（对问题②的直接回答）**：不需要也不应该「新增一个运行时实现」——并行运行时=双倍维护+治理分裂+「配置即行为」被破坏；正确形态是**继续在现有五层运行时上按触发条件领取上表 4 个遗留项**。这既符合 D-O5（不重复造轮子），也符合 36 号「借鉴架构思想而非照搬实现」的既定纪律。

### 4.2 为什么不再建并行运行时（三条件否决）

1. **维护翻倍**：dsh 是 60+ 包 monorepo、1.6 万+ commits、v0.2 预览密集破坏性迭代——任何第二运行时都要承担同量级追平成本。
2. **治理分裂**：审批/审计/事件契约/评测（agenteval）全部按单运行时建设，双运行时=每项基建×2。
3. **收益存疑**：harness 因子残留项（token meter/终端工具/continuation）在现有运行时内可增量实现，不需要换内核。

### 4.3 深化借鉴候选（观察项，挂 54 号续行，不新立项）

- token meter 单点计价（dsh 全局 token/成本单源）；KV-cache 前缀保持式压缩（压缩不改写前缀）；终端 PTY/后台任务工具（随 REQ-225 场景）。

## 五、路径三：基于 dsh 源码重开运行时——可行性与成本（对问题③的直接回答）

### 5.1 三种形态

| 形态 | 内容 | 一次性成本 | 持续成本 | 判定 |
| --- | --- | --- | --- | --- |
| **C1 fork dsh 自用** | 保持 TS 栈独立仓库深度定制，经 ACP 对接平台 | 低（fork 即得全部能力） | 分叉维护：上游预发布密集破坏性迭代（v0.2/桌面版 9-30/多版本），追平=每月人日级；双栈运维 | **唯一可接受变体**（仍属路径①），触发条件=确需魔改 dsh 本体且 MCP/profile 表达不了 |
| **C2 Go 移植重写** | 按平台 Go 栈重写 dsh：Cordis 微内核五原语 + session/deriveMessages + agent-loop turn/step 状态机 + compaction（阈值公式/事件对当锁/八段摘要）+ 工具六段流水线 + subagent + JSONL zstd/flock 持久化 + 100% 覆盖门禁工程体系 | **3~6 人月**可达用级下限（对照：REQ-201~204 借鉴式落地约 10~15 人日拿走大头收益） | 上游持续演进 → 永久追平；设计资产持续贬值 | **不推荐**：违反 D-O5/D-O15 精神，摧毁多租户「配置即行为」形态，收益已被路径②提前变现 |
| **C3 源码级直抄** | TS→Go 不可移植 | — | — | **不成立**：MIT 授予的是许可不是跨语言复用；设计已抄（41 号 12 条纪律已转入借鉴清单） |

### 5.2 不推荐 C2 的完整论证

1. **成本结构**：移植不是一次性成本。dsh 仍在 developer preview 快速漂移，重写版从落地首日起就落后于上游，追平是永久税。
2. **收益已被变现**：dsh 的差异化设计（事件日志唯一真源/能力 seam/上下文工程/工具流水线）正是 REQ-201~204 已借鉴交付的内容——重写买到的增量只有「Cordis 插件内核」本身，而 36 号已论证全面插件化**不推荐**。
3. **形态错配**：dsh 是单用户深 harness（单 workspace/本机 stdio/自有持久化），平台是多租户配置驱动平台——重写等于把平台塞进 dsh 的形态，而非把 dsh 塞进平台。
4. **风险**：MIT 无法律障碍（此点明确），但预发布期上游无兼容承诺（31 号 §13 已锁版本应对），重写版将同时承担上游漂移+自研缺陷两类风险。

## 八、需求衔接与决策点（方案 only，待拍板）

**不新立项**：三条路径的结论全部落在既有归属上（REQ-160/201~206/205/208/225/356 或配置层动作）；本轮产出为决策档（本文件），无新 REQ。

| 决策点 | 问题 | 建议默认 |
| --- | --- | --- |
| **D1** | 是否跑 T1 归因基准（需定基准模型与两份 agent 配置） | 跑——半日内可得 harness/模型因子拆分 |
