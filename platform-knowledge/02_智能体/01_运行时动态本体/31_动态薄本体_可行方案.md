## 一、定位：报告路线 × 项目语境的映射

报告的核心命题是**记忆系统视角的动态本体**：智能体长期多会话运行中存在"隐式召回失败"（当前提问与早期陈述无词汇重叠时 dense 检索漏召，Recall@10 从 0.61 跌至 0.28），运行时从对话数据自动归纳一张轻量本体图可使检索在概念层运作（Recall@10 0.706、成本较长上下文降 81%）。报告给出三档路线，其**轻量档**（固定种子 schema + 运行时仅实例填充，1-2 人 / 4-6 周）与本项目现状、开发者"低侵入"要求精准对位。

**「动态薄本体」= 报告轻量档在 eino-multiagent-lab 的落地形态**：

| 维度 | 含义 | 本项目落点 |
| --- | --- | --- |
| 动态 | 随对话运行持续生长，今天长出来的知识明天 agent 就能查到 | 旁路抽取管线 + Oxigraph 会话图增量写入 |
| 薄 | 种子 schema 固定（5 骨架类）、仅实例填充；向量层/自动门控/bi-temporal 后置（报告轻量档边界） | 最小数据模型（§五）+ 三阶段渐进（§九） |
| 隔离 | 每会话产出进独立 named graph，与主本体物理隔离，可整体摘除 | Oxigraph `GRAPH <…/graph/conv-{id}>` |
| 低侵入 | 对话主链路 0 改动、装配逻辑 0 改动、消息库只读、开关默认关 | 三原则（§六） |

## 二、当前项目实现分析（接入面盘点）

**① 会话运行链路（伴生管线的观察对象，全程不改）**：
- 入口：`backend/internal/api/handlers_runs.go` `runConversation` / `resumeConversation` → `chat.Service.Run` / `Resume`（`backend/internal/chat/runner.go`）。
- 装配：`chat/assembler.go` 按 Agent 配置（模型/工具/记忆/知识库）构建 ADK Runner——伴生开关只是 Agent 配置表的一个新字段，装配层读取后决定是否注册伴生查询工具，属配置增量。
- 执行：`runConsumer.consume` 消费 `adk.AsyncIterator[*adk.AgentEvent]`，事件经 `EmitFn` 走 SSE 到前端；运行结束以 `RunResult` 返回——**这就是伴生 worker 的天然触发点（run 收尾 + 消息库游标）**。
- 持久化：SQLite（`backend/internal/store/`），核心表 `conversation` / `message` / `run_event`（REQ-117 调试事件 `debugPersist` 入库）/ `agent` / `model_connection` 等。**消息表已有完整对话事件流，伴生抽取只读该表即可，无需在链路里埋点。**
- 中断恢复与对比运行（`checkpoint.go` / `RunCompare` 双栏）均复用同一 Run 原语，伴生管线对其透明。

**② 推理与抽取能力（复用，不新建模型通道）**：
- 推理后端：`backend/internal/inference/adapters.go` cliAdapter 多后端抽象（含 REQ-160 dsh headless 适配器在研），`/api/ontology-llm/generate`（REQ-98）代理已承载「LLM 抽 KG lightweight」方法位——伴生抽取走同一代理，prompt 库与 JSON Schema 结构化输出约束复用 REQ-127~130 M16 沉淀。

**③ 本体/KG 基础设施（分平面，边界清晰）**：
- 构建平面：`backend/internal/ontobuild/` + `ontology/ontology.go`（BuildProxy/RuntimeProxy 代理 Oxigraph 引擎；REQ-110 TTL 即 KG）。
- 知识库侧 KG：`kg_entity` / `kg_relationship` / `kg_claim` / `kg_community` 表（文档文本抽取，M16 已交付）——**伴生图不进这套表**（来源不同，避免混淆 D-O19 边界）。
- 消费平面：第五栏「消费与审计」按 D-O19 定案只展示本体 TTL 装载来源；伴生图属**第三来源（对话）**，走资产栏独立页签，来源徽标「对话」（与 REQ-163 徽标机制同构）。

**结论：四层架构所需的底座（L1 事件层=消息库、L3 符号层=Oxigraph、M2 抽取=REQ-98 代理、审计=PROV-O 习惯）项目全部已具备；新建的只有 3 块（伴生 worker、候选确认流、伴生开关），全部在旁路。**

## 五、薄本体数据模型

**种子 schema（5 骨架类，一次性预置，薄版不自动生长）**：

```turtle
@prefix bot: <http://eino-lab/ontology/thin/> .
bot:Concept  a owl:Class .   # 概念（领域实体：Pod、HPA、滚动更新…）
bot:Relation a owl:Class .   # 关系陈述
bot:Event    a owl:Class .   # 事件（带时间性动作/变更）
bot:Source   a owl:Class .   # 来源（会话/消息/文档）
bot:Agent    a owl:Class .   # 参与智能体/用户
```

**会话图（named graph 隔离 + 失效化而非删除）**：

```turtle
GRAPH <http://eino-lab/graph/conv-abc123> {
  <…/e1> a bot:Concept ; rdfs:label "Pod 扩容" ;
      bot:extractedFrom <…/msg-42> ; bot:confidence 0.86 ;
      prov:generatedAtTime "2026-09-26T00:00:00Z" ;
      prov:wasGeneratedBy <…/activity-extract-17> .
  <…/e1> bot:relates <…/e2> .
  <…/e0> bot:invalidAt "2026-09-26T00:00:00Z" .  # 矛盾旧边失效化，保留可查历史
}
```

设计要点：①构建平面 spec_json 与主本体 TTL **完全不接触**——伴生图只存在于消费平面（Oxigraph named graph），不产生第二个影子真相源；②三元组自带溯源（`extractedFrom`/`prov:wasGeneratedBy`），满足报告"一切提升带溯源"原则；③低置信度候选只进候选表不入图——对齐报告"低置信信息仍可检索但不影响图"的双存储共生原则的薄版近似。

## 六、低侵入三原则（影响面核对）

| 原则 | 措施 | 影响面 |
| --- | --- | --- |
| 旁路管线 | worker 独立 Go 模块，只读 `message` 表+消费 Run/Resume 收尾事件，不进 Eino ADK run 链路 | 对话主链路/SSE 契约 **0 改动** |
| 可选开关 | Agent 配置页「伴生本体」开关默认关；开启才触发抽取与伴生图查询 | 运行装配仅配置项增量 |
| 产物独立 | 候选表/会话图/审计独立，`DROP GRAPH` + 清候选表即整体摘除，停开关即静默 | Oxigraph 引擎 0 改动；前端 1 页签+1 开关 |

## 七、报告六大风险 → 薄版对策

| 报告风险 | 薄版对策 |
| --- | --- |
| R1 本体漂移/词表爆炸 | 种子 schema 冻结（5 类），类型发现 P3 前不开放——薄版结构性免疫 |
| R2 三元组幻觉 | LLM 只做候选生成，入图必经人工确认（人即门控）；抽取消耗走 REQ-98 代理可控 |
| R3 冷启动 | 薄版无门控预热问题（人工确认不依赖证据积累）；混合检索兜底天然存在（dense 为主） |
| R4 矛盾与时序 | 矛盾检测入候选确认流（同实体新断言提示冲突）；失效化而非删除 |
| R5 隐私治理 | 伴生图会话级隔离可整体摘除；PROV-O 全程审计；开发者数据不出本地 Oxigraph |
| R6 反馈稀疏 | 薄版不依赖反馈信号（人工确认即监督），无此风险 |

## 八、实施价值与项目定位

- **教学价值**：动态本体从论文概念到可操作工程形态的完整最小样本（抽取→确认→入图→查询），与平台"学习智能体构建"定位一致。
- **能力价值**：智能体获得跨会话概念级记忆雏形（P2 起可反查伴生图），为 REQ-103 模式 B（对话式本体构建）提供工程前奏。
- **不动存量**：智能体构建/运行/调试/对比四大既有能力零回归风险（旁路 + 默认关）。

## 十二、图作用域修正：会话隔离 → Agent 隔离（v2.5，2026-09-30，REQ-211 立项依据）

> 触发：开发者指令「发现当前实现中伴生本体是按会话隔离的，这其实不符合实际使用场景，我理解伴生本体应该是 agent 隔离，agent 下会话、agent 参与的项目是不隔离的。分析是否正常及优化方案」。本节=分析结论与详设；**状态：方向成立（开发者判断+本分析一致确认），立项 REQ-211/M44 待领取**；实施后 §五架构与 REQ-170 口径随交付轮同步修订。

### 12.1 判定：会话隔离是 M28 最小闭环的实现口径，不是产品语义——开发者判断成立

**现状盘点（代码级，2026-09-30 复盘）——伴生图五处锁点全部会话维度**：

1. 图 URI：`GraphURI(convID) = {ns}conv-{id}`（companion/sparql.go:29）——一会话一 named graph；
2. 召回全链：`RetrievalContext(conv)` → SelectLabels / SelectEntityInfo / SelectEntityNeighborhood 均传 convID，向量缓存亦按 convID 分桶（companion/retrieval.go）；
3. 入图：ConfirmCandidate / auto-confirm 写 `InsertNodeTriples(c.ConversationID,…)`（companion/service.go:442）——落候选来源会话图；
4. 对齐清单（REQ-194①）：knownEntityLabels 按**会话图**拉已有实体——同名实体跨会话重复建（aligned 只见当前会话清单）；
5. facade：sparql_query `graph=companion + conversation_id` 限定会话图（ontology-service rest.go 工具文案；且文案「graph=ln」系笔误应为本项）。

**当时成立的理由（诚实钢人）**：M28 P1 最小闭环按低侵入三原则落地——按会话 DROP 摘除语义干净、抽取游标天然按会话增量、成长图按会话呈现、named graph 隔离让 SPARQL 零改写；本方案 v1.0 即按「会话图」设计，属**有意取舍而非 bug**。

**为什么不再成立（四条断链）**：

- **① 召回断链（核心缺陷）**：A 会话确认的知识对 B 会话零召回。伴生本体的核心价值=治疗隐式召回失败（§2/32 号：对话中沉淀的领域知识应在后续对话被检索注入），会话隔离使其落空——agent 在某个会话学到「K8s 部署/回滚」术语，但使用发生在随后的所有会话。
- **② 管理已 agent 化、存储与召回仍会话化的半截状态**：REQ-193 侧板铺平、REQ-194 确认桶聚类均按 agent 维度（候选行自带 agent_id），用户心智已是「这个 agent 的伴生本体」，唯独图与召回锁在会话。
- **③ 项目会话知识不回流**：2026-09-27 归属修复让项目会话产候选，但产出锁在单会话图——agent 在项目中学到的领域知识对其独立会话不可见，反之亦然。「agent 参与的项目不隔离」正是开发者点名的场景。
- **④ 成长叙事碎片化**：REQ-154 成长图/成长序以 agent 级知识资产为叙事，会话边界把成长切成互不相通的碎片；矛盾检测（同主体+同关系名失效化）只在会话图内起作用，跨会话矛盾不可见。

**结论**：隔离边界应为 **agent**——该 agent 的全部会话与其参与的项目会话在同一张伴生图内不隔离；会话维度降级保留两处必要职责（12.2），不再作为存储与召回边界。

### 12.2 目标语义

| 维度 | 现状（会话隔离） | 目标（agent 隔离） |
|---|---|---|
| 伴生图 | GraphURI(convID)，一会话一图 | GraphURI(agentID)，一 agent 一图 |
| 召回 | 当前会话图 | 该 agent 图（全部会话+项目会话知识共享） |
| 入图 | 候选来源会话图 | 该 agent 图（来源会话降为 provenance 标注） |
| 对齐清单 | 会话图实体 | agent 图实体（跨会话同名归并） |
| 矛盾检测 | 会话图内同主体 | agent 图内同主体（跨会话矛盾可见） |
| 摘除 | 按会话 DROP | 按 agent 摘除（本体模块单入口不变） |
| 抽取游标 | 按会话 | **按会话不变**（增量正确性与图作用域正交） |
| 跨 agent | 隔离 | **隔离不变**（项目多 agent 各自伴生各自图） |

## 十三、引擎运维面与 IA 归属：方案对比分析（v2.7，2026-09-30，待开发者拍板）

> 触发：开发者指令「当前伴生本体的引擎配置在系统设置中，每个智能体的伴生本体配置和管理在智能体右侧边栏，本体模块中又有伴生本体模块。实际使用中发现多次伴生本体引擎没有启动的问题，也没有界面可以做启动或者查询操作。而且伴生本体作为智能体的功能，放到本体模块下很怪。分析如下方案哪个更好，如果有其他更合适的就提出来」。本节=现状盘点+两方案对比+推荐方案 C（详设）；**状态：待拍板，未立项未实施**。

### 13.1 现状盘点（代码级，2026-09-30）

1. **设置页并无伴生引擎配置**（澄清）：REQ-191「运行环境」分区的引擎配置=本体运行平面（runtimed 拉起方案引擎）的执行方式，与伴生引擎是两套实例；伴生引擎（backend 内置懒启动 Oxigraph :9199）当时被明确排除（「保持进程内轻量单实例不纳入」），其配置仅有 env（COMPANION_OXIGRAPH_BIN/OXIGRAPH_BIN）+固定端口 9199+固定目录 data/companion-graph，不在任何界面。
2. **「多次没启动」机制根因**：引擎生命周期「读侧只领养不拉起、写侧（confirm/抽取）懒启动」——对话收尾抽取或候选确认会把引擎带起来，但**浏览伴生页/侧板/对话召回等纯读路径引擎死了就永远空转**（AdoptRunning ping 失败→静默空图）；且 Engine.Stop 存在但无 API 端点、无任何界面可启动/停止/查健康（状态卡只有 engine_running 标签）。
3. **三处入口职责现状**：设置页（无伴生）；智能体侧板伴生视图（开关+REQ-187 三字段配置 + 跨会话候选管理，REQ-193）；本体模块伴生栏（成长图 3D+候选确认流+agent 级摘除，REQ-195/211）。
4. **判例**：REQ-213（2026-09-30）——平台助手作为智能体的功能，配置**撤出设置页、统一收敛智能体侧板**（功能配置归侧板）；REQ-214——K8s/SSH/MCP 连接器作为平台基础设施进**设置页「连接器」分区**（基础设施运维归设置）。伴生引擎属后者（平台级单例基础设施，服务所有 agent），伴生开关/字段属前者（per-agent 功能配置）。

### 13.2 两方案对比

| 维度 | 方案 1：智能体模块增模块级设置页 | 方案 2：系统设置增独立伴生配置页+增强引擎能力 |
|---|---|---|
| 引擎归属语义 | ✗ 引擎是平台级单例（服务全部 agent），非「智能体模块独有」 | ✓ 平台基础设施运维归设置，与沙箱/本体引擎执行方式同区（REQ-191/214 方向） |
| 入口收敛 | ✗ 新建智能体模块级设置页=第四个伴生入口，加剧分散；与 REQ-191「集中配置」方向相悖 | △ 独立页面偏重——设置页已有「运行环境」分区可承载，无需新页 |
| 治「没启动」 | △ 只解决操作入口，不解决读侧不拉起的机制 | ✓ 配合「读侧兜底拉起」增强可根治（浏览即拉起） |
| IA 归属怪 | △ 不触碰本体模块栏 | △ 同左（两方案均未回答） |
| 成本 | 设置页体系外新建模块设置容器+路由+深链体系 | 引擎卡并入既有分区+三个端点，最小 |

**结论**：引擎运维归设置（方案 2 方向正确），但「独立页面」应收敛为「运行环境」分区内的引擎卡；方案 1 的模块级设置页不建议（单例归属不符+第四入口）；两方案都缺的「读侧兜底拉起」才是治本增强。

### 13.3 推荐方案 C：分层归位（引擎运维→设置 · 功能入口→侧板 · 本体模块=可视化观测）

1. **引擎运维卡并入设置页「运行环境」分区**（REQ-191 同区，收回当时排除的边界）：状态卡（运行中/端点/二进制/数据目录——engine_detail 字段已有）+ **启动/停止按钮**（新端点 POST /api/companion/engine/start、/stop，Stop 复用既有 Engine.Stop）+ 健康查询 + 二进制缺失时按平台给一键下载指引（REQ-146 资产表）；可选端口/数据目录配置入 runtime_settings（DB 覆盖 env，REQ-191 同机制，改后重启生效）。
2. **读侧兜底拉起（治本，默认开，引擎卡可关）**：伴生页/侧板/对话召回等读路径发现引擎未启动→ensureStarted 兜底——单机单实例部署下浏览即拉起，「打开没数据」体验根因消除；「生命周期归写侧」纪律按部署形态放宽注记（多实例部署时关闭该开关回到领养语义）。
3. **功能主入口=智能体侧板**（REQ-193 已在位，REQ-213 判例同方向）：伴生配置页引擎状态卡加「引擎设置」深链（设置页运行环境分区），不加新管理面。
4. **本体模块伴生栏保留但定位收敛**：D-O21 六栏为拍板决策且伴生图作为图资产的可视化有本体模块语义（智能体页亦无页面级承载空间）——定位改为「**伴生图可视化观测**」（成长图 3D+跨 agent 总览为主），页头注明「功能配置与管理在智能体侧板、引擎运维在设置页」；候选确认流与侧板重复度可后续评估精简。若开发者仍觉归属怪，备选=P2 评估「伴生栏并入消费与审计栏（同为伴生图观测语义）」或随智能体页出现页面级承载空间时再议迁移（D-O21 重开需显式拍板）。

### 13.4 实施落点（拍板后立项）

后端：companion 引擎 start/stop/status 三端点+ensureStarted 读侧兜底开关（engine 卡配置）+runtime_settings 扩展（伴生端口/目录）；前端：RuntimeEnvPane 伴生引擎卡+侧板状态卡深链+伴生页页头语义文案；伴生页候选流精简评估随实施定案。验收=引擎停止状态下打开伴生页 3s 内自动拉起并有状态反馈；设置页可启停引擎且状态实时；二进制缺失时指引一键安装。

## 十四、对方案 C 的异议：伴生本体资产化分析（v2.8，2026-09-30，待开发者拍板）

> 触发：开发者对 §十三方案 C 有异议，提出三方案——①伴生本体的构建和管理与通用本体统一（不再类型区分；无法完全统一则作为一个类型）；②智能体开启伴生本体改为选择一个/创建一个空本体；③伴生本体作为本体资产中的普通本体管理，入图/拒绝管理页放到本体资产下的本体详情页。问：是否对伴生本体的管理有本质优化。

### 14.1 逐条判定

**方案 1（与通用本体统一构建管理）——完全统一=无本质优化且不可行；「作为一个类型」=成立且是 2+3 的自然结果。**

完全统一的三重冲突（代码级）：
- **数据模型冲突**：伴生=data-first 事实三元组流（bot: 固定 5 类词表/provenance 溯源/invalidAt 失效化/autoConfirmed 标记/置信度），spec_json=schema-first 结构文档（概念/关系/实例+域值域+质量门禁 11 检查项）。统一=要么伴生语义（provenance/失效化/置信）在 spec_json 无处安放被丢弃，要么改 spec 模型伤全仓库资产；
- **写入路径冲突**：伴生=confirm 即 INSERT（高频增量、无「发布」概念）；spec_json=编辑→校验→版本快照→发布→运行引擎 load。每次 confirm 走版本化不可行，绕过版本化则统一只剩存储同仓的皮；
- **消费路径冲突**：伴生召回=对话每轮内嵌注入（自研 KG 直查，REQ-194 三级召回）；通用本体消费=onto_* 工具模型主动查（经运行方案组建+start+load）。伴生图 per-agent 动态生长，运行平面的方案模型不适配；
- **已交付资产作废**：REQ-194（实体对齐/向量召回/2 跳邻域）+REQ-211（agent 图聚合/复合游标）全部建在自研 KG 上，收编即重做。

「作为一个类型」可行且零成本：资产列表来源分组（REQ-181 自建/种子/Fork）增「对话生长」组或类型徽标，详情页可见——方案 2/3 落地后自然获得，无需独立立项。

**方案 2（开启伴生=选择/创建一个空本体）——本质优化成立（三案中语义收益最大）。**
- 产物归属容器化：伴生图从「不在资产列表的匿名图」（管理「怪」的根源）变为可见本体资产；
- 隔离边界自然延伸：绑定本体后多 agent 可绑同一本体→项目协作沉淀共享——REQ-211「agent 隔离」的语义升维为「本体隔离」（绑定者集合决定边界），方向一致且更通用；
- **落地形态关键抉择：伴生子图而非本体数据本身**——伴生图挂本体 ID 下（GraphURI 换绑 ontology-{id}），自研 KG 引擎/召回链路/候选表零重写；**不挂接本体 schema**（LLM 抽取对齐本体概念体系=REQ-207/79 级重活，一期明确不做，诚实边界）；
- 开关语义升级：agent.companion_ontology（bool）→companion_ontology_id（可空引用）；开启交互=选本体或一键创建空本体（建议名「{agent 名}的伴生本体」）；
- 迁移与 REQ-211 同手法：存量 agt-{id} 图 ADD TO ontology-{id}（映射=绑定关系回填）。

**方案 3（入图/拒绝管理放本体资产详情页）——本质优化成立（管理语义自洽）。**
- 资产详情页（现 8 页签：spec/校验/版本/产物/可视化/图编辑/TTL 导出/导入）新增「**伴生候选**」页签——该本体绑定的全部 agent 候选跨 agent 列表+确认/拒绝/批量；「确认入图」发生在产物本体上，消除现伴生栏「管理匿名图」的脱节感；
- 与侧板管理页双入口并存不冗余：侧板=对话旁高频随手确认（REQ-193 铺平形态保留），详情页=本体视角集中整理（低频批量审阅）；同一 API 零一致性成本；
- 成长图 3D 挂详情页可视化区（伴生图作为该本体的可视化形态之一，与 spec 2D/3D/WebVOWL 并列）；
- **本体模块伴生栏（第六栏）退役**——REQ-180/D-O21 六栏的前提「伴生图非仓库资产（无归属容器）」被方案 2 推翻，栏职能被资产详情页+可视化完全吸收；这是 D-O21 的正式反转提案（本体模块回五栏），需显式拍板。

### 14.2 判定汇总与推荐方案 D（伴生本体资产化）

| 方案 | 本质优化 | 判定 |
|---|---|---|
| 1 完全统一 | 无（三重冲突+资产作废） | ✗ 不做 |
| 1 作为类型 | 有（资产可见，软统一） | ✓（2/3 的自然结果） |

## 十六、实际使用三问题分析：关系密度 / 异名同义归一 / 可编辑性（v2.15，2026-10-10，待开发者拍板）

> 触发：开发者指令「实际执行过程中构建的伴生本体有如下问题：①概念离散分布没有关系连线；②同一个概念有多个、或同一概念对象多个相近叫法（中文/英文/带备注）出现多份；③本体资产中伴生本体详情不支持修改编辑已构建的伴生本体——分析该如何优化」。**与已交付能力的边界**：REQ-229 同名异义提醒（E3）治的是同名字面撞车（一个名字两个含义），本节问题②是反方向的异名同义（多个叫法一个含义），未覆盖；REQ-227 印证聚合是同 slug 重复确认计数，不归并变体；关系密度与可编辑性无已交付能力重叠。

### 16.1 问题①：概念离散无关系连线（结构性质量）

**根因（四点，代码级）**：a) 抽取 prompt「宁缺毋滥」导向下概念是一等目标、关系只有一句引导（动名词+端点引用约束）——LLM 保守产出，定义型对话语料（「X 是什么」）天然少显式关系陈述；b) 分窗抽取（REQ-194③）窗与窗独立，跨窗概念对从未被作为关系候选评估；c) REQ-283 few-shot 治的是污染（自指/悬空）不是产出量；d) confirm 入图忠实于候选——候选里关系少，图就是散点。

**优化（分级）**：
- **A1 关系抽取强化（prompt，低成本）**：关系类型清单 few-shot（上下位/组成/依赖/引发/适用于/前置/对比等通用关系 + REQ-187 领域聚焦可加域内关系类型）；显式引导「定义包含类属关系（是一种/属于）时输出上下位关系」——引导不设配额，宁缺毋滥口径不变；
- **A2 关系挖掘补抽轮（P1 核心，新能力）**：伴生候选页/详情页「挖掘关系」按钮→对图内已有实体做 LLM 关系补全（实体 label+定义清单成对/邻域提示）→产出 relation 类候选进待确认流（批量审阅）。把「抽取时漏掉的关系」变成事后可补的一等能力；异步 job 沿 042 表/抽取管线先例；
- A3 属类关系规则建议（零 LLM）：定义含「是一种/属于/是…的一种」模式 → 低置信「上下位」关系候选进确认流；
- A4 空边状态可视化提示：成长图零边时诚实提示「暂无关系连线——可在伴生候选页挖掘关系」。

### 16.2 问题②：同一概念多份 / 中英文 / 备注变体（一致性质量）

**根因（五点）**：a) 归并仅 Slug 精确同名（大小写敏感、括号转下划线）——「Pod/POD/pod」三个实体；b) REQ-194① 对齐清单是 prompt 软约束（沿用原名），新实体规范名无规则；c) REQ-283 剪枝只批内去重，跨窗/跨轮重复不管；d) REQ-194② 向量只用于召回侧，入图侧无相似度归并；e) 自动入图阈值>0 放大（G3 已识别）。

**优化（分级）**：
- **B1 label 规范化（确定性，零 LLM）**：候选入图前预处理——trim/全半角统一/ASCII 大小写折叠/空格折叠/括号备注提取（括号内容转 alias）→再 Slug；「POD」并「Pod」、「Pod（容器组）」→主体「Pod」+alias「容器组」；
- **B3 bot:alias 别名机制（P1 核心，语义正确落点）**：抽取 schema 增 aliases 输出字段+prompt 规范名规则（对齐清单>中文领域术语>英文原名，其余叫法进 aliases）；入图时 alias 以 bot:alias 三元组挂已有实体——**变体不删、不丢，多叫法=同实体多别名**；词法（recallEntities）与向量（labelVectors）召回面纳入 alias——「K8s」提问命中 Kubernetes 实体；
- **B2 入图相似度归并（复用 REQ-194② 向量机制）**：confirm 时新 label embedding 与图内实体标签向量比对≥保守阈值（0.8）→并入已有实体（定义取详/置信取高/变体落 alias）；embedding 未配置降级 B1；
- **B4 人工合并工具（兜底）**：内容清单实体表「合并到…」操作——次实体变体挂 alias+出入边重定向主实体+次实体三元组失效化（审计可溯）；治理存量重复；
- B5 prompt 规范名规则随 B3 注入。

### 16.3 问题③：伴生本体详情不可编辑（可治理性）

**现状边界**：M89/REQ-285 明确「spec 编辑对伴生型开放=不做」（REQ-216 三重冲突：伴生子图无 spec 文档/confirm 即生效无版本化/编辑与对话沉淀 provenance 冲突）——实际使用反馈要求重评此边界，**但只松绑到轻量编辑，不开放全 spec 编辑**：
- **C1 轻量编辑（P1）**：详情页内容清单（实体表/关系表）行级编辑——实体：改 label/改定义/删实体（DELETE 实体三元组+关联边失效化）；关系：删关系/补关系（选两端实体+关系名+定义→INSERT 边）；置信/来源/入图时间不可编辑（provenance 事实）；编辑动作落 companion_decision 审计（事件族扩 manual_edit）+快照同步刷新（REQ-216 增量轮机制在位）；SPARQL UPDATE 天然支持，实现量中；
- **C2 晋升 spec（P2 观察）**：伴生子图一键导出 spec_json 草稿（概念/事件→概念声明，关系→关系声明+实例断言）入仓库版本化体系走 spec 编辑器——单向晋升（伴生子图只读快照不回写）不破 REQ-216 边界；
- 全 spec 编辑边界维持（C3 三重冲突不开放）。

### 16.4 汇总建议（待拍板）

三问题共同主题=伴生图三质量维度：**结构质量（关系密度）/一致性质量（实体归一）/可治理性（编辑）**。建议批次：**P1=A1+A2（关系挖掘补抽为核心新能力）+B1+B3（别名机制为核心）+B5+C1（轻量编辑）+A4 空边提示**；随行=A3 属类规则、B2 向量归并（保守阈值）、B4 人工合并（若 B1/B3 大幅消除问题可降观察）；**P2 观察=C2 晋升 spec**。验收草图：真实对话抽取 20 概念，关系边/概念比显著提升（prompt 前后对照）；「Kubernetes/K8s/容器编排」变体归一同实体且「K8s」提问可召回；详情页改 label/删关系/补关系全链审计+快照一致。


## 十七、候选×既有实体关联：机制现状与增强建议（v2.18，2026-10-10，待开发者拍板）

> 触发：开发者指令「分析在智能体对话生成伴生本体候选对象时，是否只是聚焦当次会话而没有与当时的伴生本体中已有的对象关联；分析在每轮对话生成候选对象时，是否可以将当轮会话中的本体候选对象和本体中已经存在的对象进行关联」（拉取最新代码后分析）。

### 17.1 现状判定：关联机制已存在三层，但「语义关联」与「关系层面关联」缺失

**已实现（每轮生效）**：
1. **抽取时·名称级对齐（REQ-194①）**——每轮抽取前 `knownEntityLabels` 拉绑定本体伴生子图全部实体标签（REQ-286 起 **bot:alias 别名平铺**），`buildAlignmentSection` 注入 prompt 约束节：「新事实涉及清单中的实体时必须沿用清单原名」「清单实体被进一步刻画（新增关系、定义修正）时同样沿用原名」「仅确属新实体才新造名」；relations 端点被要求引用 concepts 中的 name **或既有实体**——即 LLM 已可产出「新候选→既有实体」的关系候选；>80 条按 slug 前缀聚类取样（含「未展示实体同样适用」注记）；分窗间上一窗新实体进下窗清单（appendWindowEntities）。
2. **入图时·归并解析（REQ-286 ResolveNode）**——confirm 链上概念主体与 relation 两端做 normalizeKey 比对（大小写/空白折叠）+向量相似 ≥0.8+别名归并——抽取时没对齐的，入图时强制归并到已有实体、变体转别名。
3. **事后·关系挖掘（REQ-286 A2）**——对图内已入图实体 LLM 关系补全，产出「既有实体间」关系候选进确认流。

**真实缺口（开发者观察指向的三点）**：
- **G-a 语义对齐弱**：对齐清单只注入**名称**（无定义）——对话用不同叫法（且不在别名集）时，LLM 难以判定「对话中的 X 就是已有实体 Y」，产出独立新候选；入图向量归并 ≥0.8 保守阈值外（0.6~0.8 灰色带）漏归且**无任何提示**（确认流不可见，静默入成新实体）。
- **G-b 关系层面关联缺失**：对话文本没显式提到旧实体时，抽取不会产出「新候选×既有实体」的关系候选——对齐清单只防重名，不主动建关系；这是「概念离散无连线」（§16.1）在跨轮维度的成因之一。
- **G-c 候选确认流不可见关联**：pending 候选与已有实体的相似度没有在确认 UI 呈现（同名异义提醒 REQ-229① 有，反方向的「疑似同义」提示没有）。

### 17.2 增强建议（E1~E4，均为对既有机制的收敛增强）

- **E1 对齐清单增强（低成本）**：注入「名称+一句话定义」（SelectNodes 已有 definition 字段）；>80 时用向量预筛 topK（与当轮语料 embedding 相似度）替代聚类取样——LLM 语义对齐能力显著提升；显式引导「新概念可与既有实体直接产出关系」。
- **E2 候选落库时关联标记（零 LLM）**：ScanGenus 同层对 pending 候选 label 跑 key/向量比对（复用 ResolveNode）：≥0.8 候选 note「入图时将并入「已有实体」」（确认 UI 可见）；0.6~0.8 灰色带 note「与「X」疑似同一实体（相似度 0.7x）待人工」——关联决策前置到确认流。
- **E3 挖掘关系扩展到 pending 候选（一行清单范围）**：MineRelations 实体清单纳入 pending 候选——挖掘产出自然包含「新候选×已有实体」与「新候选×新候选」的关系候选——**正是「当轮候选与已有对象关联」的直接实现，机制已在位**。
- **E4 自动增量挖掘（可选，agent 级开关）**：抽取完成后自动跑一次窄域挖掘（只挖新候选×既有实体对），成本每轮 +1 LLM 调用；默认关。

**与既有排期的关系**：REQ-287（伴生检索纵深，M92 排队）原排期的「实体语义消解」已由 REQ-286 B 簇覆盖撤单列——本节 E1~E4 是**关联增强**（建关系+可见性），非消解（合并同名）、非检索（召回面），不与其重叠；E2 与 REQ-229① 同名异义提醒（橙徽标）同为确认流提示，方向相反互补。

### 17.3 建议批次（待拍板）

**P1=E2（关联标记，确认流可见）+E3（挖掘纳入 pending 候选，一行改动）**——直接回答「每轮候选与已有对象关联」：候选落库即标关联建议、挖掘产出补齐关系连线；**P2=E1（对齐清单带定义+向量预筛）**；**观察=E4 自动增量挖掘**（成本敏感，触发驱动）。验收草图：同义变体候选在确认流可见「将并入 X」标记；挖掘产出含新候选×既有实体关系候选；对齐清单带定义后 LLM 沿用原名率提升（prompt 前后对照）。

## 十八、「挖掘关系」黑盒与超时：问题分析与优化方案（v2.20，2026-10-12，待开发者拍板）

> 触发：开发者反馈「当前伴生本体的挖掘关系操作：①只是一个按钮，背后过程都是黑盒的；②点击之后超时了——分析优化方案」（REQ-286 A2 交付轮的诚实边界「挖掘同步接口、单次 LLM 调用」在大图场景下兑现为实际故障）。

### 18.1 根因（三点，第三点比超时更严重）

1. **同步 HTTP 绑定 LLM 调用**——POST mine-relations 在请求内同步执行 LLM；实体清单无业务上限（SelectNodes LIMIT 300 + pending 候选全量并入），大图时 prompt 巨大、思考模型调用分钟级 → 前端 fetch/代理超时。
2. **超时即白烧（比超时本身更严重）**——LLM 调用的 ctx 是 HTTP request ctx：前端断开 → ctx cancel → LLM 调用中止，已完成的工作直接丢弃（一次调用白烧，且无任何留痕）。
3. **过程黑盒**——等待期间唯一状态是按钮 loading；分了多少实体、正在挖掘第几批、产出了多少候选，全部不可见。

### 18.2 优化方案（对齐既有先例：REQ-271/282 异步 job + REQ-281 过程事件）

- **① 异步 job 化（治超时+白烧）**：POST mine-relations → **202 {job_id}** + 后台 goroutine（ctx 脱离请求，用独立超时 extractTimeout 同源）；job 状态注册在 Service 内存 map（job_id → phase/progress/result/error/created_at）——与抽取 worker 同等持久性（进程重启丢 job，前端轮询 404 → 提示重新触发，诚实注记）；GET /api/companion/mine-jobs/{id} 轮询。
- **② 分批挖掘（治根因上限）**：实体清单分批（≤40 实体/批），每批独立 LLM 调用——prompt 规模可控、单批分钟内；批间产出合并去重（复用 pruneRelationsOnly）。
- **③ 进度透出（治黑盒）**：job progress = 阶段（reading/mining N/M/ingesting）+已产出候选计数；前端按钮旁内联进度（轮询 1.5s）：「读取实体…/挖掘关系批次 2/3（已产出 12 条）…/落库完成共 K 条候选」；完成 toast+自动刷新候选与成长图；失败错误透出可重试。
- **边界**：取消不做（一期）；跨进程共享不需要（单实例部署）；挖掘完成候选照常进确认流（人工门禁不变）。

### 18.3 实施落点（拍板后立项）

后端：quality.go MineRelations 改造（分批+job 注册+progress 回调）+两端点（202/轮询）；前端：OntologyCompanionPane 挖掘按钮改异步流程+进度 UI。验收：30+ 实体本体挖掘不再超时（分批可见）；前端断开后挖掘照常完成（结果可查）；进度实时透出；单测分批合并+job 生命周期。

## 十九、本体级优化操作的详情页承载分析（v2.21，2026-10-12，待开发者拍板）

> 触发：开发者指令「分析是否有必要在伴生本体详情页中增加单独的页面处理『挖掘关系』等基于当前本体优化的操作」（§十八异步化方案之后的承载位置问题）。

### 19.1 现状：本体级操作散落在「伴生候选」页
