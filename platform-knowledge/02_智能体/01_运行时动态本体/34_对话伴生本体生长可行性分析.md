# 可行性分析：对话伴生本体生长（对话中生成并持续成长的本体）

> 状态：v1.0 ｜ 日期：2026-09-22 ｜ 提问：能否在项目 agent 中增加"通过 OntoChat 将与 agent 对话的过程生成一个本体，随着不断对话这个本体不断成长"的功能
> 关联：REQ-82（LLM 辅助创建，P1）、REQ-83（fork 扩展，P2）、REQ-99/100（semantica 消费链路）、REQ-102（侧边栏六组）、D-O10、双轨 TTL 互通（REQ-78）

## 一、结论

**可行，且项目现有设计已覆盖约 70% 基础设施**——不需要引入 OntoChat 本身的代码，而是借鉴其方法论；真正要新建的只有"对话伴生抽取管线"和"候选确认流"两块。但有一个关键前置判断：开发者描述的场景其实混合了两种不同模式，需要先拆开（见 §二），它们的技术难度和风险差别很大。

## 二、先拆清楚：两种"对话生成本体"模式

| | 模式 A：对话引导式构建（OntoChat 本义） | 模式 B：对话伴生生长（开发者描述的重点） |
| --- | --- | --- |
| 对话性质 | 专门开"建本体"会话，agent 主动引导用户讲清领域 | 日常对话（运维问答、任务执行等），本体在后台伴生沉淀 |
| 产出节奏 | 会话内逐轮产出用户故事→CQ→草稿，会话末整合入库 | 长周期持续增量写入，本体逐步"长胖长高" |
| 技术难度 | 低（REQ-82 的多轮深化） | 中高（抽取、消解、漂移控制、成本控制） |
| 风险 | 低（人工主导，草稿必审） | 幻觉入库、概念漂移、层次混乱、重复实体 |
| 对应需求 | REQ-82 增强 | **新需求**（建议 REQ-103） |

**建议定位**：先做模式 A（现成路线、风险低、价值立现），再以"模式 A 定骨架、模式 B 长实例"的混合策略引入模式 B——TBox（类/属性结构）稳定且必须人工审，ABox（实例与关系）允许较高自动度。

## 三、架构方案：现有资产映射（要新建的只有 2 块）

```
用户 ↔ Eino ADK 对话流
        │
        ├─【A 新建①：伴生抽取管线】会话触发 → LLM 结构化抽取（概念/关系/事件/CQ）
        │                                   → semantica semantic_extract / MCP extract_entities·relations
        │
        ├─【复用】候选暂存 + 实体消解：semantica deduplication REST / Entity Resolution 工作区
        │
        ├─【A 新建②：候选确认流】候选片段 → 用户在 Ontology Hub 可视化确认/修订 → 合并
        │            └─ 质量门校验（OOPS!+语法+一致性，REQ-102 质量门页）
        │
        ├─【复用】存储：双轨——构建平面 spec_json（TBox 主权威）+ semantica graph store（KG 消费）
        │
        └─【复用】成长展示：时间轴 Timeline（图演化回放/时点快照）+ Registry（变更审计）
                     + Ontology Hub 可视化编辑器（REQ-102 侧边栏本体治理组）
```

## 四、关键设计决策（模式 B 的四个坑与对策）

1. **触发策略（成本控制）**：逐轮 LLM 抽取 token 成本不可接受。建议三级触发：显式指令（"记到本体里"）→ 会话结束批量抽取 → 每 N 轮/主题转换检测。默认前两级。
2. **幻觉与质量**：抽取结果一律先进**候选区**（不下本体），经质量门 + 用户确认才合并——延续 REQ-82"草稿必须经用户预览确认后才入库"的既定原则。
3. **概念漂移**：长期对话会让类层次疯长、语义重复。对策：周期性 CQ 聚类复审（借 OntoChat 聚类分析思想）+ 实体消解自动合并 + TBox 变更强制人工审。
4. **双权威一致**：伴生生长主要发生在 ABox/语义层；TBox 主权威仍在构建平面 spec_json，经双轨 TTL 互通（REQ-78）同步到 semantica——避免 semantica 图成为第二个"影子真相源"。

## 五、分阶段落地建议

| 阶段 | 内容 | 依赖 |
| --- | --- | --- |
| **P1'：对话引导式构建（模式 A）** | REQ-82 增强：「AI 创建」升级为多轮引导会话（用户故事→CQ→草稿→确认），prompt 策略直接借鉴 OntoChat 开源 prompts | REQ-82（P1，已有排期） |
| **P2'：会话级伴生（模式 B 最小版）** | 会话结束触发批量抽取→候选区→确认合并；Timeline 展示单次会话带来的本体增量 | REQ-102 P1（Ontology Hub/Timeline 复用落地）+ stdio→HTTP 桥接 |
| **P3'：持续生长（模式 B 完整版）** | 周期触发+实体消解自动合并+CQ 聚类复审+Registry 审计+成长曲线 | REQ-102 P2（质量门/Registry/消解） |

## 六、需求衔接建议

- 不动 REQ-80~83 编号语义；**REQ-82 增加多轮引导形态**（仍是"LLM 辅助创建"范畴）；
- 模式 B 新立 **REQ-103「对话伴生本体生长」**：候选抽取管线 + 确认流 + 消解合并 + 成长可视化（Timeline/Registry 消费）；
- 决策不开新 D-O：本质是 D-O10 消费链路的自然延伸，可在 D-O10 补注。

## 七、关于"用 OntoChat 本身"的说明

OntoChat（MIT，31★）可以作为**方法论与 prompt 素材来源**（其 GitHub 开源了全部 elicitation prompt 策略，见 [63 号 OntoChat 深度调研](../../04_本体/08_调研预研/63_OntoChat深度调研_论文原理与开源实现_20261008.md) / [64 号 OntoExtend 深度调研](../../04_本体/08_调研预研/64_OntoExtend深度调研_论文原理与开源实现_20261008.md)），但不建议直接嵌入运行：它绑定 Gradio 界面 + OpenAI API 的独立形态，与本项目 Eino ADK 对话流、双轨架构不匹配；其四步工作流（用户故事→CQ→聚类→测试）作为 P1' 引导会话的设计蓝本价值更大。OntoExtend 的 Retriever→Extender→Integrator 三段式则是 P3' 增量合并的参考架构（按新内容检索相关本体片段再扩展，避免整本体塞 prompt）。

> 局限：本分析基于 03 v0.8 / 04 v0.11 / 02 v0.18 文档现状与 OntoChat/OntoExtend 论文公开信息；伴生抽取的实测成本需 P2' 原型验证后再定触发参数。
