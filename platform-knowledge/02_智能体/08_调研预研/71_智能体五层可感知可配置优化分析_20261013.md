# 智能体五层可感知与可配置优化分析

> **开发者指令**（2026-10-13）：「感觉当前智能体实现中，对于 提示词、context、harness、loop、graph等分层工具的可感知、配置等实现不够。为了让用户更能直观的感知、调试、配置智能体从 提示词到graph等多层工具保障过程，分析可以在界面和实现上做哪些优化？」

## 1. 一句话结论

**五层的「数据面」已经成体系（这是本平台的底子），感知缺口集中在「最后一公里」：事件已在 SSE 流里被前端归约器丢弃、prompt 全文已被记录但被 debug 双开关藏住、生效链已有 API 但配置页只显配置值、委派事件已在流里但零结构化重组。** 因此优化的主体方向不是补后端能力，而是三件收口：①**过程面**——Harness 审计族接进 live 流，运行中可见拦截/审批/验证结果；②**配置面**——「生效链」形态（配置值+生效值+来源）从 hooks 卡先例推广到五层各页签；③**审计面**——装配快照结构化为「提示词装配」视图、时序条加智能体泳道、委派过程重组为委派卡。少量小后端补键（生效值/上下文账单/分段装配）随批。

## 2. 概念对齐与现状盘点（一手取证）

### 2.1 概念对齐：开发者说的「五层」与平台域事实源的映射

### 2.8 跨层横切发现

1. **SSE 与落库同源（emitAndRecord）意味着「感知断层」绝大多数是前端接线问题**：事件已到达浏览器，被 `applyRunEvent` 的白名单/文案缺失丢弃。后端事件面（run_event 20+ 类型、schema_version=2）是全的，不需要新通道。
2. **调试信息的「双开关深藏」**：观测级别 0/1/2 与调试事件入库两个开关都在 TraceDrawer「显示设置」里，普通用户发现成本高；装配卡/model.step 有「仅调试档」诚实标注但缺「如何打开」的引导。
3. **「生效链」形态只有两处先例**：hooks 卡（REQ-232 配置+`/api/hooks` 生效真相）与审批生效 chip（REQ-231④）。其余页签（Context/Loop/模型）只显配置值，「配了 A 生效的是 B」无从发现（如 max_iteration 归一 25）。
4. **`describeEvent` 文案是卡片体验单点**：`artifact.saved`/`debug.cli` 在过滤组与色表已登记但无文案 case，渲染成裸事件名。
5. **前端已返回未用字段清单**（接线即得）：`toolPreview.masked`、`KBHit.sources`、`Conversation.top_k/min_score`、TraceDrawer 内 assembly 仅原始 JSON。

## 3. 缺口分析

### 3.1 三个通用结构性缺口

- **G1 live/回放不对称**：审计事件（审批决议、hook 拦截、验证背压、连接器降级）落库全量、live 全丢。用户在「等结果」的关键时刻反而信息最少——这是「感知不够」感受的最大单点。
- **G2 有数据不可见**：prompt 全文（debug=2 已记录）、委派来源（tool source）、遮蔽工具清单（masked）、wiki 溯源（sources）都已存在，分别被双开关、颜色映射、未渲染挡住。
- **G3 生效链形态不统一**：配置面五层各自为政，仅两处有「配置值 vs 生效值」对照；用户「配置了却不生效」类困惑（REQ-282 的 ONTOCHAT_LLM_TIMEOUT 认知错位是同型案例）没有结构性防线。

### 3.2 分层缺口汇总（按层→相）

| 层 | 最重缺口 | 次重 |
| --- | --- | --- |
| 提示词 | 装配分段黑盒（四段拼接无来源标注、instruction debug<2 剥离） | prompt 全文 UI 双开关深藏 |
| Context | 无上下文账单（预算/裁剪/压缩/注入量无结构化透出） | sources 未渲染、top_k/min_score 无 UI |
| Harness | 审计族 live 丢失（G1） | masked 未渲染、跨会话聚合无 |
| Loop | 无 k/N 迭代进度、生效值不透出 | verify_failed 聊天流不区分、todo 无 UI |
| Graph | 委派过程零结构化重组（无泳道/聚合/拓扑） | 委派决策理由无留痕（诚实边界：模型侧决策平台难捕获） |

## 4. 优化建议

### 4.0 设计主线：把既有「三面」收编成运行透镜，不新开框架

平台事实上已有三面：**配置面**（AgentSidePanel 七入口，REQ-264）、**过程面**（ChatWindow 事件卡族）、**审计面**（TraceDrawer+EventReplay，REQ-284）。本档所有建议都是把五层各自填进这三面的对应相，**不新增第四面、不新增顶级页面（17 号 IA 不动）**。批次划分原则：P1=现有数据接线+两处小后端补键；P2=新渲染能力；观察项=触发驱动。

### 4.1 P1 批次（A1~A7，接线为主）

| # | 项 | 做法 | 量级 |

### 4.3 观察项（触发驱动，不做承诺）

①**最终消息数组逐字快照**（完整 prompt 审计的完全体）：数据量与敏感双考量，model.step 4000 字截断维持，待真实调试场景逼出再加档；②**per-section token 归因**（54 号开放问题②/39 号 A-8）：依赖 tokenizer 引入；③**workflow_mode 拓扑推进可视**：随 REQ-205 实装同步；④**loop 级独立事件**：ADK 循环内嵌侵入性大，model.step seq 已可还原，不做；⑤**per-run 成本金额**：平台无价格表数据；⑥外部推理后端旁路的感知标注扩展（REQ-206 已降维 Harness 页签，Context/Loop 旁路段落随外部后端使用率再评）。

### 4.4 批次总览

- **P1（A1~A7）**：共同主题=「最后一公里接线」——live 白名单、装配分段、生效值透出、委派重组、账单统计。两处后端补键（assembly 分段、max_iteration_effective、context_stats）均为 run.started 既有事件加字段，schema_version=2 增量兼容。
