## 1. 方案摘要

- **推荐路线**：前端工程 monorepo 化，一套 React 代码多端复用——**Web/PWA 先行（T0~T1）→ 桌面端 Tauri 2（T1，多进程 sidecar 随壳分发）→ 移动端 Android 套壳（T2）→ iOS 与推送（T3）**。
- **关键决策**：
  1. 后端**编排逻辑零改动**多端化：Go 单二进制 + REST/SSE 天然支持多客户端，不引入 BFF/网关；
  2. 桌面端选 **Tauri 2** 而非 Electron：体积小、复用系统 WebView，且 sidecar 机制（`externalBin`）可把多个 Go 后端打进同一安装包；
  3. 移动端走 **WebView 复用路线（Tauri mobile / Capacitor）**而非 React Native：保住已拍板的蚂蚁生态（AntD 6 / Pro Components / Ant Design X 均为 DOM 组件，RN 不可用），UI 只做移动适配不重写；
  4. **桌面端进程编排是本项目区别于通用 Tauri 教程的最大难点**——不是"带一个 sidecar"，而是"编排 3~5 个进程 + 一个原生二进制 + 可选容器"，需按 §7.6 的形态分级取舍；
  5. 「服务器地址可配置」是多端形态的**前置改造**（当前客户端隐含 localhost 假设）；「认证」已拆出，见 §11.1。
- **预期收益**：同一业务代码支撑 Windows/macOS/Linux 桌面端与 Android/iOS/PWA，新增端边际成本递减；桌面端形成"安装即用"的本地平台形态。
- **最大风险**：①移动端 WebView 内 SSE 长连接在后台/弱网下的稳定性；②桌面端**多进程 + 外部二进制（oxigraph）**的跨平台产物可得性与包体；③三维图谱/画布等重交互依赖（three / xyflow）在移动端 WebView 与桌面混合渲染下的表现。
- **评审阻塞项**：无 P0 阻塞。开放问题 O-2（移动端功能裁剪边界，含重交互页面是否降级）建议在 T1 结束前确认，不阻塞本方案评审。

## 2. 背景、目标与现状基线

### 2.1 业务背景

平台定位为**本地学习用的智能体 + 本体平台**（六模块 + 设置：智能体 / 项目 / 本体 / 知识库 / 技能 / 平台知识 / 设置）。当前唯一客户端是桌面浏览器访问 `localhost:8080` 的 Web SPA。

### 2.2 现状基线（2026-09-29 核对，供后续评审直接引用）

**进程与端口：**

| 进程 | 端口 | 形态 | 桌面内嵌必需性 |
| --- | --- | --- | --- |
| `backend`（主平台） | :8080 | Go 单二进制 | **必需** |
| `runtimed`（runtime-manager，本体运行平面） | :8090 | Go 单二进制 | 本体运行功能需要 |
| `ontologyd`（ontology-service，本体构建平面） | :8091 | Go 单二进制 | 本体模块需要 |
| `oo-worker`（OpenOntologies 双轨） | :8092 | 外部二进制，可选 | 可选 |
| 伴生图引擎 | :9199 起 | **backend 内置懒启动** | 伴生本体需要 |
| `oxigraph` | 无端口 | 原生二进制（本地库） | 本体运行方案 start 需要 |
| Qdrant | :6333 | 可选容器 | 知识库可选 |
| `agentd`（沙箱内） | :8080 | Go，沙箱后端 | 沙箱执行时 |

> 结论：**桌面端"一键启动"的对象不是一个进程，而是一组进程 + 一个平台相关的原生二进制。** 这是原 v0.1/v0.2 方案最大的事实偏差，也是 T1 PoC 必须首先验证的点（O-1 已扩大范围）。

**前端技术栈：**

| 项 | 现状 | 对跨端的影响 |
| --- | --- | --- |
| React | ^18.3.1 | 无 |
| antd | **^6.6.5**（原方案口径为 AntD 5） | DOM 组件库，WebView 可原样运行；RN 不可用（E6 结论不变） |
| @ant-design/x / x-markdown | ^2.9.0 | 对话流式渲染核心，Web 专属 |
| zustand | ^5.0.2 | 方案建议的状态库**已在用**，跨端状态层无需另选 |
| 重交互依赖 | three 0.186.1 / react-force-graph-3d 1.27.0 / 3d-force-graph 1.80.0 / @xyflow/react 12.11.6 / codemirror 系列 | **新增成本**：拉大前端产物体积；三维图谱与画布在移动端 WebView 上是性能与交互双重风险点 |
| 分层 | `src/api`（client/companion/types）、`src/store/ui`、`src/lib`、`src/components`、`src/pages` | **利好**：与方案 §7.2 的 packages 语义对齐，monorepo 改造是"目录外提 + 多入口"，不是重写 |
| PWA | 仅 `index.html` 有 viewport meta，**无 manifest / 无 service worker** | PWA 仍是零起步 |

**部署形态（决定激活条件②）：**

| 路径 | 现状 |
| --- | --- |
| 本地 `run-dev.sh` / `run-dev.ps1` | 一条命令拉起本体两平面 + 主平台 |
| Docker Compose | `16` §3，官方推荐起步 |
| K8s（Helm） | `16` §4 |
| 运行环境统一配置（REQ-191） | 进程内嵌 / docker / k8s pod 可选 |
| 智能体沙箱（REQ-159） | 收敛为 docker + k8s pod 两后端 |

> 平台**已经不是纯单机**了。这使「非 loopback 访问」成为真实场景，直接支撑 §11.1 的认证结论。

### 2.3 技术目标与成功标准

| 项 | 内容 |
| --- | --- |
| 技术目标 | ①同一平台可从桌面客户端、手机 App、PWA 三种形态访问；②前端业务代码最大化复用（蚂蚁生态组件与交互基线不变）；③桌面端可离线/单机自足（壳内自带核心服务）；④移动端支持连接局域网或远程部署的后端 |
| SC-X1 | 桌面安装包双击安装后无需终端/浏览器即可完成一次完整对话（含 SSE 流式）——**本轮修正为"核心形态"（§7.6 形态 B）下的完整对话** |
| SC-X2 | Android APK 侧载后连接局域网后端完成对话与知识库问答 |
| SC-X3 | Web 代码与壳端代码复用率 ≥ 90%（壳工程不含业务逻辑，仅入口与系统能力桥接） |
| SC-X4 | **编排逻辑零改动**（仅新增增量 API，不改既有编排/存储）——原口径"后端代码改动为零"过严，本轮放宽到编排层 |

## 6. 方案选型与决策

### 6.1 关键决策一：桌面端壳 —— Tauri 2（推荐）vs Electron

| 评估标准 | 权重 | Tauri 2 | Electron | 说明 |
| --- | --- | --- | --- | --- |
| 前端复用度 | 20 | 5 | 5 | 两者都直接加载现有 Vite 构建产物 |
| 包体/内存 | 15 | 5 | 2 | Tauri 复用系统 WebView（Win=WebView2 / macOS·iOS=WKWebView / Linux=WebKitGTK，E3）；Electron 自带 Chromium |
| **多进程一体化分发** | 20 | 5 | 3 | Tauri `externalBin` 原生支持 sidecar（E8/E10）；Electron 需自行处理多进程拉起与打包 |
| 生态成熟度 | 15 | 3 | 5 | Electron 生态最成熟；Tauri 2 已稳定但移动侧较新 |
| 移动端路线一致性 | 15 | 5 | 1 | Tauri 2 桌面/移动同框架（E3）；Electron 无移动端 |
| 团队上手成本 | 15 | 3 | 4 | Electron 纯 JS；Tauri 需要少量 Rust（壳层预计 < 500 行，因多进程编排比原估 <300 行上浮） |
| **加权合计** | 100 | **4.5** | **3.2** | — |

- **推荐**：Tauri 2（当前 2.12.0）。决定性因素仍是"桌面+移动同框架"与 sidecar 一体化分发。
- **放弃 Electron 的理由**：无移动端路线、包体/内存劣势；无决定性优势项。
- **反转条件**（本轮扩充）：
  1. T1 PoC 中 **多进程 sidecar 或 updater 出现硬伤**（无法满足 SC-X1 / R-X11）；
  2. 团队不愿引入 Rust 工具链；
  3. **（新增）系统 WebView 碎片化在本项目重交互页面（3D 图谱、@xyflow 画布、codemirror 编辑器）上暴露不可接受的渲染差异** —— 此时评估 **Tauri 3 CEF 后端**（E15，代价是包体回到 Chromium 量级）或回退 Electron。
- 置信度：medium-high。

### 6.2 关键决策二：移动端路线 —— WebView 复用（推荐）vs React Native/Expo vs Flutter

| 评估标准 | 权重 | Tauri mobile / Capacitor（WebView 复用） | React Native + Expo | Flutter |
| --- | --- | --- | --- | --- |
| 蚂蚁生态 UI 复用 | 25 | 5（AntD/X 原样运行于 WebView，E11） | 1（DOM 组件库不可用，E6） | 1（同左，且跨栈） |
| 移动端体验上限 | 20 | 3（WebView 渲染；**重交互页（3D/画布）明显弱于原生**） | 5 | 5 |
| 交付速度/成本 | 20 | 5（复用 ≥90% 前端代码，仅做响应式与移动导航） | 2（对话区、管理页、SSE 流全部重写） | 2 |
| 生态/长期维护 | 15 | 4（Tauri 2.12 移动支持成熟 E3；Capacitor 8.5.2 活跃 E4） | 5（Expo SDK 58 GA，E5） | 4 |
| 与现有 Go/React 团队技能匹配 | 10 | 4 | 3 | 2 |
| iOS 后台/推送等系统能力 | 10 | 3 | 5 | 4 |
| **加权合计** | 100 | **4.25** | **3.05** | **2.75** |

- **推荐**：移动端走 **WebView 复用**（T2 用 Tauri mobile 与桌面同构；若某项系统能力缺失，单点改用 Capacitor 补位——两者同为 WebView 方案，前端代码 100% 共享）。Flutter 直接排除。
- **放弃 RN/Expo 首选的理由**：AntD 6 / Pro Components / Ant Design X 均不可用（E6），等于放弃已拍板前端选型重写第二套 UI。
- **反转条件**：
  1. 移动端对话体验经 T2 实测明显劣化且调优无果；
  2. 产品重心从"学习平台"转向"移动优先多端产品"，此时再评估 Expo 重写对话区；
  3. **（新增）三维图谱 / 画布被确认为移动端必备功能** —— WebView 路线在该项上基本无解，需上升为产品决策。
- 置信度：medium。

## 7. 目标架构

### 7.1 Context view（信任边界，本轮重画：多进程）

┌──────────────┐  │                                                                          │

- 三种客户端形态消费**同一后端进程组**；桌面端可选**内嵌模式**（sidecar 同机）或**远程模式**；移动端只有远程模式。
- **沙箱执行（E14）在内嵌模式下受限于本机是否有 Docker**：无 Docker 时沙箱降级为进程内嵌（`02` §12 M31 运行环境配置的既有能力），不新增跨端专有逻辑。

### 7.2 Component view（前端 monorepo，本轮对齐现状）

```
eino-multiagent-lab/
├─ backend/  ontology-service/  runtime-manager/   # 现有 Go 多模块（go.work）
└─ web/                          # 现有前端 → 升级为 pnpm workspace
   ├─ packages/
   │  ├─ ui/                     # ← 现 src/pages + src/components 平移
   │  ├─ api/                    # ← 现 src/api 外提（REST 封装 + SSE 客户端，baseURL/凭证注入）
   │  ├─ core/                   # ← 现 src/store 外提 + SSE 重连策略
   │  └─ platform/               # 端能力桥接接口（notification/tray/clipboard/secure-storage）
   └─ apps/
      ├─ web/                    # 纯 Web + PWA 入口（新增 manifest + service worker）
      ├─ desktop/                # Tauri 2 桌面壳（src-tauri/ + 多进程 sidecar 编排 + updater）
      └─ mobile/                 # Tauri mobile / Capacitor 壳（移动导航 + 适配层）
```

- **分层铁律**：`ui` 不直接 fetch；`api` 不含业务；`core` 不碰 DOM 之外的平台 API；端差异只出现在 `apps/*` 与 `platform` 实现。
- **T0 成本下调**（E12）：现有 `src/api` / `src/store` / `src/lib` 已承担目标分层的语义，T0 的主要工作是**目录外提 + 引入 workspace + 多入口**，而非重新划分职责。原估 1~2 周可下修（见 §13）。

### 7.3 Runtime flow（SSE 对话多端一致）

```
客户端(SSE client in packages/api)
  1  配置服务器地址（默认 localhost:8080）──▶ 连接诊断（网络/凭证/版本）
  2  POST /api/agents/:id/chat (SSE) ──▶ 事件帧(步骤/消息增量/完成)
  3  断流检测(heartbeat 超时 3s) ──▶ 指数退避重连(≤3 次)
  4  重连后 GET /sessions/:sid 补拉状态 ──▶ UI 对账(去重 by message_id)
```

- 现有 SSE 事件协议不变；重连补偿只依赖已有查询接口，后端不新增续传机制。

### 7.4 Data view

- 主数据仍归后端 SQLite；客户端仅持有：服务器地址、访问凭证（内存/安全存储）、UI 偏好（localStorage / Tauri store）。
- 不引入客户端数据库；离线只缓存只读列表（P2，可选）。

### 7.5 Failure view

| 故障 | 表现 | 降级 |
| --- | --- | --- |
| sidecar 拉起失败（端口占用/二进制缺失） | 桌面端启动报错页 | 提示改用远程模式连接已运行后端；**启动诊断页列出每个进程的就绪状态** |
| **某个 sidecar 中途崩溃** | 部分功能不可用 | 健康轮询发现 → 自动重启 ≤1 次 → 仍失败则提示（R-X11） |
| **退出时进程回收不全** | 残留孤儿进程占端口 | 退出前统一 `stop_services`；启动时端口占用检测 + 提示清理（R-X11） |
| SSE 断流 | 对话停止 | 自动重连 + 状态补拉（7.3）；3 次失败转手动重试 |
| 远程后端不可达 | 连接诊断页 | 按 DNS/端口/凭证/版本四步诊断提示（R-X1） |
| 移动端后台被杀 | 回前台白屏 | 冷启动 → 恢复最后会话列表（R-X7） |

### 7.6 桌面端进程形态分级（本轮新增，关键）

「桌面端一键启动」不是一个二元开关，而是三种形态的取舍。**建议 T1 PoC 走形态 B。**

| 形态 | 内嵌进程 | 包体 | 离线能力 | 三平台二进制矩阵 | 适用 |
| --- | --- | --- | --- | --- | --- |
| **A 全量内嵌** | backend + runtimed + ontologyd + oxigraph + 伴生图 | 最大（远超 80MB） | 完整（含本体运行） | **最难**：oxigraph 需三平台产物 | 有强离线本体需求时 |
| **B 核心内嵌（推荐）** | backend + 伴生图 | 目标 ≤80MB | 对话/知识库/伴生本体可用 | **可控**：仅 Go 交叉编译 | 主流学习场景 |
| **C 纯远程** | 无 | 最小 | 无 | 无 | 局域网/远程服务器 |

- 形态 B 下，本体两平面（:8090/:8091）与 oxigraph **按需安装或走远程**（R-X12）；首次进入本体模块时引导。
- 形态 A 的硬门槛是 **oxigraph 的 Windows/macOS 产物可得性**——Linux 侧官方提供 x86_64/aarch64 单文件（`16` §2 已记录），Windows/macOS 需自行验证或改走容器内嵌（与"轻量壳"目标冲突）。**这是 O-1 的核心。**

## 11. 安全、隐私与合规

### 11.1 认证口径调和（本轮新增，消除 v0.2 遗留阻塞）

**矛盾**：本方案原要求 R-X2「Token 认证」为前置改造；`01` Q-5 明确「不做用户注册登录、账户/多租户、权限体系」。

**调和结论：两者不在同一层，不冲突。**

| | Q-5 排除的 | 跨端/远程实际需要的 |
| --- | --- | --- |
| 是什么 | **用户账户体系**：注册、登录页、多租户、角色权限、组织架构 | **单一共享访问凭证**：一个静态 token / API Key，用于非 loopback 访问的粗粒度准入 |
| 数据模型 | users / roles / permissions 表 | 无新表，一个配置项（如 `PLATFORM_TOKEN`）+ 中间件校验 |
| 交互 | 登录/注册/退出 | 无登录页；客户端配置里填一次 |

**关键判断：这项需求已不再由"跨端"触发，而是由"远程部署"触发。** Docker Compose / K8s Helm 部署下（E13），后端已经暴露在非 loopback 网络上（`16` §3：`http://<host>:8080`），此时无凭证 = 任何能访问该网络的人可读改全部数据（含模型 API Key 配置、项目文件）。

**因此：认证应从本方案拆出，作为独立的「远程部署访问凭证」条目立项**，可先于跨端任何工作推进，也不受本方案冻结状态影响。落地形态建议：单一静态凭证 + 环境变量/配置文件启用 + loopback 豁免。

> 待开发者确认：是否按此拆分立项（见 O-6）。

### 11.2 其余安全项

| 风险点 | 控制措施 | 验证方式 |
| --- | --- | --- |
| 后端暴露局域网后的未授权访问 | §11.1 的单一访问凭证（远程模式强制；loopback 豁免） | 未带凭证请求被拒实测 |
| 明文传输（局域网 HTTP） | T2 起提供 HTTPS 指引：反代（Caddy/自签）或内网证书；App 端允许用户显式信任自签证书（P2） | 抓包验证 |
| 模型 API Key 落地客户端 | **永不落客户端**——Key 始终只在后端；客户端只持有访问凭证（Keychain/Keystore，P2） | 移动端存储审计 |
| 桌面 sidecar 本地端口被其他进程占用/冒用 | 动态端口 + 启动时校验 `/api/version` 指纹；仅绑定 127.0.0.1（内嵌模式） | 端口冲突场景测试 |
| 自动更新供应链 | updater 签名校验（Tauri 官方机制） | 升级演练（R-X10） |
