## 二、目标与触发纪律

### 2.1 目标

1. **单一执行机械**：workflow_mode=dag 档只有一套执行语义（adk 层自研 DAG Runner），消除两套设计并存的不可预期性。
2. **契约单源**：事件入 event_names.go 注册表一份；节点产出契约以变量表类型化传递为主；恢复语义按节点载体分层但在方案档一次写清。
3. **文档归一**：PRD 内不再有两套 dag 设计；Graph 域事实源（56 号）与导航（00_智能体模块）回补；锚点引用统一经 109 号复核新值。
4. **v1 硬边界清晰**：触发纪律、护栏五件、校验闭环四项在开工前落到可执行断言。

### 2.2 触发纪律（v1 硬边界，沿 zcode 决策表式做法，按平台形态落）

zcode 把触发纪律写成**决策表**供编排层机械执行而非靠模型自觉（zcode SKILL.md §1：仅显式请求才启动工作流；「结果喂后续步 / 有界循环 / 类型化分支」是脚本擅长的形态，**不是该有工作流的理由**；显式请求一经提出即绑定——不改道、不降级为普通委派或自己顺手做，只剩规模裁剪）。平台 v1 落为以下硬边界：

**v1 触发路由决策表（落 WF 技能/工具描述档原文）**：

| 用户输入形态 | 路由 |
| --- | --- |
| 未点名工作流的任何请求（无论多少步、多像编排：结果喂后续步/有界循环/按类型化结果分支） | 主智能体直答，或普通 agent_as_tool 委派（Q-4 推荐默认不变） |
| 点名工作流（「用动态工作流/DAG 编排跑」类措辞；后续可扩 /workflow 类斜杠命令） | **必走工作流路径，mandatory**；绑定后本轮及后续轮路由关闭——唯一自由度是规模（最小任务得一个小 DAG），不裁深度 |

配套硬边界四条：

1. **仅显式指令触发**：**不做自动意图识别**，主智能体不得凭「任务看起来像编排」自行切档——编排形态特征只构成「脚本擅长什么」，不构成「该有工作流」的理由。
2. **绑定后不改道**：不降级为普通委派、不自己顺手做、不以「任务太小」改道（zcode 原文：the smallest task gets a small workflow）。
3. **纪律落两处**：①WF 技能/工具描述档内写上表决策表；②会话路由状态在绑定后保持，防「顺手降级」。
4. **诚实承诺降级**：zcode 靠编译期字面量（命令集/阶段标记必须字面量、禁随机源）保证「确认窗所见即所跑」；平台计划由 LLM 生成，只能提供弱保证——**计划期快照 + 运行期偏离即暂停再确认**（确认卡内容=阶段图 + 将执行的工具/命令全集人话清单；运行中出现确认单外的新工具/命令形态即暂停二次确认）。不得向用户承诺编译期级的「确认后零新增」。

**v1 「点名→路由」执行机制落点（初稿缺平台侧机制，评审轮补，待拍板）**：zcode 的 mandatory 由脚本运行时机械执行；平台 workflow_mode 现状是项目/会话**配置面**（ProjectModal.tsx:183-191 与 ProjectSidePanel.tsx:51 均为 Select 选项，本轮亲证），v1 八件中 WF-⑥ 改动面（109 号:57：白名单+switch+前端两处 Select+冻结标注）只新增配置值与前端选项、**不含对话内路由**，且平台当前不存在既存「WF 技能档」载体。v1 机制建议如下，归一轮拍板：

- **一期纪律只在配置面生效**：用户点名工作流时，主智能体的行为契约=引导切换/新建 workflow_mode=dag 会话（或经平台助手走 REQ-186 的 rw 审批改项目配置），**不自动切档**——决策表落为工具描述中的行为约定，靠提示词约束而非运行时强制；「绑定后不改道」对应为引导话术的硬性措辞，无会话路由状态机（后者留二期，若开发者要求运行时强制则属对 WF-⑥ 改动面的显式扩面）。
- **决策表载体**：建议二选一——①挂 REQ-561 platform_cli/平台助手工具面的工具描述（REQ-186 分级口径已有 manifest 承载先例）；②落 docs/02 §8 工具描述行+01 §3.20 头部硬边界注（纯文档镜像）。推荐 ①（可被执行的工具行为契约优于纯文档），归一轮拍板。
- **增量注记**：上述行为契约与载体落点均**不在** 109 号 WF-⑥ 现行改动面内（109 号:57 原文），领号时需在 REQ-567 行显式扩面或另立随批小件，禁止隐性夹带。
