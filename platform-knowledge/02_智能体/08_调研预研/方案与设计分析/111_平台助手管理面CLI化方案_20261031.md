## 一、背景与问题定义

### 1.1 现状工具面（REQ-186 分级口径，已交付）

| 层级 | 工具 | 能力边界 |
| --- | --- | --- |
| L0 只读七件 | `doc_read/doc_list/doc_grep/list_model_connections/list_agents/list_kbs/get_assistant_config`（`backend/internal/chat/assistant_tools.go`） | 能查所有 agent/模型连接/KB/平台知识 |
| L1 写提案 | `sync_platform_kb/search_platform_kb/propose_assistant_config`（`backend/internal/chat/assistant_kb.go`） | 仅限助手自身配置+KB 导入域；两段式（暂存 10min→确认落库）；「删除类与高危写不开放」 |
| 按需装配 | `http_fetch/todo_write/run_command/save_file` 等（`backend/internal/chat/assembler.go`） | 需沙箱世界/work_dir/审批档三前提 |

### 1.2 根因

平台助手不能对话建 agent 不是架构缺失，而是**写路径从未以工具形式暴露**——REQ-186 当年刻意收窄到 L0+L1 两域的保守裁决的自然结果。用户期望（对话执行任何页面操作乃至页面没有的组合操作）需要的是能力面扩展，不是修 bug。

### 1.3 关键洞察：页面操作 ≡ API 面

前后端分离架构下，页面每个可做的操作本质都是一次 REST 调用（路由单源 `backend/internal/api/server.go`）。**覆盖 API 面 = 覆盖一切页面操作（含未来新增）**；抽象正确则新页面功能上线自动被覆盖，边际成本趋近于零。

## 二、方案选型（三案对比，定稿 CLI）

| 维度 | A 逐个适配（每功能手写工具） | B 通用管理网关（admin_call 工具） | C **CLI 化（manifest 驱动，定稿）** |
| --- | --- | --- | --- |
| 覆盖"页面有的" | 渐进、永远滞后、有暗角 | 全覆盖 | 全覆盖（同构抽象） |
| 覆盖"页面没有的组合操作" | ✗ | 多端点编排 | 多命令编排（等价且更自然） |
| 工具 schema 数 | 几十上百（token 膨胀+选择准确率下降） | 1~2 | 1~2 |
| 沙箱需求 | 无 | 无 | **免沙箱**（直 exec 可信自家二进制） |
| 人类复用 | ✗ | ✗ | ✓（运维/调试/脚本化/冒烟） |
| 外部智能体复用 | ✗ | ✗ | ✓（Claude Code 等经 CLI 操作平台，与 MCP/A2A 叙事契合） |
| 可发现性 | 无（靠 description） | 弱 | ✓（`--help` 按需查询不占常驻上下文） |
| 成本 | 8~12 人日起且持续投入 | 基建 3~4 人日+域接入 | 主体 4.5~5+接线 1~1.5 人日，此后边际≈0 |

**形态子选型**：透传型（`ontoapi GET /api/...` = curl 换皮，✗ 丢 CLI 全部价值）／**manifest 驱动生成命名子命令（✓ 定稿）**／OpenAPI 注解全自动生成（✗ 新依赖链+handler 注解维护负担，单人产品不划算）。

**裁决记录**：REQ-186 分级机制（ro 放行/写审批/删除不开放）**不反转**，反转的是覆盖面（L0/L1 两域→全管理面）——属口径演进，纪律 7 命中面（34 号/53 号）同轮补指针。

## 三、总体设计

```
内置平台助手工具面
├─ platform_cli 工具（新增，唯一接线件）
│    入参 = 子命令 + 参数（字符串数组或单命令行）
│    内部 = os/exec 调 ontoapi 二进制（超时+输出截断）
│    审批 = 包装层按 manifest 读写标记对 args 判读分级
└─ ontoapi 二进制（新增，Go 单文件跨平台）
     ├─ manifest 单源（域/子命令/method/路径/参数/读写标记）
     ├─ 命名子命令生成 + --help 自描述
     ├─ HTTP 客户端（127.0.0.1 后端，复用会话认证语义）
     └─ 错误人话归一 + JSON 输出 + --limit/--fields 裁剪
```

与现有件关系：
- **装配链**：platform_cli 走 `assembler.go` 内置工具族装配位；`EnsureAssistantTools` 内置行工具并集自愈扩项（迁移期自动并入，存量自愈）。
- **审批**：复用 approvalTool 挂起/恢复与审批卡（REQ-231 全套现成）；分级判读点在审批包装内按 manifest 标记进行，不新增审批机制。
- **拍板**：复用 `ask_human`（StatefulInterrupt 挂起→Resume 定向投递，REQ-14 现成）——模型信息不足（未指模型/缺指令）先提问再执行。
- **先例对齐**：REQ-360 对话建本体四工具=「包装自家 REST 给对话用」的已交付先例，platform_cli 是其泛化形态。

## 四、manifest 设计

每端点一条（1~3 行，高度机械），字段：

| 字段 | 说明 | 示例 |
| --- | --- | --- |
| domain / sub | 域与子命令 | `agents` / `create` |
| method + path | HTTP 方法与路径模板 | `POST /api/agents` |
| params | 参数映射（flag→body/query/path） | `--name --description --instruction --model-conn-id` |
| access | 读写标记 | `ro` / `rw` / `deny` |
| output | 默认输出裁剪 | `--limit 20 --fields id,name,model` |

```yaml
- domain: agents
  commands:
    - sub: list      ; method: GET   ; path: /api/agents          ; access: ro
    - sub: create    ; method: POST  ; path: /api/agents         ; access: rw
      params: [--name(必填), --description, --instruction, --model-conn-id, --temperature]
    - sub: get       ; method: GET   ; path: /api/agents/{id}    ; access: ro
    - sub: update    ; method: PUT   ; path: /api/agents/{id}    ; access: rw  ; etag: --from 自动 GET→PUT 组合
    - sub: delete    ; method: DELETE; path: /api/agents/{id}    ; access: deny
```

**排除清单**（不进 manifest，诚实边界）：SSE 流式端点（对话运行是助手主场）、文件上传二进制类、settings 密文导出类（backup/export）、A2A/MCP 协议面（非管理 CRUD）。

## 五、读写分级与安全（与 CLI 同轮交付，不先通后管）

| 标记 | 行为 | 口径来源 |
| --- | --- | --- |
| `ro` | 直行免审 | REQ-186「L0 只读全开」 |
| `rw` | danger 审批（审批卡附完整命令+参数摘要，拒绝即止） | REQ-186 两段式精神+REQ-231 审批机制 |
| `deny` | 不装配/调用即拒绝（人话说明走页面） | REQ-186「删除类与高危写不开放」 |

安全四条：①未知端点默认 deny（manifest 外无能力）；②密文/凭据面端点一律 deny（apikey 类字段响应侧脱敏）；③CLI 只打 `127.0.0.1` 后端（部署面如开远程访问，platform_cli 仍限本机语义——远程管理走页面）；④执行超时+输出截断（防长输出刷爆上下文，`tool.result` 32KB 截断 REQ-224⑤ 兜底）。

## 六、工具接线与提示词

- **platform_cli 工具定义**：invokable tool（`utils.InferTool` 形态），入参 `{command: string[]}`；直 exec 编译期随后端分发的 ontoapi 二进制（同进程数据根，无需发现）；信任级别=助手后端自身（自家代码+localhost+manifest 白名单），故**不 require 沙箱**——与 run_command 三前提（沙箱世界/work_dir/审批档）的本质区别。
- **提示词基座扩写**：`AssistantDefaultPrompt` 职责四条→增「系统操作代理」条目+CLI 能力十行摘要（域清单+两三个示例命令），细粒度用法让模型按需 `ontoapi --help`。
- **精装 propose_agent 降级为可选对照件**：若 CLI+审批卡体验已够则不立项；若高频场景需要 diff 预览级体验再另立项（本方案不做承诺）。

## 八、诚实边界与放弃方案存档

1. **覆盖面=管理面 API**（§四排除清单）；「页面没有的组合操作」由 CLI 多命令编排承接；数据加工类开放操作仍归沙箱 `run_command`/技能（REQ-122）；**平台根本没有的能力=功能开发另立项**，助手如实回复不硬编。
2. 放弃记录：逐个适配（线性成本+schema 爆炸）、通用网关（同构但无三重复用）、透传（无 CLI 价值）、OpenAPI 全自动（依赖链过重）——均在本档 §二留痕，重启评估以本节为基线。
3. 单机自部署边界不动（Q-5）：CLI 不开远程管理面，认证语义随部署形态演进（REQ-556 RO 凭证若落地再评估）。
4. 本方案不改变 REQ-192/213 既有裁决（两段式提案机制、非 builtin 不装配 propose 类工具），仅扩平台助手自身工具面。

## 九、验收对照（REQ-561）

1. 对话「帮我创建一个软件工程师的 agent」→ 助手经 platform_cli 完成（信息不足处 ask_human 提问拍板），结果与页面创建一致（列表可见、可运行）——真机链冒烟。
2. ro 免审直行；rw 触发审批卡、批准才执行、拒绝即止；deny 不可达；密文端点排除——分级冒烟三档。
3. 全命令 `--help` 可发现；输出可裁剪；错误人话（重名/If-Match 过期等）。
4. 现有页面与 docs/20 冒烟零回归；单测（manifest 解析/分级判读/错误归一）+headless 冒烟（隔离后端）。
