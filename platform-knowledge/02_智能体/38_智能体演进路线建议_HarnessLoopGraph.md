## 0. 一句话结论

**本项目当前处在「Harness 骨架已成、Context 几乎为零、Loop 与 Graph 只有影子」的位置，因此正确的投入顺序不是跟着业界热点从 Graph 往回补，而是严格按依赖顺序：先把 Context 从 0 补到 1，再补 Harness 的执行面（工具/hooks/验证/重试），Loop 与 Graph 才可以低成本地长出来。**

三个决定性判断（后文逐条给证据）：

1. **最大杠杆点是上下文工程，不是 Graph。** 现在主链路是**全量历史重放 + 丢弃 tool 消息 + 零压缩零预算**（`assembler.go:718`），这意味着任何长任务、任何多 Agent 协作，跑过十几轮就会自己把自己压垮。在此之上加 Graph 只会得到一个「结构精致但每次都被上下文拖垮」的系统。
2. **Harness 缺的不是编排，是「执行面」。** 装配管线（`assembleTools` 七步）写得相当扎实，但**内置工具只有 2 个**（`current_time`、`ask_human`）、**没有 hooks**、**没有验证/背压**、**明确拒绝重试**——也就是说 Agent 能"想去做什么"，却几乎没有可做的事、也拿不到确定性反馈。
3. **Loop 与 Graph 都有现成的地基，缺的是把地基接起来。** Loop 需要的「进度产物 + 恢复」已有 `CheckPointStore` 与 `run_event` 表两块砖（但 checkpoint 是**进程内内存**，重启即丢）；Graph 需要的原语 Eino `compose` 已在依赖里，而 `workflow_mode` 是**显式空壳**（`assembler.go:176` 直接告警降级为 free）。这两层不需要重新发明，只需要把已有资产接成闭环。

### 1.1 逐层细看

**(1) Prompt 层——够用，差治理**

- 有：`agent.instruction` 单字段、前端可编辑、AI 优化（REQ-167）、平台助手基座（REQ-192 后读写穿透内置行）。
- 缺：
  - **无版本管理**：改了就改了，回滚靠人肉。M23 池里躺着「Agent 配置版本/草稿与临时覆盖」一条，一直未领取。
  - **技能注入是纯字符串拼接**（`composer.go:34`）而非结构化渐进披露。对比业界 Skills 模式（独立目录 + 触发时才加载），现在是**全量注入**——挂 5 个技能就把 5 段正文塞进系统提示词，无论本轮用不用。这正是上下文工程要治的病。
  - **无提示词评估**：改完提示词没有回归基线。

**(2) Context 层——最大缺口，且是其他层的硬前置**

代码事实（`assembler.go:718`）：

```go
func BuildHistoryMessages(msgs []*store.Message) []*schema.Message {
    switch m.Role {
    case "user":      → UserMessage
    case "assistant": → AssistantMessage(m.Content, nil)   // ← 工具调用被丢弃
    case "system":    → SystemMessage
    }
}
```

三个后果，按严重度排序：

1. **tool 消息完全丢失**——历史里 assistant 消息的 `ToolCalls` 传 `nil`，模型重开对话后**看不到自己上一轮调过什么工具**。多轮工具型对话在第 2 轮就开始"失忆"。
2. **零预算零压缩**——`runner.go:222` 每轮 `ListMessages(conv.ID)` 取**全部**消息，无上限、无裁剪、无摘要。对话越长越贵、越慢、越容易触发 context rot。
3. **召回是硬编码追加**——`runner.go:271 recallKB` / `:274 recallCompanion` 在 `runOnce` 里直接 append System 消息，没有准入控制、没有去重、没有预算切分。

> 这一层不补，**后面三层建在上面都会塌**。它也是 `36` 号文档早已判定的「最大功能缺口」——本文只是把优先级再往上顶一格。

**(3) Harness 层——骨架好，执行面薄**

- **做得好的**：`assembleTools` 七步管线（内置 → 技能 → MCP → 本体 → 项目文件 → 审批包装 → 空参归一化）层次清晰、来源标注完整（`SourceOf`）、失败策略诚实（降级 + 告警，不阻断）、自引用 MCP 防护（`isSelfMCPEndpoint`）。这在同类平台里属于上游水平。
- **缺的**：
  - **内置工具只有 2 个**。Agent 的"手"几乎完全依赖外部 MCP 与本体 facade。业界共识是一组小而可组合的原语（Read/Write/Grep/Glob/Bash）；我们连文件读写都要靠项目会话条件启用（`assembler.go:478`，需 `ProjectID != "" && FilesRoot != ""`）。
  - **没有 hooks**。无法在工具调用前后注入确定性检查（lint/类型检查/危险命令拦截）。
  - **没有验证/背压**。Agent 说"做完了"就是做完了，没有独立的验证闸门。
  - **明确拒绝重试**（`assembler.go:26` 注释）。这个决定在学习尺度下是**对的**（防重试风暴），但需要有**例外通道**：对幂等且明确可重试的失败（网络抖动、超时）应当允许有限次重试。
  - **子 Agent 不是上下文防火墙**。agent_as_tool 模式下成员 Agent 的完整输出会回灌协调者上下文（`assembler.go:230 NewAgentTool`），没有"只回传压缩结论"的机制。业界 sub-agent 的核心价值恰恰是**隔离**。

**(4) Loop 层——只有两块砖，没有墙**

- 已有砖：`CheckPointStore`（中断/恢复）+ `run_event` 表（事件时间线）+ 伴生本体收尾触发（Run/Resume 后按游标增量抽取）。
- 缺：调度（无定时/触发器）、进度产物（无 feature_list / 进度文件）、Generator/Evaluator 分离、会话间交接。
- **关键阻塞**：`chat/checkpoint.go:19` 是**进程内内存 map**，注释已诚实标注「进程重启后 checkpoint 丢失」。这意味着**跨会话恢复在物理上做不到**——Loop 工程的第一块砖必须先换掉。

**(5) Graph 层——只有影子**

- `collab_mode`：`agent_as_tool`（`adk.NewAgentTool`）/ `transfer`（`adk.SetSubAgents`）两条，是**多 Agent 协作**，不是工作流编排。
- `workflow_mode`（REQ-33，P1）：`assembler.go:176` **非 free 一律告警降级**——字段在、UI 在、语义不在。
- Eino `compose` 已在依赖里（`assembler.go:15`），但目前**只用于 `ToolsNodeConfig`**，没有用于 Agent 编排图。

## 2. 路线图：四个阶段（按依赖排序）

### 总览

| 阶段 | 主题 | 优先级 | 关键交付 | 前置 |
| --- | --- | --- | --- | --- |
| **A** | **上下文工程补零** | **P0** | 历史预算 + tool 消息保全 + 压缩 + 上下文准入钩子 | 无 |
| **B** | **Harness 执行面** | **P1** | 工具原语扩充 + hooks + 验证背压 + 重试例外 + 子 Agent 结果压缩 | A |
| **C** | **Loop 最小闭环** | **P2** | 持久化 checkpoint + 进度产物 + 长任务模式 + Evaluator 角色 | A、B |
| **D** | **Graph 兑现** | **P3** | workflow_mode 落地 + 图状态持久化 + HITL 闸门 + 时间旅行回放 | C |

> **为什么是这个顺序**：A 是 B/C/D 的物理前置（上下文不治，长跑必崩）；B 是 C 的执行前置（没有可做之事与反馈，循环空转）；C 是 D 的需求前置（先有"需要跨会话推进"的真实场景，才知道图该画成什么样——**先有痛点再上结构，避免为图而图**）。

### 阶段 A · 上下文工程补零（P0 · 最高杠杆）

**目标**：让一次运行跑 30 轮仍然稳定、成本可控、不丢工具轨迹。

| # | 事项 | 落点（代码级） | 说明 |
| --- | --- | --- | --- |
| A1 | **tool 消息保全** | `assembler.go:718 BuildHistoryMessages` | 从 `message` 表读回时恢复 assistant 的 ToolCalls 与 tool 结果消息。最小方案：给 `message` 表加 `tool_calls` JSON 列（迁移），或把 tool 轮次作为 `system` 摘要消息落库。**建议先做后者**（改动小、零 schema 风险），前者留 P1 |
| A2 | **历史预算与裁剪** | 新增 `internal/chat/context.go` | 按 token 估算（不必精确，可用 `len/4` 粗估 + 可替换接口）设定预算；超出时按「保留首尾 + 中间摘要」裁剪。**默认值可配置到设置页**，学习尺度先给 3 档（紧凑/标准/完整） |
| A3 | **压缩（Compaction）** | 同上 | 触发条件：接近预算 or 轮次阈值。复用 `chat.GenerateText`（`structured.go:133`，已有现成的"system+user 纯文本生成"）做摘要，**零新依赖** |
| A4 | **上下文准入钩子** | 抽取 `runner.go:271/274` | 把 `recallKB`/`recallCompanion` 从 `runOnce` 硬编码抽成一个 `ContextProvider` 接口链（KB / 伴生 / 技能正文 / 未来第三方）。**这是 36 号文档已识别的 `agent/pre-step` 等价物**，也是阶段 B 的 hooks 的雏形 |
| A5 | **工具结果剪枝** | `runner.go` 事件消费处 | 大工具结果做 head/middle/tail 确定性剪枝（可无模型），保留定位信息与取回提示。参照 dsh `toolResultPruner` 思路 |

**验收**：一条 30 轮、含 20 次工具调用的对话——(a) 重开后模型能说出上一轮调过什么工具；(b) 单次运行 prompt token 不再随轮次线性增长（有预算上限）；(c) 20 号冒烟清单 S2 新增上下文节全过。

**风险与边界**：A2/A3 引入"上下文不再完整"，必须**在事件流里诚实标注**（已有 `run.warning` 通道，且 REQ-149 已确立"该运行未记录调试细节"这类诚实标注先例）。**不要默默丢弃历史**。

### 阶段 B · Harness 执行面补齐（P1）

**目标**：让 Agent 有手可用、有反馈可依、有闸门可守。

| # | 事项 | 落点 | 说明 |
| --- | --- | --- | --- |
| B1 | **内置工具原语扩充** | `tool/builtin.go` | 按业界共识补齐小而可组合的原语。候选（按安全递增）：`read_file`/`write_file`（**先在绑定目录内**，`fsutil` 已有 SafeJoin 校验）、`grep`/`glob`（只读，最安全）、`http_fetch`、`run_command`（**默认关，需显式开 + 沙箱后端**，对齐 REQ-114 绑定目录安全口径）。**每个工具都要在 15 号登记** |
| B2 | **Hooks 机制** | 新增 `internal/chat/hooks.go` | 在工具调用前/后、运行结束前三个点挂回调。学习尺度先做**进程内 Go 注册表**（不引外部脚本运行时，守 D-O15 不接 Python 依赖）。首个内置 hook：`cmd_guard`（危险命令拦截）+ `verify_on_stop`（结束前跑配置的验证命令） |
| B3 | **验证/背压** | Agent 配置 + `hooks` | Agent 增加 `verify_command` 字段；`verify_on_stop` 失败则**阻止标记完成**并把错误回传继续修。这是 HumanLayer 实践中**回报最高的投入** |
| B4 | **重试例外通道** | `assembler.go` 降级处 | 现状「单次失败即降级」整体保留（防风暴正确），但增加**幂等错误白名单**（context deadline / connection reset / 5xx）允许 N=2 重试。MCP 拉取超时（`mcpFetchTimeout`）与本体 facade 是首批受益点 |
| B5 | **子 Agent 结果压缩** | `assembler.go:230 NewAgentTool` | agent_as_tool 模式增加「回传模式」选项：full（现状）/ summary（只回传压缩结论）。**这是 sub-agent 作为"上下文防火墙"的核心价值**，也顺带降低多 Agent 成本 |
| B6 | **技能渐进披露** | `skill/composer.go` | 从「全量拼接」改为「索引 + 按需加载」：系统提示只注入技能名与一句话描述，正文作为可检索资产，命中才注入。**可复用 `agent_as_tool` 的思路把技能做成工具** |

**验收**：一个勾选 `grep`+`read_file` 的 Agent 能在绑定目录内完成"找出所有调用了 X 的文件并总结"；配置 `verify_command` 后，命令不通过时运行不标记完成；agent_as_tool 开 summary 模式后协调者上下文 token 显著下降。

**注意**：B1 的 `run_command` 是本项目**安全边界的一次实质扩张**，必须先有 REQ-114 的绑定目录口径 + REQ-135 的审批覆盖 + 沙箱后端（REQ-122/190/191 已就绪）三者到位才可开。**缺一不上。**

### 阶段 C · Loop 最小闭环（P2）

**目标**：让一个任务能跨会话推进，且无人值守时不会静默失控。

| # | 事项 | 落点 | 说明 |
| --- | --- | --- | --- |
| C1 | **持久化 CheckPointStore** | `chat/checkpoint.go` | 把 `memCheckPointStore` 换成 SQLite 实现（`store` 已有成熟模式）。**这是 C 阶段的物理前置**——重启即丢的 checkpoint 撑不起跨会话 |
| C2 | **进度产物（人类可读 + 机器可读双轨）** | 新表 `run_progress` 或复用 `run_event` | 按业界成熟模式：机器侧=结构化任务清单（JSON，状态 pending/done/blocked）+ 检查点；人类侧=可导出的 Markdown 进度文件。**必须记录「失败的尝试及原因」与「已知局限」——负面知识比成功记录值钱** |
| C3 | **长任务模式（LongRun）** | `chat/runner.go` | 新增一种运行形态：Initializer 会话产出任务清单 → 后续每次运行只推进一个有界增量 → 更新清单 → 结束。复用 C1/C2 |
| C4 | **Generator / Evaluator 分离** | `assembler.go assembleProject` | 在项目协作模式里新增一个 `evaluator` 成员角色（不干活、只按标准打分并打回）。**先做成可选**，因为 Anthropic 明确告诫：Evaluator 该不该存在取决于任务是否超出当前模型可靠单干能力——**脚手架不手下线就会变成技术债** |
| C5 | **调度（最小）** | 后端定时任务 | 学习尺度先做「对话级定时续跑」（用户显式设定：每 N 分钟推进一次，最多 M 次，超出即停）。**必须带 cap**（每次运行上限 / 每日上限 / 重试上限），否则就是 Token Blowout |
| C6 | **成本护栏** | `run_event` 已有 usage 数据 | 把 REQ-49 扩展（Token/成本按项目/对话维度面板）从 M23 池里提出来做掉——**C5 上线前必须有成本可见性**，这是「Cap Before You Ship」纪律的落地 |

**验收**：一个"把 X 模块重构完"的任务，跨 3 次会话推进，每次只做一个增量，重启进程后仍能接着做；任务清单可导出为 Markdown；成本面板可见累计 token 与预估费用；达到 cap 后自动停止并发事件告知。

**明确不做**：自动合并 PR、无人值守的破坏性操作、外部系统集成（超出单机学习尺度）。

## 3. 本项目的差异化机会：本体 = 结构化外部状态

这是本文最想给开发者的一条战略建议。

**五层演进的一条主线结论是：越往上，"外部状态的质量"越比"模型的聪明度"决定成败。** 而本项目恰好拥有业界少有的**结构化外部状态资产**：

| 已有资产 | 对应哪一层的最高价值件 |
| --- | --- |
| **本体（Ontology）**：spec_json、五工具 facade、Oxigraph 引擎 | Loop 层的「进度产物」可以是**本体化的**（任务/产物/约束是 typed 实体，不是自由文本）；Graph 层的「状态 schema」可以是**本体推导的**而非手写 TypedDict |
| **伴生本体（REQ-170）**：运行时动态薄本体、跨会话矛盾失效化、PROV-O 溯源 | 天然就是**跨会话记忆**——Loop 层最难的"下一个窗口如何接上"问题，本项目已有部分答案 |
| **KG / GraphRAG（REQ-127~130）**：实体、关系、claims、社区摘要 | Graph 层的「图」不只是执行流图，还可以是**知识图驱动路由**——这是 LangGraph/CrewAI 都没做的 |
| **PROV-O 溯源**（伴生入图带溯源） | Graph 层的「审计轨迹」——业界最贵的能力，本项目已有底座 |

**具体建议**：在阶段 C 的 C2（进度产物）与阶段 D 的 D2（图状态）设计上，**不要照抄 LangGraph 的 TypedDict / JSON 方案，而是优先评估「用 spec_json / 伴生图承载运行状态」的可行性**。若可行，本项目会在"Agent 运行状态可语义查询"这一点上形成真实差异化——**别人用 SQL 查状态，我们用 SPARQL 查状态**。

**但必须诚实标注风险**：这条路没有现成开源方案可抄，自研成本高；且 D-O5（Oxigraph 为 P1 唯一引擎）意味着性能与规模受限。**建议先做成 C 阶段的一个可选实验分支（双轨），跑通再决定是否主干化**，不要一次押注。

### 6.3 E5 配置治理与工作记忆（REQ-226/M54，✅ 已交付 2026-10-01）

**配置治理（P-2 落地）**：保存即版本——PUT agent 成功后自动快照「更新前」整包配置（迁移 039 agent_config_version，每 agent 版本号单调递增、保留最近 50 版惰性裁剪）；侧板「配置版本」卡=版本下拉（vN·时间·来源注记）+选中版本与当前配置的字段级 diff+一键回滚（整包写回走 UpdateAgent 全量更新；**回滚动作自身先快照「回滚前」状态可再滚回**，diff 为空时禁用按钮）。端点三件：GET config-versions / GET config-versions/{v}/diff / POST config-versions/{v}/rollback。不做「草稿态」独立工作区（保存即版本已覆盖「改坏可还原」核心诉求，草稿态列观察项）。

**工作记忆划界评估（REQ-226②，评估结论=不做新面）**：跨会话记忆注入与既有三处承载的边界——①**伴生本体**（D-O19）：对话事实型知识（「是什么」），经确认入图、按本体隔离、检索注入，已承载「知识记忆」；②**conversation.context_state**（REQ-201）：会话内压缩摘要，承载「对话内记忆」；③**todo_json**（REQ-202/204）：任务进度，承载「任务记忆」。剩余缺口是「用户偏好/长期项目背景」类记忆——当前无真实诉求（单机单用户教学场景），且其正确形态（全局注入 vs agent 记忆卡）需要产品定义。**定案：不做新记忆面**；诉求出现时优先评估「agent 级背景说明字段（静态注入 instruction）」这一最轻形态，而非新建记忆子系统。D-O19 不混排边界维持。
