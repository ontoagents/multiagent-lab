### 3.0 网络边界警告（REQ-236⑦/M63，2026-10-01）

**非回环部署时必须知晓的安全边界**（平台服务间为 loopback 信任模型，零服务间鉴权）：

1. **平台准入只覆盖 :8080**——REQ-209 `PLATFORM_TOKEN`（accessAuth）仅管 backend 的 `/api/*`；**ontology-service :8091、runtime-manager :8090 完全无鉴权**，且 accessAuth 不向它们转发凭证。因此：**:8090/:8091 绝不可暴露公网或不受信网段**〔oo :8092 已随双轨退役摘除，2026-10-08〕——Docker Compose/K8s 编排需保证三服务仅在内部网络互达（compose 默认 bridge 网络即可；K8s 用 ClusterIP 不配 NodePort/LoadBalancer）。**REQ-383/M179 加固（2026-10-24）**：两卫星服务默认监听改为 **127.0.0.1**（`:8091`/`:8090` 通配退役为 opt-in——`LISTEN_ALL=1` 或显式 `ADDR`；非回环监听启动时打告警日志）；Docker Compose 已显式 `ADDR=:端口` 保持容器互通。backend :8080 维持全接口（主入口，凭证见 §3.1）。
2. **引擎动态端口 9201+**——运行方案的引擎端口由 runtimed 在宿主回环动态分配（REQ-236③ bind 探测）；docker 执行方式自 REQ-236⑤ 起端口映射**绑定 127.0.0.1**（`-p 127.0.0.1:port:8080`，容器内 serve 必须绑 0.0.0.0 接受网桥转发，宿主侧只暴露回环——引擎 SPARQL Update 端点可写且无鉴权，此前 0.0.0.0 映射在远程部署场景即为公网可写旁路）。**升级注**：REQ-236 之前创建的存量 docker 容器仍可能是 0.0.0.0 映射，升级后对方案执行一次 stop/start 即按新口径重建。
3. **远程访问统一走 :8080 反代**——浏览器/外部 MCP 客户端只应触达 backend（凭证见 §3.1）；:8090 的 MCP facade 供本机 Agent 装配消费，远程场景经 backend 同源反代或隧道（SSH/反向代理自带认证），不建议直连端口。
4. **默认执行方式（D-O20 v0.73 变更，REQ-236④）**——runtime_config 默认 `docker`；**未安装 docker 时启动方案自动降级进程内 native**（运行期探测，配置值不写回；`GET /api/runtime-config` 的 `effective_method` 为实际生效值）。k8s 保持接口预留（显式配置必报错）；存量库中仍为 k8s 的默认值由迁移 006 翻转为 docker。

- 三个服务镜像均多阶段构建（见各 `Dockerfile`）；backend 镜像内已烘焙前端产物，单进程对外。**semantica-worker 镜像 6~10 GB（semantica 0.6.8 重依赖）**（v0.2 D-O15：归档休眠，不再构建/分发；**REQ-518/M325：已自 compose/helm 编排摘除**——helm components.enabled 旗标可恢复）。
- 数据持久化：`platform-data`（backend）、`ontology-data`、`runtime-data`（含 oxigraph 引擎数据与日志）三个卷。
- 服务间编址（容器网络内）：backend → `ontology-service:8091` / `runtime-manager:8090`；ontology-service → `backend:8080`（ai-draft 用）；runtime-manager → `backend:8080`（companion 查询归属解析用）。**契约表（REQ-518/M325——编排 env 与代码 getenv 对账单源，compose/helm 已对齐）**：

| 调用方 → 目标 | 环境变量 | compose 值 | 缺省行为（宿主直跑） |
| --- | --- | --- | --- |
| backend → runtime-manager | `RUNTIME_MGR_URL` | `http://runtime-manager:8090` | `http://127.0.0.1:8090` |
| backend → runtime-manager MCP 面 | `ONTOLOGY_MCP_URL`（缺省自 RUNTIME_MGR_URL 派生 `/mcp`） | `http://runtime-manager:8090/mcp`（双保险） | `http://127.0.0.1:8090/mcp` |
| backend → ontology-service | `BUILD_SVC_URL` | `http://ontology-service:8091` | `http://127.0.0.1:8091` |
| ontology-service → backend | `PLATFORM_URL` | `http://backend:8080` | `http://127.0.0.1:8080` |
| runtime-manager → backend | `PLATFORM_API_URL` | `http://backend:8080` | `http://127.0.0.1:8080`（companion 查询归属解析——缺省容器内必 OWNER_RESOLVE_FAILED） |
- **沙箱说明**：Docker 沙箱执行（SANDBOX_IMAGE）默认关闭；启用需让 backend 容器可访问 Docker 守护进程（挂载 `/var/run/docker.sock` + `PLATFORM_URL_EXTERNAL=http://<宿主IP>:8080`），属进阶配置。
- **K8s Pod 沙箱（SANDBOX_BACKEND=k8s，2026-09-29 真机验证配方）**：本地无集群时用 kind（`kind create cluster --image kindest/node:v1.23.4`——kind CLI 与 node 镜像须时代匹配，v0.13 配 v1.23 及以下；集群侧组件经 DaoCloud 镜像前缀 `docker.m.daocloud.io/kindest/node` 拉取后重打标签）。agentd 镜像推荐**宿主交叉编译 + alpine 底座组装**（`CGO_ENABLED=0 GOOS=linux GOARCH=amd64 go build` 后 COPY 进 alpine:3.20——容器内 go build 在小内存 Docker Desktop VM 上易 OOM）+ `kind load docker-image multiagent-lab/agentd:dev`。**两坑必读**：①`kubectl port-forward` 客户端与 server 须同带内（1.36 客户端对 1.23 server 转发黑洞——连接被接受但数据不通；放 `data/bin/kubectl` 并以 `KUBECTL_BIN` 指向）；②Docker Desktop vpnkit 不放行 Pod 网段直访宿主（192.168.65.254 从 Pod EOF）——在 kind 网桥上跑一个 TCP 中继容器（可直达 host.docker.internal），`PLATFORM_URL_IN_CLUSTER=http://<中继IP>:8080` 下发。Agent 侧 `runtime_backend` 取 docker|k8s 均视为沙箱意图，实际形态由平台 `SANDBOX_BACKEND` 统一决定（不匹配发 run.warning）。
- **自动检测（REQ-190，SANDBOX_BACKEND=auto）**：平台同时装配 K8s+Docker 双候选，按序探测（k8s readyz → docker daemon ping，3s 级超时）——可用即用、粘滞缓存（稳态零重复探测，失效自动换档）；Agent 侧 `runtime_backend=auto` 时分发前预检，**双候选均不可达自动回退进程内执行**（run.warning 诚实提示）。显式 docker/k8s 配置行为不变。推荐本地开发常置 `SANDBOX_BACKEND=auto`：有 kind 集群自动上 Pod，没有则落 docker，都不行进程内兜底。

### 3.1 远程访问凭证（REQ-209，M42）

服务器/局域网部署时在 backend 侧设置 `PLATFORM_TOKEN`（任意高熵随机串），此后**非本机**访问 `/api/*` 一律要求凭证：

```bash
# docker compose 片段
environment:
  - PLATFORM_TOKEN=${PLATFORM_TOKEN:?请生成随机 token}
```

- 客户端携带：`Authorization: Bearer <token>`（推荐）/ `X-Platform-Token: <token>` / URL 参数 `?access_token=`（EventSource 兼容）；
- **本机直连（loopback）豁免**：同机 `curl 127.0.0.1:8080` 无需凭证（开发与本地脚本零影响）；反代（Caddy/Nginx 同机部署）注入的 `X-Forwarded-For` 会使请求按远程来源对待——即同机反代也不会令凭证失效；
- 放行面：`/healthz`（存活探测）、`/mcp`（Agent 对外服务，自带 Bearer Token 鉴权 REQ-131）、前端静态资源（无数据）；
- 未设置该变量 = 不启用（本机开发默认态，行为与历史版本一致）；
- 边界（诚实标注）：这是平台级单一共享凭证（粗粒度准入），不是用户账户体系（Q-5）；明文 HTTP 局域网传输加密请经反代 HTTPS 终结（10 号 §11.2）。

## 6. 客户端打包（后期选项）

前端为纯 SPA + 本地 Go 服务，客户端化有三条路径（按推荐序）：

1. **Tauri 2（推荐，引入 Rust 工具链）**：Tauri 壳加载打包后的 SPA；三个 Go 服务 + sidecar 作为 **sidecar 进程**随应用分发（Tauri 原生支持 externalBin）。产物单安装包；Rust 仅用于壳，不侵入业务。代价：引入 Rust 工具链 + 三平台交叉编译矩阵。
2. **Electron**：生态最熟、无 Rust，但体积与内存代价大；与"开源优先、避免重壳"的项目基调不符。
3. **纯服务端 + PWA**：不打包客户端，浏览器访问自建服务（即 §3/§4 形态）；零额外成本，"客户端"体验最弱。

> 结论建议：单机自用阶段维持 §3 Compose 形态；确有离线单机分发需求时再启动 Tauri 方案（届时 Rust 工具链仅服务于壳，与主业务解耦）。

| backend | `PLATFORM_TOKEN` | 空（不启用） | **远程部署访问凭证（REQ-209，M42）**：设置后非本机访问 /api/* 须携带凭证（`Authorization: Bearer <token>` / `X-Platform-Token` 头 / `?access_token=` 参数）；loopback 直连豁免（带 X-Forwarded-For/X-Real-IP 的请求视为远程来源须凭证——同机反代部署不会令豁免失效）；/healthz、/mcp（自带 Bearer）、静态资源不受影响 |

## 8. 健康检查与排障

- `GET :8080/healthz`（主平台）、`:8091/healthz`（纯文本 ok）、`:8090/healthz`（含 profiles 状态汇总）、`:8093/health`（semantica worker，graph_loaded 区分图是否已加载）。
- 常见故障：
  - 本体导入/导出报 sidecar 错 → 容器内 `python3 -c "import rdflib"` 验证（镜像已内置则查挂载覆盖）。
  - 方案启动失败 → runtime-manager 日志 + `last_error` 字段；oxigraph 二进制缺失/端口占用是高频原因。
  - 前端白屏 → backend 日志查 `WEB_DIST` 路径；镜像内路径为 `/app/web/dist`。
  - **semantica 独立栏不可用** → worker 未启动（§2 手动 setup+run，或容器形态未部署）——独立栏有降级 Result 与指引；`data/semantica-worker.log` 查详情。

## 9. SQLite 数据增长声明（REQ-113③，v0.2 增补）

主库 `data/platform.db`（WAL 模式，另有 `-wal`/`-shm` 伴生文件）为唯一主平台存储。各表增长来源与量级（单机规模）：

| 表 | 增长来源 | 量级参考 | 清理建议 |
| --- | --- | --- | --- |
| `message` | 每轮对话按消息累积（含流式聚合后的完整文本） | 每轮 2~N 条 × 平均数 KB | 设置「数据与安全」按对话删除（级联消息与事件） |
| `run_event` | 每次运行的全程事件（delta 级别不落库，仅聚合事件；多 Agent/工具密集时每轮可达数十条） | 每轮 5~50 条 × 数百 B~数 KB | 随对话删除级联；长期不用的对话定期清理 |
| `conversation` / `project` | 人工创建 | 低速增长 | 设置「数据与安全」删除（明示级联范围） |
| `project_file` | 上传 + save_file 产物元数据（文件本体在 `data/projects/`） | 每文件一行 | 删除项目不清理已绑定本地目录的文件（本体在目录内） |
| `kg_entity`/`kg_relation`/`kg_claim` 等 | GraphRAG 库导入时 LLM 抽取 | 与文档量线性相关 | 删除对应 KB 文档/库；`/api/kg/{id}/rebuild` 可重建 |

- 单机规模下不做自动清理/归档；备份直接复制 `data/` 目录（停服后复制最稳，WAL 下热复制亦可读）。
- 密钥文件 `data/.secret` 与 DB 分离：换机迁移需一并带走，否则连接 Key 无法解密。

### 9.1 应用内备份与恢复三步（REQ-411/M207 交付；REQ-517/M324 完整性闭环补节）

**备份**：设置 →「数据与安全」→「一键备份」——产出 zip：三库 VACUUM INTO 一致性快照（platform/ontology/runtime）+ `data/projects`（项目文件、save_file 产物与 .git——唯一不可从库重建的用户产出）+ `data/.secret`（连接 Key 密钥）+ `data/companion-graph-snapshots` 与 `data/companion-snapshots`（伴生快照）+ `data/agent-files`（含子目录）。压缩包根 `manifest.json` 记录生成时间与跳过项清单（区分源缺失与读取失败）；响应头 `X-Backup-Warnings` 携带跳过数（前端备份钮 toast 提示）；主库快照失败=HTTP 500（不再产出静默缺库 zip）。

**Docker 三卷形态**：ontology.db / runtime.db 在两卫星服务容器卷内、不在主服务数据目录——manifest 如实标 `not_found`，按恢复三步后手动补备两库（`docker cp` 卫星卷内 db 文件）。

**恢复三步**：
1. 停服务（run-dev 终止 / `docker compose down`）；
2. 用备份 zip 内 `data/` 覆盖部署机 `data/` 目录（三库文件+`.secret`+projects+agent-files+伴生快照；zip 根 manifest.json 仅清单，不入 data/）；Docker 形态注意卫星库分别覆盖至 ontology-service / runtime-manager 容器卷；
3. 重启——迁移自动跑（schema_migrations），抽查一条连接「测试连接」验证 Key 可解密（以 `.secret` 一并恢复为前提）。

诚实边界：应用内不做自动覆盖恢复（单机误操作保护）；备份运行中产生的增量不进快照（VACUUM INTO 时点语义）。

## 11. 非本机部署安全指引（REQ-335/M135，v0.24 增补·2026-10-17）

> 定位：把平台当前的信任边界向开源用户讲清楚——本平台按**单机可信环境**设计（NFR-O-4），非本机暴露部署前请通读本节并完成最小加固。

### 11.1 当前信任边界（诚实陈述）

| 面 | 现状 | 说明 |
| --- | --- | --- |
| 服务监听 | backend `ADDR` 默认 `:8080` 全接口；**ontology-service/runtime-manager 自 REQ-383/M179（2026-10-24）默认 `127.0.0.1:8091/8090` 回环**——绑全接口需 `LISTEN_ALL=1` 或显式 `ADDR`（非回环启动打告警日志）；Docker Compose 内两服务显式 `ADDR=:端口` 保持容器互通，宿主端口映射建议 `"127.0.0.1:8080:8080"` | NFR-O-4「全部服务回环监听」口径向后端主入口外全部落地；backend 主入口因浏览器直连与凭证豁免语义维持全接口 |
| 服务间鉴权 | **无**（构建/运行/插件三平面互信，同机部署假设） | 8090/8091 直打即可操作仓库与引擎 |
| 访问凭证 | `PLATFORM_TOKEN` 启用后 `/api/*` 需 Bearer（REQ-209：loopback 且无代理转发头豁免；X-Forwarded-For 出现即视为远程须凭证）；**未设置=零防护** | 默认未设置（本机开发零影响） |
| 引擎子进程 | oxigraph 端口 9201+ 逐实例分配（127.0.0.1 回环探测取口）；Docker 引擎经 docker-proxy 绑 127.0.0.1 | native 模式引擎监听地址随启动参数，建议部署后 `ss -tlnp` 核查 |
| 数据面 | SQLite 明文（本体/对话/配置）+ 模型连接密钥加密存储 | 数据目录（data/、各服务 DB）泄露=全量泄露 |

### 11.2 暴露风险（为何不能直接裸暴露）

- `/api/*` 全平面无内建认证（未设 PLATFORM_TOKEN 时）：任何可达网络的客户端可**读写删除本体资产、发起 LLM 对话（消耗你的模型额度）、执行 SPARQL、上传文件**。
- 服务间无鉴权：暴露 8080 的同时，反代若误配 8090/8091 转发即绕过一切应用层控制。
- 连接器插件（:8093）与 K8s/Docker 执行通道具备宿主操作能力（REQ-214 阶段二），暴露等级更高。

### 11.3 最小加固清单（按投入排序）

1. **不暴露（推荐默认）**：平台只在可信内网/本机使用；远程访问走 VPN/SSH 隧道（`ssh -L 8080:127.0.0.1:8080`），服务保持只听回环或防火墙全禁入站。
2. **绑定地址收敛**：两卫星服务 REQ-383 起默认已回环（无需配置）；backend 若仅本机使用设 `ADDR=127.0.0.1:8080`；Docker Compose 端口映射改 `"127.0.0.1:8080:8080"`。
3. **启用访问凭证**：`PLATFORM_TOKEN=<随机长串>` 启动 backend，客户端/浏览器以 Bearer 携带（REQ-209 语义：loopback 直连豁免、经反代强制鉴权）。
4. **反代层收口**：nginx/caddy 终结 TLS + Basic Auth/OAuth2 proxy，上游 proxy_pass 到 127.0.0.1:8080；**切勿**把 8090/8091/9201+ 加入反代。
5. **防火墙**：云主机安全组仅放行反代端口；`ufw deny` 直连三服务端口。
6. **引擎端口核查**：部署后 `ss -tlnp | grep -E "8090|8091|9201"` 确认监听面与预期一致。

### 11.4 不做清单（边界即设计）

服务间 mTLS/内建多用户体系/细粒度 RBAC——属多租户服务器化改造范畴，与本平台单机可信环境定位（NFR-O-4）冲突，出现真实多用户部署诉求时先立项评审（REQ-236 已交付工作台白名单/端口探测/docker 绑回环等安全收口子集，为边界内的既有积累）。
