# 领域分析与概念抽取

> 学习中心方法论卡片 · REQ-90 模块二（深度版，v0.2）。

## 输入与输出

领域分析的输入是文档、访谈、流程图与既有数据表；输出是一份**候选概念清单 + 关系草案**。这一步的质量决定后面所有阶段的工作量。

## 三个实用技法

### ① 名词/动词扫描

在需求文本里圈出**名词**（候选概念或实例）与**动词**（候选关系）。"Pod 暴露 Service" → 概念 Pod、Service；关系 exposes。

### ② 上下位追问

对每个候选问两个问题，层次自然浮现：

- "它**是什么的一种**？" → 得到父类（Deployment 是一种工作负载）
- "它**有哪几种**？" → 得到子类（工作负载分 Deployment / StatefulSet / DaemonSet）

### ③ 边界测试

- 两个概念若属性完全相同 → 合并。
- 若只在某个属性上不同 → 考虑父子而非平级。

## 类与实例的区分

**Pod 是类，pod-nginx-7f9 是实例。** 一个词条在 CQ 里被"逐个列举"时往往是实例；被"概括描述"时往往是类。spec_json 里 `concepts` 放类、`instances` 放实例，关系（`relations`）只定义在类之间，实例间关系由实例的 `relations` 字段断言。

## 在本平台的落点

- 「本体构建 → 自定义构建 → S2」编辑器直接落地概念/关系/实例三要素。
- 任务卡 `task_s1_first_ontology`：每条来源路径都走一遍，对比产物形态。

## 深度版：从候选清单到可校验 Spec

### 每条来源路径的差异

- **文档/访谈**：名词动词扫描最有效，但要警惕"文档描述的是流程而非结构"——流程步骤常被误抽为概念。
- **既有数据表**：表结构是现成的概念草案（表→概念、外键→关系），但注意"连接表"是多对多关系的物化，不该抽成概念。
- **既有词表**：见模块三；先查重再自造。

### 层次泛滥反例

初学者常把层次建得过深："缺陷 → 软件缺陷 → 在线缺陷 → 支付在线缺陷"。判断标准：**每多一层，必须能说出该层独有的属性或关系**；说不出就合并。另一个信号是推理代价——层次越深，subClassOf 传导的查询结果越难预期。

### 属性 vs 关系的判定

问一句"这个值以后要不要当查询主体？"——要（如"找出所有由张伟负责的项目"）就是关系；不要（如展示字段）就是属性。属性是"描述"，关系是"可导航的连接"。

### 在本平台的落点

- AI 创建（REQ-82）的 LLM 草稿常犯"层次过深"毛病——用本节的判定标准去校订草稿，比逐字段检查更高效。
- 「组织与人员」示例的组 ⊑ 部门是"层次有价值"的正例：组确实继承了部门的承接关系语义。
